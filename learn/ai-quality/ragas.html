⓪ 一句話

Ragas 是一套開源的 LLM 應用評測框架,把「這個回答忠不忠於資料、切不切題、檢索到的內容夠不夠準夠不夠全」這些原本靠人主觀感覺的判斷,轉成 0–1 之間的客觀分數。它的做法是讓一個 LLM 當「裁判(LLM-as-a-Judge)」把回答拆成可查核的原子單元,再套用數學公式算出比例,於是品質變成可以跨版本比較、可以設門檻、可以塞進 CI 的量化訊號。

定位對照:本頁是站內〈讓 AI 產生高品質文件〉裡「⑥ 代表性開源專案 → Ragas / DeepEval」那一格的深入版。那頁講方法論,這頁講 Ragas 具體怎麼把品質算成分數。

① 它解決什麼問題

問題一:生成品質沒有客觀數字

RAG / LLM 應用的輸出是自然語言,「答得好不好」天生模糊。傳統字串比對(BLEU、ROUGE、精確匹配)對同義改寫、換句話說幾乎無能為力——語意對了,分數卻很低。於是團隊只能靠人工抽樣讀、憑感覺打分,慢、貴、而且無法回歸測試:改了 prompt 或換了檢索,到底變好還是變壞,說不清。

問題二:直接叫 LLM「打個分」很不穩

把整份回答丟給模型說「請給 1–10 分」,分數會飄:同一份輸入多跑幾次給的分不一樣,也說不出扣在哪。這正是站內〈高品質文件〉一開頭講的病——模糊的評分指令會換來缺乏依據的高分與客套評語。

Ragas 的切入點:不問「這篇幾分」,而是把大問題拆成一串小到可以二元判定的查核(這個 claim 有沒有被上下文支持?這個 chunk 相不相關?),再用比例公式聚合。判斷顆粒越小,LLM 裁判越穩,分數越可複現——這與站內主張的「二元檢核比給幾分穩定得多」是同一個道理。

② 核心機制:LLM-as-a-Judge + 數學指標

Ragas 幾乎所有指標都遵循同一套「先拆解、再判定、後聚合」的三段式流程。理解這個骨架,就理解了全部指標:

1. 拆解(Decompose) LLM 把「回答」或「參考答案」拆成一串原子 claim(可獨立查核的最小陳述) │ ▼ 2. 判定(Judge) 對每個 claim / 每個 chunk 做二元或分類判定: 「這條能不能被 retrieved context 支持?」是/否 │ ▼ 3. 聚合(Aggregate) 把一串是/否套進數學公式(比例、precision@k、F1、cosine),得出 0–1 的分數

兩類判定工具交替使用:

  • LLM 判定(LLM-based):語意層的「支持與否 / 相關與否 / 蘊含與否(NLI)」交給模型,取代脆弱的字串比對。
  • 數學/嵌入指標:比例、precision@k、precision/recall/F1、cosine similarity 等確定性公式負責把一堆判定收斂成一個數字——這一步不靠模型發揮,所以結果穩定可重現。
關鍵設計:模型只做它擅長、且顆粒夠小的局部語意判斷;「怎麼合成總分」交給寫死的數學。把「主觀」關進最小的籠子裡,再用確定性公式包在外面——這就是 Ragas 讓分數可信的核心手法。因為要拆 claim、要跑 NLI,大多數指標都需要你指定一顆 evaluator LLM(有些還要 embeddings)。
核心指標逐一拆解

③a 忠實度 Faithfulness — 有沒有在編

量什麼:回答與「檢索到的上下文(retrieved context)」在事實上有多一致。分數 0–1,越高代表回答裡的說法越都有依據;這是對付幻覺最直接的指標——回答講的東西,上下文裡到底有沒有。

怎麼算:(1) LLM 把回答拆成一條條 claim;(2) 逐條判定該 claim 能否從 retrieved context 推得;(3) 套公式:

Faithfulness = 回答中「被上下文支持」的 claim 數 ÷ 回答的 claim 總數

一份回答只有在「所有 claim 都能被 retrieved context 支持」時才算完全忠實。只要有一條 claim 是模型自己腦補、上下文找不到依據,分數就會被拉低。

對應站內概念:這正是〈高品質文件〉④「事實錨定(Grounding)」的量化版——「凡宣稱必須有依據」被算成了一個具體比例。

③b 相關性 Answer Relevancy — 有沒有切題

量什麼:回答對「使用者問題」有多切題。分數越高代表越直接回應了原問題;它會懲罰答非所問、不完整、以及灌水冗長的回答(堆一堆廢話反而扣分)。注意:它衡量的是「切不切題」,不衡量事實對不對(那是忠實度的事)。

怎麼算(反向出題法):

  1. 讓 LLM 讀著「回答」反推出若干個「這個回答像是在回答什麼問題」的人造問題(預設約 3 個,可用 strictness 調整);
  2. 算每個「反推問題」與「原始使用者問題」的 embedding cosine 相似度;
  3. 取平均。
Answer Relevancy = (1/N) · Σ cosine( 反推問題ᵢ 的嵌入 , 原問題的嵌入 )

直覺:如果回答真的切題,拿它反推出來的問題就會跟原問題很像;如果回答跑題或灌水,反推出的問題會偏離原問題,相似度就低。因為要算 cosine,這個指標需要 embeddings。

③c Context Precision — 檢索有沒有把對的排前面

量什麼:評估檢索器(retriever)把「相關的 chunk」排在「不相關的 chunk」前面的能力。它關心的不只是「有沒有撈到相關內容」,而是相關內容有沒有被排到前排——因為靠前的 chunk 才最會被模型用到。

怎麼算:對 retrieved context 裡每個位置 k 的 chunk 判定其相關性(vk ∈ {0,1}),計算各位置的 precision@k,再做加權平均(Context Precision@K):

Precision@k = 前 k 個中的 true positives ÷ (true positives + false positives) @k Context Precision@K = Σₖ ( Precision@k · vₖ ) ÷ 前 K 個中的相關項目總數

因為是按排名加權,把不相關的 chunk 排在越前面,對分數的傷害越大;排在很後面則影響輕微。這讓它成為衡量「檢索排序品質」的敏感指標。

③d Context Recall — 該撈的有沒有漏掉

量什麼:回答一個問題「所需要的相關資訊」,檢索到底撈齊了沒有。分數越高代表漏掉的相關內容越少。Precision 問「撈進來的準不準」,Recall 問「該撈的有沒有漏」——兩者是檢索品質的一體兩面。

怎麼算(LLM 版 LLMContextRecall):用參考答案(reference)當作 ground truth 的代理——因為逐字標註「理想上下文」太耗人力。做法:LLM 把參考答案拆成一條條 claim,逐條判定「這條能不能歸因到 retrieved context」,理想情況下參考答案裡每一條 claim 都該在檢索內容裡找到支持:

Context Recall = 參考答案中「被 retrieved context 支持」的 claim 數 ÷ 參考答案的 claim 總數
注意前提:Context Recall(以及下面的 Factual Correctness)需要一份 reference / ground truth 才能算——它是拿「標準答案」在比對。Faithfulness、Answer Relevancy、Context Precision 則有不需要參考答案的變體,較適合線上、無標註的情境。(各指標的必要欄位以官方 repo 為準。)

③e 其他常用指標(README / docs 有列)

除了上面四個 RAG 經典指標,Ragas 的 available_metrics 還收了一批,常見的有:

指標量什麼 / 怎麼算
Factual Correctness
事實正確性		 把「回答」與「參考答案」都用 LLM 拆成 claim,再用 NLI(自然語言推論)比對兩邊事實重疊,算 precision / recall / F1(mode 可選,預設 F1)。TP=兩邊都有、FP=只在回答、FN=只在參考。還可用 atomicity / coverage 調拆解顆粒度。
Aspect Critic
面向評判		 二元評判:針對你自訂的面向(如 harmlessness、correctness)讓 LLM 回一個是/否(0/1)。用 DiscreteMetric 定義 allowed_values 與 prompt,回傳分類值 + 理由。對應站內「檢核清單二元化」。
Noise Sensitivity
雜訊敏感度		 系統「用了檢索內容卻給出錯誤 claim」的頻率。逐條檢查回答的 claim 是否正確(對 ground truth)且能否歸因到上下文;公式 = 錯誤 claim 數 ÷ claim 總數。越低越好(0 最佳)。
Context Entities Recall
實體召回		 以「實體」為單位算 recall:參考答案中的關鍵實體,有多少比例出現在 retrieved context。適合看檢索有沒有漏掉關鍵名詞。
Semantic Similarity
語意相似度		 用 embeddings 算「回答」與「參考答案」的語意相似度(非字面比對)。
Rubrics-based / Summarization / SQL / Multi-Modal 等 還有 Rubric 評分、摘要品質、SQL 語意等值、多模態忠實度/相關性等專用指標。完整清單與定義以官方 repo 為準。
怎麼挑:一條 RAG 鏈可拆成「檢索」與「生成」兩段。檢索好不好看 Context Precision / Context Recall;生成好不好看 Faithfulness(有沒有編)/ Answer Relevancy(切不切題)。有標準答案時再加 Factual Correctness;有安全/風格要求時加 Aspect Critic。
落地與定位

④ 用法:把資料變成 dataset,再 evaluate()

資料模型

Ragas 用結構化的樣本承載一次評估所需的欄位,常見四個:user_input(問題)、retrieved_contexts(檢索到的片段清單)、response(系統回答)、reference(參考答案,需要 ground truth 的指標才用到)。單筆用 SingleTurnSample,整批用 EvaluationDataset(可由 EvaluationDataset.from_list(...) 從 list of dict 建立)。

一行跑分

核心入口是頂層的 evaluate(dataset=..., metrics=[...], llm=...):傳入資料集、想算的指標清單、以及一顆當裁判的 LLM(需要 embeddings 的指標再傳 embeddings),回傳每個指標的分數。裁判模型用 wrapper 包裝以接不同供應商,例如 LangchainLLMWrapper(...)。

整合與 CI

  • 框架整合:與 LangChain、LlamaIndex 等主流 RAG 框架整合,可直接評估既有 pipeline 的輸出(整合清單以官方 repo 為準)。
  • 測試資料生成:沒有現成測試集時,Ragas 能從你的文件自動生成測試問題集(test set generation),補上「沒有標註資料」的缺口。
  • 進 CI:因為輸出是客觀數字,可對關鍵指標設門檻(如 Faithfulness ≥ 0.9),在 CI 對每次改動跑回歸——分數掉了就擋 PR,把「改 prompt / 換檢索有沒有變糟」變成自動檢查。
對照站內流水線:這一步對應〈高品質文件〉的「3. 品質評估」層——把生成結果換成客觀分數,未達門檻就退回重寫,形成自動迭代迴圈。

⑤ 最小範例(以官方 repo 為準)

安裝

# 官方 README
pip install ragas

A · 評估一條 RAG 鏈(dataset + evaluate)

把資料整理成 list of dict(含 user_input / retrieved_contexts / response / reference)→ 建 EvaluationDataset → 選指標 → 跑 evaluate():

from ragas import EvaluationDataset, evaluate
from ragas.llms import LangchainLLMWrapper
from ragas.metrics import LLMContextRecall, Faithfulness, FactualCorrectness

# dataset：每筆含 user_input / retrieved_contexts / response / reference
evaluation_dataset = EvaluationDataset.from_list(dataset)

evaluator_llm = LangchainLLMWrapper(llm)          # 包一顆裁判 LLM
result = evaluate(
    dataset=evaluation_dataset,
    metrics=[LLMContextRecall(), Faithfulness(), FactualCorrectness()],
    llm=evaluator_llm,
)
print(result)                                     # 各指標分數

B · 自訂一個二元 / 分類指標(Aspect Critic 風格)

README 的 quickstart 展示了用 DiscreteMetric 定義「允許值 + prompt」的裁判指標,回傳分類值與理由:

import asyncio
from openai import AsyncOpenAI
from ragas.metrics import DiscreteMetric
from ragas.llms import llm_factory

client = AsyncOpenAI()
llm = llm_factory("gpt-4o", client=client)

metric = DiscreteMetric(
    name="summary_accuracy",
    allowed_values=["accurate", "inaccurate"],
    prompt="""Evaluate if the summary is accurate and captures key information.
Response: {response}
Answer with only 'accurate' or 'inaccurate'.""",
)

async def main():
    score = await metric.ascore(
        llm=llm,
        response="The summary of the text is...",
    )
    print(f"Score: {score.value}")
    print(f"Reason: {score.reason}")

if __name__ == "__main__":
    asyncio.run(main())

⑥ 在「高品質文件流水線」的位置

回到站內〈高品質文件〉的四層流水線,Ragas 精準地坐在第 3 層「品質評估」:它把生成層產出的文件/回答,轉成一組客觀分數,交給第 4 層決定要不要退回重寫。

1. 結構定義 Pydantic / JSON Schema + Metadata(讀者/領域/必備章節) │ ▼ 2. 生成流程 多 Agent:撰寫者 ⇄ 審查者(Map-Reduce 分塊) │ ▼ 3. 品質評估 Ragas → Faithfulness / Answer Relevancy / Context Precision·Recall │ 忠實度 = 事實錨定的量化版(claim 有沒有被上下文支持) ▼ 4. 自動迭代 未達門檻 → 帶「扣分原因」退回重寫(Reflexion loop) │ └──▶ 達標輸出
站內方法論概念Ragas 的對應量化
事實錨定 / 強制引用(消滅幻覺)Faithfulness:回答 claim 被 retrieved context 支持的比例
精準回答 vs 堆廢話Answer Relevancy:反推問題與原問題的 cosine 相似度
上下文契合 / 範疇正確Context Precision / Recall:檢索排序準度與召回完整度
二元檢核 / RubricAspect Critic / Rubrics-based:自訂面向的是/否與評分
品質門檻 → 退回重寫對指標設閾值,進 CI 做回歸與 gating
一句話收斂:〈高品質文件〉主張「把評分演算法化」;Ragas 就是這句話在 RAG / LLM 應用上最成熟的一個實作——它把「忠實度、相關性、上下文精準/召回」做成現成、可組合、可進 CI 的量化指標,讓「品質」第一次有了能跨版本比較的座標。

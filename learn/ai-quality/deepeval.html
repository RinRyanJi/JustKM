🧪 DeepEval:LLM 版的 pytest 評測框架

把「LLM 輸出品質」變成可以 assert 的單元測試 —— 開源、pytest 風格、可進 CI/CD 的 LLM 評估框架(confident-ai/deepeval)

開源評測框架 pytest 風格 LLM-as-a-Judge · G-Eval
📑 目錄
⓪ 一句話定位 ① 它解決什麼 ② 核心機制:三件套 ③ 核心指標與 G-Eval ④ 用法:TestCase / metrics / 執行 ⑤ 最小範例 ⑥ 在高品質文件流水線的位置 ⑦ 來源

⓪ 一句話定位

DeepEval 官方自述為「The LLM Evaluation Framework —— 一個簡單易用的開源 LLM 評估框架,用於評估大型語言模型系統」。用一句話類比:它是 「LLM 版的 pytest」——沿用 pytest 的測試哲學,但專門用來對 LLM 應用做單元測試。你像寫測試檔一樣寫評測,再用 deepeval test run 執行。(以官方 repo 為準)

核心轉念:傳統上「這個回答好不好」是人肉主觀判斷;DeepEval 把它變成可自動執行、可通過/失敗、可回歸(regression)、可進 CI 的測試斷言。品質從「感覺」變成「測試套件的綠燈與紅燈」。
一 · 為什麼需要它

① 它解決什麼:把 LLM 輸出品質變成可跑的單元測試

LLM 應用(聊天機器人、RAG、agent)的輸出不確定、難以用固定字串比對。傳統 assert output == expected 在這裡幾乎無效——同樣正確的答案可以有一千種寫法。這帶來三個實務痛點:

  • 改了 prompt / 換了模型,品質有沒有退步? 沒有測試套件就只能靠人工抽看。
  • RAG 到底錯在哪? 是檢索沒撈到對的段落,還是模型撈到了卻答錯(幻覺)?需要能分層量化。
  • 怎麼進 CI/CD? 要能在每次提交自動跑、低於門檻就讓 pipeline 失敗。

DeepEval 的答案是:提供一組研究背書的評測指標(metric),把「好不好」拆成可打分、可設門檻(threshold)的維度;再用 pytest 風格把這些打分包成測試,低於門檻就 fail。官方定位它能對 LLM 應用做端到端(黑箱)、完整 agent 軌跡、以及單一步驟的評估,協助你挑出最佳模型 / prompt / 架構,並防止 prompt 漂移(prompt drift)。(以官方 repo 為準)

與站內方法論的呼應:這正是 「讓 AI 產生高品質文件」 一頁裡「把評分演算法化、結構化」的工具化版本——DeepEval 就是那套流水線裡的「品質評估層」。
二 · 怎麼運作

② 核心機制:test case + metric + assert_test 三件套

DeepEval 的心智模型只有三個零件,組合起來就是一條測試:

零件角色對應 pytest
Test Case
LLMTestCase		 一次待評估的互動,承載 input、actual_output、expected_output、retrieval_context 等欄位 測試的「輸入與實際結果」
Metric
如 GEval、AnswerRelevancyMetric		 評分準則,帶一個 threshold(門檻);對 test case 打出 0~1 的分數並判定通過與否 斷言的「判準」
assert_test() 把一個 test case 丟給一組 metrics 跑;任何 metric 未達門檻就讓測試 失敗 assert ...

pytest 風格整合 → 直接進 CI/CD

你把 assert_test(...) 寫進 test_xxx.py 的 test_ 函式裡,然後用官方 CLI 執行:

# 像跑 pytest 一樣跑 LLM 評測
deepeval test run test_chatbot.py

因為它相容 pytest 的執行方式,可以直接掛進既有的 CI pipeline:每次提交自動跑評測,分數低於門檻就讓 build 變紅,達成「LLM 品質的回歸測試」。若不想走 pytest,也可以用純函式的 evaluate([...], [...]) 直接在腳本裡批次評估。(以官方 repo 為準)

三種評估粒度:官方強調 DeepEval 可評估「端到端黑箱輸出」、「完整 agent 軌跡(trajectory)」與「單一步驟」——對複雜 agent,可用 dataset.evals_iterator() 之類的迭代器捕捉整條決策路徑再逐段評分。
三 · 指標:品質怎麼被量化

③ 核心指標:從 RAG 到 agent,以 G-Eval 為靈魂

DeepEval 內建數十種 metric。以下依用途分類(以 README 為準,實際清單與參數以官方 repo 最新版為準):

RAG 指標(檢索增強生成)

指標量化什麼
Answer Relevancy(答案相關性)回答是否精準對應提問,而非答非所問、堆廢話
Faithfulness(忠實度)回答是否忠於檢索到的上下文、有無事實依據(對抗幻覺)
Contextual Precision(上下文精準度)檢索出的段落中,相關的是否排在前面
Contextual Recall(上下文召回率)該撈到的關鍵資訊是否都被檢索到
Contextual Relevancy(上下文相關性)檢索到的上下文整體與提問的相關程度
RAGAS整合式的 RAG 綜合分數

Agentic 指標(代理行為)

用於評估 agent 的行為與工具使用,例如:Task Completion(任務完成度)、Tool Correctness(工具呼叫正確性)、Goal Accuracy(目標達成準確度),以及 Argument Correctness、Plan Adherence 等軌跡層面的指標。(以官方 repo 為準)

多輪對話指標

如 Knowledge Retention(跨輪記憶)、Conversation Completeness(對話完整度)、Turn Relevancy、Role Adherence(是否守住設定角色)等。

安全與其他

Hallucination(幻覺)、Bias(偏見)、Toxicity(毒性)、JSON Correctness(格式正確性)、Prompt Alignment 等。

🌟 G-Eval:用自然語言 rubric 的 LLM-as-a-Judge

官方把 G-Eval 描述為「一個研究背書的 LLM-as-a-judge 指標,能以接近人類的準確度,對任意自訂準則評分」。它的關鍵在於:你不必寫程式定義評分邏輯,只要用自然語言寫下 rubric(評分準則),G-Eval 就會據此讓 LLM 當裁判打分。

from deepeval.metrics import GEval
from deepeval.test_case import LLMTestCase, SingleTurnParams

correctness_metric = GEval(
    name="Correctness",
    # ↓ 用一句自然語言描述「什麼叫對」,這就是 rubric
    criteria="Determine if the 'actual output' is correct based on the 'expected output'.",
    evaluation_params=[SingleTurnParams.ACTUAL_OUTPUT, SingleTurnParams.EXPECTED_OUTPUT],
    threshold=0.5
)

運作上,G-Eval 會把你的 criteria 展開成一串評估步驟(chain-of-thought 式的評分推理),再讓裁判模型依步驟對指定的 evaluation_params(這裡是實際輸出 vs 期望輸出)打分。換一個評分維度,只要換一句 criteria——這讓「品質標準」變成可版本控管、可調整的文字資產。

呼應站內 Rubric 方法論:站內 Rubric-based Evaluation 講「把主觀印象轉為明確錨點、按點評分」;G-Eval 正是這套 rubric 思路的工具化落地——你把「得分要包含什麼、缺什麼扣分」寫進 criteria,LLM 就照 rubric 當裁判。兩者是同一件事的「方法論版」與「框架版」。
注意 LLM-as-a-Judge 的邊界:裁判本身也是 LLM,可能有偏差或幻覺。這也是站內方法論強調「多次採樣取中位數」與「強制引用反向驗真」的原因——把單次裁判的偶然誤差與幻覺理由壓下去。
四 · 實際寫法

④ 用法:LLMTestCase、metrics、assert_test / evaluate

1. 造一個 test case

用 LLMTestCase 描述一次互動。RAG 情境常帶 retrieval_context(檢索到的段落),讓 Faithfulness、Contextual 系列指標有依據可評:

from deepeval.test_case import LLMTestCase

test_case = LLMTestCase(
    input="What if these shoes don't fit?",
    actual_output="You have 30 days to get a full refund at no extra cost.",
    expected_output="We offer a 30-day full refund at no extra costs.",
    retrieval_context=["All customers are eligible for a 30 day full refund at no extra costs."]
)

2. 選 metrics 並設門檻

每個 metric 帶一個 threshold;可同時掛多個 metric 一起評:

from deepeval.metrics import AnswerRelevancyMetric

answer_relevancy_metric = AnswerRelevancyMetric(threshold=0.7)

3a. pytest 路線:assert_test

寫進 test_ 函式,任何 metric 未達門檻即 fail,再用 deepeval test run 執行(見下節完整範例)。

3b. 腳本路線:evaluate

不想走 pytest,就用 evaluate() 直接批次評估一組 test cases:

from deepeval import evaluate
from deepeval.metrics import AnswerRelevancyMetric
from deepeval.test_case import LLMTestCase

answer_relevancy_metric = AnswerRelevancyMetric(threshold=0.7)
test_case = LLMTestCase(
    input="What if these shoes don't fit?",
    actual_output="We offer a 30-day full refund at no extra costs.",
    retrieval_context=["All customers are eligible for a 30 day full refund at no extra costs."]
)
evaluate([test_case], [answer_relevancy_metric])

4. 用 dataset 批次跑

可把多筆評估組成資料集(dataset / golden),對整個資料集批次評估;DeepEval 也支援合成資料集生成(single-turn 與 multi-turn),並提供 evals_iterator() 之類的迭代器,把資料集餵過你的應用、逐筆評分。(以官方 repo 為準)

組裝方式很自由:一個 test case 可以掛多個 metric(例如同時測 Answer Relevancy + Faithfulness + 一個自訂 G-Eval);一次評估可跑多個 test case。門檻(threshold)決定紅綠燈,因此「要多嚴」由你按專案風險調。

⑤ 最小範例:一個完整的 LLM 測試檔

以下為 README 的入門範例(逐字引用),把三件套組成一條可跑的測試:

import pytest
from deepeval import assert_test
from deepeval.metrics import GEval
from deepeval.test_case import LLMTestCase, SingleTurnParams

def test_case():
    correctness_metric = GEval(
        name="Correctness",
        criteria="Determine if the 'actual output' is correct based on 'expected output'.",
        evaluation_params=[SingleTurnParams.ACTUAL_OUTPUT, SingleTurnParams.EXPECTED_OUTPUT],
        threshold=0.5
    )
    test_case = LLMTestCase(
        input="What if these shoes don't fit?",
        actual_output="You have 30 days to get a full refund at no extra cost.",
        expected_output="We offer a 30-day full refund at no extra costs.",
        retrieval_context=["All customers are eligible for a 30 day full refund at no extra costs."]
    )
    assert_test(test_case, [correctness_metric])

執行:

deepeval test run test_chatbot.py
讀法:這條測試在問——「機器人回覆(actual_output)在語意上是否等同於期望回覆(expected_output)?」判準不是字串相等,而是 G-Eval 用 criteria 這句 rubric 讓 LLM 當裁判打分;分數 ≥ threshold(0.5)才通過。(範例欄位如 SingleTurnParams 之命名以官方 repo 最新版為準)
五 · 放回大圖

⑥ 在「高品質文件流水線」的位置:品質評估層 + 自動迭代門檻

回到站內 高品質文件產出流水線。DeepEval 對應的是第 3 層「品質評估」與第 4 層「自動迭代」的門檻判定——把生成好的文件/回答量化打分,分數低於門檻就退回重寫。

1. 結構定義 Pydantic / JSON Schema + Metadata(讀者/領域/必備章節) │ ▼ 2. 生成流程 多 Agent:撰寫者 ⇄ 審查者 對立協同 │ ▼ 3. 品質評估 DeepEval:G-Eval(自訂 rubric)+ Faithfulness/Relevancy → 客觀分數 │ ▼ 4. 自動迭代 分數 < threshold → assert 失敗/退回重寫(Reflexion loop) │ └──▶ 達標輸出 / CI 綠燈
流水線需求DeepEval 提供的機制
把「品質」變成客觀分數一組研究背書的 metric(RAG / agent / 安全 / G-Eval 自訂 rubric)
設定「達標門檻」以自動迭代每個 metric 的 threshold;未達即 assert_test 失敗
防幻覺、對照依據Faithfulness / Contextual 系列,依 retrieval_context 評分
進 CI/CD、防 prompt 漂移pytest 相容的 deepeval test run,可掛進 pipeline 做回歸
一句話收斂:站內方法論教你「怎麼想」(Rubric、二元檢核、強制引用、角色分離、自動迭代);DeepEval 給你一套「怎麼跑」的現成框架——尤其 G-Eval 把你的 rubric 直接變成可執行、可設門檻、可進 CI 的裁判。兩者合起來,就是「把品質工程化」。

🚢 CrewAI:角色化多 Agent 協作框架

用「像真實團隊般分工」的方式編排自主 AI agent —— 每個 agent 有 role/goal/backstory,任務串接,流程可選 sequential 或 hierarchical。獨立於 LangChain 的精簡 Python 框架。

⓪ 一句話

CrewAI 是一個精簡、快速、獨立於 LangChain 的 Python 框架,專門用來編排「角色化(role-playing)、自主的 AI agent」與可上線的多 agent 工作流。它的核心比喻很直接:把一群各有專長的 AI agent 組成一個「crew(小組)」,像真實團隊一樣分工、把工作交接下去,合力完成一件事。

官方定位(以官方 repo 為準):README 將其描述為 “Framework for orchestrating role-playing, autonomous AI agents.”,並強調它是「a lean, fast Python framework built specifically for orchestrating autonomous AI agents and production-ready agentic workflows」。

① 它解決什麼問題:要像真實團隊般分工協作

單一 agent + 單一 prompt 想一次做完「研究 → 撰寫 → 審查」這種複合任務,常常顧此失彼:研究不夠深、寫作分心、又缺乏獨立審查。人類團隊怎麼解?分工——把不同職責交給不同專長的人,並定義好交接與協調方式。

CrewAI 把這個直覺搬進程式:

  • 每個 agent 是一個「有職稱的專才」:你用自然語言給它 role(職位)、goal(目標)、backstory(背景與觀點),它就會用那個身分去思考與行動。
  • 工作被拆成 task(任務),分派給對應的 agent,並可把前一個任務的產出當作下一個任務的輸入(交接)。
  • crew(小組)負責編排:決定任務照什麼流程跑——是照順序(sequential),還是由一個 manager agent 動態指派與協調(hierarchical)。
設計哲學:不是靠「一個更聰明的巨無霸 prompt」,而是靠角色分離 + 明確任務 + 流程編排,讓多個各司其職的 agent 協作出比單體更可靠的結果。這與本站反覆出現的主題一致——靠更好的環境與流程,而非只靠更強的模型。

② 核心概念:Agent / Task / Crew / Process / Tools / Memory

CrewAI 是「自帶原語(primitives)」的獨立框架。官方 FAQ 明確表示:「CrewAI is a standalone Python framework with its own primitives for agents, tasks, crews, flows, tools, and orchestration.」以下是幾個要角(以官方 repo 為準)。

Agent(角色化的執行單位)

一個 agent 由三個基礎屬性定義出「它是誰」:

屬性意義例子
role職位/功能,決定它扮演誰「資深技術研究員」
goal主要目標,它一切行動的方向「找出並整理最可靠的一手資料」
backstory背景、專長與觀點,塑造語氣與判斷「你有十年產業研究經驗,重視引用與查證」

agent 還可以配備 tools(工具)與是否啟用 memory 等設定。

Task(工作單位)

一個 task 描述「要做什麼」與「期望產出(expected output)」,並指派給某個 agent 執行。任務可串接——把前一個任務的輸出交給下一個任務作為上下文(context)。

Crew(小組)

把一組 agent 與一組 task 收攏在一起,用一個指定的流程(process)去編排它們的協作。crew 是你最終「按下啟動鍵」的對象。

Process(流程:sequential / hierarchical)

流程怎麼跑適用
sequential任務照定義的順序一個接一個執行,前一個的產出可餵給後一個清楚的線性流水線(研究→撰寫→審查)
hierarchical由一個自動的 manager agent 負責協調:動態決定該把哪個任務交給哪個 agent、如何整合需要動態調度、任務分派不固定的情境

Tools(工具)

agent 為了完成工作可以呼叫的外部能力(搜尋、讀檔、呼叫 API 等)。工具讓 agent 從「只會講話」變成「能實際動手取得資料、產生副作用」。

Memory(記憶)

agent 可以在互動之間保留與引用資訊,讓跨任務、跨回合的協作保有連貫的上下文,而不是每一步都失憶重來。

③ 應用於「文件編寫 + 審查團隊」

把 CrewAI 的原語對映到一個典型的文件生產小組,正好落在本站主線主題上:研究員 / 撰寫員 / 稽核員各有 role 與 goal,任務串接,由 manager 協調;稽核依 checklist 評分,未達門檻退回重寫。

Agentrolegoal(重點)
研究員 Researcher資深技術研究員蒐集可靠的一手資料,整理成有出處、可查證的素材
撰寫員 Writer技術文件撰寫者依邊界條件(讀者/領域/必備章節)把素材寫成完整文件
稽核員 Auditor嚴格的品質稽核者照 checklist / rubric 逐項評分,找缺失並要求原文引用

任務怎麼串接

三個任務可以照 sequential 流程接力:研究任務的產出(素材與出處)成為撰寫任務的 context;撰寫任務的初稿再成為稽核任務的輸入。若採 hierarchical,則由 manager agent 動態決定何時該回頭補研究、何時該送審。

研究員 role/goal:找可靠一手資料 + 出處 │ 產出:素材 + 引用來源 ▼ 撰寫員 role/goal:依邊界條件寫成完整文件 │ 產出:文件初稿 ▼ 稽核員 role/goal:照 checklist 逐項評分 + 強制引用 │ ├─ 分數 ≥ 門檻(如 85) ──▶ 通過,輸出 └─ 分數 < 門檻 ──▶ 帶「扣分原因 + 原文對照」退回撰寫員重寫 (由 manager / 流程串成自動校正迴圈)
與方法論頁的對應:這正是 高品質文件方法論 第 ③ 節「角色對立(生成者 vs 稽核者)」與第 ⑥ 節「稽核員依 CheckList 評分,低於門檻退回重寫」的框架實作版——CrewAI 提供的正是把這種「分工 + 退回重寫」落地的編排骨架。
務實提醒:「退回重寫」的迴圈與門檻判斷通常需要你在流程層自行設計(例如用條件分支或 Flows 控制,見下節);CrewAI 提供的是 agent/task/crew 的編排能力,實際的評分門檻與迭代邏輯由使用者組裝。具體 API 與可用機制以官方 repo 為準。

④ Flows:較新的事件驅動編排

除了 crew 這種「小組協作」的抽象,CrewAI 另提供 Flows——一種事件驅動(event-driven)的編排方式,用來對複雜自動化流程做精準的控制。

依 README 所述(以官方 repo 為準),Flows 提供 “precise, event-driven workflows that deliver precise control over complex automations”,特點包括:

  • 狀態管理(state management):在流程各步驟間帶著、更新共享狀態。
  • 條件分支(conditional branching):依事件或中間結果走不同路徑。
  • 與純 Python 程式交織:把一般 Python 程式碼與 agent/crew 的執行組合在同一個流程裡。
兩種抽象怎麼選:粗略地說,Crew 適合「讓一組 agent 自主協作把事情做完」的開放式任務;Flows 適合「我要對步驟、分支、狀態有明確掌控」的結構化自動化。兩者可以搭配使用(在 Flow 裡呼叫 crew)。實際 API 以官方 repo 為準。

⑤ 最小範例:定義 agent + task + crew.kickoff()

以下範例改寫自官方 repo 的用法(以官方 repo 為準),示意最小的「定義 agent → 定義 task → 組成 crew → kickoff()」流程。CrewAI 常見兩種寫法:直接實例化,或用 @CrewBase 裝飾器 + YAML 設定。

寫法一:直接實例化(概念示意)

from crewai import Agent, Task, Crew, Process

researcher = Agent(
    role="資深技術研究員",
    goal="找出並整理最可靠的一手資料",
    backstory="你有十年產業研究經驗,重視引用與查證",
)
writer = Agent(
    role="技術文件撰寫者",
    goal="把研究素材寫成完整、有出處的文件",
    backstory="你擅長把複雜主題寫得精準而好讀",
)

research_task = Task(
    description="研究主題:{topic},整理重點與來源",
    expected_output="帶出處的重點清單",
    agent=researcher,
)
write_task = Task(
    description="依研究結果撰寫一篇結構完整的文件",
    expected_output="Markdown 文件",
    agent=writer,
)

crew = Crew(
    agents=[researcher, writer],
    tasks=[research_task, write_task],
    process=Process.sequential,
    verbose=True,
)

result = crew.kickoff(inputs={"topic": "AI Agents"})
print(result)

寫法二:@CrewBase 裝飾器(取自官方 repo 用法)

@CrewBase
class LatestAiDevelopmentCrew():
    @agent
    def researcher(self) -> Agent:
        return Agent(config=self.agents_config['researcher'])

    @task
    def research_task(self) -> Task:
        return Task(config=self.tasks_config['research_task'])

    @crew
    def crew(self) -> Crew:
        return Crew(agents=self.agents, tasks=self.tasks,
                    process=Process.sequential, verbose=True)

crew = LatestAiDevelopmentCrew().crew()
crew.kickoff(inputs={'topic': 'AI Agents'})
注意:上述程式為說明用意的示意,實際欄位、匯入路徑與最新 API(尤其 @CrewBase 與 YAML 設定結構)請以官方 repo 與文件為準;CrewAI 迭代較快,細節可能隨版本調整。

⑥ 在「高品質文件流水線」的位置

回到本站主線:高品質文件方法論把品質拆成「結構定義 → 多 agent 生成 → 品質評估 → 自動迭代」四層。CrewAI 主要落在其中的「生成流程」這一層——它提供把角色對立(撰寫者 vs 稽核者)與階層流程(manager 協調)組裝起來的編排骨架。

方法論的層CrewAI 對應
結構定義(邊界/Schema)寫進 task 的 description / expected_output,或以 Flows 的 state 帶入(仍常搭配 Pydantic 等)
生成流程(多 agent 對立協同)CrewAI 的主場:role/goal/backstory 定義研究員/撰寫員/稽核員;Process 決定 sequential 或 hierarchical 協調
品質評估(客觀分數 + 引用)由稽核 agent 依 checklist/rubric 評分;評分規則與強制引用由使用者在 task 中設計
自動迭代(未達門檻退回重寫)用流程/條件分支(或 Flows)串成「不達標 → 退回撰寫員」的迴圈
一句話收斂:CrewAI 不是評分演算法本身,而是把「誰負責寫、誰負責審、怎麼交接、什麼時候退回重寫」這套分工與流程變成可宣告、可執行的程式。它讓方法論頁講的「角色分離 + Reflexion 迴圈」有了現成的編排載體。

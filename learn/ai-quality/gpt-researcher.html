⓪ 一句話認識它

GPT-Researcher(GitHub:assafelovic/gpt-researcher)自我定位為「第一個開源的深度研究 Agent(open deep research agent),同時支援針對任意題目做網路研究與本地文件研究」。你丟一個題目,它自主完成「規劃研究問題 → 派 agent 上網檢索 → 逐份資料摘要與追蹤來源 → 聚合過濾 → 產出一份帶引用的長篇研究報告」。

它是什麼、不是什麼:它不是聊天機器人,也不是單次 prompt 的「幫我寫一篇」。它是一條把研究行為流程化的自動化流水線 —— 這正是本站〈高品質文件〉反覆強調的:品質靠流程與環境,而不是靠一次更會寫的模型輸出。
一 · 動機與機制

① 它解決什麼問題

官方 README 列出當前 AI 研究的幾個核心痛點,這些也正是「文件品質」的天敵:

痛點對文件品質的傷害
人工研究耗時:一份客觀結論常要花數週、大量資源成本高、更新慢
LLM 訓練資料過時,容易幻覺(hallucinate)或給出不相關內容無中生有、與現況脫節
Token 限制使模型難以一次生成長篇報告內容被截斷、深度不足
來源太少導致偏誤與淺薄結果單薄、片面、易被錯誤資訊帶偏
選擇性取材把偏見帶進研究任務結論失衡、不客觀
核心觀察:「內容空洞、無中生有、單一 agent 研究深度不足」不是換個更大的模型就能解決的。GPT-Researcher 的答案是 —— 用多個 agent 平行擴大取材面、用強制引用把每句話綁回來源、用聚合階段突破單次 token 上限。

② 核心機制:計畫 → 檢索 → 摘要 → 聚合 → 撰寫

planner / executor 架構(規劃者 / 執行者)

系統採三類角色分工:一個 planner agent(規劃者) 依題目生成一組研究問題;多個 execution agents(執行者 / 爬蟲 agent) 針對每個問題各自去搜集資料;最後由發布 / 聚合角色(publisher) 把發現彙整成報告。這是典型的「先拆解、再平行、後聚合」。

五階段流水線

README 描述的工作流程可對應為以下多階段流水線:

1. 計畫 Plan 由 query 建立任務專屬 agent,生成一組能形成「客觀觀點」的研究問題 │ ▼ 2. 檢索 Search 對每個問題各派一個 crawler/executor agent 平行上網搜集資料 │ ▼ 3. 摘要 Summarize 逐份資料做摘要,並「追蹤與記錄來源」(source tracking) │ ▼ 4. 聚合 Aggregate 過濾、彙整各問題的摘要 —— 突破單次 token 上限 │ ▼ 5. 撰寫 Write 由聚合後的素材產出帶引用的長篇研究報告

大綱拆解 → 多子 agent 平行

把一個大題目拆成多個子問題後,每個子問題交給獨立的執行 agent 平行搜集與處理。這種「拆解 + 平行」正是能同時擴大來源覆蓋面與維持每塊深度的關鍵 —— 單一 agent 順序處理往往顧此失彼。

為什麼有效:把「研究一個大題目」拆成「並行研究 N 個子問題再聚合」,同時解掉三件事 —— ①單次 token 上限(分塊產生);②取材偏窄(多問題多來源);③深度不足(每塊獨立聚焦)。這與站內〈高品質文件〉講的 Map-Reduce 分塊寫作是同一套思路。

③ 事實錨定:每段強制附資料來源引用

GPT-Researcher 的報告全篇附帶引用(citations throughout)。關鍵在於:系統在摘要與聚合階段就持續追蹤來源(source tracking) —— 也就是每一份被摘要的資料,它的出處會一路被帶到最終報告,而不是最後才補引用。

這是對「無中生有」的直接反制:當每個論述段落都必須錨回一個真實檢索到的來源,模型就很難憑空杜撰 —— 因為沒有來源可掛的內容,根本進不了聚合與撰寫階段。這正是本站〈高品質文件〉第④節「事實錨定與強制引用」在生成端的具體實作:引用不是產出後才驗,而是從檢索源頭就綁定。

對照站內方法論:評分端我們談「稽核 Agent 提扣分要附逐字引用、再用程式反查引用是否存在」;生成端 GPT-Researcher 則是「每段內容都掛著它來自哪個檢索來源」。一端驗引用、一端建引用,兩端合起來才是完整的反幻覺閉環。
二 · 特性與用法

④ 關鍵特性

特性說明
深度研究(Deep Research)支援樹狀展開(tree-like exploration)的深入研究模式,能沿子題目逐層鑽研,而非只做一層淺搜
網路 + 本地文件可用網路來源與本地文件產生詳細研究報告
來源引用報告全篇附引用,並在流程中持續追蹤來源
多種輸出格式報告可匯出為 PDF、Word 等格式
可配置 LLM / 檢索器可切換不同 LLM 供應商,並整合自訂檢索器(retriever)(如 Tavily、MCP)
強化的網頁抓取支援啟用 JavaScript 的網頁爬取,能處理動態頁面
AI 生成內文配圖可用 Google Gemini 產生內文插圖(以官方 repo 為準)
可配置性 = 可落地性:「LLM 可換、檢索器可換、輸出格式多樣」意味著它能被接進你既有的知識庫與模型棧,而不是綁死一家。這對想把它當成「文件生成流水線一環」的團隊很關鍵。

⑤ 最小使用範例

以官方 README 為準,最小安裝與基本呼叫如下。

安裝

# 以套件形式安裝
pip install gpt-researcher

基本 Python 呼叫

from gpt_researcher import GPTResearcher

query = "why is Nvidia stock going up?"
researcher = GPTResearcher(query=query)

# 執行研究流程(計畫→檢索→摘要→聚合)
research_result = await researcher.conduct_research()

# 由聚合後的素材撰寫帶引用的報告
report = await researcher.write_report()
讀這段程式碼:兩步剛好對應機制 —— conduct_research() 是「計畫→檢索→摘要→聚合」,write_report() 是最後的「撰寫」。研究與撰寫分階段,正是它能先把來源錨定好、再落筆成文的原因。此外兩個方法都是 async,反映其「多個子 agent 平行搜集」的並行本質。實際部署另有 Web 前端與 API 等用法,細節以官方 repo 為準。

⑥ 在「高品質文件流水線」的位置

回到站內主軸 —— 〈讓 AI 產生高品質文件〉把高品質拆成一條流水線。GPT-Researcher 幾乎是其中「生成端」的一個完整實作:

站內〈高品質文件〉的原則GPT-Researcher 的對應實作
Map-Reduce 分塊寫作:大綱拆解 → 平行寫各塊 → 聚合潤飾planner 拆研究問題 → 多個 executor 平行檢索摘要 → publisher 聚合成報告
事實錨定 + 強制引用:每個論述都要有可追溯來源摘要/聚合階段全程 source tracking,報告全篇附引用
角色分離:不同職責交給不同 agentplanner(規劃)/ executor(檢索)/ publisher(彙整)三類角色分工
突破單次生成上限,避免長文品質衰退分子問題平行產生、再聚合,繞開單次 token 限制
怎麼一起用:把 GPT-Researcher 當「生成 + 事實錨定」的前段(產出帶引用的初稿),再接上站內談的「Rubric 評分 + 反向引用驗真 + Reflexion 重寫」評分後段 —— 一端負責把來源建進文件,一端負責把品質量化並逼近達標,就湊成一條完整、可迭代的高品質文件流水線。

⓪ 轉貼把話講歪了

Hux 的轉貼把這場演講收成兩句口號：「內部已經不怎麼寫 prompt，寫的是循環」，以及「一次通過錯誤少 97%、驗收快 30%」。對照她台上講的內容，兩句都要改回來。

她沒有說 Anthropic 內部不再寫 prompt。她講的是 context engineering：記憶怎麼從一份 CLAUDE.md 走到代理自己管的檔案系統，再加上班外的 dreaming，在兩次會話之間把記憶整理到還能用。

97% 與 30% 出現在投影片「What teams see with memory」的客戶引言標題，不是她口頭報的實驗室數字。她口頭只做了定性摘要。那張投影片裡的百分比、引言與職稱，見 ⑥，不要當成 Anthropic 自己的基準。

本頁的用法：只記她講過、或投影片上標明出處的東西。看片時沒讀準的專有名詞直接略過，不補一個「大概是誰」。

① 講者與議程

Lamis Mukta，Anthropic Member of Technical Staff，Applied AI team。這個位子夾在研究、產品與 go-to-market 之間。她跟新創與創辦人一起工作。

場合是 AI DevCon by Tessl。YouTube 上的標題寫成 AI Native DevCon London／June 2026。投影片上的演講題是 “Learning while you Sleep: Beyond Memory to Dreaming”。

議程投影片三點：

  1. Context engineering so far — 從 prompt 走到自己管理上下文的 agent。
  2. State of the art in memory today — CLAUDE.md、skills，以及代理自己管理的 memory 目錄。
  3. Dreaming up the path to continual learning — 在會話之間、班外，把記憶鞏固起來。

她自己也用這套記憶寫簡報：喜歡怎麼寫、喜歡投影片長什麼樣。所以這不是只給寫程式的機制。她把這裡的 context engineering 放在過去大約一年，而且還沒收斂。

② 瓶頸一：持續學習

智力本身不會複利。投影片三點：

  • Cold start。每個任務都從零開始。
  • Domain-specific。讓 agent 做好「你的」工作的那些東西，不會因為模型變大就自己長出來。
  • No compounding。第 50 個任務並不比第 1 個更好。

她說這一大塊上下文跟模型智力是正交的：換一個新模型，它還是不知道怎麼在你的組織裡把事情做成。Context engineering 的角色，是在模型變聰明時把智力乘上去。

熟悉的失敗長這樣：agent 不認識 codebase、不知道使用者偏好、不從錯誤裡學。

她的工作原則：“Do the simple thing that works.” 後面的時間線講的是過去這一年，起點是 Claude Code 的 CLAUDE.md。

③ 過去一年：四步，不是一次設計完

每一步都留下一樣東西，也暴露下一個瓶頸。順序是她排的，不是事後把四個名詞排成產品路線圖。

圖 1 · 記憶載體的演進：CLAUDE.md → memory tool → skills → 代理自己管的 memory/。下方三句是「The lessons so far」投影片的措辭。

1. CLAUDE.md

一份 markdown，會話一開始注入。裡面是慣例、怎麼交付、偏好。拿來轉向（steering）好用到不合理。失敗模式是檔案變很長之後的 context bloat。留下來的是：人讀得懂、人也寫得了、代理也寫得了的 markdown。

2. memory tool

介面是 memory_read()、memory_write()、memory_edit()。代理自己決定什麼時候讀、寫、改。這是班內（in-band）：發生在這次會話裡面。自主這件事是有效的。後來他們對「工具該長什麼形狀」變得沒那麼有主見。

3. skills

程序性記憶，給一條你已經有意見的端到端流程。漸進揭露：代理先只看到 front matter（兩三句），需要時才載入正文。她的比喻是書架——對方講法文，你抽出法文字典，不會把七年法文課一直攤在桌上。

瓶頸還在：什麼東西值得做成一個 skill，仍然是人跟代理在下判斷。

4. memory/ 檔案系統

這是他們現在建議的做法。就是 markdown 檔。投影片上的例子是 notes/deploy.md、team/rules.md。代理用平常的工具，bash 和 grep，不再走專用的 memory 工具。搜尋對上漸進揭露：不必把整個 store 載進上下文，而且這個 store 可以建索引。

「The lessons so far」

這張投影片以看得比較清楚的那次為準。另一次觀看時，同一張片子部分被回顧疊層蓋住，曾把某個詞讀成別的東西；本頁不採用那個讀法。

  • Format — Markdown 行得通（CLAUDE.md → skills → memory/）。
  • Reading — 漸進載入：front matter 和 grep，不是整庫。
  • Writing — 自主贏了：值得留下什麼，由代理決定。

她說，如果只做到這裡，單一任務上會感覺到持續學習。一進生產，這套感覺就破。

④ 瓶頸二：把記憶產品化

要擴到很多 agent、長時間跑、複雜 codebase。投影片列三個破綻：

  1. Concurrent writes。很多 agent 改同一批檔。
  2. Lost attribution。這條是誰寫的——你，還是 agent——以及什麼時候寫的。
  3. Stale and mixed scopes。組織知識和工作筆記纏在一起；舊上下文污染後來的執行。

她口頭舉的例子：兩個 agent 寫同一個檔；一個 agent 把錯誤事實寫進大家都會讀的組織級上下文；人跟 agent 一起改；記憶會過時、當初就寫錯，或被惡意注入。所以要有護欄。

⑤ 四條原則

1. Versioning

每次寫入都歸給一個作者、一次會話、一個時間。歷史要能查看、能回滾。也要知道是哪一次會話／哪份 transcript 促成這次更新。

投影片圖示以 team/deploy.md 為例：版本 v1 v2 v3 v4 HEAD，寫入前有一個 content sha256 前置條件。示例內文是：

Deploy via make ship, not ./deploy.sh. Reason: user corrected this in PRs #432, #431, #212.投影片圖示裡的示例內文，不是本頁另外查到的 PR 紀錄。

同一張圖上有作者欄位。這次看片沒把那個作者字串讀準，名字不記。只保留「圖上有 author 欄位」。

2. Concurrency

內容雜湊前置條件做在 harness，不放進模型。流程是：agent 先雜湊、起草、寫入前再雜湊一次；對不上，表示別人寫過了，於是重新拉、重寫草稿、再試。她說他們就是用這個，讓數千個 agent 放在同一個 store 上。

3. Permissioning

共用的組織知識是唯讀；自己的工作記憶可讀寫。你不會讓一個 agent 改寫組織級上下文；草稿區（scratchpad）才是可寫的。

範圍權限投影片上的檔
org-conventions read-only notes/style-guide.md、security.md、oncall.md
team-memory read-write deploy.md、flaky-tests.md、repo-layout.md
會話標籤 — sess_01、sess_02、sess_03

4. Portability

它就是檔案，加上一支獨立的 API。記憶要能在不同產品表面上移動。策展是組織／使用者／任務各自的，值得保持可取用，而不是鎖在某一個介面裡。

⑥ 投影片「What teams see with memory」

下面三則是投影片上的客戶標題與引言，職稱也是投影片上的。她口頭的摘要是另一件事，而且沒有唸這些百分比：

  • 第二次跑更準，因為它記下了哪裡出錯。
  • 二階效果是 token 花費和延遲下降，因為 agent 更常一次做對。
  • 記憶自己在跑，產品開發者可以把注意力放回產品，持續學習的迴圈照轉。
不要把它讀成 Anthropic 的實驗室結果。轉貼裡的「一次通過錯誤少 97%、驗收快 30%」對上的是前兩則的標題。第一則引言正文裡還有 27% 成本與 34% 延遲，那同樣是這位客戶的話，不是她報的內部數字。

97% fewer first-pass errors

“Memory lets us put continuous learning into production at scale — at 27% lower cost and 34% lower latency, and learning stays under our control.”GM, AI for Business, global commerce platform

30% faster verification

“In our document-verification pipeline, cross-session memory lets agents remember common issues — including ones we didn't think about.”Head of Machine Learning, document AI platform

Focus on the product

“A lot of our work is making sense of fast-moving, messy conversations between teams and their agents. Memory lets us stop building memory infrastructure and focus on the product itself.”Founder, early-stage AI startup

⑦ 瓶頸三：記憶放久了

班內記憶會碰到自己的上限。投影片三點，她另外也提到延遲：

  • Split focus。agent 要把注意力拆成「把任務做完」和「維護記憶」。
  • Patterns obfuscated。跨會話、跨 agent 的模式它看不到。
  • Memories go stale。出現互相矛盾的複本，而且錯得很有把握。

Claude Code 的例子：一次會話主要只看得到自己的上下文。

她用學校類比。學生交作業、老師批改；校長有專門的容量，看得到整隊人，也能改課程。班內的 agent 像在改自己那份作業的老師；dreaming 要補的是校長那一層。

⑧ Dreaming：班外的第二層批次

Dreaming 是二階的、班外（out-of-band）的批次工作，有自己的 token 預算，只有一件事：整理記憶，讓它保持有效、保持更新，讓 agent 真的在學。

流程：一段時間內的既有 memory store加上session transcripts → 一個 agent 兩邊都看，找出記憶哪裡可以更好 → 輸出一份新的 memory store，裡面是提議的變更。隔天的會話因此更聰明。

她舉的三個例子

  • 地理課。每個學生都錯同一題，因為那個主題根本不在課程裡 → 把主題加進去。
  • GCSE 數學。所有人都用弧度作答，題目要的是度。對應的做法是告訴他們怎麼設定計算機。Agent 版本：某個工具的設定是錯的，工具呼叫一直失敗。他們看的是工具呼叫和 metadata，不只是聊天文字。
  • 組織級。破折號太多 → 加一條指示不要這樣寫。

一次 dreaming pass 裡面

輸入 store 是 $MEM，複製成輸出 $MEM_OUT。編排器對每份 session transcript 派一個子代理。人可以引導：對這個組織來說什麼重要。編排器只留下夠普遍的模式，提出逐條修改，並附上示例 transcript，以及這個問題有多常見的統計。人來接受或拒絕。她說這樣運作得很好。

⑨ 合在一起：兩條軌道平行跑

不是用 dreaming 換掉班內記憶。兩條同時在：

  • Memory，班內、即時。讓下一次會話更早變好。投影片上的檔在 team-memory 底下：deploy.md、flaky_tests.md、repo-layout.md。會話是 agent A／B／C。（檔名拼寫依這張片子；權限那張寫的是 flaky-tests.md。）
  • Dreaming，週期性、在會話之間。做三件事：Verify、Organise、Enrich。讀的是 session transcripts。

圖 2 · 統一系統。上：白天班內，agent 直接寫 team-memory。下：班外 dreaming 讀 transcript 與既有 store，產出提議中的新 store，人接受或拒絕。

她講的取捨：班內有注意力分裂，視野也窄；dreaming 多花 token，但有效的記憶會把成本降下來，因為 agent 更常一次做對。

⑩ 三個 takeaway

收尾投影片三點：

  1. Do the simple thing that works.一份好的 CLAUDE.md、定義清楚的 skills、再加上 agent 自己寫的記憶，已經走很遠。
  2. 為很多長時間運行的 agent 設計。產品化是一支艦隊：permissioning、versioning、concurrency、portability。
  3. 加上 dreaming，班外鞏固記憶。在會話之間做 verify、organise、enrich。

她的收束句是：“Keep thinking, keep learning, keep dreaming.”

⑪ 問答（只記她答了什麼）

企業要的是記憶庫，不是筆電上的檔案

她前面避開了產品呼籲。然後說：這套架構（versioning、雜湊等）可以透過 Claude Managed Agents 的 memory 與 dreaming API 取得。她指向的文件見來源；本頁不把文件裡的參數表摘進來當成演講內容。

幾百個使用者時，dreaming 怎麼跟著權限走

提問的人提到一次 Claude Code 外洩。她的回答是：一個 dreaming 工作不一定要吃進某個時間窗裡的每一份 transcript。你選擇要附上哪些 transcript，也可以把 agent 的權限集合鏡射過來。

這是不是在重造資料庫

versioning、concurrency、耐久性，看起來像資料庫該做的事。她說他們在畫一條界線：哪些由 agent 自主做，哪些在 harness 裡用程式寫死。一開始是讓 agent 寫 markdown、然後把寫出來的東西提交掉；等這些基本動作被證明有用，雜湊和版本就改成確定性的、寫進程式裡。方向是併回已知的軟體工程，不是重造輪子。

⑫ 跟本站其他頁

Dreaming 是班外整理記憶，不是讓模型自己改權重。驗證心態那頁講的是別把檢查當成通過。

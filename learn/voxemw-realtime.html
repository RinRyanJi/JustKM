A · 兩階段語義判停

① 兩階段:Silero(便宜)+ SmartTurn(語義)

「什麼時候該接話」是即時對話最像/最不像真人的分水嶺。VoxEMW 用兩棒接力,把「便宜的觸發」與「昂貴的判斷」分開:

你在說話 ──▶ 第一棒 Silero VAD(便宜,持續跑) │ 偵測到停頓,軟判停門檻 ~64ms ▼ 第二棒 SmartTurn v3.2(語義複核,GPU ~10ms) │ 分析語調+語言線索,輸出「講完機率」 ┌───────────┴───────────┐ 機率 ≥ 0.5:講完了 機率 < 0.5:只是換氣/在想 ▼ ▼ 觸發 STT→LLM 回話 繼續聽,不搶話(沉住氣)
為什麼分兩棒:SmartTurn 是模型、要花算力,不能每一幀都跑。所以先用幾乎免費的 Silero 抓「有停頓」(64ms 軟判停),只在有停頓時才叫SmartTurn 做一次語義複核。這是「便宜的粗篩 + 昂貴的精判」典型組合——只有 ~0.08s(64ms + 10ms)。

可調參數(configs → VAD passthrough)

VoxEMW 把 VAD 參數透傳給上游語音管線:min_silence_ms、min_speech_ms、min_speech_continuation_ms、speech_pad_ms、max_speech_ms、smart_turn_model_path——判停鬆緊可調。

② SmartTurn 模型原理:分析波形,不是文字

SmartTurn(pipecat-ai/smart-turn,BSD-2)是開源的語義 VAD / 話輪結束偵測模型。關鍵特點:

  • 直接分析原始波形(不靠轉寫文字)——所以能捕捉語調(intonation)與語言線索這類「人類判斷話說完沒」的自然訊號;
  • 輸出單一機率:≥ 0.5 = 說話者已完成這一輪;
  • v2 多語(14 種含中文)、僅 360MB、比 v1 快 3×、L40S 上約 12ms;v3 支援快速 CPU 推理。
與傳統 VAD 的根本差別:傳統 VAD 只分「有沒有人聲」(靜音=停);SmartTurn 判「這句話語義/語調上完整了沒」。所以你說「我想想喔……」中間停頓,傳統 VAD 會誤判成講完而搶話,SmartTurn 能看出「還沒完」。這就是「語義判停」四個字的實質。

③ 800ms 重開寬限:接話後還留一扇門

就算判定「講完了」開始回話,VoxEMW 仍預留 ~800ms 重開寬限:這段時間內如果你又開口(例如補一句),系統能把話輪重新打開,而不是硬生生把你的補充當成打斷或丟掉。

三道防線疊起來:Silero(別太早)→ SmartTurn(語義確認)→ 800ms 寬限(給反悔的機會)。三者合力,才有「你停頓他沉住氣、你說完他秒接、中途停頓不搶答不丟字」的體感。
B · 串流管線

④ 串流管線與 OpenAI Realtime 事件協定

VoxEMW 的語音管線建於 huggingface/speech-to-speech,內部講 OpenAI Realtime API 的事件(input_audio_buffer.*、response.*、*.audio.delta…)。orchestrator(aiohttp :8000)是瀏覽器唯一入口:

瀏覽器 ──WebRTC(VP8+Opus,TURN 走 coturn :3478)──▶ orchestrator :8000 └─WS 控制/麥克風/轉寫─────────────────────▶ orchestrator ├─▶ s2s 管線 :8765 ①VAD → ②STT → ③LLM → ④TTS(講 Realtime 事件) ├─▶ avatar :8767 ⑤AVTR-1(TensorRT,說話+傾聽雙流) └─▶ llama-server :8081 本地 Qwen3.8-27B(+ MTP 投機解碼) 下行:TTS 音訊 delta 雙寫 → AVSyncScheduler(RTC 音軌)+ avatar(驅動口型) 音畫走 WebRTC 媒體軌(排程器打戳對齊,瀏覽器 RTP 原生同步);WS 只留控制/轉寫

關鍵設計:

  • 音訊走 WebRTC 媒體軌,不走 WS:延遲低、瀏覽器原生對齊;WS 只傳事件與轉寫(音訊 delta 事件會被剝掉 base64 音訊體,只留事件)。
  • TTS delta 雙寫:同一份音訊同時餵給「RTC 音軌(給你聽)」與「avatar(驅動嘴型)」——音畫從源頭同源。
  • 單用戶單會話:s2s 只有 1 個管線槽位,新瀏覽器連線立即頂掉舊(換網路的僵屍會話不用等超時)。

⑤ MTP 投機解碼:把最大宗的 LLM 延遲壓下去

1.3s 裡 LLM 首句 ~0.8s 是最大宗。VoxEMW 的 LLM 是 Qwen3.8-27B,用 UD-Q6_K_XL 量化 + MTP(Multi-Token Prediction)投機解碼,在 4090 上跑到 55.5 tok/s。

投機解碼(speculative decoding)白話:讓一個「小/快的草稿」先一次猜好幾個 token,再由大模型一次平行驗證——猜對的就直接採用,省掉逐 token 的來回。MTP 是把「多 token 預測」內建進模型的一種做法。

通用啟示:即時系統壓 LLM 延遲有三招常一起用——① 量化(模型變小跑更快)、② 投機/多 token 解碼(一次多吐)、③ 串流 + 只等首句。VoxEMW 三招全上。
C · 打斷時序

⑥ 打斷(barge-in)時序:你一開口,他就停

即時對話必須能被打斷。VoxEMW 的打斷由一個事件觸發、連鎖一整套動作:

數字人正在說話…… │ 你開口 ──▶ s2s 偵測到 input_audio_buffer.speech_started ▼ orchestrator 收到 → 連鎖: ① 對 s2s 送 response.cancel(interrupt_response=true) 停止繼續生成 ② 通知 avatar 丟棄未消費音訊 + 運動上下文歸位 嘴立刻閉上 ③ AVSyncScheduler.flush():清隊列、播放游標歸零 音畫停 ④ 封殺在途的陳舊 speech 幀(reset 前已渲染的) 不會播到舊嘴型 ⑤ 算出「你實際聽到多少」→ heard_prefix 回寫上下文(見下) 記得說到哪 ⑥ idle_mode 切 listening,數字人轉為傾聽表情 開始聽你
狀態機:speech_active(首個音訊 delta 開、response.done/打斷關)——說話期間禁止 avatar 生成 idle 幀(否則句間停頓插 idle 會卡畫面);idle_mode 有 listening(你開口)/ thinking(你說完)/ calm(他說完) 三態,決定待機表情與驅動音。

⑦ 「已聽」回寫:讓 LLM 知道你其實只聽到一半

這是最精巧的一步。你打斷時,數字人的回答只播了一部分。如果上下文記成「它講完了整段」,下一輪對話就會錯亂。VoxEMW 的做法:

  1. 量到底播了多久:reply_played_seconds = (已播樣本 − 本條開播時的游標) / 16000(16kHz),即你真的聽到的秒數;
  2. 估出你聽到的文字前綴(heard_prefix):
    n = len(轉寫) × min(1, 已播秒/總音訊秒)——中文語速在一條回覆內夠均勻,播放比例≈聽到的文字比例;
  3. 不足 2 字就回空:上游會把整條回覆從上下文回滾(零前綴=保持回滾,當作沒說過);
  4. 截斷回退到最近標點:避免半個詞留在上下文;
  5. 把這個「已聽前綴」寫回對話上下文,LLM 於是知道「我剛只說到這裡就被打斷了」。
def heard_prefix(transcript, audio_seconds, played_seconds):
    if not transcript or audio_seconds <= 0 or played_seconds <= 0: return ""
    n = int(len(transcript) * min(1.0, played_seconds / audio_seconds))
    if n < 2: return ""            # 太少 → 整條回滾,當沒說過
    cut = transcript[:n]
    if n < len(transcript):        # 回退到最近標點,不留半個詞
        for i in range(len(cut)-1, 0, -1):
            if cut[i] in "。！？；，、…—.!?;,": cut = cut[:i+1]; break
    return cut
為什麼是「打斷記憶」的關鍵:沒有這步,被打斷後 LLM 要嘛以為整段講完(下輪答非所問)、要嘛完全忘記(重複剛才)。用「播放進度→文字前綴」精確回寫,數字人才會「記得剛才說到哪」。這對齊 AVTR-1 官方 SpeechScheduler 的 played_duration 語義。

⑧ 音畫同步與 av-scheduler

嘴型與聲音要對上,是另一個時序難題。AVSyncScheduler 的做法:

  • lead 秒緩衝:新回覆/打斷後,音訊等 lead 秒再播,讓渲染(嘴型幀)先追上來,避免「聲先到、嘴後動」;
  • 幀超前就等音訊時鐘:若嘴型幀跑在已播音訊之前 → 停下來等音訊,以音訊為主時鐘;
  • flush 保留最後一幀 _last_jpeg:打斷清隊列時不黑屏,新幀到達前先定格;
  • 兩軌游標各自連續推進(RTC track 側),flush 不動它們——保證計時基準連續。
一句話:VoxEMW 的「即時感」不是靠某個神模型,而是靠一整套時序工程——兩階段判停決定「何時開口」、串流+投機解碼決定「多快出聲」、打斷回寫+音畫同步決定「被插話時多自然」。這正是 總覽頁說的「延遲預算工程」的骨肉。

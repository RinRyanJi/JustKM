⌚ K2 Horizon 0.9B:能塞進手錶的「全開源」小模型

2026/09 · IFM(MBZUAI · LLM360 血統)推出的六模型艦隊裡最小的一員 · 主打「小到能跑在手錶/眼鏡上」的端側推理 · Apache 2.0 連訓練資料與方法全開 —— 但「跑在手錶」目前是定位語,不是實測 demo

⓪ 一句話總結

K2-Horizon-0.9B 是一個約 0.9B 參數、稠密解碼器的小型語言模型,主打「端側/穿戴裝置」上的本地推理。它出自 IFM(MBZUAI 的基礎模型研究院,也就是 LLM360 開源血統的團隊),是 2026/09 一次發布的六模型艦隊(0.9B → 375B)裡最小的一員。最大賣點有兩個:(1) 徹底開放——Apache 2.0,連權重、程式碼、訓練資料與方法都公開;(2) 小到量化後約 633MB,理論上能塞進手機甚至手錶。

先說清楚一個誠實的落差:「跑在手錶上」是官方的定位宣稱(0.9B 針對手錶/眼鏡、3.7B/7B 針對手機),不是一個已被公開驗證的實機 demo——查不到任何真正在手錶上跑的 tok/s 數據。而且發布當下它還不能直接在 Ollama / LM Studio 載入,得用 IFM 自家的 llama.cpp 分支或 vLLM;獨立實測也發現首發權重有 bug。所以本頁會把「很棒的地方」和「別被行銷帶跑的地方」都講清楚。

① 為什麼「0.9B 端側小模型」重要

把一個能推理、會用工具的模型縮到能在手機、手錶、眼鏡上本地跑,好處是直接的:

  • 零延遲、零網路:不必往返雲端,離線也能用。
  • 隱私:資料不出裝置。
  • 零 token 費:推理成本從「每次呼叫付費」變成「一次性算力」。

難點也很直接:穿戴裝置的記憶體與算力極小。要塞得進去,模型本身要夠小(參數少)、還要靠量化把每個權重從 16-bit 壓到 4-bit,把足跡壓到幾百 MB。K2 Horizon 0.9B 就是衝著這個目標設計的——它是 2024–2026「能幹活的 sub-1B 端側模型」這股浪潮裡的一員(見 ⑦ 對照)。

② K2 Horizon 是什麼

K2 Horizon 是一次發布的六個模型,從能塞進手錶的 0.9B,到號稱「史上最大全開源」的 375B,共用同一套訓練配方。0.9B 是最小、最端側的那個。

③ 小而強的關鍵:多師 on-policy 蒸餾

一個 0.9B 要在數學、程式、工具呼叫上打得動,靠的不是硬堆資料,而是向更強的「老師模型」學。K2 Horizon 的主要槓桿是 mOPD(multi-teacher on-policy distillation,多師在線蒸餾):針對不同領域,用各自的專科老師來教這個小學生。

← 左右滑動看完整圖 →
▲ 「on-policy」= 讓學生自己先產生答案,再用老師的訊號去修正它實際會走的路徑(而非只背老師的標準答案)。多位專科老師分別把各自的強項蒸給同一個小學生。
可偷師的一點:當你要一個小模型「樣樣通」,與其找一個全能大老師,不如用一組專科老師分頭蒸餾——每科由最強的那個教。這和站內 訓練小模型做單一任務、CharTool 的以小博大 是同一種「不靠參數量、靠訓練配方」的思路。

④ 怎麼塞進小裝置:量化足跡

0.9B 的原始 16-bit 權重約 2GB;要塞進端側,靠 4-bit 量化把足跡壓到幾百 MB。

⑤ 本地安裝路徑(Local Setup)

影片標題的「Local Setup」,實際可行的路徑按「發布當下真的能跑」排序:

① llama.cpp + GGUF(最貼近端側的路)

# 從 IFM/K2-Horizon-0.9B-GGUF 下載一個 4-bit 量化檔(約 633MB)
# 例如 K2-Horizon-0.9B-Q4_K_M.gguf
./llama-cli -m K2-Horizon-0.9B-Q4_K_M.gguf -p "你的問題"
# 或起一個本地伺服器
./llama-server -m K2-Horizon-0.9B-Q4_K_M.gguf
# ⚠️ 發布當下需要 IFM 自家的 llama.cpp 分支(架構/工具解析尚未併回上游)

② vLLM(伺服器 / GPU)

vllm serve IFM/K2-Horizon-0.9B --trust-remote-code \
    --dtype bfloat16 --tool-call-parser k2_horizon

③ Ollama / LM Studio(最想要、但發布當下不 work)

這兩個「下載即用」的 App 發布當下並不能直接載入 K2-Horizon-0.9B(架構未被上游支援;早期低位元 GGUF 也被回報不相容 LM Studio)。若影片示範用 Ollama,很可能是靠自訂 Modelfile / 更新版建置,或稍嫌理想化。

務實建議:要真的在小裝置上動手,現階段最可靠的是 GGUF + llama.cpp(IFM 分支),跑在手機或一台 CPU 小機上;等上游 llama.cpp 併入支援後,Ollama/LM Studio 的「一鍵」體驗才會到位。

⑥ 行銷 vs 實測:誠實的落差

K2 Horizon 0.9B 有真本事,但發布敘事和實測之間有幾道要提醒的縫:

宣稱 / 亮點實測 / 需保留
「跑在手錶上」是定位語;查無真正在手錶上跑的公開 demo 或 tok/s。Q4 約 633MB 讓它「有機會」,但未被驗證
「同尺寸最佳,數學/推理/工具」可查證:AIME 2026 ≈ 48.5(官方自述 AIME 僅 30 題、變異大)、HumanEval+ ≈ 79.9、BFCL 工具呼叫同級領先。強是真的強——就其尺寸而言
「下載即用」發布當下不能在 stock Ollama / LM Studio 載入,需 IFM 的 llama.cpp 分支或 vLLM recipe
「前沿表現」獨立實測(如 MindStudio)發現首發權重有 bug:從零產生 HTML/CSS/JS 會壞、vLLM 的工具呼叫解析器未真正執行呼叫。有明顯「跑分到實用」的落差
結論:K2 Horizon 0.9B 最扎實的價值是「徹底開放(連資料與方法都給)+ 用蒸餾把 0.9B 的數學/工具能力拉滿」。把它當成「一個很開放、很小、數學/工具導向的研究級模型」來看最準確;「手錶上的前沿 AI」這種標語,保留三分。

相對於 Gemma/Qwen/Llama「在 Ollama 秒載」,K2 Horizon 的差異化在開放程度(Apache 2.0 + 資料 + 方法)與推理/工具的取向;而它的短板正是生態成熟度。

⑧ 值得偷師的思路 / ⑨ 來源

  1. 尺寸效率靠訓練配方,不靠參數量。多師 on-policy 蒸餾:每科用最強的專科老師教一個小學生——這是把小模型拉到「同級最佳」的關鍵槓桿。
  2. 量化是端側的入場券。16-bit → 4-bit 把 2GB 壓到 ~633MB;沒有量化,就沒有「進手機/手錶」的對話。
  3. 「檔案小」≠「跑得順」≠「生態就緒」。足跡、執行期 RAM、runtime 支援是三件事;評估端側模型要三個一起看。
  4. 對行銷語保留判斷。「跑在手錶」是定位、「同級最佳」限定於尺寸、「前沿」有跑分到實用的落差——這正是 看穿宣稱、以證據為準 的實例。

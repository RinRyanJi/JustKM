🌳 Git Worktree：一個 repo，同時開多個工作目錄

告別 git stash 與反覆切分支之苦 · 觀念教學 + 核心指令 + 實務場景 + 優缺點

⓪ 一句話總結

Git worktree 讓「同一個 repo」同時 checkout 多個分支到不同資料夾——每個資料夾各自有獨立的工作目錄與暫存區，但共用同一份 .git 物件庫。於是你可以在 A 資料夾開發功能、B 資料夾修 hotfix、C 資料夾跑測試，互不干擾、不用 stash、不用重新 clone。

📌 名稱澄清：它是 Git 內建功能（git worktree，Git 2.5+），不是 GitHub 專屬的東西。任何用 Git 的專案、任何託管平台（GitHub/GitLab/自架）都能用。

① 它解決什麼痛點

沒有 worktree 時，一個 clone 只能同時待在一個分支。要切去別的分支,常見的痛：

  • 手上功能改到一半 → 老闆要你緊急修 main 的 bug → 得先 git stash 或硬 commit 半成品,修完再切回來、再 stash pop。
  • 切分支會改動整個工作目錄 → IDE 重新索引、建置快取失效、node_modules 可能要重裝、開發伺服器要重啟。
  • 想同時跑「A 分支的測試」又繼續「B 分支的開發」→ 一個目錄辦不到。
  • 想並排比較兩個分支的實際檔案 → 只能一直切來切去。

Worktree 把這些痛一次解決：多開幾個工作目錄，各自停在不同分支,同時存在。

② 心智模型：一顆大腦，多雙手

把 repo 想成:一份共用的「物件庫/歷史」(.git) + 多個各自獨立的「工作檯」(worktree)。

圖 1 · 共用歷史、獨立工作檯：任一邊 commit，其他邊 git log 立即可見
  • 主 worktree(main worktree):你一開始 git clone 出來的那個目錄。
  • 連結 worktree(linked worktree):之後用 git worktree add 加出來的,各自是一個獨立資料夾。
  • 它們共享同一份歷史與物件,所以在任一邊 commit,其他邊 git log 都看得到。
⚠️ 一條鐵律：同一個分支不能同時在兩個 worktree 被 checkout。Git 會擋下並提示「already checked out at …」——這是刻意設計,避免兩邊同時改同一分支而打架。(要並行同一分支,通常改用 detached HEAD 或另開分支。)

③ 核心指令速查

指令做什麼
git worktree add <路徑> <分支>在指定路徑開一個 worktree,checkout 既有分支
git worktree add -b <新分支> <路徑> [起點]建立新分支並同時開 worktree
git worktree add --detach <路徑> <commit>以 detached HEAD 開(用來看某個 commit,不佔分支)
git worktree list列出所有 worktree、各自路徑與目前分支(--porcelain 給機器讀)
git worktree remove <路徑>安全移除一個 worktree(乾淨才允許,--force 強制)
git worktree prune清掉已被手動刪除目錄後殘留的中繼資料
git worktree move <來源> <目的>搬移一個 worktree 到新路徑
git worktree lock / unlock <路徑>鎖定(避免被 prune,例如在外接硬碟上的 worktree)
git worktree repair修復被搬動而失聯的 worktree 連結
💡 常用一行：git worktree add ../myrepo-hotfix main —— 在旁邊開一個目錄、停在 main,馬上就能修 bug,原本的功能開發原地不動。

④ 運作原理:什麼共用、什麼各自獨立

這是理解 worktree 的關鍵——搞清楚「哪些是全 repo 一份」「哪些是每個 worktree 一份」。

共用（整個 repo 一份）各自獨立（每個 worktree 一份）
物件庫(所有 commit / blob / tree)工作目錄裡的實際檔案
分支、tag、remote 設定HEAD(目前停在哪個分支)
config(預設全域共用)index(暫存區 staging)
hooks、stash、packed-refs建置產物 / node_modules / IDE 快取

技術上,連結 worktree 的中繼資料放在主 repo 的 .git/worktrees/<名稱>/;而每個連結 worktree 目錄裡的 .git 其實是一個檔案(不是資料夾),裡頭寫著指回主 repo 的路徑。

📌 想要「每個 worktree 各自的設定」?開啟 git config extensions.worktreeConfig true,就能用 git config --worktree <key> <value> 設定只作用於當前 worktree 的設定(例如不同的 user.email 或 hooks 路徑)。

⑤ 實務場景:什麼時候該用

圖 2 · 兩條並行時間軸：功能開發（綠）不中斷，hotfix（橘）在獨立 worktree 中插隊完成

其餘常見場景：

  • 緊急 hotfix 插隊:功能開發原地凍結,旁邊開一個 main worktree 修 bug。
  • 長時間任務並行:一個 worktree 跑測試/建置/部署,另一個繼續開發,建置產物互不覆蓋。
  • Code Review / 試跑 PR:把 PR 分支開在獨立目錄實際執行,不弄髒你手上的工作。
  • 並排比較分支:重構前後、兩個實作方案,兩個目錄直接對照。
  • 發佈用分支:例如把 gh-pages / docs 開成一個 worktree,建置輸出直接寫進去再 push。
  • ⭐ 平行 AI 編碼代理:讓多個 AI agent 各自在一個 worktree 同時改不同分支,彼此隔離、不會互相踩檔(許多 agent 工具內建此隔離機制)。

⑥ 手把手:一個完整範例

情境:你正在 feature/login 開發,突然要緊急修 main 的 bug。

# 你現在在主目錄 ~/proj，分支 feature/login，改到一半（不想 commit 半成品）

# 1) 旁邊開一個 worktree，停在 main —— 原目錄完全不動
git worktree add ../proj-hotfix main

# 2) 進去修 bug（這是獨立資料夾、獨立 index）
cd ../proj-hotfix
# …改檔、測試…
git switch -c hotfix/crash        # 開修復分支
git commit -am "Fix null crash on login"
git push -u origin hotfix/crash

# 3) 回主目錄，你的 feature/login 還在原地，完全沒被打斷
cd ../proj                        # 繼續寫功能

# 4) 事後清理：確認乾淨後移除 hotfix worktree
git worktree remove ../proj-hotfix
git worktree list                 # 確認已移除
💡 建議的擺放慣例：把所有 worktree 放在主 repo 的「旁邊」(如 ../proj-hotfix、../proj-pr42),或集中在一個 ../proj.worktrees/ 資料夾。不要把 worktree 開在主工作目錄「裡面」——會造成 gitignore 與工具混淆。

⑦ 優點 / 缺點

✅ 優點

  • 瞬間切換、零 stash:多分支同時存在,不必暫存半成品。
  • 省空間、省時間:共用物件庫,不像 git clone 要再抓一整份歷史。
  • 建置隔離:各 worktree 有獨立的建置產物/快取,不會互相清掉、不必反覆重建。
  • 真並行:長測試、部署、AI agent 各佔一個目錄,同時進行。
  • 單一 remote 設定:全部 worktree 共用同一組 remote 與認證,少一份維護。

⚠️ 缺點 / 代價

  • 每個 worktree 仍是一整份工作檔:大 repo 開很多個會佔不少磁碟(省的是歷史,不是原始碼)。
  • 依賴要各裝一份:node_modules、venv、build cache 每個 worktree 各自一份,得各自安裝。
  • 同分支不能重複 checkout:偶爾會被這條規則卡到。
  • 認知與清理成本:容易忘了自己開過哪些、忘記 remove/prune,目錄越積越亂。
  • 工具相容性:少數工具/IDE 假設「一個 repo 一個工作目錄」,對 worktree 支援不完美;submodule 場景也較複雜。

⑧ 常見坑 + 最佳實踐

坑解法 / 最佳實踐
用 rm -rf 直接刪 worktree 目錄改用 git worktree remove;若已誤刪,跑 git worktree prune 清中繼資料
把 worktree 開在主目錄「裡面」一律開在旁邊或集中資料夾,避免 gitignore/索引混亂
「already checked out」錯誤該分支已在別的 worktree;改用別的分支,或 --detach 看 commit
忘記開過哪些 worktree養成 git worktree list 的習慣;採一致命名(如 proj-<用途>)
依賴/環境變數各不同每個 worktree 各自 install;搭配 direnv/mise 管環境;需要時開 extensions.worktreeConfig
搬動目錄後連結壞掉git worktree move 來搬;若手動搬過,用 git worktree repair 修復
💡 清理節奏：任務結束就 git worktree remove,並定期 git worktree prune。把 worktree 當「用完即拋的臨時工作檯」,而不是長期並存的十個分身。

⑨ 該用 worktree、還是 clone、還是切分支?

需求建議
只是換到另一個分支工作,手上沒有未完成的改動git switch 切分支就好(最輕)
要同時存在多個分支的工作目錄、共用歷史git worktree
要完全獨立的環境(不同 remote/config/實驗性破壞)git clone 另一份(較重但最隔離)

worktree vs clone 快速對照

git worktree另做一份 git clone
歷史/物件共用一份(省空間)各一份(重複)
建立速度快(不用重抓)慢(重新 clone/fetch)
commit 互通立即共通(同一物件庫)要 push/fetch 才同步
隔離程度工作目錄隔離,設定共用完全隔離
適合並行分支、hotfix、review、平行 agent完全獨立的環境/實驗

⓪ 一句話總結

不是把模型做大，而是把「任務做小」。挑一顆現成的小模型（1–8B），用幾百到幾千筆「輸入 → 你要的輸出」範例，透過 LoRA / QLoRA 微調，就能讓它在單一任務（分類、抽取、格式轉換、工具呼叫…）上追平、甚至超越大模型 —— 而且便宜 10–30 倍、跑得更快、還能自己部署。

💡 核心心法：大模型是「通才」，小模型是「專才」。當你只需要一件事被穩定、便宜、快速地重複做好時，訓練一個專才幾乎永遠是更划算的選擇。NVIDIA 2026 的研究甚至主張：小模型才是 Agent 系統的未來。
你想做的事建議做法本單元章節
只是想試效果、量少、不想訓練先用 Prompt / RAG（免訓練）④ 決策樹
固定任務、要穩定 + 省成本LoRA / QLoRA 微調⑤⑥⑦

① 什麼是 SLM（Small Language Model）

SLM 指參數量相對「小」的語言模型。業界常用的分界是 10B 參數以下，實務上做單一任務最常用的是 1B–8B 這個甜蜜區間。

類別參數量代表模型（示意）能跑在哪
超小 / 邊緣0.5B – 1.5BQwen 0.5B/1.5B、Gemma 2B、SmolLM手機 / 樹莓派 / CPU
小（主力甜蜜區）3B – 8BLlama 3 8B、Mistral 7B、Phi、Gemma 7B單張消費級 GPU
中~13BLlama 13B 類單張較大 GPU
大（通才 LLM）70B+ / 數百 BGPT / Claude / Llama 70B 等雲端多卡 / API
📌 觀念釐清：「訓練小模型」在 99% 的情況下不是從零開始（那要海量資料 + 巨額算力）。而是拿一顆已經預訓練好的開源小模型，做「微調（fine-tuning）」——只教它你的那一件事。這才是個人 / 小團隊能負擔的路。

② 為什麼要「專攻單一任務」的小模型

2026 年 NVIDIA Research 一篇論文《Small Language Models are the Future of Agentic AI》把這件事講得很直白：Agent 系統大多數的呼叫，其實只是反覆做少數幾個很窄的任務——解析一個指令、選一個工具、把結果整理成固定的 JSON。這種工作，用大模型是「殺雞用牛刀」。

專才小模型的四大好處

面向大模型（通才）專才 SLM
成本API 按 token 計費，長期昂貴推論成本常低 10–30 倍；一次微調很便宜
速度大、慢、常要排隊參數少 → 反應快，適合即時 / 高頻
穩定性通才、輸出容易發散只學一件事 → 格式穩定、更可預測
掌控權資料要送到雲端可自己部署、資料不出門、可離線
實例（NVIDIA）：把 Llama 3 8B Instruct 微調來做「程式碼審查的嚴重度評分」這一個窄任務，嚴重度預測準確率提升約 18%——用的是一顆 8B 小模型，不是幾百 B 的巨獸。
💡 一句話：當任務「窄且重複」時，一顆便宜的專才，往往打敗一顆昂貴的通才。這就是為什麼「小模型 + 單一任務」是 CP 值最高的組合。

③ 哪些任務適合 / 不適合小模型

選對任務，成功一半。小模型最擅長「輸入 → 固定形式輸出」的窄任務。

任務類型例子適合度
分類 / 標籤情緒分析、意圖分類、垃圾訊息判定、緊急度分級非常適合
資訊抽取從文件抓出金額、日期、人名、把病歷轉結構化欄位非常適合
格式轉換自然語言 → 固定 JSON / SQL / 指令非常適合
工具呼叫 / 路由Agent 裡選對工具、填對參數非常適合
固定風格改寫 / 摘要把客服對話濃縮成三行重點、統一語氣適合
單一領域問答只回答某產品 / 某法規的問題（常配 RAG）適合
開放式長篇推理寫小說、跨領域自由對話、複雜多步規劃留給大模型
需要廣博世界知識百科式通才問答留給大模型
💡 判斷準則：如果你能用「一句話 + 幾個範例」把任務規則講清楚、而且輸出有固定形狀，那它幾乎一定適合小模型。反之，越開放、越需要世界知識，越該交給大模型。

④ 三條路線 + 決策樹（先別急著訓練！）

讓小模型「會做一件事」有三條路，成本由低到高。永遠從最便宜的開始試，不夠好再往下走。

路線做法成本什麼時候用
A · 提示工程 / RAG不改模型，靠 Prompt + 範例，或外掛知識庫最低先驗證可行性、資料會變動、量少
B · 微調（LoRA/QLoRA）用你的資料調整模型權重（的一小部分）中任務固定、要穩定 + 省成本 + 可部署
C · 知識蒸餾用大模型當老師，造資料再教小模型中沒有現成標註資料時（常與 B 併用）

🌳 決策樹

你要小模型做一個單一任務 │ ▼ Q1：先用 Prompt + 幾個範例，效果夠好嗎？ │ ┌────┴─────┐ 夠好 不夠好 │ │ ▼ ▼ 收工！用路線 A Q2：你手上有「輸入→正確輸出」的標註資料嗎？ （最省） │ ┌───┴────┐ 有 沒有 │ │ ▼ ▼ 路線 B Q3：有一顆好用的大模型可當老師嗎？ LoRA/QLoRA 微調 │ ┌────┴────┐ 有 沒有 │ │ ▼ ▼ 路線 C→B 先回去補資料 蒸餾造資料再微調 （人工標一批種子）
⚠️ 新手最常見錯誤：一上來就想微調。其實很多任務光靠「把 Prompt 寫好 + 給 3~5 個範例」就解決了。微調是最後手段，不是第一步。

⑤ 微調六步流程（路線 B 全貌）

幾乎所有 SLM 單一任務微調，都是這六步。先看全景，再看細節。

① 定義任務 ─► ② 準備資料 ─► ③ 選底模 ─► ④ 設定 LoRA ─► ⑤ 訓練 ─► ⑥ 評估 & 部署 (規則+格式) (輸入→輸出) (1–8B) (r/alpha/lr) (跑幾輪) (達標→上線) │ 沒達標 ↺ 回②補資料 / 調參數

定義任務與「成功長什麼樣」

寫下：輸入是什麼、輸出的固定格式是什麼、怎樣算對。這一步決定了資料格式和評估指標。含糊的任務 = 訓不出好模型。

準備資料集（見 ⑥）

整理成「輸入 → 期望輸出」的成對範例。品質 > 數量。切成 train / validation 兩份。

選一顆底模（base model）

依任務難度與部署硬體挑 1B–8B 的開源 Instruct 模型。任務越窄、硬體越小 → 選越小的。先小後大，不夠再換大。

設定 LoRA / QLoRA 參數（見 ⑦）

設定 rank（r）、alpha、target modules、learning rate、epochs。用 QLoRA 可讓 7B 塞進單張 ~16GB GPU。

訓練

跑 1–3 個 epoch，盯著 validation loss。Loss 不再降、或開始上升 → 該停了（過擬合）。

評估 → 部署（見 ⑩）

用「模型沒看過」的測試集算準確率 / F1 等指標，和微調前、和大模型比。達標就合併權重、量化、部署（Ollama / vLLM 等）。

⑥ 資料集怎麼準備（成敗關鍵）

微調界有句老話：「Garbage in, garbage out.」模型好壞，八成看資料。單一任務的好處是：資料需求量遠比你想像的少。

要準備多少筆？

任務難度大致筆數（起步）備註
簡單分類 / 固定格式抽取數百 ~ 1,000任務越窄需求越少
中等（風格改寫、結構化）1,000 ~ 5,000多樣性比數量更重要
較複雜（多步、含推理）5,000 ~ 數萬常搭配蒸餾造資料
💡 研究發現：資料少的時候，蒸餾（用大模型造資料）幫助最大；而只挑「最難的那些題目」來訓練，往往比塞一堆簡單題更有效。品質、難度、多樣性，都比純數量重要。

資料長什麼樣（常見格式）

最通用的是 instruction / chat 格式的 JSONL，一行一筆：

jsonl · 意圖分類範例 
{"messages": [
  {"role": "system", "content": "你是意圖分類器，只輸出以下其中一個標籤：查訂單 / 退款 / 投訴 / 其他"},
  {"role": "user", "content": "我上週買的東西到現在還沒到，到底在哪？"},
  {"role": "assistant", "content": "查訂單"}
]}
{"messages": [
  {"role": "system", "content": "你是意圖分類器，只輸出以下其中一個標籤：查訂單 / 退款 / 投訴 / 其他"},
  {"role": "user", "content": "這產品根本是壞的，我要退錢！"},
  {"role": "assistant", "content": "退款"}
]}

品質檢查清單

  • 輸出格式 100% 一致 —— 標籤大小寫、JSON 欄位、標點都要統一，模型會照抄你的不一致。
  • 涵蓋邊界案例 —— 模糊的、罕見的、容易搞錯的例子要放進去（這些最有教學價值）。
  • 類別平衡 —— 別讓某一類佔九成，否則模型會「無腦猜多數類」。
  • 切出乾淨的驗證/測試集 —— 且絕不能和訓練集重疊，否則你會被虛高的分數騙。
  • 去除敏感資訊 —— 尤其資料來自真實日誌時。

⑦ LoRA / QLoRA 白話解說 + 建議參數

為什麼不「整個模型重訓」？

一顆 7B 模型有 70 億個參數，全部重訓要巨量顯存與時間。LoRA（Low-Rank Adaptation）的聰明之處：凍結原本的權重不動，只在旁邊掛上一小組「可訓練的補丁」，訓練時只更新這些補丁。

  • 省顯存最多 ~90%、訓練快 2–3 倍。
  • 產物只是一個幾 MB ~ 幾十 MB 的小檔（adapter），可以隨插隨用、一個底模掛多個任務。
  • QLoRA = 先把底模量化成 4-bit（更省顯存）再套 LoRA。代價是極小的品質損失，換來「7B 塞進單張 ~16GB 消費級 GPU」。
原始權重 W（凍結，不動） │ 輸入 ─────►│─────────────────► 輸出 │ ▲ └──► A × B（LoRA 補丁，只訓這個）┘ 小、可訓練、幾十 MB QLoRA：把上面的 W 先壓成 4-bit，再掛 A×B

建議起手參數（單一任務通用）

參數建議值白話說明
r（rank）8–16（難任務可 32–64）補丁的「容量」。越大越能學複雜關係，但也更易過擬合、更吃資源
lora_alpha常設為 r 的 1–2 倍（如 r=16→alpha=16 或 32）補丁的「影響力縮放」
target_modules所有線性層（q/k/v/o + gate/up/down proj）掛越多層通常效果越好；只掛注意力層更省
lora_dropout0.05輕微防過擬合
learning_rate1e-4 ~ 2e-4比全量微調可以大一點
epochs1–3單一任務通常 1–3 輪就夠，過多會過擬合
batch + 梯度累積小 batch + 累積到等效 16–32顯存不夠就靠梯度累積湊大 batch
⚠️ 調參心法：先用上面這組「保守起手值」跑一次拿到基線，一次只改一個參數再比較。别一次改五個，否則你不知道是誰讓結果變好或變壞。

⑧ 知識蒸餾：用大模型「教」小模型（沒資料時的救星）

最常見的卡關是：「我知道要微調，可是我沒有標註好的資料。」知識蒸餾（Knowledge Distillation）正是解法——讓一顆強大的大模型當老師，幫你生成訓練資料，再拿去教小模型（學生）。

師生流程（兩步）

Step 1 · 老師造資料 你 ─(給一批輸入 + 清楚指令)─► 大模型（老師） ─► 高品質「輸出」/ 含推理過程 │ ▼ 一份合成訓練集（輸入→輸出） Step 2 · 學生學習 合成訓練集 ─► LoRA 微調小模型（學生） ─► 學會用老師的方式做這件事
  • 老師的輸出比人工標註更「營養」：人工可能只寫「緊急」，老師卻能示範判斷理由、格式、信心程度，讓學生一起學起來。
  • 蒸餾最適合定義清楚的窄任務：分類、資訊抽取、問答、工具呼叫——正好就是小模型的主場。
  • 造越多、越多樣的資料，蒸餾效果越好；但在資料本來就多時，蒸餾的邊際好處會遞減。
  • 老師不必是最頂級的巨獸——師生差距別太大，學生反而更容易學得像。
💡 實務組合技：「蒸餾 → 微調」是黃金搭配。先用大模型/API 造 1–2 千筆漂亮資料，人工快速抽查修正，再用 LoRA 微調小模型。之後線上跑的就是便宜的小模型，大模型只在「造資料」階段出場一次。

⑨ NVIDIA 的「LLM → SLM」六步轉換法（Agent 場景）

如果你已經有一個用大模型驅動的 Agent，NVIDIA 論文給了一套把昂貴的大模型呼叫，逐步替換成便宜專才小模型的標準流程。核心精神：大模型只留給「決策 / 規劃」的關鍵時刻，其餘重複雜活全交給小模型。

資料收集（Data Collection）

把現有 Agent 對大模型的每一次呼叫（輸入 + 輸出）安全地記錄下來，累積真實使用資料。

資料清理（Curation）

去除個資與敏感內容，清洗成可用的訓練素材。

任務分群（Task Clustering）

把這些呼叫依「在做什麼」分群，找出反覆出現的少數幾種窄任務（例如：意圖解析、工具選擇、JSON 格式化）。

挑選小模型（SLM Selection）

依每一群任務的難度與需求，各挑一顆合適的小模型。

微調（Fine-Tuning · PEFT）

用該群的資料，以 LoRA/QLoRA 等 PEFT 方法，把小模型練成那一群任務的專才。

持續迭代（Iteration）

上線後持續收集新資料、監控表現，週期性地重新微調，讓小模型越用越準。

📌 落地策略：先用大模型把整個任務跑通、畫出地圖 → 找出「熱點」（被呼叫最多、最重複的節點）→ 一個一個換成專才小模型 → 迭代微調 + 監控。這樣既保留大模型的彈性，又吃到小模型的成本與速度紅利。

⑩ 評估與驗證：怎麼知道「訓練成功了」

沒有評估的微調 = 盲飛。你至少要能回答：它比微調前好嗎？比大模型省又不差嗎？

選對指標（看任務類型）

任務主要指標
分類 / 標籤Accuracy、F1（類別不平衡時看 F1）、混淆矩陣
資訊抽取欄位級 Precision / Recall / F1
格式轉換（JSON/SQL）格式合法率（能不能被解析）+ 內容正確率
工具呼叫選對工具率 + 參數填對率
摘要 / 改寫ROUGE 等自動分數，再加人工抽查 / 用大模型當裁判

三個一定要做的比較

  1. 微調前 vs 微調後（同一顆小模型）—— 證明微調真的有效。
  2. 小模型 vs 大模型 / API —— 證明你「省了成本卻沒掉太多品質」。
  3. 看 loss 曲線 —— 訓練 loss 一直降但驗證 loss 開始升 = 過擬合，該減少 epoch 或 rank。
🚫 頭號陷阱：資料洩漏（data leakage）。如果測試題目（或幾乎一樣的題目）出現在訓練集裡，分數會虛高得離譜，上線後現形。務必確保測試集是模型完全沒看過的。

下面用 Hugging Face 生態（peft + trl）示意一段 QLoRA 微調骨架。重點是看懂每一段在做什麼，實際跑請在有 GPU 的環境（如 Google Colab 免費 T4 就能跑小模型）。

QLoRA 微調骨架（示意）

python · 概念示意，非逐行可執行 
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig
from peft import LoraConfig
from trl import SFTTrainer, SFTConfig
from datasets import load_dataset
import torch

BASE = "meta-llama/Meta-Llama-3-8B-Instruct"   # 換成你要的小模型

# 1) 4-bit 量化載入底模（QLoRA 的 Q）
bnb = BitsAndBytesConfig(
    load_in_4bit=True, bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=torch.bfloat16,
)
model = AutoModelForCausalLM.from_pretrained(BASE, quantization_config=bnb, device_map="auto")
tok = AutoTokenizer.from_pretrained(BASE)

# 2) 你的資料集（⑥ 準備的 JSONL：欄位 messages）
data = load_dataset("json", data_files="my_task.jsonl", split="train")

# 3) LoRA 設定（⑦ 的建議起手值）
lora = LoraConfig(
    r=16, lora_alpha=32, lora_dropout=0.05, bias="none", task_type="CAUSAL_LM",
    target_modules=["q_proj","k_proj","v_proj","o_proj","gate_proj","up_proj","down_proj"],
)

# 4) 訓練設定
cfg = SFTConfig(
    output_dir="out", num_train_epochs=2,
    per_device_train_batch_size=2, gradient_accumulation_steps=8,  # 等效 batch=16
    learning_rate=2e-4, logging_steps=10, save_strategy="epoch",
)

# 5) 開訓！只更新 LoRA 補丁
trainer = SFTTrainer(model=model, train_dataset=data, peft_config=lora, args=cfg)
trainer.train()
trainer.save_model("out/adapter")   # 產物是幾十 MB 的小 adapter

⑫ 常見坑 + 出發前檢查清單

五個新手最常踩的坑

坑症狀解法
該用 Prompt 卻硬要微調花大力氣，效果跟寫好 Prompt 差不多先試路線 A，不夠再微調
資料格式不一致模型輸出忽大忽小寫、JSON 時好時壞把輸出格式標準化到 100% 一致
過擬合訓練分數超高，一上真實資料就崩減 epoch / 減 rank、增資料多樣性
資料洩漏測試分數美到不真實確保測試集完全獨立、沒重疊
一次改太多參數不知道到底哪個改動有效一次只改一個，對照基線

✅ 出發前檢查清單

  • ☐ 任務夠窄、輸出有固定形狀了嗎？（③）
  • ☐ 先用 Prompt / RAG 試過了嗎？真的需要微調嗎？（④）
  • ☐ 有一份格式一致、含邊界案例、乾淨切分的資料集嗎？（⑥）
  • ☐ 選了合適的小底模，並用 QLoRA 起手參數了嗎？（⑦）
  • ☐ 有獨立的測試集 + 選好指標，能和「微調前 / 大模型」比較嗎？（⑩）
  • ☐ 上線後有持續收資料、週期性再訓練的計畫嗎？（⑨）

  1. 什麼樣的任務該用小模型、什麼該留給大模型？

  3. 沒有標註資料時，怎麼用蒸餾生出訓練集？

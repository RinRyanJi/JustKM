🧠 為什麼 LLM 會「忘記」被賦予的 Skill

明明給了 System Prompt / 工具 / 微調,模型卻在長對話裡漸漸不照做、或有工具不用 · 拆解五個核心機制(從注意力、截斷、災難性遺忘到指令衝突),配上四招經過驗證的工程解法

⓪ 一句話總結

「LLM 忘記 Skill」不是一種毛病,而是至少五個不同機制的共同表象。它們分屬兩大類:推論時(上下文側)——注意力被稀釋、關鍵定義掉進「中間」被忽略、被截斷/摘要掉、被最近幾輪帶偏、被後續使用者指令壓過;以及訓練時(權重側)——微調把舊技能的觸發邏輯覆蓋掉。對症的解法各不相同,把「遺忘」當單一問題去救,通常救錯地方。

核心心法:先分辨你遇到的是哪一類——是「模型看不到規則了」(上下文側),還是「模型權重裡的規則被改壞了」(權重側),還是「規則還在但被更近/更強的訊號壓過」(近期效應/指令衝突)。診斷對了,才知道要用 Anchor 重注入、RAG 掛載、約束解碼,還是 Critic 看門狗。

② 注意力稀釋與「中間迷失」(Lost in the Middle)

在長對話或複雜 Agent 流程裡,上下文長度會快速膨脹,而 Transformer 的 Self-Attention 不是均勻地看每個 token。

  • 注意力權重分散:面對數萬到數十萬 token,最開頭定義的 System Prompt(Skill 定義、Tool schema、調用規則)拿到的注意力,會隨對話變長而逐漸被稀釋。
  • 位置偏差(U 形曲線):研究《Lost in the Middle》發現,模型對 context 最前端與最尾端資訊的召回率最高,中間最差。若 Skill 定義夾在大量工具輸出、錯誤日誌、程式碼片段之間,就很容易被忽略。

▲ 經典 U 形:兩端高、中間低。原論文指出,關鍵資訊落在中間時,表現最多可掉約 20 個百分點,最壞情況甚至低於「完全不給資料」的基線(數字以原論文為準)。

更深一層的原因

  • Attention sink:模型會把不成比例的注意力丟在最前面幾個 token(StreamingLLM 的發現)——這解釋了「開頭」為何吃重,也提示只保留少數 sink token 就能穩定長流。
  • RoPE 的距離衰減:旋轉位置編碼天生讓注意力隨相對距離衰減,結構上就偏重近距離、輕忽遠距離。
  • Context Rot:Chroma 2025 的報告更進一步——就算是很簡單的任務,只要輸入變長,準確率就會下降,而且還沒到視窗上限就開始掉、各模型退化不一。所以「視窗夠大」不等於「內容都被用上」。

③ 上下文截斷與滑動窗口

很多框架(LangChain、AutoGPT、各類 Agent 腳本)為了省 token 或防止超過上限,會用截斷策略:滑動窗口(丟最舊訊息)、摘要壓縮、刪除歷史。

問題是:如果 Skill 的使用範例(Few-shot)、工具狀態、觸發條件在壓縮過程中被 summarize 掉,模型在後續輪次裡本質上就「看不見」這項技能的具體要求——不是它不想用,而是規則已經不在它眼前了。這跟第②節不同:②是「還在但被稀釋」,③是「根本被刪掉」。

常見陷阱:摘要器通常為「對話語意」優化,而不是為「保留硬性規則」優化。它很樂意把「你必須先呼叫 validate() 再回覆」這種一次性但關鍵的規則,壓縮成一句「討論了驗證流程」——語意保住了,可執行的約束卻蒸發了。

④ 微調中的「災難性遺忘」(權重側)

如果 Skill 是透過 LoRA 或全參數微調(SFT)寫進權重,遺忘的機制就完全不同了——問題出在權重本身,而非 context。

  • 梯度覆蓋:學新技能/新資料時,參數更新可能破壞原有的權重分佈,把先前學會的 Skill 觸發邏輯覆蓋掉。這個現象最早由 McCloskey & Cohen(1989)提出,稱「災難性干擾」。
  • 泛化衝突:若訓練資料的分佈,與推論時的真實場景(Prompt 措辭、上下文格式)差太多,權重裡的 Skill 隱式特徵就激活不了。
  • LoRA 只是減輕、不是根治:研究顯示 PEFT/LoRA 比全微調少一些遺忘,但不會消除;而且退化常先表現為「指令遵循能力下降」。
對策方向(權重側專屬):標準解法是 replay(回放)——微調資料裡混入原始分佈/通用指令/對話資料,別讓模型只看到新技能的樣本。這是 Prompt 工程救不到的地方,因為病灶在權重不在 context。

⑤ 近期效應、語意漂移與指令衝突

LLM 本質是「依機率生成下一個 token」的自回歸模型,這帶來兩個很實務的問題:

模仿最近的模式(Recency Bias & 語意漂移)

對話進入深水區後,模型會強烈傾向模仿最近幾輪的輸出風格與模式。如果前一兩輪因為環境報錯、格式混亂、或模型自己試了別的替代做法,它就會順著這股慣性繼續走,脫離原本被設定的 Skill 路徑。

有多快?近期多輪研究指出,對「較早輪次指令」的遵循度會隨輪數單調下降——有研究測得某強模型從第 1 輪到第 3 輪準確率由約 88% 掉到 71%;另一研究發現約 74% 的漂移案例在第 2 輪就出現首次違規。有趣的是,模型往往還「記得」那條被違反的規則——是「知道但不做」,而非真的忘了(數字以各原論文為準)。

強指令衝突(System vs. User)

使用者在後續提問中的隨意指令,容易在局部壓過最外層 System 定義的嚴格 Skill 規則。根因被 OpenAI 的《Instruction Hierarchy》講得很直白:模型常把 System Prompt 和使用者輸入視為「同等優先級」,所以後來的使用者話語就能覆蓋前面的系統規則。移除 System Prompt 更會造成全面退化。

⑥ 工具選擇歧義(有工具卻不用的假象)

在 Tool Use / Function Calling 的 Skill 機制裡,「遺忘」常常是一種假象——工具明明掛著,模型卻退回用通用知識或純文字硬推:

  • 邊界模糊:存在多個功能重疊的 Skill(如 read_file 與 search_code),模型難以判斷該用哪個。
  • 描述過寬:Skill 的 description 寫得太籠統、缺少觸發條件,模型不確定何時該用,乾脆不用。
  • 工具太多:可選工具一多,選對率就掉。研究《RAG-MCP》顯示,改用「按需檢索工具」後,工具選擇準確率從約 13.6% 提升到 43.1%,同時 prompt token 省下逾一半。
直覺陷阱:「把所有能力都掛上去」通常反而更弱。工具不是越多越好——每多一個功能重疊、描述含糊的工具,都在稀釋模型「選對那一個」的機率。

⑦ 四招經過驗證的工程解法

← 左右滑動看完整圖 →
▲ 四招可疊加:先用 RAG 只掛需要的 Skill(治⑤⑥),把關鍵規則 Anchor 到底部(治①②),用約束解碼鎖死輸出格式(治語意打混),再由 Critic 看門狗兜底(治所有漏網)。
解法怎麼做主要治哪個機制
① 動態 System Prompt 注入(Anchor)每輪推論前,把關鍵 Skill 規格與強制規則重新拼接到最近上下文的最底層(User Prompt 前後),用「近期效應」強行拉高注意力權重① 中間迷失、⑤ 近期效應
② 語意檢索動態掛載(RAG Skills)別一開始把所有 Skill 塞進 context;依當前問題用 Vector DB 只檢索最相關的 1~2 個 Skill注入當前輪次⑥ 工具歧義、② 稀釋、③ 省 token
③ 結構化約束(Constrained Decoding)用 JSON Schema / BNF 文法強制輸出必須符合特定 Tool Call 格式,在解碼時遮蔽非法 token,堵死「用自然語言打混過去」⑤ 漂移、⑥ 不呼叫工具
④ 反思 / 看門狗(Critic)引入輕量驗證步驟:發現未調用預期 Skill 或格式違規就自動 reject,攜帶修正 Prompt 要求重做(Reflexion / Self-Refine 家族)兜底所有機制

幾個值得加進工具箱的延伸招式

  • Sandwich(前後夾):把最關鍵那條規則同時放在最前面和最後面——一次吃 primacy、一次吃 recency,避開中間。
  • 工具回應壓縮:主動摘要或丟棄過時的工具輸出,別讓日誌/中繼結果把規則擠出視窗(Context Rot 的實務對策)。
  • 記憶分層(MemGPT 式):把「系統指令 + 最近歷史 + 可寫暫存區」放在主視窗,其餘用函式呼叫分頁進出外部記憶——像作業系統的虛擬記憶體。
  • Instruction Hierarchy:選用有「指令階層」訓練的模型/API,讓 System 規則天生高於使用者臨時指令。
  • 約束解碼的代價:過度約束會有「alignment tax」——可能傷到推理品質。鎖格式,但別把思考空間也鎖死。

💡 DeepSeek Harness 的 agent 設計思路:不只是插件

插件只是表層。底下有一組更深的主張——把 agent 當「可組合的作業系統」而非單體循環

依原始碼與 docs 逐處查證 9 個獨到思路

⓪ 核心主張:agent 是「可組合的作業系統」

一般 agent 常是「一個寫死的迴圈:呼叫 LLM → 解析工具呼叫 → 執行 → 回填」。DeepSeek Harness 的不同,不在「它用了插件」,而在它把 agent 拆成一套作業系統式的結構:

  • 一份只追加的事件日誌當唯一真相,模型看到的歷史是從日誌推導出來的;
  • 持久事實與即時控制兩個平面分離;
  • 擴充點是中介層(waterfall)——不改迴圈就能包住每一步;
  • 安全用單調守衛(只能收緊、不能放寬);
  • 每個註冊都是可逆副作用(能熱插拔);
  • 能力藏在可替換的 seam 後面(可換真模型、可重放、可離線測試)。
下面九節逐一拆解;每節開頭用「一般 agent → 它的做法」點出差異。本頁依撰寫時 clone 的原始碼與官方 docs/ 整理,dsh 為開發者預覽,細節以官方最新為準。

① 事件日誌即真相:兩個平面分離

一般 agent → 把「messages 陣列」當狀態,邊跑邊改。  它 → 只追加的事件日誌是真相,模型歷史從日誌推導。

Harness 把資訊分成兩個平面:

  • 持久回放事實 存在 session/event(只追加的 SessionEvent 日誌)——turn/*、step/*、user/message、assistant/*、tool/* 都是這種。重新載入後仍在。
  • 即時控制與狀態 走 agent/* 事件(inbox、步驟、狀態、請求、驗證、續跑)——觀察/攔截進行中的工作用它。

關鍵一句(架構文件原文):「從日誌推導 model history」。也就是說,「模型這一步看到什麼」不是某個被就地修改的陣列,而是對不可變事件日誌的一次投影。

為什麼強:① 天生可回放、可稽核、可時間旅行(compaction、branch 都只是日誌上的條目);② 崩潰復原=重讀日誌;③ 任何「壓縮/修剪」都不動真相,只改投影。這跟 Prime Agent 的 JSONL 樹狀 session 是同一家族思路。

② Waterfall 中介層:不改迴圈就能擴充

一般 agent → 要加功能就改迴圈的 if/else。  它 → 迴圈固定,擴充是「環繞中介層」。

關鍵事件(agent/pre-step、agent/request、llm/stream、三個 tools/*)是 waterfall:監聽器收 (...args, next),像洋蔥式中介層——

  • 呼叫 next() → 執行下游,可包裝其回傳再往外傳;
  • 不呼叫 next() 直接 return → 短路(有決策權的策略監聽器就這樣攔截)。

於是 timeout、retry、metrics、權限、沙箱、結果改寫,都是掛在 seam 上的監聽器,而agent loop 本身一行都不用改——連 agent loop 都是可換的插件(ctx.agentLoop)。

對照四種分發模式:emit(純觀察)、waterfall(可包裝/短路)、parallel(並行 await)、serial(按序 await 有回傳)。選對事件域與分發模式,是大多數改動的第一個決定——這把「擴充」變成宣告式的,而非改核心。

③ 單調守衛與 fail-closed:安全只能收緊

一般 agent → 權限靠散落的 if 判斷,容易被繞過或「預設放行」。  它 → 守衛「只能拒絕或棄權,永不授予」。

工具執行流水線裡有一層單調守衛(monotonic guards),原文特性:「deny or abstain; identity protected」——守衛只能拒絕或棄權,不能授予權限。這是刻意的單調性:多加一個守衛只可能讓事情更嚴,不可能放寬。搭配:

  • Approval 一次性提示(ctx.approval):不存在或無法回答時 → 一律 deny(fail-closed,失敗時傾向拒絕而非放行);
  • fs 意圖閘:工具對檔案的變更要先過 fs/write-intent / fs/edit-intent;
  • identity protected:守衛不能竄改呼叫者身分。

工具執行流水線(把關的完整順序)

assistant 訊息含 tool-call │ tool/call(執行前先記日誌) ▼ tools/pre-execute waterfall ← hooks、權限、沙箱 │ allow │ deny → 跳過工具本體 │ ask → ctx.approval 一次性 ▼ 單調守衛(deny 或 abstain;身分受保護) │ allow ▼ tools/execute waterfall（環繞:timeout / retry / metrics） │ ▼ 工具 execute() 本體 ─▶ fs/write-intent | fs/edit-intent（僅檔案變更） ▼ tools/post-execute waterfall ← accept / block / replace / 加 context ▼ 外層正規化(pipeline 拋錯 → isError) ─▶ finalizeContent ─▶ tool/result（凍結的權威結果,單一面向模型的結果） ▼ active-batch additionalContexts FIFO（在記錄的 tool result 之後,注入 user/message）
三個獨到點:① 拋錯會被正規化成 isError(不讓例外亂竄);② tool/result 是凍結、權威、單一面向模型的結果(不會有兩種說法);③ 額外 context 用 FIFO 在 tool result 之後注入,而不是硬塞進本次呼叫。

④ 可逆副作用 + 熱替換:每個註冊都能乾淨拔除

一般 agent → 註冊工具/提示常是全域可變狀態,難以卸載。  它 → 每個註冊都經 ctx.effect()/ctx.on(),teardown 自動撤銷。

提示片段、工具 schema、模型適配器、監聽器…全都是可逆副作用:reload 或 teardown 時「按預期撤銷」。每個註冊都應有對應的 disposer(從 ctx.effect() 回傳、或用框架輔助方法),若卸載順序有要求就放同一個 effect。這帶來:

  • HMR(熱模組替換):插件與設定可以熱替換(vendored 的 cordis-plugin-hmr);
  • Profile/bundle 的 patch 疊加能安全替換任一條目的整段 config,因為舊的能乾淨退場;
  • 「沒有需要打補丁的特權內核」——擴充=把插件掛旁邊,不是改核心。

⑤ 能力 seam:可替換、可重放、可離線測試

一般 agent → 直接 import 某家 SDK,綁死。  它 → 能力藏在穩定的 ctx.<key> seam 後面,實作可換。

同一個服務鍵背後可掛不同實作(從能力圖 capability-seams 可見):

seam(ctx 鍵)可替換的實作妙用
ctx.llmllm-deepseek / llm-pi-ai / llm-replayllm-replay = 用錄好的回應重放 → 測試不燒 token、可重現
ctx.sessionPersistencesession-persistence-jsonl / -sqlite存法可換(檔案 or DB)
ctx.storagestorage-json / -sqlite非 session 資料的儲存中樞
ctx.toolResultPrunercompaction-tool-result-pruner不用模型就能修剪工具結果(確定性壓縮)
ctx.tokenMetertoken-meter重放式 token 量測
ctx.credentials / ctx.settingscredentials-local / settings-file憑證/設定都是 seam
兩個特別有意思的:① llm-replay——把模型串流錄下來重放,讓 agent 行為可重現、可離線測(一般 agent 很難做到);② model-free 的工具結果修剪——壓縮不一定要再叫一次模型,可用確定性規則,省錢又穩定。

⑥ inbox 與非同步紀律:「非同步狀態 ≠ 同步狀態」

一般 agent → followup 當成「送一則、拿一則結果」的同步呼叫。  它 → 訊息進 inbox,run 區間要顯式定義。

輸入都經同一個 inbox 到達驅動器:有些訊息立即喚醒它;注入的 context 會留在 inbox,直到另一條訊息把它喚醒。這支撐了 steering(中途引導)——running 期間插話改方向——與背景注入。

防禦模式文件把一條紀律講得很清楚:「非同步狀態不是同步狀態」——

  • agent.followup() 沒有逐訊息的完成狀態或結果;多條排隊後續、steering、注入工作可能共用同一個 running 區間。
  • 所以不能把 agent/status 或 whenIdle() 當成某次 followup 的結果;真正擁有一次 run 的呼叫方必須顯式定義區間(例如從某訊息的 inbox 回執,到 agent 下次進入 idle)。
洞見:它正視「多輪、可插話、可背景注入」的 agent 是真並發系統,而不是請求-回應。很多 agent bug 就出在把非同步當同步——它用型別與紀律把這件事擋在門外。

⑦ 防禦性工程:把踩過的坑寫成規則

一般 agent → 出事再修。  它 → 把「發布過或差點發布」的缺陷,固化成防禦規則。

docs/defensive-patterns.md 是「來之不易的缺陷類別規則」。幾條對 agent 特別關鍵:

  • 正交結果獨立上報:一個結果可同時「超時 + exit 0 + 收到 signal」;timedOut/signal/exitCode 各自獨立回報,別把提前終止誤判成成功。
  • 公共約定兩側規範化:LlmRuntime.stream() 只用終止型 finish 分片暴露模型失敗(不靠拋例外),讓消費方不必猜例外來自 provider、包裝層還是自己。
  • dispose 要停穩,不只發停止訊號:清理要等子進程真的退出,並先關監聽器讓遲到事件靜默 → 不留孤兒進程。
  • 分發器隔離回調例外:一個行為不當的訂閱者絕不能破壞核心生命週期或餓死後面的監聽器。
  • 憑證衛生:啟動命令用清理過的環境變數,移除名稱含 *KEY*/*SECRET*/*TOKEN*/*PASSWORD* 的項;spill/暫存檔放 0700 私有目錄、隨機檔名、0600 獨佔開啟 → 防止憑證經工具輸出或 spill 檔外洩。
為什麼這對 agent 尤其重要:agent 會跑模型生成的指令、把輸出餵回模型。任何「憑證漏進輸出」「孤兒進程」「例外亂竄」都會被放大。把這些寫成發布規則而非口頭約定,是成熟度的訊號。

⑧ 供應鏈衛生:vendored + 可核驗的自動改名

一般專案 → 直接依賴上游套件。  它 → 把框架 vendored 進來、rescope 成自己的 scope。

Cordis 及其基礎庫以原始碼形式 vendored 在 vendor/,並改名發布到 @deepseek-ai scope(如 @deepseek-ai/cordis)。理由:每個 harness 包把框架列為 peer dependency,發布 harness 會連帶發布這層,用上游名發布等於在 registry 上占用別人的名字。而且:

  • 改名由 scripts/rescope-vendor.ts 承載,可 report、可 --apply、可回退(不靠手改);
  • 目錄名、版本號、依賴 range、上游 runtime 標識符刻意不動,讓 vendored 樹仍讀作一份上游快照;
  • 文件雙語配對還有 verify-translation-pairing 校驗。
思路:連「用了別人的框架」這件事,都用工程紀律處理——可重現、可核驗、可回退、不占用他人命名空間。這是把「供應鏈」也當成一等公民。

⑨ 一句話總結:它到底哪裡不一樣

面向一般 agentDeepSeek Harness
狀態可變 messages 陣列只追加事件日誌,歷史是投影
擴充改迴圈 if/elsewaterfall 中介層,迴圈不變
安全散落的權限判斷單調守衛 + fail-closed
生命週期全域可變、難卸載可逆副作用 + HMR
能力直接綁 SDK可替換 seam(可重放/離線測)
並發當請求-回應inbox + 顯式 run 區間
品質出事再修缺陷固化成防禦規則
收斂:DeepSeek Harness 真正的特色,是把 agent 從「一個聰明的迴圈」升級成「一個有事件日誌、中介層、單調安全、可逆生命週期、可替換能力的作業系統」。插件只是這套哲學的外顯。這與本站 自我演化綜述的「模組架構/拓撲演化」、以及 Prime Agent 的分層設計,指向同一個方向——agent 的競爭力越來越在「工程結構」,而非只在模型。

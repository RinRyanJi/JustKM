1. 架構總覽

系統設計原則

Codex Usage Tracker 採用 本機優先（local-first）的設計，由兩層架構組成：

  • Python 後端：負責 JSONL 檔案解析、SQLite 資料存儲、CLI 報表與成本估算
  • Next.js 前端：提供互動式儀表板，直接查詢同一個 SQLite 資料庫

核心優勢：

  • 完全本機儲存，無需網路連接
  • 增量匯入機制，避免重複處理相同檔案
  • 靈活的隱私控制（payload 捕捉選項）
  • 模型定價別名與成本估算
~/.codex/sessions/ └── rollout-*.jsonl ───→ Python Parser ───→ UsageEvent │ ↓ SQLite Database (events, sessions, turns, content_messages, tool_calls) ↓ ┌──────────────────────────┼──────────────────────────┐ ↓ ↓ ↓ CLI Report Next.js API Routes Web Dashboard (table/json/csv) (filter, aggregation) (charts, insights)

定價資料來源：

  • 預設定價：內嵌於 report.py（保守估算）
  • 自訂定價：從 SQLite 旁邊的 config.json 讀取
  • 環境變數覆蓋：CODEX_USAGE_CONFIG

3. JSONL 事件模型

典型 Rollout JSONL 事件結構

Codex rollout JSONL 檔案包含多種事件類型，核心的 token 使用事件如下：

{ "type": "token_count", "timestamp": "2026-03-15T10:23:45Z", "context": { "session_id": "sess_abc123def456", "model": "gpt-5.2-codex", "directory": "/home/user/project" }, "token_usage": { "total": 2847, "input": 1200, "cached": 0, "output": 1647, "reasoning": 0 }, "status": "success", "lifecycle": { "total_input": 5000, "total_output": 3500, "lifetime_total": 125000 } }

事件類型清單

事件類型 說明 主要欄位
token_count 單一 turn 的 token 使用統計 total, input, output, cached, reasoning
status_snapshot 會話狀態快照（5h/weekly 限制百分比） limit_5h_percent, limit_weekly_percent, context_window
session_start 會話初始化元資料 session_id, cwd, git_info, cli_version
turn_start turn 開始標記 turn_index, model, approval_policy
message 對話訊息（user/assistant） role, message_type, content
tool_call 工具調用事件 tool_type, tool_name, input, output, status

Token Count 事件詳解

欄位含義：

  • total：本次 turn 的所有 token 總和（input + output）
  • input：普通輸入 token（不含快取）
  • cached：快取輸入 token（如果存在）
  • output：模型輸出 token
  • reasoning：推理層 token（針對 reasoning 模型）
關鍵區別： total 通常等於 input + output，但在某些情境下可能包含推理 token。系統會分別追蹤 cached_input_tokens。

Lifetime（生命週期）Token

某些事件會附加累積統計：

  • lifetime_total_tokens：此會話自開始以來的 token 累積
  • lifetime_input_tokens：累積輸入 token
  • lifetime_output_tokens：累積輸出 token
用途： Lifetime token 用於驗證重複計算、檢測丟失事件或判斷會話的總消耗量。

4. 解析演算法

核心解析流程

系統採用逐行流式解析（streaming）JSONL 檔案，避免一次性載入整個檔案：

JSONL 檔案逐行讀取 ↓ ┌─────────────────────────────────┐ │ 嘗試 JSON 解析當前行 │ ├─────────────────────────────────┤ │ 成功？ │ │ ├─ 是 → 檢查 "type" 欄位 │ │ └─ 否 → 記錄警告，跳過此行 │ └─────────────────────────────────┘ ↓ ┌──────────────────────────────────┐ │ 根據 type 路由到對應解析器 │ ├──────────────────────────────────┤ │ • "token_count" → parse_token_usage() │ │ • "status_snapshot" → parse_status_panel() │ │ • "session_start" → parse_session_meta() │ │ • 其他 → extract_activity_event() │ └──────────────────────────────────┘ ↓ ┌──────────────────────────────────┐ │ 構建 UsageEvent / SessionMeta │ │ 物件（含時間戳記轉換） │ └──────────────────────────────────┘ ↓ 存儲到 SQLite

時間戳記轉換

JSONL 事件通常包含 UTC 時間戳記。系統會：

  1. 讀取 UTC 時間戳記（timestamp 欄位）
  2. 根據配置的時區轉換為本機時間（預設：Europe/Stockholm）
  3. 同時存儲兩個時間戳記：captured_at（本機）和 captured_at_utc（UTC）
from datetime import datetime from zoneinfo import ZoneInfo utc_time = datetime.fromisoformat(event['timestamp']) local_tz = ZoneInfo('Europe/Stockholm') local_time = utc_time.astimezone(local_tz) captured_at_utc = utc_time.isoformat() captured_at = local_time.isoformat()

去重機制

為避免重複計算相同事件，系統使用兩級去重：

第一級：檔案級去重

使用 ingestion_files 表追蹤：

  • path：檔案的絕對路徑
  • mtime_ns：檔案修改時間（納秒）
  • size：檔案大小（字節）
  • last_ingested_at：上次匯入時間戳記
  • content_hash：檔案內容 SHA256 雜湊（可選）

邏輯：若 mtime 和 size 未變，則跳過此檔案。

第二級：事件級去重

使用 sources

  • 為每個事件記錄 source_id（檔案來源）
  • 計算事件內容的雜湊值（session_id + timestamp + type + token 值）
  • 使用 INSERT OR IGNORE 避免重複插入

CLI 日誌與 App-server 日誌解析

CLI 日誌解析（ingest-cli）：

典型行格式：
Token usage: total=2847 input=1200 output=1647
或帶快取：
Token usage: total=10,857 input=10,562 (+ 48,000 cached) output=295
或帶推理：
Token usage: total=120 input=100 output=20 (reasoning 5)

正則表達式（parser.py）：
TOKEN_USAGE_RE = re.compile(
    r"Token usage:\s*total=(?P<total>[0-9,]+)\s+input=(?P<input>[0-9,]+)"
    r"(?:\s*\(\+\s*(?P<cached>[0-9,]+)\s+cached\))?\s+output=(?P<output>[0-9,]+)"
    r"(?:\s*\(reasoning\s+(?P<reasoning>[0-9,]+)\))?",
    re.IGNORECASE,
)

App-server JSON-RPC 日誌解析（ingest-app-server）：

解析 JSON-RPC 方法調用，提取：

  • turn_started 事件 → turn 計時開始
  • item_started 事件 → 工具調用、命令執行計時
  • turn_completed 事件 → turn 計時完成與狀態

6. 計算公式

基本 Token 計算

/* 本次 turn 的計算 */ turn_total_tokens = input_tokens + cached_input_tokens + output_tokens /* 如果包含推理 token（某些模型） */ if reasoning_output_tokens > 0: turn_total_tokens = input_tokens + cached_input_tokens + output_tokens + reasoning_output_tokens /* 累積（lifetime）驗證 */ expected_lifetime = previous_lifetime + turn_total_tokens actual_lifetime = event.lifetime_total_tokens if expected_lifetime != actual_lifetime: log("Possible missing events or session restart")

成本估算公式

系統使用 per 1M tokens 的定價模型：

/* 基本成本計算 */ cost = (input_tokens × input_rate + cached_input_tokens × cached_input_rate + output_tokens × output_rate) / 1_000_000 例子（GPT-5.2 Codex）： input_rate = 1.75 美元/百萬 cached_input_rate = 0.175 美元/百萬 output_rate = 14.00 美元/百萬 假設事件： input_tokens = 1000 cached_input_tokens = 500 output_tokens = 800 cost = (1000 × 1.75 + 500 × 0.175 + 800 × 14.00) / 1_000_000 = (1750 + 87.5 + 11200) / 1_000_000 = 13037.5 / 1_000_000 = $0.0130

聚合與報表成本

按時間段聚合：

  1. 按時段（日/週/月）和分組（模型/目錄/會話）查詢事件
  2. 對每個組合求和：SUM(input_tokens), SUM(cached_input_tokens), SUM(output_tokens)
  3. 使用聚合後的 token 數重新計算成本
/* SQL 查詢示例 */ SELECT DATE(captured_at) AS period, model, SUM(input_tokens) AS total_input, SUM(cached_input_tokens) AS total_cached, SUM(output_tokens) AS total_output FROM events WHERE captured_at >= ? AND captured_at <= ? AND event_type = 'token_count' GROUP BY DATE(captured_at), model ORDER BY period, model; /* 報表行計算 */ for each (period, model) group: pricing = lookup_pricing(model) cost = (total_input × pricing.input_rate + total_cached × pricing.cached_input_rate + total_output × pricing.output_rate) / 1_000_000

5 小時限制與週限制計算

5 小時限制（5h rate limit）：

  • 顯示為 limit_5h_percent_left（剩餘百分比）
  • 當 percent_left = 50% 表示已使用 50% 的 5 小時額度
  • limit_5h_resets_at 欄位指示下次重置時間
  • 5 小時窗口是滑動的，不是固定的日期邊界

週限制（weekly limit）：

  • 預設重置時間：Thursday 09:15 Europe/Stockholm
  • 可透過環境變數 CODEX_USAGE_WEEKLY_RESET 覆蓋
  • 顯示為 limit_weekly_percent_left
  • 系統會計算週配額估計（基於上個完整週的使用）
/* 週配額估計邏輯 */ last_week_start = current_time - (days_since_reset + 7) days last_week_end = current_time - days_since_reset days if last_week_end < current_time: last_week_total = sum_tokens(last_week_start, last_week_end) weekly_quota_estimate = last_week_total current_week_used = sum_tokens(last_week_end, current_time) if weekly_quota_estimate > 0: weekly_percent_used = (current_week_used / weekly_quota_estimate) × 100

Context Window 計算

/* 每個事件的 context 信息 */ context_used = tokens used in this turn context_total = maximum context window size context_percent_left = ((context_total - context_used) / context_total) × 100 /* 模型典型 context 大小（GPT-5 系列） */ GPT-5.2-Codex: ~128K tokens (128,000) GPT-5.4-Codex: ~128K tokens GPT-5 家族: 通常 128K-200K
Context 計算注意： Context window 是 最大可用容量，而非實際使用。context_used 反映本次 turn 實際消耗的 token；context_percent_left 基於剩餘百分比，不是 token 超限警告。

7. 去重與增量匯入

增量匯入策略

Codex Usage Tracker 核心優勢在於避免重複處理相同檔案。運作流程：

第 1 步：檔案發現與篩選

# 在 rollout.py 中 files_to_process = [] for rollout_file in discover_rollout_files(start_dir): file_stat = rollout_file.stat() mtime_ns = file_stat.st_mtime_ns size = file_stat.st_size # 若檔案修改時間在要求範圍內 if is_in_time_range(mtime_ns, time_start, time_end): files_to_process.append((rollout_file, mtime_ns, size))

第 2 步：查詢已處理檔案

# 查詢 ingestion_files 表 existing = conn.execute( "SELECT mtime_ns, size, content_hash FROM ingestion_files WHERE path = ?", (str(rollout_file),) ).fetchone() if existing: if existing['mtime_ns'] == mtime_ns and existing['size'] == size: # 檔案未變，跳過 print(f"Skipping unchanged: {rollout_file}") continue

第 3 步：解析與去重

# 逐行解析新檔案 with open(rollout_file) as f: for line in f: event = json.loads(line) parsed = parse_event(event) # 返回 UsageEvent 物件 # 計算事件雜湊（用於去重） event_hash = compute_hash( parsed.session_id, parsed.captured_at_utc, parsed.event_type, parsed.total_tokens ) # 使用 INSERT OR IGNORE insert_event(parsed, event_hash)

第 4 步：更新追蹤表

# 處理完成後更新 ingestion_files 表 conn.execute(""" INSERT OR REPLACE INTO ingestion_files (path, mtime_ns, size, last_ingested_at, content_hash) VALUES (?, ?, ?, ?, ?) """, ( str(rollout_file), mtime_ns, size, datetime.now().isoformat(), file_content_hash # 可選 ))

去重衝突處理

情況 1：檔案修改（新增事件）

  • 若 rollout 檔案新增了事件行（大小增加），系統會重新讀取
  • 新事件與舊事件一起插入（舊事件透過 INSERT OR IGNORE 被跳過）
  • 效率：只新增增量部分的成本

情況 2：檔案未修改

  • mtime 和 size 完全相同 → 整個檔案跳過
  • 不進行任何雜湊計算或行掃描

情況 3：檔案截斷或修改（罕見）

  • 若檔案被編輯，重新讀取整個檔案
  • 重複的事件會透過 source_id + content_hash 被去重
  • 新事件被新增，舊事件保留在資料庫
最佳實踐： Rollout 檔案通常是 只追加（append-only）的，因此增量匯入非常高效。若手動編輯了 rollout 檔案，可能需要重新匯入。

8. 隱私與 Payload 模式

三層隱私控制

模式 CLI 旗標 content_messages tool_calls payload 用途
預設 無 不儲存 NULL 隱私優先；Token 數據仍被追蹤
Payload --with-payloads 完整儲存 完整儲存 調試、完整審計；需要更多儲存空間
無內容 --no-content 不儲存 不儲存 最高隱私；僅 token 計數與元資料

儲存配置

隱私設定儲存在 meta 表中：

INSERT INTO meta (key, value) VALUES ('storage_profile_version', '3'), ('capture_payloads', 'true'), -- true 或 false ('tool_payload_profile_version', '1');

Payload 淨化命令

移除已儲存的 payload：

  • codex-track purge-payloads：刪除訊息，消毒工具呼叫
  • codex-track purge-content：刪除訊息和工具呼叫
  • codex-track vacuum：回收刪除後的磁碟空間

UI 隱私設定

在儀表板 Settings → Privacy 中可設定：

  • 「Store full message text and tool call payloads in the DB」複選框
  • 變更會立即影響後續匯入
  • 不會回溯修改已儲存的資料
注意： 預設不儲存 payload。若需要完整審計日誌，需明確啟用 --with-payloads 或在 UI 中開啟。

9. 限制與可能誤差

已知限制

限制 說明 影響 緩解方案
遺失事件 若 rollout 檔案損壞或不完整 Token 數據不完整 檢查 lifetime_tokens 差異；定期備份
時區轉換誤差 DST（夏令時）切換可能導致邊界混亂 日邊界附近的報表±1 小時誤差 使用 UTC 時間戳記進行跨時區比較
定價別名延遲 新模型發布後，內嵌定價不會立即更新 新模型成本估算可能不準確 透過 config.json 手動設定定價
Cache 計算精度 某些模型可能不報告快取 token cached_input_tokens 為 0（underestimate） 手動審視原始 rollout 檔案
Context 超限檢測 系統不進行主動的 context 超限檢測 無法警告 context window 即將滿 監控 context_percent_left 欄位
SKU 別名不同步 模型可能用多個名稱報告（gpt-5-codex vs gpt-5.2-codex） 報表分組不一致 使用 config.json 設定模型別名映射

可能的計算誤差來源

1. Lifetime Token 不匹配

/* 檢測邏輯 */ for event in events_in_session: expected = previous_lifetime + event.total_tokens actual = event.lifetime_total_tokens if expected != actual: print(f"WARNING: Lifetime mismatch at {event.timestamp}") print(f" Expected: {expected}, Actual: {actual}") print(f" Possible: missing event, session restart, API error")

2. Token 總和驗證失敗

/* 事件級驗證 */ reported_total = event.total_tokens calculated = event.input_tokens + event.output_tokens cached = event.cached_input_tokens if reported_total != calculated and not event.reasoning_output_tokens: log(f"Token sum mismatch: reported={reported_total}, " f"calculated={calculated}, cached={cached}")

3. 時間戳記不連續

  • 若事件時間戳記出現倒序，可能表示系統時鐘調整或時區變更
  • 建議使用 UTC 時間戳記進行排序和比較

資料驗證檢查清單

  • ✓ 定期執行 codex-track status 驗證最新快照
  • ✓ 比較 total_tokens = input + output
  • ✓ 監控 lifetime_total_tokens 是否單調遞增
  • ✓ 驗證時間戳記順序（按 captured_at_utc）
  • ✓ 檢查 rollout 檔案大小是否增加（append-only）
  • ✓ 定期備份 SQLite 資料庫

Token 文字片段的最小計費單位

Context Window 模型可同時處理的最大 token 數
5h Limit 最後 5 小時內的 API 使用配額
Weekly Limit 本週（通常週一-週四）的 API 使用配額
Rollout JSONL Codex 記錄的事件日誌檔案（逐行 JSON）
Payload 完整的訊息文本和工具呼叫參數
Incremental Ingestion 只處理變更檔案，避免重複計算

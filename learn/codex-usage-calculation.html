Codex 使用量計算原理

這些數字從哪來、怎麼變成報表、以及什麼時候不能盡信 —— 用例子講，不用公式。

適用版本：schema v8 · 文中每個說法都對應到程式碼位置，可自行覆核

九個觀念

  1. 數字不是我們算的，是 Codex 自己記的
  2. 「這一輪」和「整段對話」是兩個不同的數字
  3. cached 是 input 的一部分，不是額外多出來的
  4. 成本是估算，不是帳單
  5. 三種百分比長得很像，意思完全不同
  6. 配額的絕對值是反推出來的
  7. 重複匯入為什麼不會重複計算
  8. 預設不會存下你的對話內容
  9. 什麼情況下這些數字會不準

觀念 1數字不是我們算的，是 Codex 自己記的

這個工具是讀者，不是計量器。它不攔截任何 API 請求、也不自己數 token；它只是去讀 Codex CLI 早就寫在你硬碟上的日誌。

你每次跟 Codex 對話，Codex 都會在 ~/.codex/sessions/ 下寫一個 rollout JSONL 檔案 —— 一行一個事件，其中一種事件就是「這一輪用了多少 token」。這個工具做的事只有三件：找到這些檔案、把裡面的數字搬進 SQLite、然後查詢它們。

推論

因為是「讀」而不是「量」，所以有一條鐵律：Codex 沒寫進 JSONL 的東西，這個工具永遠看不到。

  • Codex 版本升級後改了日誌格式 → 新欄位要等工具跟上才讀得到
  • 你在 ChatGPT 網頁版或其他工具用掉的量 → 完全不在這裡
  • 把 ~/.codex/sessions/ 刪掉 → 歷史就真的沒了（不過已經匯入 SQLite 的還在）

反過來說，這也是它的優點：全部在本機，不需要登入、不需要網路、不會把你的用量送去任何地方。

程式碼：檔案發現與 JSONL 解析在 rollout.py；資料寫入在 store.py。（順帶一提，parser.py 處理的是另一件事 —— CLI 純文字日誌裡 /status 面板的文字，跟 JSONL 無關。）

觀念 2「這一輪」和「整段對話」是兩個不同的數字

每個 token 事件裡同時有兩組數字：last_token_usage（剛剛這一輪）和 total_token_usage（這個 session 從頭到現在的累計）。用途不同，不能互換。

這是最容易搞混的一點，因為兩組數字的欄位名稱一模一樣（都有 input、output、total）。差別在於：

數字意思拿來做什麼
last_token_usage 剛剛這一次請求用掉的量 存進 events 表、算報表、算成本
total_token_usage 這個 session 累計用掉的量 拿來算 context 用了多少（見觀念 5）
例子

一段三輪的對話，Codex 記下來大概是這樣（只列關鍵數字）：

第 1 輪 這一輪 12,000 session 累計 12,000 第 2 輪 這一輪 15,500 session 累計 27,500 第 3 輪 這一輪 9,200 session 累計 36,700

報表要的是「這段時間總共用了多少」，所以加總的是左欄：12,000 + 15,500 + 9,200 = 36,700。

如果誤把右欄加起來，會得到 76,200 —— 灌水一倍以上。這就是為什麼兩者不能混用。

順帶一提：每筆事件的 total 也是 Codex 給的，不是工具把 input + output 相加得出來的。所以偶爾會遇到 total 跟各分項對不太起來的情況 —— 以 Codex 給的 total 為準，工具不會去「修正」它。

程式碼：rollout.py 讀取 last_token_usage / total_token_usage（約 L786-L826）；報表加總見 report.py L422。

觀念 3cached 是 input 的一部分，不是額外多出來的

cached_input_tokens 是 input_tokens 裡面已經被快取的那一部分，不是另外一筆。算錢的時候要把它從 input 扣掉，用比較便宜的費率單獨計價。

這是整份文件最重要、也最容易算錯的一個觀念。因為兩個數字是包含關係，如果當成並列的兩筆，成本會被高估。

例子

某一輪的數字是 input = 1,000、cached = 800、output = 500，費率用 gpt-5.2 的每百萬 $1.75 / 快取 $0.175 / 輸出 $14.00。

正確：先把 cached 從 input 扣掉

實際要全價的 input = 1,000 − 800 = 200 200 × $1.75 ÷ 1M = $0.00035 800 × $0.175 ÷ 1M = $0.00014 500 × $14.00 ÷ 1M = $0.00700 ───────── $0.00749

常見的錯誤算法：把 input 和 cached 當兩筆並列

1,000 × $1.75 ÷ 1M = $0.00175 800 × $0.175 ÷ 1M = $0.00014 500 × $14.00 ÷ 1M = $0.00700 ───────── $0.00889 ← 多算了約 19%

單筆差幾釐錢看不出來，但長期對話的快取命中率常常在 80% 以上，累積下來誤差非常可觀。

例外：Pro 系列模型（gpt-5.2-pro、gpt-5.4-pro…）沒有公布快取折扣價，所以工具把它們的快取費率設成跟一般 input 一樣。這時扣不扣 cached 結果都相同。

程式碼：report.py L249 的 non_cached = max(input_tokens - cached_tokens, 0) 就是這件事。

觀念 4成本是估算，不是帳單

費率表是寫死在程式裡的。它不會去查你的方案、你的折扣、也不知道 OpenAI 什麼時候調價。這個數字用來看趨勢和比例，不要拿去對帳。

三件跟這個估算有關、值得知道的事：

一、模型名稱會被正規化

日誌裡的模型名稱五花八門，工具會依序嘗試對應到費率表：完全相同 → 去掉 (fast) 這類裝飾 → 去掉日期後綴 → 查別名表。

例子
"gpt-5.2-codex (fast)" → 去掉裝飾 → gpt-5.2-codex "gpt-5.2-codex-2026-01-15" → 去掉日期 → gpt-5.2-codex "gpt-5-codex" → 查別名 → gpt-5.2-codex "某個沒見過的模型" → 找不到 → 這筆不計成本

注意最後一種：認不出來的模型不會被當成 $0，而是整筆跳過不算。所以報表會另外告訴你「涵蓋率」—— 有多少事件真的算得出成本。看到涵蓋率不到 100%，代表有模型不在費率表裡，成本被低估了。

二、成本是一筆一筆算完再加總

不是「把整天的 token 加起來再乘費率」。因為一天之內你可能換過模型，先加總再乘會用錯費率。工具的做法是每個事件各自套自己模型的費率算完，再把金額相加。

三、費率可以自己改

在 SQLite 檔案旁邊放一個 config.json 就能覆蓋任何模型的費率（或新增費率表裡沒有的模型），也可以改幣別標籤。想放別的位置就用 CODEX_USAGE_CONFIG 環境變數指定。這是讓估算貼近你實際方案最直接的辦法。

還有一點：reasoning_output_tokens 只是記錄下來給你看，計價時只用 output_tokens，不會再另外加一次。

程式碼：費率表 report.py default_pricing()；名稱正規化 _resolve_pricing_model_name()；覆蓋設定 config.py。

觀念 5三種百分比長得很像，意思完全不同

介面上會看到三個「還剩百分之幾」：context、5 小時限制、週限制。它們互相獨立，一個滿了不代表另一個也滿了。
百分比在衡量什麼範圍怎麼恢復
Context 剩餘 這段對話塞了多少進模型的視窗 單一 session 開新對話 / 壓縮上下文
5h 限制剩餘 滾動 5 小時內的用量配額 整個帳號 等時間過去（滑動視窗）
週限制剩餘 這一週的用量配額 整個帳號 等每週重置點
例子

你剛開始一段大型重構，聊了兩小時：

Context 剩餘 18% ← 這段對話快塞爆了 5h 限制剩餘 86% ← 帳號額度還很充裕 週限制剩餘 61%

該做的是開一段新對話（或壓縮），而不是停下來等額度恢復 —— 因為額度根本沒問題。反過來如果是 5h 剩 4%、context 還很空，那就是真的得等了。

Context 用的是「累計」不是「這一輪」

Context 剩餘的算法是拿整個 session 的累計 token去比模型的視窗大小 —— 這正是觀念 2 裡 total_token_usage 的用途。所以它會隨著對話一路往下掉，不會因為某一輪問得短就回升。

視窗大小不用猜：Codex 會在日誌裡直接告訴工具這個模型的 context 上限（model_context_window），所以不同模型會自動用各自的數字，不需要記憶哪個模型是幾 K。

程式碼：rollout.py 約 L819-L835 —— context 用 total_token_usage.total_tokens，5h/週則來自日誌裡的 rate_limits.primary / rate_limits.secondary。

觀念 6配額的絕對值是反推出來的

Codex 只告訴你「用掉了百分之幾」，從來不說配額本身是多少 token。所以「你這週還能用多少」是工具用比例反推的估計值。

反推的邏輯其實很直覺：如果我知道上週用了多少 token，也知道那時候最高用到了幾 %，就能推出 100% 是多少。

例子

上一個完整週：實際記錄到 3,200,000 tokens，期間看過的最高用量是 80%。

3,200,000 是整週配額的 80% ↓ 整週配額 ≈ 3,200,000 × (100 ÷ 80) = 4,000,000 tokens

有了這個估計值，本週用掉的量就能換算成百分比，成本也用同樣比例放大成「整週配額值多少錢」。

這個估計什麼時候會偏：
  • 那週用得很少 —— 最高只到 5%，等於用 1/20 的樣本去推全體，一點誤差都會被放大 20 倍
  • 剛開始用這個工具 —— 沒有完整的上一週資料，就退回用最近一次算過的估計值
  • 方案改了 —— 配額變了，但估計值還停留在舊方案的水準

至於「這一週」從哪天算起：預設是週四 09:15（Europe/Stockholm）重置，可以用 CODEX_USAGE_WEEKLY_RESET 環境變數改成符合你帳號的時間。這個設定只影響工具怎麼切週界線，不影響 OpenAI 那邊真正的重置時刻 —— 兩者對不上的話，跨週的數字就會怪怪的。

程式碼：cli.py _estimate_weekly_quota()，關鍵是 scale = 100 / used_percent_max 那一步。

觀念 7重複匯入為什麼不會重複計算

你可以放心地一天跑十次匯入。工具有兩道防線：檔案沒變就整個跳過；檔案變了就只認新事件。

第一道：檔案層級

每個處理過的檔案，工具都記下它的修改時間和大小。下次再看到同一個路徑，先比對這兩個值 —— 一模一樣就直接跳過，連開都不開。這讓「幾千個歷史檔案 + 今天剛寫的兩個」這種情況，只需要處理那兩個。

第二道：事件層級

但有一種情況第一道防線擋不住：還在進行中的 session。它的檔案每講一句就變大一次，所以每次匯入都得重讀。這時靠的是事件本身的去重 —— 已經在資料庫裡的事件不會再插一次，只有新長出來的那幾行會被寫入。

例子
早上 10:00 匯入 → session A 讀進 8 個事件 （你繼續跟 Codex 聊，A 又多了 3 輪） 下午 15:00 匯入 → 檔案變大了，重讀整個 A 前 8 個已存在 → 略過 後 3 個是新的 → 寫入 結果：11 個事件，沒有任何重複
什麼時候該強制重新匯入：如果你曾用「不存內容」的模式匯入、後來想補上對話內容，光靠增量匯入是不會回頭補的 —— 因為那些檔案在工具眼中「已經處理過了」。這種情況需要明確要求重新處理。

程式碼：store.py file_needs_ingest()（比對 mtime/size）與 ingestion_files 表。

觀念 8預設不會存下你的對話內容

開箱即用的模式只存數字，不存文字。要存內容必須自己明確打開，而且每一筆資料都會記下它是用哪種模式存進來的。
模式存了什麼適合
預設 token 數、模型、時間、目錄、工具呼叫的中繼資料 只想看用量與成本
--with-payloads 以上 ＋ 完整訊息文字與工具參數 想搜尋「我上次是怎麼問的」
--no-content / --redact 只留骨架，訊息與工具內容一律不存 共用機器、要給別人看資料庫

值得注意的是，就算選了最嚴格的模式，原始的 rollout JSONL 還是完整躺在 ~/.codex/sessions/ —— 那是 Codex 寫的，不歸這個工具管。隱私模式管的是「要不要抄一份進 SQLite」。

程式碼：模式定義在 cli.py 的 IngestMode（full / redact_payloads / none）。

觀念 9什麼情況下這些數字會不準

誠實地說：這是一份可靠的相對指標，不是精準的絕對值。知道它哪裡會偏，比相信它更有用。
狀況會發生什麼怎麼判斷
模型不在費率表 該筆完全不計成本，總額被低估 看報表的成本涵蓋率是否 100%
費率過期或方案有折扣 金額整體偏高或偏低 用 config.json 填自己的真實費率
上週用量很低 週配額估計嚴重失真（觀念 6） 看那週觀察到的 used_percent 高不高
週重置時間設錯 跨週的統計切在錯的地方 對照 Codex 顯示的實際重置時間
匯入時的時區跟現在不同 舊資料的「本地時間」是當初那個時區的 比對 UTC 欄位（兩種時間都有存）
Codex 升級改了日誌格式 新欄位讀不到，可能整段沒有數字 看某個時間點之後事件數是否突然歸零

一句話總結這份文件：拿它來回答「我這週比上週多用了多少」、「哪個專案最燒 token」、「什麼時候該開新對話」很可靠；拿它去跟 OpenAI 的帳單對到分，不會準。

🐋 Orca ADE：平行 Agent 編排與 git worktree

Orca 是 ADE／編排層，不是自家 LLM。把 Claude Code、Codex、OpenCode、Pi 等 CLI agent 各放進隔離 worktree，在同一個 Electron 桌面（加手機伴生）裡監控、分流與合流。本頁拆定位、使用架構、扇出流程、技術棧與核心設計邊界。

⓪ 一句話定位

Orca = ADE（Agent Development Environment）／編排器，不是自己的 LLM。它不取代 Claude、Codex、Grok CLI 等推理引擎；它提供桌面殼、git worktree 隔離、PTY 終端、狀態總覽、SSH／WSL 執行主機、手機伴生與可腳本化的 orca CLI，讓你用自己的訂閱帳戶並行養一艦隊 coding agent。

上游：stablyai/orca；站點 onOrca.dev；授權 MIT。產品自稱「The AI Orchestrator for 100x builders」——本頁把它讀成控制平面 + 執行隔離，不把行銷數字當架構結論。

寫作當下快照（2026-09-20 台北時間）：GitHub 約 73k★（持續變動，請以倉庫為準）。下文以「約七萬星／持續更新」表述，不釘死精確星數。

① 為什麼重要：多 Agent／Claude×Codex 雙棧

JustKM 後續會反覆碰到三個壓力：

  • 同一任務要試多個 agent／模型：Claude Code 擅長長程編輯；Codex 擅長另一套工具節奏。你需要「同一提示、多隔離副本」而不是在同一個 checkout 上互踩檔案。
  • 雙棧不是雙訂閱面板：真正難的是帳號／用量、worktree 邊界、誰在跑、誰卡住、誰該 merge——這些是編排問題，不是再包一層 chat UI。
  • 終端原生 vs IDE 聊天：多數 coding agent 本來就活在 CLI／PTY。Orca 的賭注是：把 Ghostty 級終端、worktree、diff 標註、GitHub／Linear 任務、手機推播收進同一 ADE，而不是另發明一個「假 agent」。
和 JustKM 已有頁的界線：Herdr 偏「終端多工器＋狀態感知」；oh-my-pi／DeepSeek harness 偏「單一 agent 運行時」；Orca 偏「多 agent 艦隊的 ADE／編排層」。三者互補，不是互斥替代。

② 使用架構：人／手機 → Electron → main → N worktree

把產品讀成一條控制與執行鏈（依 README 功能面＋ AGENTS.md／docs/reference 邊界整理；內部模組名可能隨版本演進）：

  1. 人與手機伴生：桌面操作，或用 iOS／Android companion 監控、推播、遠端追問（產品宣稱）。
  2. Electron UI（renderer）：側欄狀態、Monaco 編輯、xterm 終端分割、diff 標註、內嵌 Chromium Design Mode、GitHub／Linear 任務瀏覽。
  3. Main／runtime：建立／管理 git worktree、node-pty、SSH／WSL 執行主機、agent 狀態 store、通知與 CLI 控制平面。
  4. N 個隔離 checkout：每個 worktree 跑一個（或一組）CLI agent；檔案互不踩踏，最後比較結果再 merge 勝者。

③ 典型扇出（fan-out）工作流

README 的「Parallel Worktrees」敘事可壓成一條可複現的操作環（產品宣稱）：

  1. 選任務：從本機 repo、GitHub PR／issue、或 Linear 任務開一個工作區。
  2. 扇出：同一提示複製到多個 agent（例如 3–5 個），每個落在獨立 git worktree。
  3. 並行執行：各 PTY 裡的 CLI agent 用各自訂閱跑；側欄／手機看狀態與未讀。
  4. 人在迴路（HITL）：在 diff 上標註回饋給 agent、Design Mode 點 UI 元素餵 HTML／CSS／截圖、必要時從手機追問。
  5. 合流：比較結果，merge／rebase 勝者；其餘 worktree 可清掉。
  6. 可腳本化：用 orca worktree create、snapshot、click、fill 等 CLI 把重複流程自動化（產品宣稱）。

⑤ 核心設計點

← 左右滑動看設計點 →
圖 4 · 六個應記住的設計錨點（細節見 docs/reference）

1. Worktree 隔離

平行 agent 的第一性原理是檔案系統隔離。git worktree 讓每個 agent 有自己的 checkout／分支視角，避免五個程序同時改同一個 working tree。文件也提醒：不是每個 workspace 都是 git worktree——資料夾 workspace 同樣要考慮。

2. 編排 ≠ 推理

Orca 賣的是艦隊操作面：建立環境、餵提示、觀察狀態、標註 diff、合流。模型選擇、工具循環、上下文壓縮仍在各 CLI agent 內。混淆這層會導致你把「裝了 Orca」誤當成「換了更強模型」。

3. 執行主機擁有 agent 狀態

docs/reference/agent-status-store.md 與 ssh-execution-boundary.md 的硬規則：

  • 執行主機上有一份權威 store；側欄、orca worktree ps、手機、dashboard 都是訂閱者。
  • 裁決詞彙固定為 live／unverifiable／exited——沒有同義詞；失去聯繫只能是 unverifiable。
  • 客戶端不得把本機觀察寫回遠端主機當成真相。

4. 終端原生

「Works with any CLI agent — if it runs in a terminal, it runs in Orca。」（README）這決定了適配策略：優先吃 PTY 畫面與既有 CLI，而不是要求每家實作 Orca 專屬 SDK。

5. HITL + 可腳本 CLI

人可以標註 diff、用 Design Mode、從手機介入；同時 orca CLI 讓 agent／腳本驅動 worktree 與 UI 操作。兩條路並存，才同時服務「探索式寫碼」與「可重複流程」。

6. 跨平台深度

AGENTS.md 大量篇幅在 Windows 殼層、WSL argv、glibc 地板、SSH relay 版本隔離、Git 二進位相容——說明 ADE 的真正成本在執行環境真實度，不在再畫一層 chat bubble。

⑥ 與 JustKM 即將／相關議題的銜接

JustKM 議題Orca 提供的抓手仍要你自己決定的事
Claude × Codex 雙棧 同一 UI 養兩家（或多家）CLI；帳號切換／用量追蹤（產品宣稱） 何時用哪家、如何評勝者、merge 策略、測試閘門
決策權（decision rights） HITL：diff 標註、推播介入、手機追問；狀態可見 哪些步驟允許全自動、哪些必須人簽核（Orca 不替你立法）
MCP／Skills：主機 vs agent 工具 主機側有 Design Mode、Computer Use、orca CLI、任務整合——那是編排主機工具 各 agent 自己的 MCP／Skills 仍掛在 agent runtime；勿把主機工具誤當成「所有 agent 共用的 MCP 池」
Worktree 基礎 產品級工作流把 worktree 當一等公民 仍建議先讀站內 git worktree，搞懂分支／路徑／清理成本
記一句：Orca 放大「你已經有的 agent」；它不消解「誰有決策權、工具掛在哪一層」——那兩題仍要在 JustKM 工作流／Skills 線裡寫清楚。

⑦ 何時用／不用

← 左右滑動看決策 →
圖 5 · 使用／不使用決策速查

建議使用情境

  • 同一規格要 Claude／Codex／其他 CLI 並行出方案，再人工或半自動選勝者。
  • 長任務需要桌面總覽＋手機推播，或把重活丟到 SSH 遠端機。
  • 已有多個 CLI agent 訂閱，缺的是 ADE／編排，不是再買一個「更聰明的聊天框」。

較不適合

  • 你要的是訓練／微調模型、或自研 agent harness 內部協定（請看 DeepSeek harness／Prime Agent 線）。
  • 單人、單 agent、短迭代——終端＋worktree 手操可能更輕。
  • 把 Orca 誤當「不需訂閱的免費 LLM」：推理仍走各 agent 自己的帳號／配額。

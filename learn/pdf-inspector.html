📄 pdf-inspector:先分類再抽取,54% 的 PDF 根本不用 OCR

Firecrawl 做的 Rust 庫:把 PDF 轉成乾淨 Markdown,但先問一個便宜的問題——「這份 PDF 是本來就有文字,還是掃描檔?」。本來有文字的(約佔 54%)就在本機 200ms 內直接抽出來,跳過又慢又貴的 OCR;真的是掃描檔,才把需要的那幾頁送去 OCR。一套 Rust 核心,同時出 Rust / Python / Node / 瀏覽器 WASM 綁定。MIT。

⓪ 一句話總結

一個「不急著 OCR」的 PDF → Markdown 庫。多數人處理 PDF 的習慣是「全部丟去 OCR」,又慢又花錢。pdf-inspector 反過來:先用極便宜的方式判斷 PDF 類型(TextBased / Scanned / ImageBased / Mixed),本來就含文字的直接在本機抽取——還帶座標、多欄閱讀順序、表格、乾淨 Markdown——完全不碰 OCR;只有真的缺文字的頁,才走選擇性 OCR。核心是 Rust,同一份解析器以原生、CLI、Python、Node、瀏覽器 WASM 五種形式交付。

它屬於哪一類:這是「餵給 LLM/RAG 前的乾淨文字」那條線的基礎建設,和站內 文件切塊(slm-document-segmentation) 是上下游:先把 PDF 變成結構化 Markdown,再切塊進向量庫。由 Firecrawl 打造,用來在本機處理 text-based PDF,替那 ~54% 不需要 OCR 的檔省下 OCR 服務的錢與延遲。

① 核心洞察:先分類,就能跳過大部分 OCR

OCR(光學字元辨識)是給掃描檔/圖片用的——把像素認成字,慢(每份 2–10 秒)又要雲端服務。但很多 PDF(報告、論文、發票、合約)本來就是用文字排版產生的,裡面就存著真正的字元與座標,根本不用「認」,直接讀出來即可。pdf-inspector 的整個設計就建立在這個分流上:

▲ 便宜的分類(~20ms)擋在最前面,把大多數 PDF 導向快路。省的是錢(OCR 服務計費)與延遲(秒級 → 毫秒級)。

而且分類不是「整份要或不要 OCR」的二分,而是回傳 pages_needing_ocr——精確到哪幾頁缺文字。一份 300 頁、只有 3 頁是掃描插頁的文件,就只有那 3 頁走 OCR,其餘本機秒抽。

② 秒級分類怎麼做:只看 content stream 的幾個運算子

分類快(~10–50ms,連 300+ 頁也在毫秒級)的祕訣是:不完整載入整份 PDF,只做最少的工:

  1. 解析 xref 表與頁面樹(不載入全部物件)。
  2. 依 ScanStrategy 選要看哪幾頁(預設取樣 8 頁:首、尾、中間)。
  3. 在這些頁的 content stream 裡找文字運算子 Tj / TJ 與影像運算子 Do。
  4. 依「有沒有文字運算子」在取樣頁上的分布,判定四種類型之一,並給 0.0–1.0 信心分數。
為什麼這樣就夠:PDF 的文字是用 Tj/TJ 這些運算子畫上去的,圖片是用 Do。頁面裡有沒有文字運算子,基本就決定了它是「可直接抽字」還是「只是一張圖(要 OCR)」——不必真的把內容渲染出來看。

四種掃描策略

策略行為適合
EarlyExit掃每一頁,遇到第一個非文字頁就停把 TextBased 導向快抽的流水線
Full掃每一頁,不提早結束要準確區分 Mixed vs Scanned
Sample(n)(預設 Sample(8))均勻取樣 n 頁(首/尾/中)超大 PDF,速度比精準重要

③ 文字抽取:不是倒出字串,是帶座標的版面

確定要本機抽取後,它做的遠不只「把字拉出來」。每個文字片段都是一個 TextItem,帶著:字型資訊、X/Y 座標、一個軸對齊外框。有了座標,才能還原人類眼中的版面:

  • 多欄閱讀順序:自動偵測報紙式多欄排版,按正確順序(而不是把左右欄的字橫著讀串在一起)輸出;支援 RTL(由右至左)文字。
  • 旋轉文字:頁邊的直排戳記、圖表座標軸標題這種被旋轉的文字,會保留真正的軸對齊外框並回報 rotation 角度,而不是被壓成「寬度為零」而消失。
  • CID 字型:對 Type0 / Identity-H 這類字型做 ToUnicode CMap 解碼,支援 UTF-16BE / UTF-8 / Latin-1 編碼——這是中日韓等文字能正確還原的關鍵。
  • 編碼問題偵測:自動標記壞掉的字型編碼,讓呼叫方知道「這頁抽出來是亂碼,改走 OCR」。

CLI 的 --items-json 會把這些結構原封不動吐出來:軸對齊外框、rotation、字型、paint(填色/描邊色、render mode)、底線資訊,座標相對於可見頁框。

④ 從座標還原 Markdown 結構

PDF 本身沒有「標題」「清單」「程式碼」這些語意,只有「某個字,某個字型大小,畫在某個座標」。pdf-inspector 的 Markdown 轉換器靠一堆啟發式規則,把這些視覺線索反推回結構:

粗體 / 斜體字型名稱樣式(Bold / Italic / Oblique)

⑤ 表格:兩種模式一起上

表格是 PDF→Markdown 最難的部分,也是這庫的強項(基準裡表格分數明顯領先)。它用雙模式:

  • Rectangle-based:直接讀 PDF 的繪圖運算子(畫線/畫框),用 union-find 把框線湊成格線 → 欄列指派 → 儲存格。有畫格線的表就靠這招。
  • Heuristic:很多表沒有格線,只靠文字的對齊。這模式從文字的 X 對齊關係推斷欄位邊界。

還特別處理:財務表(把被合併的數值 token 切開)、註腳、以及跨頁的續表。整條表格管線是:detect_rects(框線)+ detect_heuristic(對齊)→ grid(欄列→儲存格)→ format(儲存格→Markdown 表)。

⑥ 選擇性 OCR 與「預設純淨」的輕量化

要用到 OCR 時,它也不是「整份硬 OCR」,而是只渲染被路由到的那幾頁,在本機跑 PP-OCRv6 Small 模型,並保留每頁來源(provenance)與「建議改走雲端文件管線」的 fallback 建議。OCR 的 JSON 封包有版本號,回報路由頁、每頁來源與信心、警告。

關鍵的工程取捨——預設保持純淨:預設的 Rust 與瀏覽器建置是純抽取,完全不含 OCR。原生 Python / Node 套件雖內建 OCR 整合,但 PDFium、ONNX Runtime、模型檔都留在外部,只有真的有頁被路由到 OCR 時才會碰它們。這讓「只想抽文字」的多數使用者保持極輕,不被一堆笨重的 OCR 依賴拖累。

各語言怎麼開 OCR:Rust/CLI 在編譯期 opt-in(cargo install pdf-inspector --features ocr,執行時用 PDFIUM_LIB_PATH / ORT_DYLIB_PATH 指向外部庫,--ocr auto);Python/Node 直接呼叫 process_pdf_with_ocr,乾淨文字 PDF 不會載入外部 OCR runtime。

七個帶得走的重點

  1. 先分類再抽取:~54% 的 PDF 本來有文字,不必 OCR。
  2. 分類只看 content stream 的 Tj/TJ/Do,~10–50ms,連 300+ 頁都毫秒級。
  3. 路由精確到頁(pages_needing_ocr),不是整份要或不要。
  4. 抽取是座標感知:多欄閱讀順序、旋轉文字保角度、CID 字型 ToUnicode。
  5. Markdown 靠啟發式反推結構(字型大小→標題、對齊→表格…)。
  6. 表格雙模式(框線 + 對齊),含財務表/續表。
  7. 一套 Rust → Rust/Python/Node/瀏覽器 WASM;預設純抽取,OCR 依賴全外部。

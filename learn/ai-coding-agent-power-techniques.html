① 核心心智模型:上下文是第一約束

官方最佳實踐開宗明義:「大部分最佳實踐,都源自同一條約束——Claude 的上下文視窗會很快填滿,而 LLM 的效能會隨上下文填滿而下降。」視窗裝的是你整段對話:每則訊息、每個讀進來的檔案、每筆指令輸出。一次除錯或探索,動輒就吃掉數萬 token。填太滿,模型會開始「忘記」先前指令、犯更多錯。

▲ 頂尖用戶的共同習慣:把上下文當「最寶貴資源」主動管理,而不是讓它自然膨脹。

由此推導出的實戰動作

  • /clear 在不相關任務之間重置:換題目就清乾淨,別讓舊脈絡拖累新任務。
  • /compact 收尾一個階段:同一件事做完一段,壓縮成摘要繼續;可 /compact 專注在 API 變更 指定保留重點。
  • 研究交給 subagent:讀一堆檔案的探索丟給子代理,它在獨立視窗跑完只回報摘要,不污染你的主視窗。
  • /rewind(Esc ×2)回溯:每個 prompt 都是檢查點,可還原對話/程式碼/兩者,或從某點「摘要」。
  • 糾正超過兩次就 /clear 重來:反覆糾錯會讓失敗嘗試塞爆上下文;乾淨會話 + 更好的 prompt 幾乎總是勝過拖長的髒會話。
  • 用 /context 看載入了什麼、用自訂 statusline 持續監看用量。

高手加強招:讓 AI 先「訪談你」再寫規格

大功能別自己硬寫 prompt。丟一句最小描述,叫它用 AskUserQuestion 反過來訪談你——問技術實作、UI/UX、邊界案例、取捨,直到覆蓋完整,再把結論寫成 SPEC.md。然後開一個乾淨的新會話照規格實作(新會話上下文全給實作用)。

我想做 [簡述]。請用 AskUserQuestion 詳細訪談我:
技術實作、UI/UX、邊界案例、疑慮與取捨。別問顯而易見的,
挖我可能沒想到的難點。問到覆蓋完整,再把完整規格寫進 SPEC.md。
為什麼有效:最有用的規格是「自足」的——點名相關檔案與介面、寫明什麼不在範圍、並以一個端到端驗證步驟收尾。花時間把規格寫精準,比花時間盯著它實作值得多了。

③ 給它一個能自己驗證的方法(Grader 驗證體系)

Agent 會在「看起來做完」時停手。沒有可跑的檢查,「看起來做完」就是唯一訊號,而你就變成那個驗證迴圈——每個錯都要等你發現。給它一個能產生「過/不過」的檢查,迴圈就能自己閉合:做→跑檢查→讀結果→迭代到過為止。

檢查可以是:測試套件、build 的 exit code、linter、把輸出 diff 對比 fixture 的腳本、或把螢幕截圖和設計稿比對。關鍵心法:「要它拿出證據,而不是宣稱成功」——貼測試輸出、貼跑了什麼指令與回傳、貼截圖。

④ 確定性護欄:hooks > CLAUDE.md(「一定要發生」就用 hook)

影片講的「系統提示詞注入權限高於一般 rules」,方向對,但更精準的分野是:CLAUDE.md / skills 是「建議」(requests,不保證);hooks 才是「確定」(deterministic,保證發生)。——「如果某件事一定要發生,它屬於 hook。」

hooks:生命週期事件上的確定性動作

  • 常見事件:PreToolUse(工具執行前)、PostToolUse(之後)、SessionStart(開場)、Stop(回合結束前)。
  • 典型用途:每次寫檔後自動格式化、編輯後跑一輪快速測試、在明顯危險的 shell 指令執行前擋下來、擋住對 migrations/ 的寫入。
  • Claude 能幫你寫 hook:「寫一個 hook,每次編輯檔案後跑 eslint」;手動則編 .claude/settings.json,用 /hooks 瀏覽。

精簡 CLAUDE.md:太長 = 被忽略

CLAUDE.md 每次會話都會載入,太長會讓重要規則淹沒在雜訊裡,反而被忽略。逐行自問:「刪掉這行會不會讓 Claude 犯錯?」不會就刪。該放的 vs 不該放:

✅ 該放❌ 別放
猜不到的 Bash 指令讀程式碼就能懂的東西
與預設不同的風格規則模型已知的標準語言慣例
測試指令與偏好的 test runner詳細 API 文件(改放連結)
repo 規矩(分支命名、PR 慣例)會頻繁變動的資訊
專案特有的架構決策、環境怪癖、常見雷「寫乾淨的程式」這種不言自明的話
實用訣竅:若某條規則老是被跳過,只在那一行加 IMPORTANT;若你到處強調,就沒有一條突出。checked-in 的 CLAUDE.md 可跑 /doctor 讓 Claude 幫你提議可刪的內容。/init 產生起手版。

⑤ 跨會話記憶與持續學習

預設情況下,Agent 每次會話結束上下文就歸零。頂尖用戶讓它「像員工一樣有工作記憶」。官方其實有兩套互補記憶:

  • CLAUDE.md(你手寫):慣例、指令、硬規則,每次會話載入。
  • 自動記憶(它自己寫):根據你的糾正與偏好,在背景抽取重點、存成結構化摘要到磁碟,不需你動手。
← 左右滑動看完整圖 →
▲ 關鍵零件是 SessionStart hook——它在啟動、/clear、resume、壓縮後都會觸發,正好是「會話剛丟失狀態」的接縫,可用來重新載入上次的狀態。

頂尖用戶的做法

  • 自動寫記憶檔:用腳本/hook,在會話結束或上下文快滿時,把「進度、決策、未解問題」寫進本機暫存檔;新會話由 SessionStart hook 自動載入。
  • learner 資料夾 + 持續學習:設一個專屬 learner/(或技能),每次糾正 Claude 後,自動抽取「偏好、輸出格式、寫作風格」存起來,避免重複犯同樣的錯。
  • 現成外掛:社群的 claude-mem、claude-remember 都用 SessionStart hook 注入前次壓縮後的脈絡,省得自己造。

⑥ Token / 成本優化

核心原則一句話:「便宜的模型做簡單的事,貴的模型做複雜的事。」把貴模型放在「會改變答案」的地方(架構、推理),其餘全部降一階(路由、查文件、格式化)。更多可落地的招:

  • 模型分層路由:架構/推理用高階模型;路由、查文件、雜務用平價模型。重複委派就路由到同一個常駐 worker,別每次都開新的。
  • plan mode 先計劃再做:在動手前先讓它規劃、你先核准——能早點抓出誤解(例如它想讀 6 個檔案但你只要 2 個),省下亂讀的 token。
  • /clear vs /compact 用對:同一件事做完一段用 /compact(摘要有價值);換不相關的新工作用 /clear(摘要沒用還照樣花錢)。
  • 別在寫程式中途亂壓縮:寫到一半觸發壓縮容易丟掉關鍵狀態;在 CLAUDE.md 指定壓縮時務必保留「修改過的檔案清單與測試指令」。
  • MCP 輸出很肥 → 用 context-mode 之類外掛:把工具輸出導進沙盒知識庫、只回摘要,能把 MCP 相關 token 砍 50–90%(多 MCP server 使用者的最高槓桿單點改動)。
  • CLI 工具最省脈絡:用 gh、aws 這類 CLI 跟外部服務互動,比塞一堆 API 回應省 token,也避免未授權請求撞 rate limit。
  • 把探索範圍縮窄,或丟給 subagent,別讓「調查一下」變成讀幾百個檔案。
提醒:「省一半 token」≠「省一半錢」——輸入/輸出與快取命中的計費權重不同(可對照站內 SLPI 那頁:令牌 ↓~49% 但成本只 ↓~33%)。

⑦ 並行化與 subagent 編排

熟練一個 Claude 之後,用並行把產出倍增。但要先分清兩個東西:

  • Subagent:同一會話內 Claude 生出的工作者,各有獨立上下文與受限工具,由主 Claude 一回合一回合編排。適合「讀很多檔的研究」與「驗證」。
  • 並行會話:你自己開多個終端/實例分工。搭配 git worktrees——把同一 repo 的不同分支簽出到不同目錄(共用一個 .git),每個目錄跑一個 Claude,編輯互不相撞。
← 左右滑動看完整圖 →
▲ 可靠模式=三件事分離:協調(誰做哪塊)、worktree(隔離檔案變更)、整合車道(驗證合併結果)。

高手常用的並行招式

  • Writer / Reviewer 雙會話:A 會話寫、B 會話用全新脈絡審(不偏袒自己剛寫的碼);把 B 的意見貼回 A 修。測試也可:一個寫測試、另一個寫碼去通過。
  • /batch 扇出:把一個大改動拆成 5–30 個獨立單元,每個丟一個背景 subagent 在獨立 worktree 裡實作、跑測試、開 PR。
  • headless 腳本扇出:claude -p "..." 迴圈跑大量檔案(如大遷移),用 --allowedTools "Edit,Bash(git commit *)" 限縮權限;先在 2–3 個檔案試 prompt 再全跑。
  • 別開太多:同時處理的實例不要超出你自己的腦力負荷;各任務間最好沒有互相依賴。

⑧ 技能、斜線指令與外掛

把「重複的工作」與「領域知識」從 CLAUDE.md 移出去,變成按需載入的技能,不必每次會話都塞:

  • Skills(.claude/skills/SKILL.md):給 Claude 專案/團隊/領域知識,相關時自動套用,或 /技能名 直接叫。
  • 自訂斜線指令 = 可重複工作流:把「修 issue」這種流程寫成 SKILL.md,/fix-issue 1234 一鍵跑完(查 issue→找檔→改→測→lint→commit→PR)。有副作用的工作流設 disable-model-invocation: true,只允許手動觸發。
  • 自訂 subagent(.claude/agents/*.md):定義專才(如 security-reviewer),限定工具與模型,主 Claude 需要時委派。
  • 外掛(/plugin):把 skills/hooks/subagents/MCP 打包一鍵裝。社群當紅的 Superpowers(Jesse Vincent)裝了一整套紀律化工作流——brainstorm、TDD、除錯、code review、skill 撰寫(社群統計逾 80 萬安裝)。typed 語言可裝 code-intelligence 外掛給精準符號導航。
  • 團隊共用:專案技能放 .claude/skills/ 並 commit,全隊就有同一套斜線指令、同一套標準。
怎麼選:「一定要發生」→ hook;「有時才需要的知識/流程」→ skill;「每次都適用的少量規則」→ CLAUDE.md;「外部系統」→ MCP;「讀很多檔的隔離工作」→ subagent。

⑨ Codex 這邊怎麼玩(對應做法)

OpenAI Codex 的心法和 Claude Code 高度平行——「給對的脈絡、給明確的合約、驗證後再信任」。要精通的是五個系統:

Codex 系統作用 / 對應 Claude Code
AGENTS.md倉庫層級的「長效指引」,別塞進每個 prompt——等同 CLAUDE.md
config.toml把 Codex 調成你的工作流(模型、審批、預設)
sandbox / 審批模型控制它能碰什麼、何時要你核准——對應權限模式/sandbox
MCP接外部系統(同 Claude Code 的 MCP)
skills把重複工作變成可重用技能

Codex 高手的多介面用法

  • 五個介面各司其職:Cloud 跑長任務、CLI 做確定性的 repo 操作、IDE 外掛做緊湊編碼迴圈、桌面 App 做規劃協調、瀏覽器外掛做登入態的網頁工作流。
  • 長效指引進 AGENTS.md、把穩定流程變 skills、用 MCP 接外部系統——和 Claude Code 的「精簡 memory + skills + hooks + MCP」是同一套思路。
  • 模型/努力度分層:複雜任務用高階、雜務降階(與 ⑥ 同理)。Codex 也在 2026 走向多模型代號(如 Astra/Sol/Terra/Luna 等命名),請以當下官方推薦為準。
兩邊共通的鐵律:不管 Claude Code 還 Codex——給明確合約、能自我驗證、精簡長效指引、把一定要發生的事變成確定性機制、並行時隔離 + 整合驗證。工具會換,這套心法不太會過時。站內另有 Codex 用量計算、codex-chatgpt-web 可延伸。

⑩ 帶走清單 · 反模式 · 來源

十條可以今天就用的

  1. 把上下文當第一資源:/clear 換題、/compact 收尾、研究丟 subagent。
  2. 大功能先讓 AI 訪談你 → 寫 SPEC.md → 開新會話實作。
  3. 永遠給一個能自跑的檢查(測試/build/lint/截圖),要它拿證據不要它宣稱。
  4. 「一定要發生」的事寫成 hook,不要只寫在 CLAUDE.md。
  5. CLAUDE.md 狠狠精簡;老被跳過的那行才加 IMPORTANT。
  6. 用 SessionStart hook 注入上次狀態,做跨會話記憶 + learner 持續學習。
  7. 模型分層:貴的放會改變答案的地方,其餘降一階。
  8. 並行用 worktrees 隔離、Writer/Reviewer 交叉審、/batch 扇出。
  9. 重複工作變 skill / 斜線指令;有副作用的設手動觸發。
  10. Codex 同理:AGENTS.md + config.toml + sandbox + MCP + skills。

五個要避開的反模式(官方點名)

  • 雜燴會話:一個會話塞不相關任務 → /clear 分開。
  • 反覆糾錯:糾兩次還不對 → /clear 重寫更好的 prompt。
  • 過長 CLAUDE.md:規則被淹沒 → 狠刪、能轉 hook 就轉。
  • 信而不驗:看起來對但沒處理邊界 → 沒驗證就別出貨。
  • 無邊界探索:「調查一下」讀爆幾百檔 → 縮窄範圍或丟 subagent。

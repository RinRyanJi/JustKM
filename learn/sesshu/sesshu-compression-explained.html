Sesshu 壓縮技術：核心觀念與方法

一份給人看的說明 —— 不談實作細節，先講「為什麼這樣設計」。對應原始碼：src/sesshu/

一句話版本：Sesshu 不是把對話「壓小」，而是把對話搬家 —— 從昂貴、會被塞爆的 context window，搬到便宜、可以無限長大、而且能被搜尋的磁碟檔案。context 裡只留一份約 600 字的結構化摘要，和一組「要更多細節就去這裡找」的路徑。

1. 先看問題：對話為什麼會「死掉」

與 AI coding agent 的對話，逐字稿（transcript）是只增不減的。每一次工具呼叫、每一份檔案內容、每一段錯誤訊息，都會永久累積在同一個 .jsonl 檔裡，並且在每一輪都重新餵給模型。

結果是兩件事同時惡化：成本隨輪數平方成長（第 N 輪要重讀前面 N-1 輪），而且遲早會撞到 context window 上限。撞到之後，你只有兩個選擇：忍受 agent 開始遺忘，或是 /clear 從零開始 —— 把所有脈絡一起丟掉。

2. 四個核心觀念

整套系統其實只建立在四個想法上。理解這四個，實作細節都只是它們的自然結果。

觀念 1卸載（offload），不是刪減（truncate）

一般的「壓縮」直覺是把文字砍短 —— 但砍掉的資訊就永久消失了。Sesshu 的做法是把資訊移到另一層儲存，並在 context 裡留下一個指標。

這等於在 agent 身上建立了三層記憶結構，跟 CPU 的 L1 / L2 / 主記憶體是同一個概念：

觀念 2游標式增量攝取：只讀新的那一段

如果每次都把整份逐字稿丟給摘要模型，那摘要本身就變成了第二個平方成本問題。Sesshu 用一個 cursor.json 記住「這份逐字稿我已經讀到第幾個字元」，之後每次只處理游標之後新增的那一段。

這裡有個關鍵的正確性細節：游標只在成功時才前移。如果語言模型呼叫失敗，游標留在原地，下一輪會帶著完整的 diff 重試 —— 資訊不會因為一次失敗就被跳過。

觀念 3固定 12 節結構：讓摘要可以被「更新」而不是「重寫」

這是 Sesshu 跟一般「請幫我摘要這段對話」最不一樣的地方。摘要不是自由格式的段落，而是一份固定 schema 的 wiki 頁，永遠有這 12 個標題：

固定結構帶來三個好處：

  • 可驗證 —— 程式可以逐行檢查標題在不在，不在就要求模型重寫。摘要品質不再靠運氣。
  • 可增量更新 —— 第二次以後的提示詞是「這是既有的 wiki 頁，這是新發生的事，請更新它」，而不是「請重新摘要全部」。既有結論被保留，新資訊被歸位到對應章節。
  • 有記憶負片 —— ## Rejected Approaches（被否決的做法）這一節特別重要：它記住了「不要再試什麼」，這正是一般摘要最容易弄丟、卻最浪費時間重踩的資訊。

觀念 4分層降級：語言模型是加分項，不是單點故障

摘要用的是本機或遠端的小模型（預設 Ollama 上的 qwen2.5:7b）。它可能沒開、可能逾時、可能回傳垃圾。Sesshu 的設計是兩條軌道並行：一條確定性的、一條語意的。

這個設計有個一箭雙鵰的巧思：那份用程式硬解出來的事件清單（改了哪些檔、跑了哪些 git 指令、出了哪些錯），不只是在 LM 掛掉時當備胎 —— 它平常就會被貼進 LM 的提示詞裡。小模型很容易在長逐字稿裡把檔名記錯，給它一份確定正確的清單，等於幫它把事實釘死，只讓它負責它擅長的部分：歸納意圖與決策。

3. 方法：資料是怎麼一層層變小的

把上面四個觀念接起來，一次壓縮的資料流長這樣。注意每一階段的縮減機制都不同 —— 有的是切窗、有的是抽取、有的才是真正的語意壓縮。

為什麼最後要「加回」原文？摘要擅長保留結論，卻會抹掉語氣與最後那句沒說完的話。保留最近 4 組對話的原文，是為了讓 /clear 之後的第一句話能無縫接上 —— agent 知道「剛剛我們正在做什麼」，而不只是「這個 session 整體在做什麼」。

量級感

以預設值粗估：觸發門檻是 120,000 字元的逐字稿，注入回去的 seed.md 大約是 600 字摘要（約 4,000 字元）加上最多 8 則各 800 字元的近期對話，合計約 10,000 字元上下。也就是大約一個數量級的縮減，而被拿掉的那 90%＋並沒有消失，它們在 wiki/sessions/ 裡等著被搜尋。

4. 三個時間點：完整生命週期

Sesshu 全部的行為都掛在 agent runtime 的 hook 上。它從來不主動跑，也從來不修改逐字稿本身。

5. 那 wiki 讀回來不會又塞爆嗎？

不會，因為注入 context 的是路徑，不是內容。SessionStart 只放進去五行檔案路徑，加上一句「如果摘要不夠細，用 Read 工具去讀對應的頁」。

這把「要不要花 token 讀細節」的決定權，從壓縮時（那時還不知道哪些細節會有用）延後到使用時（那時 agent 已經知道自己在找什麼）。這就是惰性取用：資訊隨時可得，但只有真正需要時才付代價。

要讓「找得到」成立，Sesshu 在寫入每一頁時就同步維護一個 SQLite FTS5 全文索引（沒有 FTS5 就退回 grep）。挑頁的流程是：從當前 seed 的 Goal / Tasks / Current state 等章節抽出關鍵詞 → 查索引 → 取前 5 名；查不到東西時，退回「最近 5 頁」。

索引與檔案可能不同步（例如手動刪了某頁）。讀取前會先跑一次對帳，把新增、修改、刪除的頁面補進索引 —— 檔案永遠是唯一真相，索引只是加速層。這也意味著索引整個刪掉也不會壞事，最多是慢一點。

6. 三條不可違反的紀律

這套東西跑在別人的開發流程中間，一旦出錯就會擋住整個 agent。所以有三條硬規則貫穿全部程式碼：

紀律原因
永遠回傳 exit 0 hook 只要非零退出就會中斷 agent。所以任何失敗 —— 模型掛了、檔案讀不到、JSON 壞了 —— 都是靜默記錄後正常退出。最壞情況是「這次沒壓縮」，絕不會是「你的 agent 卡住了」。
絕不碰逐字稿 只讀取，不寫入、不截斷、不刪除 .jsonl。原始紀錄是使用者的資產，壓縮產物一律另存他處。這也讓 Sesshu 隨時可以整包移除而不留後遺症。
提示訊息只陳述事實 給使用者看的 systemMessage 只能是「狀態描述 + 簡短建議」，不能寫成給 agent 的任務指令 —— 否則 agent 會把它當成新任務去執行，然後再次觸發 Stop hook，形成無限迴圈。

7. 常見誤解

Q：這跟 runtime 內建的 auto-compact 有什麼不同？
內建壓縮的產物活在 context 裡，下次再壓還是會被壓一次，資訊逐輪衰減，而且你看不到、改不了。Sesshu 的產物是磁碟上的 Markdown 檔，永久、可讀、可手改、可跨 session 搜尋。
Q：為什麼摘要要用另一個模型，不用主模型？
摘要是高頻、低難度的工作，用小模型跑在本機既便宜又不佔主模型的 context。也因為預設走本機 Ollama，逐字稿內容不必離開你的機器。
Q：小模型摘要品質不好怎麼辦？
這正是「固定 12 節 + 結構驗證重試 + 結構化事件錨點」三件事要解決的問題 —— 把模型的自由度壓到最低，讓它只做歸納，事實部分由程式提供。真的失敗時還有 LM-free 備援頁墊底。
Q：每次 Stop 都呼叫 LM，不會很慢嗎？
不會。預設有 300 秒的節流閘，多數 Stop 事件會直接跳過。若仍嫌卡，可把攝取模式切成背景子行程，Stop hook 立即返回，壓縮在背景完成。
Q：壓縮失敗會不會遺失那段對話？
不會。游標只在成功寫入後才前移，失敗時下一輪會帶著同一段 diff 重試；而且逐字稿本身從未被修改，原始紀錄一直都在。

🔐 找到公司憑證:企業 CA / TLS 檢查憑證怎麼找、怎麼用

公司網路常做 TLS 檢查(MITM),會把一張「企業根憑證」預先裝進你的電腦信任庫。它是公開憑證(不含私鑰),你在公司電腦上就能找到並匯出——本頁整理各系統的找法、如何確認、以及找到後怎麼餵給各種工具。

⓪ 一句話總結

是的,通常「直接在公司電腦上找就有」。做 TLS 檢查的公司,會把一張企業根憑證(root CA)預先安裝在作業系統的信任庫裡;你有權限的話就能找到並匯出它——因為那是公開憑證(只有公鑰、沒有私鑰),匯出不算洩密。

找它的通用邏輯:打開系統的「受信任根憑證」清單 → 找名稱像公司名或代理商(Zscaler、Netskope、Palo Alto、Cisco Umbrella、Forcepoint…)的那張 → 匯出成 .crt / .pem。找到後,把需要的工具指向它即可正常連線(見 ⑦)。

什麼時候需要它:某個工具在公司網路報「憑證驗證失敗 / self-signed certificate in chain / PKIX / unable to get local issuer」時,通常就是它沒讀到這張企業根憑證。把工具指向這張憑證就能修好,而不是去停用 TLS 驗證。

① 為什麼公司電腦上會有這張憑證

公司為了資安/稽核,會在網路出口放一台會「拆解」HTTPS 的代理(TLS inspection / MITM)。它的運作是:

沒讀到這張根憑證的工具(curl、python、node、git…)會因為「不認得簽發者」而報憑證錯誤。
▲ 瀏覽器通常沒事(它用系統信任庫);報錯的往往是命令列工具,因為它們有自己的一套 CA 讀取方式,沒被設定指到企業根憑證。

所以「找到這張憑證」的目的通常有二:(1) 把它交給某個一直報憑證錯誤的工具;(2) 確認你連線是否被檢查、由誰簽發。

② Windows 怎麼找

圖形介面

  • Win + R → 輸入 certlm.msc(本機層級)或 certmgr.msc(目前使用者)。
  • 展開 「受信任的根憑證授權單位 → 憑證」。
  • 找名稱像公司名或代理商(Zscaler、Netskope、Palo Alto、Cisco Umbrella、Forcepoint…)的那張 → 右鍵 所有工作 → 匯出,選 Base-64 編碼(.cer)。

PowerShell(找 + 匯出)

# 列出本機根憑證,依名稱過濾
Get-ChildItem Cert:\LocalMachine\Root |
  Where-Object { $_.Subject -match "公司名|Zscaler|Netskope|Palo Alto" } |
  Format-List Subject, Issuer, Thumbprint, NotAfter

# 依 Thumbprint 匯出成 Base-64 .cer
$c = Get-Item Cert:\LocalMachine\Root\<Thumbprint>
Export-Certificate -Cert $c -FilePath C:\temp\corp-ca.cer -Type CERT
來源:這類憑證多半是 IT 透過群組原則(GPO)或 Intune / MDM 推下來的;Windows / Chrome / Edge 都用系統信任庫。

③ macOS 怎麼找

圖形介面

  • 打開 「鑰匙圈存取」(Keychain Access) → 左側選 系統(System) 或 系統根憑證(System Roots)。
  • 搜尋公司名 → 找到後右鍵 匯出 成 .pem / .cer。

命令列

# 傾印系統鑰匙圈所有憑證成 PEM(可再 grep 公司名)
security find-certificate -a -p /Library/Keychains/System.keychain

# 依名稱找特定一張並輸出 PEM
security find-certificate -c "公司名" -p /Library/Keychains/System.keychain > corp-ca.pem

# 若是描述檔(Configuration Profile)推的,列出描述檔
profiles list        # 新版可能需 sudo

描述檔也可在 系統設定 → 一般 → 裝置管理 / 描述檔(Profiles) 查看。

④ Linux 怎麼找

發行版放憑證的來源目錄合併/更新指令
Debian / Ubuntu/usr/local/share/ca-certificates/*.crtsudo update-ca-certificates → 併入 /etc/ssl/certs/ca-certificates.crt
RHEL / Fedora / CentOS/etc/pki/ca-trust/source/anchors/sudo update-ca-trust
 
# 列出目前信任的 CA(p11-kit)
trust list | grep -i -A2 "公司名或代理商"

# 直接在合併後的 bundle 裡找
awk -v cmd='openssl x509 -noout -subject' '/BEGIN/{c=""} {c=c$0"\n"} /END/{print c | cmd; close(cmd)}' \
  /etc/ssl/certs/ca-certificates.crt | grep -i "公司名"
對照本站雲端環境:像 Claude Code 的雲端 session,其代理 CA 就直接放在 /root/.ccr/ca-bundle.crt(與 /root/.ccr/agent-proxy-ca.crt)——這正是「憑證通常擺在機器上某個已知路徑」的活例。

⑤ 瀏覽器:Firefox 有自己的信任庫

大多數瀏覽器共用系統信任庫,但 Firefox 例外——它自帶一套 CA 庫(除非開了企業政策 security.enterprise_roots.enabled 才會讀系統庫)。

  • Firefox → 設定 → 隱私與安全性 → 憑證 → 檢視憑證 → 憑證機構(Authorities)。
  • 搜尋公司名 → 選取 → 匯出。
  • Chrome / Edge:在 Windows/macOS 直接用系統信任庫,查法同 ②③。

⑥ 怎麼確認「這張就是公司 MITM 憑證」

最快:看瀏覽器的憑證鏈

打開任一 HTTPS 網站 → 點網址列鎖頭 → 檢視憑證 → 憑證鏈(Chain)。如果最上層的發行者(Issuer)不是公開 CA(DigiCert、Let's Encrypt、GlobalSign…),而是公司名或代理商,那張根就是企業 MITM 憑證。

命令列:看代理實際回傳的鏈

# 看某網站在你的網路下被誰簽(注意 issuer 那行)
openssl s_client -connect example.com:443 -showcerts </dev/null 2>/dev/null \
  | openssl x509 -noout -issuer -subject

# 驗證某工具用某張 CA 能不能通
curl --cacert corp-ca.pem https://example.com -I
安全提醒:如果你在非公司網路(家裡、咖啡廳)也看到憑證被不明的根重簽,那可能是惡意攔截,不是正常公司檢查——這時該停下來查清楚,而不是照單全收。

⑦ 為何瀏覽器自動通、程式卻要另外設定(甚至重 build)

一個常見困惑:同一張公司 CA,瀏覽器一開就通,命令列工具卻報憑證錯誤——甚至有人說要「重新 build」才行。差別不在憑證本身,而在「信任清單從哪裡讀」每個程式不一樣。

← 左右滑動看完整圖 →
▲ 憑證沒變,變的是「誰去哪讀信任清單」。瀏覽器接到 OS 那份會被 IT 動態更新的庫;各 runtime 帶著自己出廠的 CA 清單,看不見後來才裝的公司 CA。

各程式的信任清單其實來自不同地方

消費者信任清單從哪讀看得到後裝的公司 CA?
Chrome / Edge / Safari作業系統信任庫(schannel / Keychain)看得到(IT 已推入)
Firefox自帶 NSS 庫(除非開 security.enterprise_roots)預設看不到,開了才讀系統
Pythoncertifi 的 cacert.pem看不到
Node.js內建 OpenSSL roots看不到
Java(JVM)自己的 cacerts keystore看不到
Go / curl / git依 build 而定的內建 bundle多半看不到
靜態 binary / 精簡容器映像build 時烤進去的 roots看不到(信任集被凍死)

「要不要重 build」——多數情況其實不用

所謂「重 build」是被誤解的最後手段。真相分兩層:

  1. 絕大多數:不用重編譯,把 CA「指過去」就好。用環境變數或參數告訴工具去讀這張憑證(SSL_CERT_FILE、NODE_EXTRA_CA_CERTS、REQUESTS_CA_BUNDLE、GIT_SSL_CAINFO…),或把公司 CA 接到現有 bundle 檔尾巴。具體對照見下一節 ⑧。(本站雲端環境的 /root/.ccr/ca-bundle.crt 就是「接到 bundle 尾巴」這種做法。)
  2. 只有信任集在 build 階段就凍死時,才真的得重 build。例如靜態連結的 musl binary、把 roots 嵌進二進位的 Go 程式、或精簡到沒有系統憑證目錄的容器映像——這些沒有「執行期再指過去」的縫,只能重打映像/重編,把公司 CA 一起放進去。
一句話:憑證本身不需要「編譯」。會讓人以為要重 build,是因為那些工具的信任清單不是動態從 OS 讀,而是隨自己 runtime 一起打包、凍結的。瀏覽器剛好接到 OS 那份會被動態更新的庫,所以看起來「自動」。首選永遠是「指過去」,重 build 只在信任集被烤死在 build 階段時才逼不得已。

⑧ 找到之後怎麼用:把工具指向這張憑證

多數「憑證驗證失敗」都是因為某工具沒讀到企業根憑證。把它指過去即可,不要停用驗證:

工具 / 語言設定方式(指向 PEM)
curl--cacert corp-ca.pem,或環境變數 CURL_CA_BUNDLE=/path/corp-ca.pem
通用(OpenSSL 系)SSL_CERT_FILE=/path/corp-ca.pem(Python/Ruby/Go 多會讀)
Python requestsREQUESTS_CA_BUNDLE=/path/corp-ca.pem;pip 用 PIP_CERT 或 pip.conf cert=
Node.jsNODE_EXTRA_CA_CERTS=/path/corp-ca.pem;npm 用 npm config set cafile
gitgit config --global http.sslCAInfo /path/corp-ca.pem,或 GIT_SSL_CAINFO
AWS CLIAWS_CA_BUNDLE=/path/corp-ca.pem
Java(JVM)匯入 truststore:keytool -importcert -alias corp-ca -file corp-ca.pem -keystore $JAVA_HOME/lib/security/cacerts(密碼預設 changeit),或 -Djavax.net.ssl.trustStore=...
系統層(一勞永逸)Linux 放進系統來源目錄再 update-ca-certificates / update-ca-trust(見 ④);macOS/Windows 匯入系統信任庫
 
# 範例:讓這個終端機的多數工具一次認得企業 CA
export SSL_CERT_FILE=/path/corp-ca.pem
export REQUESTS_CA_BUNDLE=/path/corp-ca.pem
export NODE_EXTRA_CA_CERTS=/path/corp-ca.pem
export CURL_CA_BUNDLE=/path/corp-ca.pem
export GIT_SSL_CAINFO=/path/corp-ca.pem

⑨ 重點與注意事項

  1. 你找到的是公鑰,不是私鑰。根憑證檔(.crt/.pem/.cer)只含公開憑證;私鑰只在公司代理伺服器上,電腦上不會有,所以匯出這張憑證不算洩密。
  2. 能不能匯出看權限。一般讀取/匯出根憑證多半允許;若被 IT 鎖住,或你不確定哪張才對,最保險是直接向 IT 索取官方 CA 檔,避免信任到錯的憑證。
  3. 永遠不要用「停用 TLS 驗證」來繞過。curl -k、NODE_TLS_REJECT_UNAUTHORIZED=0、git -c http.sslVerify=false 這類做法會讓你對所有連線失去保護——正解是把工具指向正確的企業 CA。
  4. 非公司網路也被重簽 = 警訊。正常的企業檢查只發生在公司網路;在外面看到不明根憑證攔截,要當成潛在的中間人攻擊處理。
  5. 優先用工具自己的 CA 選項,其次才動系統庫。先試環境變數/參數(影響範圍小、好回復);要一勞永逸再匯入系統信任庫。

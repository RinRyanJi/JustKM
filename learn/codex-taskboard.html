⓪ 一句話總結

Codex Taskboard 是一個「本地優先」的議題板:資料存在本機 SQLite,一個 HTTP API 同時餵給 React 前端與 taskctl 命令列,並能直接嵌進 OpenAI Codex(ChatGPT 桌面 App)的側邊欄。但它對 KB 讀者真正的價值,是隨附的一份 Codex Skill(manage-taskboard)——它把「一張 issue 從被看見到被驗收」寫成一套可被多個 AI agent 安全併發的工作協定。

為什麼收進 JustKM:市面上任務板很多,但很少有把「agent 該怎麼認領一張票、怎麼防止兩個 agent 搶同一張、什麼時候才准標記完成」寫成明文協定的。這份 repo 的 SKILL.md 與 AGENTS.md 幾乎是一份「多代理任務執行的操作手冊」——這才是本頁的重點,而不是看板 UI。

① 這到底是什麼

拆成三層看最清楚:

層是什麼給誰用
資料 / 服務層本機 Node 服務 + SQLite(.data/taskboard.sqlite),一個 HTTP API,議題/留言/附件變更用 SSE 即時廣播給所有開著的用戶端底層,人與 agent 共用

② 核心:把「議題生命週期」寫成 Agent 協定

隨附的 manage-taskboard Skill 定義了七個狀態與一套誰都不准跳過的流程。狀態機本身很普通,但「什麼時候才准轉場」的規則是精華:

backlog ──(需人明確授權)──▶ todo ──(認領/claim)──▶ in_progress ──(驗證+留言)──▶ in_review ──(人明確驗收)──▶ done │ │ └── 未批准,agent 不得認領、不得動它 ├──▶ blocked (卡住,暫停) └──▶ canceled (不再繼續)

五條「反直覺但關鍵」的規則

  • backlog = 尚未批准執行。agent 不得認領、不得改狀態、不得做任何實作;「被指派」本身不等於授權。這把「待辦池」和「可執行隊列」分開,避免 agent 自作主張。
  • 先認領再動手。要開工,先把 todo 用它當前的 version 搬到 in_progress;搬成功前不准讀碼、不准下載附件、不准分析。認領是一個原子動作,不是一句口號。
  • 留言即需求。開工前先 issue get + comment list + attachment list,把最新留言當成當前需求(包含被退回的返工)。留言說「先等、別做」就停下回報,不改狀態。
  • 驗證後才進 in_review。做完要留一則留言寫清楚:改了什麼、驗證結果、結論、殘留風險——再讀一次 issue、用當前 version 搬到 in_review。
  • done 是人的權力。只有使用者明確驗收或明確要求標記完成時,才可移到 done。agent 永遠不能自己宣稱「我做完了所以關票」。
可偷師的一點:把「授權邊界」寫進狀態轉場——backlog→todo 需要人、in_review→done 需要人,中間的 todo→in_progress→in_review agent 可自走。這等於用狀態機把「哪些決定必須留給人」固化下來,而不是靠 prompt 裡一句「請小心」。

增量同步:每個列表各自記 cursor

長對話裡最貴的是「每次都把整張 issue 重讀一遍」。Skill 的做法:第一次接手讀全量,並各自保存 issue get / comment list / attachment list 的 nextCursor;同一張票再次恢復時,只用各自的 cursor 帶 --after 取回「新增或改動」的部分。這是很典型的「context 經濟學」——同站內 上下文壓縮 是同一種焦慮的不同解法。

③ 併發紀律:樂觀版本鎖 + 五欄位身份綁定

一旦允許「多個 agent 同時處理一個看板」,就會踩到分散式系統的兩個經典問題:寫入衝突與身份混淆(誰擁有這張票)。這份 repo 的兩招都很值得抄。

① 樂觀並發:version + --if-version

每張 issue / comment 都帶一個 version。任何寫入都要用 --if-version N 帶上「我看到的版本」:

# 認領:用當前 version 從 todo 搬到 in_progress
taskctl issue move ISSUE_ID --status in_progress --if-version 7 ...

# 若別人先改過,version 已變 → 衝突(退出碼 5)
# 規則:重讀 issue + comment,只有在「仍是可認領的 todo、
# 沒被別的對話綁定、需求沒變」時,才用最新 version 重試一次。
# 不得無限重試、不得搶走別人的認領。

注意規則不是「衝突就重試到成功」,而是衝突就重讀、只在條件仍成立時重試一次,否則停下回報。這避免了 agent 之間互相打架、或硬把別人正在做的票搶過來。taskctl 甚至把退出碼標準化:0 成功、2 輸入錯、3 服務不可用、4 API 錯、5 衝突——衝突是一等公民。

② 身份綁定:完整 threadBinding(防搶單)

光有版本鎖還不夠——你得知道「這張 in_progress 的票屬於哪一場對話」,否則 agent B 會把 agent A 正在做的票當成「無主的 in_progress」接手。解法是每張被認領的票都要存一組五個欄位的完整身份:

欄位意義
threadIdCodex 對話 ID(來自 CODEX_THREAD_ID 環境變數)
codexProjectId對應的 Codex 專案
codexProjectKind專案種類(如 local)
codexHostId宿主 ID(如 local)
workspacePath工作區絕對路徑

規則極嚴:五個欄位任一缺失,就不准把票搬到 in_progress;絕不允許只存 threadId 的「殘缺綁定」。之後每次保留擁有權的 issue move 都要原封不動帶回這五個值,不得從當前 context 重建、不得取代別的對話所擁有的綁定。

這解決的真實痛點:多 agent 併發時,「這張票是誰的」不能靠時間或直覺猜。用一組不可偽造、必須完整的身份鍵,把「認領」變成一個可驗證的擁有權宣告——這跟 DeepSeek Harness 的單調守衛、Prime Agent 的並發設計 是同一個家族的紀律:讓危險的併發操作有明文、可檢查的前置條件。

④ 協調者 / 執行者:一份多代理操作手冊(AGENTS.md)

repo 的 AGENTS.md 更進一步,把「一個協調對話 + 多個執行對話」的分工寫成明文。裡面有幾個對任何在做多代理系統的人都通用的觀念:

E3 循環:Estimate → Execute → Expand

  1. Estimate(估):先估 context、步驟、重疊與風險,把工作分成 small / medium / high risk,並先講清楚打算怎麼直接驗證。
  2. Execute(做):先證明再實作——用「入口 → 使用者/agent 動作 → 元件/API/資料變更 → 可觀察結果」寫下真實操作路徑,再做能讓它動起來的最小改動。
  3. Expand(擴):只有在直接驗證失敗、證據推翻了原本的根因、或使用者回報新案例時,才擴大讀取/修改範圍。

反過度設計,寫成硬規則

這份文件反覆強調的一條主張,值得任何 agent 系統的設計者記住:

「在使用者確認功能可用之前,不要主動加護欄、回歸測試、相容層、防禦性擴充或臆測性 fallback。」——先讓被要求的功能真的動起來,把最小根因改動做對;測試與護欄只在使用者明確要求、或回報了具體失敗場景時才加。

這是對「AI 一寫程式就狂加防禦、把小需求做成大工程」的直接反制。它把「altitude(改在對的高度、不過度)」寫進了團隊規則。

併發按「衝突域」而非「票數」切

  • 不設固定的執行道數。十張票可能變成幾個並行組、也可能合成一個連貫組,取決於重疊程度。
  • 併發由共享資源決定:共享檔案、feature 狀態、Codex App 行程、Launcher runtime、CDP、瀏覽器審查狀態、CI 容量、發布資源——而不是「票多就開更多 worktree」。
  • 共享可變 runtime 不併發:獨立的程式路徑可以並行;但同一個 App 環境的 Launcher / 注入 / 更新 / 簽章 / 發布,一次只能跑一個。
  • 程式改動用 worktree 隔離;研究、分診、回覆這類不改碼的工作通常不需要 worktree。

依風險審查(review by risk)

低複雜度的改動由執行 agent 自己 review;複雜或高風險的,才由該執行對話自己把 PR 丟給「ChatGPT web Pro」做更重的審查——而且只在使用者已確認功能可用之後才送審(不能拿 Pro 來判斷一個沒做完的功能能不能動)。協調者只檢查交接證據齊不齊,不重做程式審查。

一句話總覽這份手冊:把「最小可行改動 + 直接驗證 + 依衝突域併發 + 依風險審查 + 人掌驗收」寫成明文,讓一群 agent 能像一個克制、有紀律的工程團隊那樣協作,而不是各自暴衝。

⑤ 嵌進 Codex 的工程(不改 app.asar)

看板要「長在 Codex 側欄裡」,但作者刻意不去 patch ChatGPT 桌面 App 本體。做法是走 CDP(Chrome DevTools Protocol)注入:

  • 用獨立 CDP 埠起一個 Codex 實例(如 --remote-debugging-port=9231),再跑注入腳本 codex-taskboard.user.js(1800+ 行),在 renderer 裡插入一個「Taskboard」側欄項與一個 iframe。
  • OOPIF + CSP 繞過:新版 Codex 的 renderer CSP 會擋任意 HTTP iframe;Launcher 因此對該 renderer 啟用 CSP bypass、reload 一次、裝上 document-start 腳本,等到 Taskboard 的 OOPIF 真的載入為止。
  • 不動原生資料:腳本只用 Codex 既有的專案、composer、route 標記;不 patch React、不替換 fetch、不載入私有 chunk、不改 Codex 資料檔。選另一個 Codex 頁面就會還原原生介面。
  • 對話歸屬:「在對話中打開」會開一個未送出的原生 composer,帶上 e-taskboard 指令與該 issue 的真實識別碼;等對話真的處理了這張票,taskctl 讀 CODEX_THREAD_ID 把該 ID 記回 issue——形成前面說的 threadBinding。
安全提醒(repo 自己標的):CDP 對同機其他行程是未認證的,所以「只在 Launcher 活躍時執行可信的本地程式」。這也是為什麼 LAN 模式明說「同一信任網段內任何人都能讀寫看板」,公網/雲端才需要認證邊界。把威脅模型講清楚,是這份 repo 值得學的態度。

桌面版(Tauri 打包的 macOS / Windows / Linux App)則把 Node runtime、服務、UI、Skill、CLI 與注入腳本全包進去,目標機只要裝了官方 Codex App 就能用,不需要這個 repo 或系統級 Node。

⑥ 資料面:本地優先,雲端是可選的第二形態

模式資料在哪認證適用
本機(預設)本地 SQLite .data/taskboard.sqlite無(loopback)單人 / 自己的 agent
LAN 共享同上,綁 0.0.0.0無——同網段皆可讀寫同一信任網段的隊友
Cloudflare 雲D1 為權威業務庫、R2 私有桶存附件、Worker Static Assets 出 UIHTTPS Basic Auth(共享密碼)兩位可信協作者

幾個工程細節:

  • SSE 即時廣播:議題/留言/附件變更推給每個開著的用戶端;斷線重連的用戶端做一次全量刷新,不漏掉離線期間的變更。
  • 雲端不 fallback、不雙寫:cloud 模式下,上游寫入失敗就失敗,絕不回退或同時寫本地 SQLite——避免「兩份真相」。
  • loopback companion:雲端模式下 taskctl 仍打一個「本機環回服務」,由它套 Basic Auth、存裝置本地的專案路徑映射、保留 Codex/Git/Skill/MCP 能力在本機。每台裝置的 checkout 映射各自獨立。
  • schema 有版本:除了內建 help,每個成功命令都輸出一個帶 schemaVersion 的 JSON 物件(目前為 2),讓 agent 消費輸出時有穩定契約。

⑦ 值得偷師的思路(不做看板也用得到)

  1. 把「授權邊界」編進狀態機:用 backlog→todo(需人)、in_review→done(需人)固化「哪些決定必須留給人」,中間放手讓 agent 自走。比 prompt 裡叮嚀「請小心」可靠得多。
  2. 認領要原子、衝突要一等公民:樂觀版本鎖 + 標準化的「衝突退出碼」+ 「只重試一次」規則,讓多 agent 併發不打架。
  3. 身份要完整才算數:五欄位 threadBinding——寧可缺一欄就拒絕開工,也不接受殘缺身份。這是防「搶單/接錯票」的根。
  4. context 經濟學:各列表各記 cursor、只取增量;一則認領留言 + 一則收尾留言,不寫「還在等」的流水帳。
  5. 反過度設計寫成規則:「使用者確認前不加護欄/測試/相容層/臆測 fallback」——直接壓制 AI 把小需求做成大工程的傾向。
  6. 併發按衝突域切、不按票數:由共享檔案/行程/runtime 決定並行度,而不是「票多就開更多道」。
  7. 擴充宿主別 patch 本體:用 CDP 注入 + OOPIF 把 UI 掛進 Codex,不改 app.asar、不換 fetch——可還原、風險可控,並老實寫出威脅模型。

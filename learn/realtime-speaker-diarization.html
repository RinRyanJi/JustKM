⓪ 一句話總結

「即時語者分離」要在音訊還在串流進來時,同步回答兩個問題:現在有沒有人在說話(VAD)、以及是誰在說話(diarization)。離線做這件事已經很成熟;難的是把它壓進幾百毫秒的延遲、還要能在 CPU 或輕量 GPU 上全本地跑。

這份規格給的答案是一條務實的管線:Silero VAD 過濾靜音 → CAM++(ONNX Runtime)抽語音特徵向量 → 線上餘弦相似度 + EMA 做分群 → Faster-Whisper 轉文字 → 按時間戳把「文字」和「語者編號」對齊 → 條件觸發本地小 LLM 做摘要。核心取捨是:不追求離線等級的重疊語音精度,換取超低延遲與極小資源佔用。

誰會需要這個:會議即時字幕與紀錄、客服/銷售通話的即時分軌、直播逐字稿、本地語音助手要區分「主人 vs 其他人」。凡是「邊聽邊要知道誰在講什麼」、又不想把音訊送上雲端的場景。

① 語者分離是什麼、即時為何難

語者分離(Speaker Diarization)回答的是「誰在什麼時候說話(who spoke when)」——它不認識你是張三還是李四(那是語者辨識),只負責把同一段錄音切成「說話者 1、說話者 2……」並標出各自的時間區段。它和語音轉文字(ASR)是兩件正交的事:ASR 給你「說了什麼」,分離給你「這句是誰說的」,兩者對齊後才是完整的對話紀錄。

離線批次做很好辦:可以拿到整段音訊、來回掃描、全域分群。即時(串流)則同時被三個約束夾住:

  • 看不到未來:只能靠「到目前為止」的音訊做決定,不能等整段講完再回頭修正。
  • 語者數未知且會增長:不能預設「就兩個人」,得能在第 3 個人插話時當場註冊一個新語者。
  • 延遲預算極緊:從「聲音進來」到「標好是誰」若超過 1 秒,體感就不即時了;而重疊語音、短句、背景雜訊都在跟你搶這點時間。
最難的一塊是「重疊語音(overlap speech)」——兩人同時講話。離線模型可以用大模型硬解,串流下多數輕量方案會退讓:先把它當成主要語者,精度換延遲。這是選型時要睜大眼睛看的地方(見 ②)。

② 三種即時語者分離模型選型

規格裡把候選收斂到三條路線,分別代表「極致輕量、極致精度、原生串流」三種取向:

模型 / 架構特性ONNX / 串流適用場景
CAM++
(3D-Speaker 開源)		 模型極小(參數僅數百萬)、運算極快,單次向量擷取在一般 CPU 上約數十毫秒 結構單純,匯出 ONNX 很順,ONNX Runtime 可做極致推論最佳化。只負責抽特徵向量(embedding),分群要另配本地演算法(移動平均 + 餘弦比對) 追求超低延遲、資源受限的 CPU 或輕量 GPU 本地環境
Pyannote.audio
(3.x)		 語者分割精度極高,處理兩人互相插話、聲音重疊的場景表現最好 分割與特徵模型皆可轉 ONNX,但串流推論需要較大的滑動視窗(約 1–2 秒),延遲較高 對精準度與重疊語音分離要求極高的會議紀錄

③ 推薦組合與為什麼這樣配

規格的最終建議是把它拼成一條可組裝的本地管線,而不是賭單一大模型:

推薦核心組合:
Silero VAD(靜音過濾) + CAM++ / ONNX Runtime(特徵向量) + 線上餘弦距離比對(分群)。
——在資源消耗、實作複雜度、延遲三者之間取得最佳平衡。

為什麼不是直接上 Pyannote 或 NeMo?

  • VAD 先擋掉靜音:真實對話裡靜音佔比很高。用一個極小的 Silero VAD 先把沒人講話的訊框丟掉,後面昂貴的特徵擷取與 ASR 就只在「真的有聲音」時才跑——這是最划算的一刀。
  • CAM++ 只做它最擅長的一件事:把一段語音壓成一個定長向量(embedding)。它不做分群,所以你可以用自己完全可控、可調門檻的線上演算法來決定「這是舊語者還是新語者」。
  • 分群留在本地程式碼裡:用餘弦相似度 + 指數移動平均(EMA)維護一個「語者向量庫」,不需要額外的重模型。這讓整條管線在 CPU 上也能即時。
代價要講清楚:這條路犧牲的是重疊語音的精度。若你的場景是高頻互相插話、且對「誰壓過誰」要求極高的會議存證,Pyannote 的滑動視窗方案會更穩;若你有 NVIDIA GPU 且能吃 NeMo 工具鏈,Sortformer 的原生串流會更省心。先確定你的延遲/精度/硬體約束,再選路線。

④ 端到端五階段資料流

整套系統由五個階段串成一條非同步管線。每一個訊框(frame)/區塊(chunk)像水一樣往下流,前一段的輸出就是後一段的輸入:

← 左右滑動看完整圖 →
▲ 五階段管線。關鍵設計是「非同步佇列解耦」+「③④ 平行、依時間戳合流」,讓昂貴的步驟不阻塞音訊擷取。

第一階段 · 系統音訊擷取(Audio Capture)

  • 透過系統底層 API(如 Windows WASAPI Loopback)擷取系統正在播放的聲音串流——這讓你能錄下線上會議/影片的對方聲音,而不只是麥克風。
  • 統一格式化為 16kHz 取樣率、16-bit 單聲道(mono)、float32 陣列——這是語音模型的通用輸入格式。
  • 以每 30ms 一個訊框(frame)持續推入內部非同步佇列。

第二階段 · 語音活動檢測(VAD)

  • 用 Silero VAD(ONNX 加速)對 30ms 訊框做過濾:無人說話的靜音區段直接丟棄,不浪費算力。
  • 偵測到持續聲音時,把音訊累積成 500ms–1000ms 的區塊(chunk)。
  • 若靜音超過 500ms,就標記「這句話結束」,把區塊往下送。

第三階段 · 語者分離與特徵比對(Speaker Tracking)

  • 把有聲區塊送進 CAM++ ONNX 模型,萃取 512 維語音特徵向量並做 L2 正規化。
  • 在記憶體維護一個「已知語者向量庫」,用餘弦相似度比對新向量與各已知語者的距離(細節見 ⑤)。

第四階段 · 語音轉文字與時間戳對齊(ASR Alignment)

  • 把同一個音訊區塊平行送進 Faster-Whisper 或 Whisper.cpp 即時解碼,並開啟字詞時間戳(word timestamps)。
  • 合流模組依時間戳,把「文字內容」與第三階段的「語者編號」結合成結構化資料(語者、起訖時間、文字)。

第五階段 · 本地大型語言模型分析(LLM Inference)

對齊後的對話推入上下文緩衝區(context buffer),用條件觸發驅動本地小模型(見 ⑦),不是每次辨識都硬跑,避免佔滿 CPU/GPU。

⑤ 語者追蹤:餘弦相似度 + EMA + 門檻

這是整條管線裡「不靠大模型、靠一小段演算法」的關鍵。CAM++ 只給你一個向量,「這是誰」的判斷全在這裡:

← 左右滑動看完整圖 →
▲ 餘弦相似度落在門檻(例:0.65)之上→歸為舊語者、用 EMA 平滑更新中心;之下→動態註冊新語者。門檻與 EMA 係數 α 是這套方法最關鍵的兩個旋鈕。

為什麼用「餘弦 + EMA」而不是重跑分群

  • 餘弦相似度只看向量方向、不看長度,對音量變化穩健;配上 L2 正規化,比對變成一次點積,快到可忽略。
  • 指數移動平均(EMA)讓每個語者的「中心向量」隨新樣本緩慢漂移,吸收語調、距離麥克風遠近的自然變化,又不會被單一雜訊區塊帶歪。
  • 門檻決定靈敏度:調高→更容易把相近的人拆成兩個(over-split);調低→更容易把兩個人併成一個(under-cluster)。這個值要按你的麥克風與場景實測校準,沒有萬用數字。
已知弱點:這套線上分群不回頭修正。一旦早期把 A、B 誤併,後面很難自動拆開;短區塊(<0.5s)抽出的向量也較不穩。若場景要求高,可用較長區塊、或定期對緩衝做一次小範圍離線再分群來校正。

⑥ ASR 對齊:文字 × 語者怎麼合流

第三階段給出「這個區塊是 Speaker K」,第四階段給出「這個區塊的字詞各自落在哪個時間點」。合流就是把兩條時間軸對齊:

# 概念示意:依時間重疊把語者標籤貼到每個字/句上
for seg in asr_segments:            # Faster-Whisper 的字詞/句段(含 start/end)
    spk = speaker_at(seg.start, seg.end)  # 查該時間區間屬於哪個 Speaker
    emit({
        "speaker": spk,             # 來自 ③ 的語者編號
        "start": seg.start,
        "end":   seg.end,
        "text":  seg.text,        # 來自 ④ 的文字
    })

實務上兩件事要留意:

  • 時間戳要同源:VAD 切塊時就要記下每個區塊在總時間軸上的絕對起點,ASR 的相對時間戳才能加回去對齊,否則語者與文字會錯位。
  • 邊界歸屬:一句話橫跨語者切換點時,按「字詞時間戳落在誰的區間較多」來歸屬;短促的「嗯/對」很容易被錯貼,可設最小時長門檻過濾。

Faster-Whisper 與 Whisper.cpp 都是 Whisper 的高效本地實作,能在 CPU/GPU 上串流解碼並輸出字詞時間戳——這也是站內 VoxEMW 即時對話工程 裡同一類「串流 STT」的技術族。

⑦ 條件觸發本地 LLM:不要每句都燒算力

最後一段把對話餵給本地小模型(如 Qwen2.5-1.5B/3B 或 tiny LLaMA)。重點是「條件觸發」而非「每次都跑」——即時管線的 CPU/GPU 已經被 VAD/CAM++/ASR 佔著,LLM 只在划算的時機出手:

觸發模式條件做什麼
週期摘要觸發 文字累積達一定長度(例:150 字)或 對話切換語者超過 4 次 在背景自動總結重點,滾動更新會議摘要
關鍵字主動觸發 ASR 辨識到特定觸發詞(如「總結一下」「待辦事項有哪些」) 立即擷取前段對話送模型,輸出即時提示與摘要
為什麼這樣設計:把 LLM 從「串流管線的一環」降級成「被事件喚醒的背景服務」,它就不再和即時辨識搶延遲預算。摘要晚個一兩秒沒關係,但字幕不能卡——優先級要分清楚。

這條「用小模型 + 條件觸發做本地摘要」的思路,和站內 訓練小模型做單一任務、端側小模型 K2 Horizon 是同一種「把合適大小的模型放在合適的位置」的工程取向。

⑧ 值得偷師的思路 / 來源

  1. 把「有沒有人說話」和「是誰說話」拆開。VAD 是最便宜的一刀,先擋掉靜音,昂貴的模型只在有聲時跑——這是即時管線省算力的第一原則。
  2. 讓大模型只做它最擅長的一件事。CAM++ 只抽向量、不做分群;分群留在可控的本地演算法裡。這種「特徵擷取 vs 決策邏輯」分離,讓你能單獨調門檻而不動模型。
  3. ONNX Runtime 是把研究模型變產品的橋。結構單純的模型(CAM++、Silero VAD)匯出 ONNX 後能做極致推論最佳化,是「CPU 也即時」的關鍵。
  4. 非同步佇列 + 平行 + 依時間戳合流。不讓任一段阻塞音訊擷取;分離與 ASR 平行跑、最後用同源時間戳對齊——這是串流系統的通用骨架。
  5. 把 LLM 降級成事件驅動的背景服務。條件觸發(長度/語者切換/關鍵字)取代「每句都跑」,讓摘要不和即時字幕搶延遲。
  6. 誠實面對取捨。這條輕量路線換來的是超低延遲與 CPU 可跑,代價是重疊語音精度與「不回頭修正」——選型前先量好你的延遲/精度/硬體約束。

📝 讓 AI 產生高品質文件：多 Agent 協同與自動化評分

把「評分」演算法化、把「生成」流水線化 —— 用結構取代感性,用引用消滅幻覺,用角色分離消滅自我感覺良好

⓪ 單一 Prompt 的局限與客觀評分架構

AI 本身缺乏主觀意識與真實的標準感知。若只給模糊的評分指令(如「請幫我評分」),AI 往往給出缺乏依據的高分或客套評語。要建立客觀、不失真、具一致性的評分機制,必須把評分過程「演算法化與結構化」。

四個核心替換:① 用 Rubric/CheckList 取代感性評語;② 用 Metadata 邊界條件 限制審查範疇;③ 用 強制引用 解決幻覺;④ 用 角色分離(生成者 vs 稽核者)解決「自我感覺良好」。
一 · 五大核心評分方法論

① 從主觀印象轉為客觀指標(Rubric-based Evaluation)

引入評分量規與錨點

明確定義每個分數對應的具體特徵與條件,而非只給分數等級。例如:規定得分必須包含「具體的專案範疇、時間節點、風險因應策略」,缺少特定要素即按點扣分。

檢核清單二元化(Binary Verification)

把高層次標準拆成二元檢查清單(True / False),例如:

  • 是否包含摘要? ✅/❌
  • 程式碼區塊是否標示語言種類? ✅/❌
為什麼有效:二元判斷比「給幾分」穩定得多——AI 對「有沒有」的判斷一致性遠高於「好不好」。把主觀的「品質」拆成一串可勾選的客觀事實,分數自然變得可複現。

② 元資料導向:上下文契合度檢驗(Metadata-driven Alignment)

每份文件在生成或評分前都附帶一段邊界條件聲明(文件類型、目標讀者、領域情境、必須包含的章節…)。評分機制據此檢驗三件事:

維度檢驗什麼
受眾契合度文件用語深度是否符合目標讀者設定(給工程師 vs 給主管)
結構完整度章節是否完全覆蓋「必備章節清單」
領域精準度專業術語是否符合特定領域規範
連結:這正是站內 Skills 分析專區 說的「好 Skill 的 description 要講清楚目標讀者與邊界」的評分版——先聲明邊界,再照邊界審。

③ 機制設計:多重 Prompt 與角色對立架構

角色分離與對立機制

把生成與審查職責分離:生成 Agent 負責撰寫;另設稽核 Agent 扮演嚴格審查者,專門找缺失、並要求附帶原文引用。

先推理後評分(Chain-of-Thought)

強制 AI 在給分前先列出具體扣分原因與原文對照,避免「先給隨機分數、再編造理由」。

多次採樣求中位數(Self-Consistency)

對同一份文件多次獨立評估取平均或中位數,降低單次輸出的偶然誤差。

站內深挖:這兩招在研究上都有專頁——Self-Consistency(多路取樣→多數決/中位數)與序列自我修正的 Reflexion。角色對立=「生成者 vs 稽核者」正是 多代理 的評測應用。

④ 事實錨定與扣分反向驗證(Grounding & Proof Verification)

強制原文引用

稽核 Agent 提出扣分時,必須精確引用文件中的原始文句作為依據。

反向程式驗證

用獨立程式或輕量模型檢查評分報告引用的段落是否真實存在於原文;若引用不存在,該次扣分判定無效——防止 AI 產生「幻覺扣分」。

這是全套機制的樞紐:「強制引用 + 程式反查引用是否存在」把 AI 評分從「它說了算」變成「它得拿出證據,而且證據要能被機器驗真」。沒有這一步,前面的 Rubric 也可能被幻覺理由架空。

⑤ 結構化 Prompt 實作規範

評分 Prompt 必須:

  • 設定預設滿分 + 嚴格按點扣分規則;
  • 禁止輸出主觀評語;
  • 要求以結構化格式(如 JSON)輸出:各維度得分、扣分明細、引用原文、扣分理由。
{
  "dimensions": {
    "structure":  { "score": 18, "max": 20 },
    "audience_fit":{ "score": 15, "max": 20 }
  },
  "deductions": [
    { "points": -5, "reason": "缺少風險因應章節",
      "quote": "<原文中被引用以佐證的句子>" }
  ]
}
設計含義:「預設滿分、按點扣分」比「從零加分」更嚴——AI 傾向給高分,所以讓它找理由扣而非找理由加,配合強制引用,分數才不會虛高。
二 · 開源專案與核心技術

⑥ 代表性開源專案

專案定位核心機制
GPT-Researcher → 詳解 全自動深度報告/技術文件生成 「計畫→檢索→摘要→聚合→撰寫」五階段流水線;大綱拆解後派多個子 Agent 平行搜集與撰寫;每段強制附資料來源引用(事實錨定)
AutoGen / CrewAI → 詳解 多角色協作框架(模擬編寫+審查團隊) 「生成者 vs 審查者」對立;分工研究員/撰寫員/稽核員;稽核員依 CheckList 評分,低於門檻(如 85 分)退回重寫,形成自動校正迴圈
DocuWriter.ai / Quivr 基於 RAG 的結構化文件生成(接程式碼庫/知識庫) 「AST 語法樹解析 + 上下文注入 RAG」;直接讀原始碼,把抽象語法樹與註解抽成 Metadata,確保文件與底層實作高度一致、防幻覺
Ragas / DeepEval → 詳解 文件評分與量化評估框架 「LLM-as-a-Judge + 數學指標」;量化忠實度(有無事實依據)、相關性(精準回答 vs 堆廢話)、上下文召回率/精準度

⑦ 開源專案採用的核心方法論與技術

Map-Reduce 與分塊寫作(Chunked Generation)

長篇文件易出現品質衰退或前後矛盾。做法:Map 階段把文件拆成 JSON 階層式大綱 → Execution 階段由獨立 Prompt 分別寫各章節 → Reduce 階段由編輯器 Agent 做全篇銜接潤飾與格式統一。

對照:這與 Prime Agent 的 rlm(...) 平行子代理、以及 綜述 的「拓撲/多代理」是同一思路——把大任務拆成可平行、可各自驗收的小塊。

強制 Schema 與 JSON Mode

為避免 Markdown 結構缺失/排版錯位,用 Pydantic 或 TypeChat 嚴格限制輸出資料結構(必須含標題、摘要、技術細節、風險評估等欄位)。未通過 Schema 驗證的輸出直接觸發重試。

反思與自我校正(Self-Correction / Reflexion Loop)

初稿 + 評分標準(Rubric)一起餵給稽核 Agent → 產生具體批判與修改計畫 → 生成 Agent 二次修正。一到兩輪自動迭代顯著提升品質。

站內深挖:這正是 Reflexion / Self-Refine 的文件應用——把「失敗回饋」寫成文字,下一輪帶入修正。

動態 Prompt 編譯與優化(DSPy 框架 → 詳解)

不手寫固定 Prompt,而是把 Prompt 當可編譯模組。DSPy 依你設定的評分標準,自動測試、調整、編譯出高精準度 Prompt,解決品質不穩與 prompt 漂移。

對照:站內 EvoAgentX 的 MIPRO(DSPy 系)與 TextGrad 就是這種「提示自動優化器」;它把「調 prompt」從人肉試錯變成可搜尋的優化問題。

⑧ 高品質文件產出流水線架構總結

1. 結構定義 Pydantic / JSON Schema 設定格式約束 + Metadata(讀者/領域/必備章節) │ ▼ 2. 生成流程 多 Agent:撰寫者 ⇄ 審查者 對立協同(Map-Reduce 分塊) │ ▼ 3. 品質評估 Ragas / DeepEval → 客觀分數 + 對照引用(強制原文引用 + 反向驗真) │ ▼ 4. 自動迭代 未達門檻 → 帶「扣分原因 + 原文對照」退回重寫(Reflexion loop) │ └──▶ 達標輸出
層手段解決的問題
結構定義Pydantic / JSON Schema + Metadata格式缺失、範疇失焦
生成流程多 Agent 撰寫者/審查者對立自我感覺良好、缺乏審查
品質評估Ragas / DeepEval + 強制引用主觀評語、幻覺扣分
自動迭代品質門檻 + 扣分對照重寫一次到位不可靠、品質不穩
一句話收斂:高品質不是靠「更會寫的模型」,而是靠一套把品質拆成可勾選事實、把扣分綁上可驗真引用、把生成與審查分開、並自動迭代到達標的流水線。這與本站反覆出現的主題一致——不靠更強的模型,靠更好的環境與流程。

⑨ 可直接複製的 Prompt 範本

把前面八節落成四塊可貼上就用的模板。用法:先寫 A 邊界條件 → 生成時附 B → 評分時用 C(稽核 Agent)→ 再用 D 反查引用真偽。占位符用 <…> 自行替換。

A · 文件邊界條件(Metadata)宣告

每份文件在生成/評分前先定義邊界,後續一切照它審:

{
  "doc_type": "<技術規格書 | API 文件 | 決策摘要 | …>",
  "audience": "<資深後端工程師 | 非技術主管 | …>",
  "domain": "<金融風控 | 雲端基礎設施 | …>",
  "required_sections": ["摘要", "範疇", "時程", "風險與因應"],
  "must_include": ["具體時間節點", "風險因應策略"],
  "style": { "code_blocks_need_language": true, "tone": "技術、精簡、無客套" }
}

B · 生成 Agent 系統提示

你是撰寫 Agent。依附上的「邊界條件(Metadata)」撰寫文件。
規則:
1. 必須涵蓋 required_sections 的每一個章節,缺一不可。
2. 用語深度必須符合 audience;術語必須符合 domain 規範。
3. must_include 的每一項都要有具體內容(不可含糊帶過)。
4. 程式碼區塊一律標示語言種類。
5. 只寫有依據的內容;凡引用事實/來源,標註出處。禁止杜撰。
輸出:純文件內容(Markdown)。

C · 稽核 / 評分 Agent 系統提示(核心)

你是嚴格的稽核 Agent,不是作者的朋友。任務:依 Rubric 對文件扣分。
鐵律:
1. 【預設滿分,按點扣分】每個維度從滿分起算,發現缺失才扣,不「從零加分」。
2. 【先推理後給分】每筆扣分必須「先寫理由 + 精確引用文件原文」,再結算分數。
3. 【強制引用】每筆扣分都要附 quote:一段逐字出現在文件中的原文。
   若某缺失是「缺少某章節」,quote 填該處前後最近的原文,並在 reason 註明「缺章」。
4. 【禁止主觀評語】不准出現「寫得不錯 / 大致良好」這類話。
5. 【二元優先】能拆成 True/False 的先用檢查清單判定(見下)。
檢查清單(每項 True/False,False 即依 Rubric 扣分):
  - 是否包含 required_sections 的每一節?
  - must_include 各項是否都有具體內容?
  - 程式碼區塊是否都標語言?
  - 用語深度是否符合 audience?
  - 術語是否符合 domain?
Rubric(各維度滿分與扣分點,依你的專案調整):
  - 結構完整度 /30:缺一必備章節 −10;章節順序混亂 −5
  - 受眾契合度 /25:深度不符 −10;出現不該有的術語/過度簡化 −5
  - 領域精準度 /25:術語誤用 −10(每處);缺關鍵領域要素 −5
  - 事實與可佐證 /20:出現無依據宣稱 −10(每處);引用缺失 −5
只輸出 JSON,格式如下,不要任何其他文字。
{
  "total": 0,
  "dimensions": {
    "structure":     { "score": 0, "max": 30 },
    "audience_fit":  { "score": 0, "max": 25 },
    "domain":        { "score": 0, "max": 25 },
    "grounding":     { "score": 0, "max": 20 }
  },
  "checklist": [ { "item": "包含『風險與因應』章節", "pass": false } ],
  "deductions": [
    { "dimension": "structure", "points": -10,
      "reason": "缺少『風險與因應』章節",
      "quote": "<逐字引用文件中最接近的原文>" }
  ]
}
多次採樣:把 C 對同一份文件獨立跑 3–5 次(temperature 稍高),取各維度分數的中位數,再合計——降低單次偶然誤差(即 Self-Consistency)。

D · 反向引用驗證(防幻覺扣分)

拿 C 的輸出,用獨立程式逐筆檢查 quote 是否真的在原文裡;不在就作廢該筆扣分並把分數加回:

import re, json
def verify(report_json, doc_text):
    rep = json.loads(report_json)
    norm = re.sub(r"\s+", " ", doc_text)          # 正規化空白
    valid = []
    for d in rep["deductions"]:
        q = re.sub(r"\s+", " ", d.get("quote", "")).strip()
        if q and q in norm:                  # 引用真的存在 → 扣分有效
            valid.append(d)
        else:                                 # 幻覺引用 → 作廢,分數加回
            dim = d["dimension"]
            rep["dimensions"][dim]["score"] -= d["points"]  # points 是負值→加回
    rep["deductions"] = valid
    rep["total"] = sum(x["score"] for x in rep["dimensions"].values())
    return rep
自動迭代收尾:若 total 低於門檻(如 85),把「deductions 的 reason + quote」連同初稿退回 B 重寫,跑一到兩輪(Reflexion loop)直到達標。對「缺章」類扣分,程式無法用 quote 驗真,可改驗「required_sections 的標題字串是否出現在文件」。

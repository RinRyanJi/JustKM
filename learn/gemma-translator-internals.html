⓪ 一句話總結

讀進原始碼後,這台翻譯機的後端其實是兩個各司其職的 Python 行程,不是一個大程式:

  • backend/litert_session_server.py —— 常駐的翻譯引擎。把 LiteRT-LM 當函式庫載入(litert_lm.Engine),維持一個長生命週期的對話、把 KV cache 跨句重用,對外開一個 OpenAI 相容的 HTTP API(127.0.0.1:9379)。
  • backend/server.py —— 對前端的閘道。用 Python 標準庫 http.server(不是 Flask)自己寫路由:靜態檔、Moonshine STT/TTS、系統音量/GPIO/kiosk,以及一個 /proxy 把 LLM 請求轉發到 9379。
一句話抓住設計精神:把「重的模型」關進各自的常駐行程、對外只露 HTTP + SSE,前端與膠水層完全不碰模型 SDK。這讓 LLM 可被任何 OpenAI 相容後端替換、STT/TTS 可獨立快取與熱載——是很乾淨的「行程邊界即介面」設計。

本頁依 repo main 分支原始碼(backend/*.py、start.sh、download_model.sh、frontend/package.json)整理;函式/變數名以原始碼為準,若日後改版以最新程式碼為準。

② LiteRT-LM 常駐翻譯器:把 KV cache 跨句重用

核心類別是 PersistentTranslator。它做的兩個關鍵決定,是這台在樹莓派上還能即時的原因:

(1) LiteRT-LM 當「函式庫」而非子行程

它 import litert_lm 並建立 litert_lm.Engine(帶模型路徑、backend=CPU、token 上限),引擎在 __init__ 就常駐、整個 server 生命週期不重載——避免每次翻譯都冷啟模型。

(2) 單一長生命週期 conversation + 系統提示只預填一次

PersistentTranslator 全程只維持一個 self.conversation,用 threading.Lock() 保護。系統提示來自 SYSTEM_PROMPT 環境變數,透過 engine.create_conversation(system_message=SYSTEM_PROMPT) 在建立對話時就預填進 KV cache(指示模型「每次收到 來源語言/目標語言/文字 就翻譯」)。之後每句翻譯都重用同一份 KV,不必每次重吃系統提示。

← 左右滑動看完整圖 →
▲ LITERT_RESET_AT_TOKENS(預設 3200)在每次推論前檢查;超過就 reset_conversation()。LITERT_MAX_NUM_TOKENS(4096)是引擎能處理的硬上限——3200 留了緩衝,避免撞到 4096。

(3) 串流:send_message_async → SSE

stream(prompt) 迭代 self.conversation.send_message_async(prompt),用 _text_from_chunk() 從每個 chunk 取出 text 欄位;Handler.do_POST() 把每塊用 emit() 包成 data: {json}\n\n 的 SSE,最後送 [DONE]。對外長得就跟 OpenAI 的 /v1/chat/completions(stream=true)一模一樣。

可偷師:「一個常駐對話 + 系統提示只預填一次 + 到門檻才重置」是端側 LLM 服務的省算力範式——把重複的前綴留在 KV 裡,把記憶體/延遲用 token 門檻夾住,還順手做了「推論出錯就重置恢復」的韌性設計。

③ SSE 為何能「不緩衝」直通瀏覽器

server.py 的 /proxy 把前端的 LLM 請求轉發到 9379。串流的關鍵只有一行選擇——用 read1() 而不是 read():

# server.py:handle_proxy() 轉發回應時
read_chunk = getattr(response, 'read1', response.read)
while True:
    res_body = read_chunk(4096)
    if not res_body:
        break
    self.wfile.write(res_body)
    self.wfile.flush()          # 立刻沖出,不等整包

read() 會等到湊滿要求的位元組才回傳,會把一串 token「攢起來」再送,體感就一頓一頓;read1() 是「有多少先給多少」(底層一次 read),配合每塊都 flush(),LiteRT-LM 產一個 token、就幾乎立刻推到瀏覽器——原始碼註解稱這是「保留 LiteRT-LM 的 SSE token timing」。

為什麼要多一層 /proxy 而不讓前端直連 9379?因為 9379 只綁 localhost(引擎不對外),而前端可能從區網其他裝置連進 :3000。/proxy 還白名單只准轉發到 localhost:9379、統一補 CORS、優雅處理 broken pipe / 連線重置——是個把「內部引擎」安全地暴露給前端的薄閘道。

④ Moonshine 的 LRU 模型快取與語言預備

聽與說由 server.py 直接呼叫 Moonshine(STT)與 moonshine-voice(TTS)。因為每種語言一組模型,記憶體吃緊,所以用 LRU 快取控管:

_stt_recognizers = OrderedDict()   # language -> recognizer
_tts_engines     = OrderedDict()   # language -> TextToSpeech
MAX_MODELS = max(2, int(os.environ.get("TRANSLATOR_SPEECH_MODEL_CACHE_SIZE", "2")))
# 要新語言且滿了 → popitem(last=False) 淘汰最舊;命中就 move_to_end
  • 支援語言:{en, ar, es, ja, zh, ko};用 threading.RLock()(可重入)保護快取。
  • 預載:啟動時讀 TRANSLATOR_PRELOAD_LANGUAGES(預設 zh,en),背景執行緒 prepare_languages_background() 先載好。
  • 隨需載入 + 進度回報:POST /api/languages 觸發背景 daemon 下載/載入,狀態經 set_language_prepare_status() 記進 _language_prepare_status(queued→preparing→ready);前端輪詢 GET /api/languages 畫進度條。tracked_download_file() 還 patch 了 moonshine 的下載函式來攔截進度。
路徑方法資料流
/api/sttPOST收 {audio_base64, language} → 解 base64 成 numpy.float32 → recognizer.transcribe_without_streaming(audio, 16000) → 回 {text}
/api/ttsGET?text=&lang= → engine.synthesize(text) → 浮點取樣夾到 [-1,1] → 16-bit PCM → 回 audio/wav
/api/languagesGET/POST查詢/觸發語言模型預備與進度
可偷師:端側多語音服務的通用招式——LRU 夾住同時常駐的模型數(預設 2)、預載熱門語言、其餘隨需背景載入並回報進度。把「一次全載會爆記憶體」變成「常用即時、少用稍等」。

⑤ 模型與啟動編排

模型:確定是 Gemma 4 E2B-it

download_model.sh 從 Hugging Face litert-community/gemma-4-E2B-it-litert-lm 抓 gemma-4-E2B-it.litertlm(註解標為「generic CPU build,正確用於樹莓派」;另有 *_Google_Tensor / *_intel / *_qualcomm 加速版),再用 litert-lm import 匯入其本地儲存。約需 5.2GB 磁碟(HF 快取 ~2.6GB + 匯入副本 ~2.6GB)。這也確認了概覽頁的命名:是 Gemma 4 E2B-it(非 3n)。

啟動:start.sh 的順序與等待

  1. 最多等 15 秒網路連線;缺 npm 依賴則安裝;正式模式先 vite build 出 frontend/dist。
  2. 用 wpctl / amixer 把系統音量開到最大(設 XDG_RUNTIME_DIR 給 PipeWire)。
  3. (可選)GPIO bridge deploy/whisplay_plus_gpio.py;接著 LiteRT-LM(9379)→ 等埠就緒(最多 180 秒)→ API(3000)→ Vite(5173,僅開發)。
  4. PYTHONUNBUFFERED=1 讓 log 即時進 systemd。
值得注意的韌性細節:API server 會等 LiteRT-LM 埠就緒最多 180 秒才啟動——因為在樹莓派上載入 ~2.6GB 模型很慢,這個等待避免了「前端先起來、後端還沒好」的競態。這種「啟動順序 + 埠健康等待」在端側家電式部署很關鍵。

⑥ 前端與 /proxy 的設計

前端專案名 gemma-offline-translator,刻意極簡:只有 react / react-dom(18.3)、@fontsource/roboto-mono(復古終端機字體),建置用 vite(5.3)、格式化用 oxfmt——沒有任何 UI 框架或狀態管理庫。對一台只有 480–640px 小螢幕的家電來說,這種「零肥料」前端能省下載入與記憶體。

  • 正式模式不跑 Vite:由 server.py 直接送 frontend/dist 靜態檔,少一個行程。
  • 所有 LLM 呼叫走 /proxy(見 ③),STT/TTS 走 /api/*——前端完全不知道 9379 的存在,只跟 :3000 對話。
  • 周邊控制也走 API:/api/volume(音量)、/api/hardware(讀 /tmp/whisplay-plus-gpio-state.json 的 GPIO 狀態)、/api/kiosk/exit(關 Chromium kiosk)——這些敏感操作限 localhost。
  • 互動偏好(如 keyboardMode)存瀏覽器 localStorage。
設計一致性:無論 LLM、語音、還是硬體控制,前端一律透過 server.py 的 HTTP 介面。server.py 是唯一對外的面,把「模型行程、系統周邊」全部藏在後面——換模型、換語音引擎、換硬體,前端都不用動。

⑦ 值得偷師的思路 / 來源

  1. 行程邊界即介面。把重的模型(LLM、STT/TTS)關進常駐行程,對外只露 HTTP+SSE;膠水層與前端不碰模型 SDK。換引擎、換硬體都不牽動其他層。
  2. OpenAI 相容是免費的可替換性。翻譯引擎講 /v1/chat/completions,等於任何 OpenAI 相容後端(vLLM、llama.cpp server…)都能直接替換 LiteRT-LM。
  3. 常駐對話 + KV 重用 + token 門檻重置。系統提示只預填一次、跨句重用 KV、到 3200 就重置——端側 LLM 省算力與控延遲的範式,還附「出錯即重置」韌性。
  4. read1() + flush() 是串流順不順的關鍵。轉發串流別用會湊滿才回的 read();read1() 有多少送多少,才保住 token 的即時節奏。
  5. LRU 夾住常駐模型數 + 預載 + 隨需背景載入。多語音服務在小記憶體上的通用解;配進度輪詢給使用者回饋。
  6. 啟動順序 + 埠健康等待(180s)。端側載大模型慢,先等後端就緒再起前端,避免競態——家電式部署的必備細節。

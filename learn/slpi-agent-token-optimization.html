💸 SLPI(SoL-Pi):不換模型,幫 Coding Agent 省下近半令牌

同一個編碼任務,原本燒 1,339 美元,一層「運行時優化」把它壓到 894 美元——令牌流量少了約 44.7–49%、API 成本降約 33%。它不換模型、不改你的原始碼,只接管 Agent 的「運行時動作」來減少模型往返。代價是得分掉約 6%、狀態管理變複雜。本頁用教學方式拆解它的四個機制、省在哪、賠在哪、什麼時候該用。

⓪ 一句話總結

SLPI(Search-based Lightweight Pi,影片標題寫作「SoL-Pi」)是一層「運行時優化」。它不替換模型(仍用 GPT-5.6S、Opus 5 這些)、不修改你的原始碼,而是接管 Agent 執行時的動作——工具調用、上下文整理、觀察結果處理、任務委派——想辦法減少模型一來一回的往返次數。往返少了,重複塞進去的上下文就少,令牌與費用就下來了。

一句話權衡:省下約 44.7–49% 的令牌流量、約 33% 的 API 成本,代價是得分只保留約 93.7–94.3%(掉約 6%),而且狀態管理、快取改寫、失敗回退都變得更複雜。適合長軌跡任務,不適合短任務或不能接受掉分的場景。

① 為什麼 Coding Agent 那麼燒錢:往返 = 令牌通膨

要理解 SLPI 省在哪,得先懂 Coding Agent 為什麼貴。一個編碼 Agent 的運作是個迴圈:模型想一步 → 呼叫工具(讀檔、改檔、跑測試)→ 拿到觀察結果 → 再想下一步。問題是:

  • 每一次往返,都要把「先前所有上下文 + 這次的新輸出」整包再送一次給模型。對話越長,每一輪要送的 token 就越多。
  • 工具輸出很膨脹:一次測試 log、一份檔案內容、一段 build 輸出,動輒上千 token,還會被反覆帶在上下文裡重送。
  • 步驟很多:改一行、跑一次測試、看結果、再改……長任務可能幾十上百次往返,token 像滾雪球。

▲ 貴的根源不是「單次很貴」,而是「往返很多次 × 每次都重送一大包」。SLPI 就是從這兩個乘數下手。

② 核心主張:不換模型、不改原始碼,只接管「運行時」

SLPI 的定位很克制——它不碰兩件事:

  • 不替換模型:你還是用 GPT-5.6S / Opus 5,推理能力不變。
  • 不修改你的專案原始碼:它不是要你改程式或換框架。

它動手的地方是夾在「Agent 迴圈」與「模型」之間的運行時層,接管四類動作:工具調用、上下文整理、觀察結果、任務委派。核心目標只有一個:讓模型少往返幾次、每次少帶一點。

▲ 因為它只在「運行時」動手,你可以把它想成裝在 Agent 與模型之間的一個「省流管家」——換不換模型、改不改程式都不需要它出手。

③ 四個運行時機制(逐一教學)

SLPI 的省,來自四個彼此收斂的機制。它們各自砍掉「往返次數」或「每次帶的量」其中一項:

← 左右滑動看完整圖 →
▲ ① 砍往返次數;②③④ 都在縮「每次帶進模型的量」。四者疊起來,就是省下近半令牌的來源。

① Action Fusion(行動融合)

本來「改一行 → 送模型 → 模型要求跑測試 → 送模型 → 看結果」要好幾次往返。行動融合把編輯與測試合併在一次工具請求裡一起做完,模型一次就拿到「改了 + 測了」的結果。直接減少往返次數。

② Online Context Compact(線上上下文壓實)

不等上下文爆掉才壓,而是邊跑邊壓實計劃與上下文——把已完成的步驟、過時的細節收斂成精簡摘要,只留還需要的。每一輪送進模型的東西因此更小。

③ Observation Pack(觀察打包)

工具的大輸出(長 log、整份檔案)不再整包塞進上下文,而是先收好、發一個「控制代碼(handle)」。模型只看到精簡摘要 + 代碼;真的需要細節時,再按代碼(on-demand)取回。避免大輸出被反覆重送。

④ Evidence Preserving Reducer(證據保留歸約器)

Agent 常反覆產生類似的日誌。這個機制用可驗證的「收據」取代反覆的完整日誌——上下文裡放輕量、可查核的憑證,但原始證據與失敗回退仍被保留,需要時能還原。既瘦身又不失可追溯性。

教學重點:四個名詞聽起來炫,但骨子裡就兩招——「合併動作以減少往返」(①)與「按需取用、只帶精華以縮小每輪上下文」(②③④)。任何 Agent 想省 token,都繞不開這兩個方向。

2. 狀態管理變複雜

因為引入了行動融合、線上壓實、觀察打包、證據歸約這些機制,系統要多管很多事:

  • 狀態管理:壓實與打包後,「模型看到的」和「系統實際保存的」不一致,要小心對齊。
  • 快取改寫:上下文被線上壓實會改動,原本的 prompt 快取容易失效或需要重算。
  • 失敗回退:動作被融合、證據被歸約後,一旦某步失敗,要能精準還原、回退到可用狀態——這條路更難走。
本質:SLPI 是把「模型端的成本」換成「系統端的工程複雜度」。省下的錢是真的,但你得有能力維護這套更複雜的運行時,否則省下的會被除錯與故障吃回去。

⑥ 什麼時候該用 / 不該用

適合不適合
任務型態長時間、多工具調用的長軌跡任務(往返多,省得多)短任務(往返本來就少,省不了多少,還多擔複雜度)
品質要求能接受約 6% 得分損失、以預算為重強一致性要求、或不能接受掉分的專案
目標在有效控制預算的同時維持「基本」效能追求每一分、要頂尖正確率
一句話決策:任務越長、工具調用越密、越吃預算,SLPI 越划算;任務越短、越要求極致正確,越不該用。先問自己「這 6% 掉分我吞得下嗎?」再決定。

⑦ 帶走的觀念 · 關聯 · 來源

六個帶得走的觀念

  1. Coding Agent 貴在往返多 × 每次重送一大包,不是單次貴。
  2. 省 token 有兩條路:合併動作減往返、按需取用縮上下文。SLPI 兩條都走。
  3. 四機制:Action Fusion(砍往返)、Online Context Compact、Observation Pack、Evidence Preserving Reducer(縮上下文)。
  4. 它不換模型、不改原始碼,只接管運行時——所以可加裝、可移除。
  5. 「令牌 ↓ ~49%」≠「省一半錢」,成本只降約 33%(計費權重不同)。
  6. 代價是約 6% 得分 + 系統複雜度;長任務划算,短任務/強一致性別用。

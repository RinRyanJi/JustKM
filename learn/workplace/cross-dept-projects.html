🧭 跨部門專案怎麼不散掉:決策權、利害關係人與依賴管理

姊妹頁「跨部門溝通」解決人的對立;這頁解決結構的失控——當一個專案橫跨好幾個部門,誰決策、誰負責、依賴怎麼管、卡住了往哪升級。整理常用的實證框架(RACI、Bain RAPID、Mendelow 利害關係人矩陣)並落地成可抄的做法。

⓪ 一句話總結

跨部門專案散掉,九成不是因為「人不好」,而是因為「結構沒定義」——沒人是唯一負責人、決策權沒寫清楚、部門間的依賴沒人管、卡住不知道往哪升級。溝通技巧(姊妹頁)能降低摩擦,但摩擦的根源常是這些結構空白。

解法是四件可落地的事:(1) 用一份專案章程把目標/範圍/贊助者/成功指標/決策權釘死、指定單一負責人;(2) 用 RACI / RAPID 把「誰做、誰批、誰決定」寫成表;(3) 用利害關係人矩陣把力氣花在對的人;(4) 把團隊間的依賴與介面當成合約來管、並定好節奏與升級路徑。

一句話抓重點:跨部門專案的本質是「權責的接縫工程」。接縫沒定義好,再多的善意溝通都會在灰色地帶耗損;把接縫寫成契約,人就不必天天靠交情硬撐。

① 為什麼跨部門專案特別容易散

單一部門的專案,老闆只有一個、優先序清楚。跨部門一來,結構就出現幾道天生的裂縫:

← 左右滑動看完整圖 →
▲ 成員被兩條線拉扯:垂直的部門主管(掌考績)vs 水平的專案負責人(掌交付、卻沒考績權)。沒有贊助者定優先序時,成員理性上會先做「打考績的那條線」。
  • 雙重匯報(矩陣組織):成員的考績在部門主管手上,專案負責人卻要他交付——優先序一衝突,專案就排後面。
  • 沒有唯一負責人:「大家一起負責」= 沒人負責。出事時互指,決策時沒人拍板。
  • 局部最佳化:每個部門都在優化自己的 KPI(業務要快、法務要穩、研發要少改需求),缺少共同的成功指標就會各拉各的。
  • 決策權模糊:「這要誰同意?」沒答案時,決策卡在無限的來回會議。
  • 康威定律(Conway's Law):系統/流程的樣子會長得像組織的溝通結構——部門之間溝通不良,交付出來的東西接縫也會裂。

② 專案章程:把模糊變契約

開工前先花半天寫一份專案章程(Project Charter),把所有人「以為有共識、其實沒有」的東西攤開寫死。它是後面所有爭議的仲裁依據:

章程欄位要回答的問題(寫具體、可驗收)
目標與成功指標做完長什麼樣?用一個共同的數字衡量成功(不是各部門各自的 KPI)。
範圍 / 不做什麼明確寫「不在範圍內」的項目——防止範圍潛變(scope creep)。
贊助者(Sponsor)誰有權定優先序、解跨部門僵局、要資源?通常是各部門共同的上級。
單一負責人指定一個人對交付結果負全責(Amazon 的「single-threaded owner」、Apple 的「DRI, Directly Responsible Individual」)。
決策權哪些決定誰能拍板?(用 ③ 的 RACI / RAPID 寫成表)
里程碑與依賴關鍵時間點,以及跨部門的交付依賴(見 ⑤)。
最關鍵的兩格:單一負責人 + 共同成功指標。前者解決「沒人負責」,後者解決「局部最佳化」。這兩格定好,超過一半的跨部門專案問題會自動消失。

③ 決策權寫清楚:RACI vs RAPID

跨部門最耗的不是做事,是「這件事到底誰說了算」。兩個常用框架把它寫成表:

RACI:每個任務,四種角色

角色意思鐵律
Responsible 負責執行實際動手做的人可多人
Accountable 當責對成敗負最終責任、有拍板權每個任務只能有一個 A
Consulted 諮詢做決定前要徵詢(雙向)控制人數,別讓人人都是 C
Informed 知會結果通知(單向)只需知道,不參與

RAPID(Bain):複雜決策,五種角色

當一個決定牽涉很多部門、RACI 的「一個 A」不夠細時,用 Bain 的 RAPID 把決策拆成五個角色(實際順序是 Recommend → Input → Agree → Decide → Perform):

← 左右滑動看完整圖 →
▲ RAPID 最大的價值:把「Input(有意見但不能否決)」和「Agree(能否決)」分開。很多跨部門癱瘓,是因為把「有意見的人」都當成「能否決的人」。
怎麼選:日常任務分工用 RACI 就夠;遇到重大、跨多部門、容易吵不完的決策(要不要改架構、預算歸誰、上線與否),用 RAPID 把決策權切細。核心都一樣:拍板權收斂到一個人,其他人分清楚是「諮詢/意見」還是「否決」。

④ 利害關係人地圖:力氣花在對的人

跨部門專案的利害關係人一大票,不可能對每個人都同等投入。用 Mendelow 權力—利益矩陣(Power-Interest Grid)把他們分四類,對症下藥:

← 左右滑動看完整圖 →
▲ 對「高權力高利益」緊密管理(頻繁對齊)、對「高權力低利益」維持滿意(定期簡報、別讓他們意外)、對「低權力高利益」保持告知(常是實際使用者)、對「低權力低利益」監看即可。
接回 RACI:把矩陣的分類對回 RACI——高權力高利益通常是 A / C,低權力高利益多是 C / I,高權力低利益至少要 I(別讓有權的人被意外)。清單要動態更新:專案階段變,人的權力/利益也會變。

⑤ 依賴與介面:把團隊之間當「合約」管

跨部門專案最常爆的地方,是團隊之間的交接點:「我以為你會給我 X」「那不是我們負責的」。解法是把依賴與介面明確化、當合約管:

  • 依賴地圖:把「A 團隊要等 B 團隊先交付什麼」畫出來,標上日期與負責人。看不見的依賴,就是未爆彈。
  • 介面契約 / 內部 SLA:團隊之間約定「我提供什麼、什麼格式、什麼時候、品質標準是什麼」。像 API 合約一樣,把交接點寫死,減少灰色地帶。
  • 康威定律的逆用:既然系統會長得像組織溝通結構,那就刻意設計溝通結構——讓負責相鄰模組的團隊有固定溝通管道(例如共同的介面同步會)。
  • 規模化時的協調機制:團隊多到一定程度,用制度化的跨團隊同步——Scrum of Scrums(各團隊代表定期對齊依賴)、或 SAFe 的 PI Planning(大型計畫定期把所有團隊拉在一起排依賴)。
最容易被略過的一步:依賴要雙方確認,不能只寫在你的計畫裡。B 團隊沒點頭的「依賴」,只是你的一廂情願。每個跨團隊依賴都該有對方的一個具名負責人 + 承諾日期。

⑥ 節奏與升級路徑:別等爆了才知道

機制頻率目的
啟動會(Kickoff)一次對齊章程、角色、依賴——讓所有部門在同一頁。
工作同步每週(或每日站會)進度、卡點、依賴變化;短、聚焦在「誰卡住誰」。
指導委員會(Steering)雙週 / 每月贊助者 + 部門主管看大局、定優先序、解重大僵局。
共享儀表板持續單一事實來源:進度、風險、依賴狀態人人可見,取代「用轉述打聽」。

升級路徑(Escalation Path)要事先講好

卡住時最怕「不知道找誰、也不敢往上報」。事先定義三級升級:① 團隊間先自己解(有時限,例如 2 天)→ ② 專案負責人協調 → ③ 贊助者/指導委員會裁決。把「什麼情況、多久沒解、往哪升」寫進章程,升級就不再是「打小報告」,而是正常的流程。

心法:好的跨部門專案把壞消息的傳遞速度做快。卡點越早浮上檯面越好——共享儀表板 + 明確升級路徑,就是讓壞消息不必靠勇氣、而是靠制度往上走。

⑧ 值得偷師的思路 / 來源

  1. 跨部門專案是「權責的接縫工程」。散掉多半因為結構空白,不是人不好;先補結構,再談溝通。
  2. 拍板權收斂到一個人。單一負責人(DRI / single-threaded owner)+ 每任務一個 A——「大家一起負責」等於沒人負責。
  3. 把「有意見」和「能否決」分開。RAPID 的 Input vs Agree 是終結會議癱瘓的關鍵區分。
  4. 一個共同成功指標,壓過各部門的局部 KPI。沒有共同數字,局部最佳化必然發生。
  5. 依賴與介面當合約管,而且雙方確認。看不見、沒對方點頭的依賴,都是未爆彈。
  6. 把壞消息傳遞做快。共享儀表板 + 事先講好的升級路徑,讓卡點靠制度浮出、不靠勇氣。

Part A · packages/ai 的統一 provider 抽象

① 問題與三層模型

packages/ai(@earendil-works/pi-ai)是一個「統一 LLM API」工具包:自動模型探索、provider 設定、token/成本追蹤,以及對話 context 的持久化與 mid-session 換模型。它只收支援 tool calling 的模型(agentic 必需)。

抽象拆成三層:

層是什麼例
Provider「誰家」——一個廠商/端點(含憑證)anthropic、openai、google、prime-inference… 共 20+ 家
API「用哪種線協定」——一種 wire 協定的實作anthropic-messages、openai-completions、openai-responses、google-generative-ai、bedrock-converse-stream、mistral-conversations
Model某 provider 上的一個具體模型(綁定一種 API)anthropic/claude-sonnet-4、openai/gpt-5-mini

KnownProvider 型別聯集列出 20+ 家:amazon-bedrock、anthropic、google、google-vertex、openai、azure-openai-responses、openai-codex、prime-inference、deepseek、github-copilot、xai、groq、cerebras、openrouter、vercel-ai-gateway、zai、mistral、minimax、moonshotai…。多家 provider 可共用同一個 API 實作(例如一堆 OpenAI 相容端點都走 openai-completions)。

關鍵洞見:抽象的接縫在「API」——真正要寫程式適配的是「wire 協定」(anthropic-messages / openai-completions…),而 provider 多半只是「換 baseUrl + 憑證 + 模型清單」。所以支援一個新的 OpenAI 相容 provider,常常不用寫新 API 實作。

② 統一事件流(AssistantMessageEvent)

不論底層是哪家,每個 provider 的 stream*() 都回傳同一種 AssistantMessageEventStream,吐出標準化事件——這是「統一」的核心:

type AssistantMessageEvent =
  | { type: "start"; partial }
  | { type: "text_start" | "text_delta" | "text_end"; contentIndex; delta?; ... }
  | { type: "thinking_start" | "thinking_delta" | "thinking_end"; ... }
  | { type: "toolcall_start" | "toolcall_delta" | "toolcall_end"; toolCall? }
  | { type: "done";  reason: "stop"|"length"|"toolUse"; message }
  | { type: "error"; reason: "aborted"|"error"; error };

約定:先送 start,中間是 partial 增量(text / thinking / toolcall 各有 start-delta-end),最後以 done(帶最終 AssistantMessage)或 error 收尾。每個 provider 檔案的職責就是把「該家的 SSE/串流」翻譯成這組事件。

StopReason 也統一成 stop / length / toolUse / error / aborted 五種。上層(agent/coding-agent)因此完全不需要知道底層是誰。

③ 統一介面 vs 各家細節

兩層 API:streamSimple / completeSimple vs stream / complete

  • streamSimple(model, context, SimpleStreamOptions):跨家統一選項(如 thinking 開關、thinking level),不管哪家都一樣寫。
  • stream(model, context, <Provider>Options):要用某家專屬選項時走這條,吃 provider-specific options 介面。

Model 介面(統一描述一個模型)

interface Model {
  id; name; api; provider; baseUrl;
  reasoning: boolean;
  thinkingLevelMap?;              // pi 的 thinking 等級 → 各家對應值(null=不支援)
  input: ("text"|"image")[];
  cost: { input; output; cacheRead; cacheWrite };  // $/百萬 token
  contextWindow; maxTokens;
  featured?;                      // 旗艦,排在 picker 前面
  compat?;                        // OpenAI 相容端點的相容性覆寫(否則從 baseUrl 自動偵測)
}

thinkingLevelMap 把 pi 的抽象「思考等級」映射到各家實際參數;compat(如 OpenAICompletionsCompat)處理各家 OpenAI 相容端點的差異(支不支援 store、developer role、reasoning_effort、stream_options.include_usage…),不用時從 URL 自動偵測。

④ 加一個 provider 要動哪些接縫(看見抽象邊界)

官方「新增 provider」清單最能揭示抽象的接縫:

  1. types.ts:在 Api 聯集加 API id、建一個 extends StreamOptions 的 options 介面、加進 ApiOptionsMap、在 KnownProvider 加名字。
  2. providers/<name>.ts:export stream<Provider>()(回 AssistantMessageEventStream)、streamSimple<Provider>()、options 介面、訊息/工具轉換函式、把回應解析成標準事件(text/tool_call/thinking/usage/stop)。
  3. register-builtins.ts:用 lazy loader 註冊(不靜態 import 實作);env-api-keys.ts 加憑證偵測。
  4. generate-models.ts:抓/解析該家模型清單,映射到標準 Model 介面(不可手改 models.generated.ts)。
  5. coding-agent:model-resolver.ts 加預設模型、provider-display-names.ts 加登入顯示名、args.ts 加 env 文件。
讀法:1–2 是「協定適配」的核心(新 API 才需要);3–5 多是「登錄與 UI 接線」。若新 provider 用既有 API(如又一個 OpenAI 相容端點),第 2 步幾乎可重用 openai-completions,只補 compat 與模型清單。

⑤ 跨 provider 交接(mid-session 換模型)

同一段對話裡可以中途換家(Claude → GPT-5 → Gemini),context 自動轉換相容:

訊息類型轉換規則
User / toolResult原樣傳遞
同 provider/API 的 assistant原樣保留
不同 provider 的 assistant其 thinking block 轉成 <thinking> 標記文字
tool call / 一般 text原樣保留

於是可以「快模型先答 → 換強模型做複雜推理 → 用專用模型做特定任務」,甚至在某家 provider 出狀況時換家續跑而不斷對話。測試則有 registerFauxProvider() 提供記憶體內的假 provider(可設 tokens/sec、預設回應),不碰真 API。

Part B · Session JSONL 格式

⑥ 檔案格式與樹狀結構

Session 存成 JSONL:每行一個帶 type 欄位的 JSON 物件。entries 透過 id/parentId 形成樹——可就地分支而不用開新檔。

# 位置(現行為扁平目錄)
~/.prime/agent/sessions/<session-id>.jsonl

header 記錄工作目錄。版本演進:

版本結構
v1線性 entry 序列(legacy,載入時自動遷移)
v2樹狀,以 id/parentId 連結
v3把 hookMessage role 更名為 custom(extensions 統一)

載入舊 session 會自動遷移到 v3。刪除 = 刪 .jsonl(或在 /resume 選中按 Ctrl+D,可用時走 trash CLI 避免永久刪除)。/tree 導覽與 compaction/branch summary 的 entry 也存在同一棵樹裡(見深挖三題 ③)。

⑦ 訊息型別

Session entry 承載 AgentMessage。內容是型別化 content block 陣列:

TextContent    { type:"text"; text }
ImageContent   { type:"image"; data(base64); mimeType }
ThinkingContent{ type:"thinking"; thinking }
ToolCall       { type:"toolCall"; id; name; arguments }

基礎訊息(來自 pi-ai)

role重點欄位
usercontent(text/image)、timestamp
assistantcontent(text/thinking/toolCall)、api / provider / model、usage、stopReason、errorMessage?
toolResulttoolCallId、toolName、content、isError、details?

每則 assistant 都記下是哪個 api/provider/model 產生的——這正是跨 provider 交接(⑤)判斷「同家/異家」的依據。Usage 帶 input/output/cacheRead/cacheWrite/totalTokens 與對應 cost(逐項 + total)。

擴充訊息(來自 coding-agent)

role作用
bashExecutioncommand/output/exitCode/cancelled/truncated;excludeFromContext(!! 前綴指令)
customextension 訊息:customType、display(要不要顯示)、details?
branchSummary分支摘要:summary、fromId
compactionSummary壓縮摘要(對應 CompactionEntry)
怎麼解析一個 session:逐行讀 JSON → 依 type/role 分派 → 用 id/parentId 重建樹 → 從 root 沿到某 leaf 就是一條對話路徑;遇到 compaction entry 就用「摘要 + firstKeptEntryId 起的訊息」重建 LLM 看到的 context。

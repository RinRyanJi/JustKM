🏭 拆解 Matt Pocock 的 AI 程式開發流程

從需求到 Code Review 的一條生產線：grill → spec → tickets → implement(TDD) → review，把隨機的 AI 馴服成可控的工程師

AI 輔助開發 TDD · 垂直切片 雙軸 Code Review 含流程圖 + 手動版
📑 目錄

⓪ 一句話總結

Matt Pocock 把「用 AI 寫程式」從一次性的許願（「幫我做一個登入功能」）改造成一條有紀律的生產線：先讓 AI 反問你把需求釘死並建立共享語言(grill)，寫成規格(spec)、拆成一張張能獨立驗證的垂直切票(tickets)，再在約定好的測試接縫上做 TDD(implement)，最後用「標準 × 規格」雙軸審查(code-review)才提交。每一站都有專屬 Skill 把關。

💡 為什麼值得學：核心不是「更聰明的模型」，而是「更好的環境與溝通」。這套流程對治 AI 的四大病：誤解意圖、話太多、程式跑不動、架構腐爛。即使你不用 Claude Code，把這套「小步 + 先釐清 + 先測試 + 雙軸審查」的節奏搬進任何 AI 對話，產出品質就會立刻不同。

① 核心哲學：小步，而回饋速度就是你的速度上限

整套系統只有一句總綱：

“Always take small, deliberate steps. The rate of feedback is your speed limit.”
永遠踏出小而審慎的一步——你能拿到回饋的速度，就是你能前進的速度上限。

它為 AI 開發的四種典型崩壞，各安排了對應的關卡：

AI 的病症狀這條生產線怎麼治
誤解意圖做出你根本沒要的東西grill 反問到共識、spec 白紙黑字
話太多 / 冗長回一堆廢話、改一堆無關的共享語言(CONTEXT.md)、垂直薄切片
程式跑不動看起來對、跑起來錯TDD 紅綠循環、頻繁 typecheck
架構腐爛越改越亂、技術債滾雪球深模組設計、雙軸 code-review

② 兩種 Skill 怎麼組合

所有 Skill 沿一條軸線分成兩類，理解這點才看得懂整套怎麼運作：

類型誰來啟動裝著什麼例子
🔵 使用者呼叫
(user-invoked)		你打 /指令 才啟動流程編排（把一件事從頭帶到尾）grill-with-docs、to-spec、implement
🟣 模型呼叫
(model-invoked)		AI 判斷時機自動援引（你也能手動叫）可複用的紀律（某件事的正確做法）tdd、code-review、diagnosing-bugs
📌 組合規則：使用者呼叫的 Skill 可以援引模型呼叫的 Skill（例如 implement 內部叫 tdd 和 code-review），但不會一個使用者指令再去串另一個使用者指令。這讓「大流程」與「小紀律」清楚分層、可自由拼裝。

③ 生產線總覽

下面逐站拆解。每張卡片標明它是🔵 使用者呼叫還是🟣 模型呼叫。

④ grill-with-docs — 釐清需求，同時長出共識文件

grill-with-docsUser 使用者呼叫

“A relentless interview to sharpen a plan or design, which also creates docs (ADRs and glossary) as we go.” 一邊不留情地追問把設計磨利，一邊即時產出文件（架構決策紀錄 ADR + 詞彙表）。

底層引擎：grilling（一次只問一題）

它背後是可複用的 grilling 訪談迴路，紀律很鮮明：

  • 一次只問一個問題，問完等你回答再往下——避免認知過載。
  • 沿著決策樹一根一根分支走，逐一解開決策之間的相依。
  • 事實類自己查（翻檔案、用工具），決策類一定交給你拍板，而且會附上「建議答案」引導你思考。
  • 達成共識前絕不動手。

產物：CONTEXT.md（純詞彙表）+ ADR

grill-with-docs 把 grilling 和 domain-modeling 疊在一起，邊問邊把共識寫成實體文件：

  • CONTEXT.md：一份純詞彙表，「完全不含實作細節」。它不是規格、也不是草稿本，只定義專案的共享語言。
  • ADR（架構決策紀錄）：只在「難以反轉、對未來讀者意外、且牽涉真實取捨」時才提議建立。
💡 為什麼共享語言這麼關鍵：一份好的 CONTEXT.md 能降低冗長、統一命名、幫助導覽、還省 token。當人與 AI 對同一個詞的理解一致，往後每一次溝通都更短、更準。這是整套系統「省話」的祕密武器。

domain-modeling 磨詞彙的四招

  1. 詞彙稽核：你用了和 CONTEXT.md 衝突的詞，當場標記澄清。
  2. 精準化提議：把模糊詞換成正典詞——例如把「帳號」拆成 Customer 與 User。
  3. 情境壓力測試：捏造具體邊界案例，逼你講清概念之間怎麼關聯。
  4. 對照程式碼：找出「你嘴上說的」和「程式實際做的」之間的矛盾。

⑤ to-spec / to-tickets — 把共識規格化、切成可執行的票

to-specUser 使用者呼叫

把「已經討論過」的內容直接綜合成一份規格並發到 issue tracker——不需要再訪談一次。

它的步驟

  1. 探勘程式碼：了解現況，套用專案詞彙、尊重相關區域的 ADR。
  2. 定義測試接縫(seam)：優先用既有接縫、選最高層級；非必要不新增。理想是整份規格只落在一個接縫上。
  3. 寫規格並發布，貼上 ready-for-agent 標籤。

規格包含

問題陳述、解法、詳盡的編號 User Stories、實作決策（模組/介面/schema 變更）、測試決策、Out of Scope、補充註記。

⚠️ 刻意避開的陷阱：規格裡少寫會過期的實作細節（例如寫死的檔案路徑）——用詞彙與決策描述，而非易腐的細節。若有 prototype 能比文字更好地表達決策，就用 prototype。
to-ticketsUser 使用者呼叫

把計畫/規格拆成一張張會宣告自己相依關係的工作票。

兩個核心觀念

  • Tracer-bullet 票 = 垂直切片，不是水平分層。每張票穿透 schema → API → UI → 測試，自己就能 demo；大小能塞進一個 context window。✗ 不要「只做 UI」或「只做資料庫」這種水平票。
  • Blocking edges（阻擋邊）：宣告哪張票要先完成，形成相依圖。你永遠在「前緣」（相依已解、可立即動工的票）上工作，還能平行推進。
大型重構的手法：expand–contract（擴張—收縮）——先加上新形態、分批把呼叫端遷移過去、最後刪掉舊形態。批次大小要顧及「爆炸半徑」，全程保持 CI 綠燈。

⑥ implement + tdd — 在接縫上做測試驅動開發

implementUser 使用者呼叫

把規格/票變成能動的程式，全程用 TDD 驅動、頻繁驗證、以 code-review 收尾。

它的流程

解析需求 ─► 在預先約定的接縫(seam)上寫測試(先紅) ─► 寫最少的碼讓它綠 │ ├─ 頻繁 typecheck、常跑單一測試檔及早抓錯 │ └─► 全部完成後跑整套測試 ─► /code-review ─► commit
tddModel 模型呼叫

紅 → 綠迴圈，產出「值得留下的測試」。

TDD 的鐵律

  • 先寫測試再寫實作；不加投機性的多餘功能。
  • 垂直切片：一次一個測試、一個實作，別把所有測試先寫完（水平切片）。
  • 只在公開接縫(public seam)上測，絕不測內部細節、不 mock 內部。
  • 重構屬於 code-review，不屬於 implement 迴圈。
  • 每個測試是「曳光彈」——回應前一輪揭露的東西。
🚫 好測試 vs 壞測試：好的測試「讀起來像規格」且「撐得過重構」，因為它驗的是使用者可見的行為、透過公開邊界，而非實作。要避開三種爛味道：同義反覆斷言（期望值照抄程式邏輯）、實作耦合（mock 內部）、水平切片。期望值必須來自獨立的真相來源——已知正確的字面值、手算範例、或規格本身。

⑦ code-review — 標準 × 規格的雙軸審查

code-reviewModel 模型呼叫

審查 HEAD 與某個固定基準點之間的差異，沿兩條互相獨立的軸檢查。

兩條軸（刻意分開）

軸在問什麼依據
Standards 標準寫得好不好？專案文件化的規範 + 一組程式碼壞味道基準（Fowler《重構》第 3 章：神祕命名、重複、依戀情結、資料泥團、基本型別偏執、發散式變化、霰彈式修改…）。專案自有規範優先於基準。
Spec 規格有沒有忠實實現需求？原始 issue / PRD / 規格。檢查缺漏或半成品功能、範圍蔓延(scope creep)、實作錯誤。

審查流程

  1. 釘住基準點：確認 user 指定的 SHA/branch/tag 可解析，git diff <基準>...HEAD 非空。
  2. 找出規格：先翻 commit 訊息找 issue 參照，再看 user 給的路徑、docs/、specs/、.scratch/；找不到就問。
  3. 蒐集標準來源：CODING_STANDARDS.md、CONTRIBUTING.md 等 + 壞味道基準。
  4. 平行子代理：Standards 與 Spec 兩份審查同時各派一個子代理，各自 <400 字，區分「違規」與「判斷題」。
  5. 分開彙整：兩份報告各自呈現、不混排，各給摘要與最嚴重問題。
📌 為什麼兩軸要分開：一份改動可能一軸過、一軸不過。分開才不會讓「程式寫得漂亮」掩蓋「根本沒做到規格要的事」，反之亦然。

⑧ 支撐紀律（隨時援引的模型呼叫 Skill）

🐛 diagnosing-bugs — 一條反直覺的除錯鐵律

鐵律：不准先猜。在建立起「能穩定重現 bug 的緊迫回饋迴路」之前，禁止讀程式碼去建立理論——「直接跳到假設，正是這個 Skill 要防的失敗」。沒有可重現的指令，就不准進入下一階段。

六階段迴圈：

  1. 建回饋迴路（最關鍵）：做一個能穩定變紅的訊號來重現 bug——失敗測試、curl 腳本、最小 harness、bisect…要確定性、快、可無人值守。
  2. 重現 + 最小化：確認和使用者描述相符，再把非必要元素一一拿掉，直到每一塊都是關鍵。
  3. 提假設：給 3–5 個排序過、可證偽的預測，先給使用者看（他常一眼就幫你重排）。
  4. 下探針：一次只改一個變數，優先用除錯器而非 log，所有除錯輸出打標籤好清理。
  5. 修 + 測：在正確的接縫寫回歸測試，驗證測試與原情境都過。
  6. 清理 + 事後檢討：移除探針，記錄「什麼架構改動能根絕此類 bug」。

🧱 codebase-design — 深模組、小介面

設計深模組：把大量行為藏在極小的介面後。呼叫者用最少的學習成本換到最多的能力。反例是「大介面藏不了多少邏輯」的淺模組——只會製造維護負擔。

  • 依賴注入（接收依賴而非自己建，方便測試替換）、純函式優先（回傳結果而非改狀態）、介面表面積最小化。
  • 「一個 adapter 是假設，兩個才是真實」——真的有多種實作時才引入變化點，別為想像中的彈性過度設計。
  • 刪除測試：想像把這個模組刪掉。若複雜度隨之消失 → 它只是穿堂（不及格）；若複雜度散落到眾多呼叫端 → 它掙到了存在的價值。

🔬 prototype — 用拋棄式原型回答設計問題

當「這個狀態機行得通嗎？」→ 做一個互動式終端小程式測邊界；「這該長怎樣？」→ 生多個可用 URL 參數切換的 UI 版本。刻意拋棄式：命名標明是 prototype、不寫測試不加抽象、一鍵可跑、完整顯示狀態變化；驗證後提交到拋棄式分支並記下結論，只把驗證過的邏輯併回主線。

🗺️ wayfinder — 超大型工程的跨 session 作戰地圖

面對「大到裝不下一個 session」的工程，它只產出決策、不產出交付物：在 issue tracker 上建一張 wayfinder:map 索引，把大問題拆成一張張調查/決策票（類型：research / prototype / grilling / task）。地圖刻意留白——還太模糊、不足以開票的部分放在「尚未指定(fog of war)」區，隨前緣推進再逐步具體化。一個 session 只解一張票（research 除外）。

其餘（README 列出，同屬工具箱）

  • triage：把四面八方的許願強制排成狀態機流水線，還能教 AI 幫你擋掉不合理需求。
  • resolving-merge-conflicts：逐 hunk、依「意圖」解合併衝突。
  • improve-codebase-architecture：掃描「可加深」的機會，產出視覺化 HTML 報告。
  • research：對照第一手來源調查問題，產出有引用的 Markdown。
  • handoff：把過長對話壓縮成交接文件，讓新視窗/子代理無縫接手（對治「長對話降智」）。

⑨ 可偷走的 8 條心法

把所有 Skill 疊起來看，會浮現同一組原則——就算不用這套工具，也值得搬進你自己的流程：

小步，回饋速度是速度上限

每一步都小到能快速驗證。拿不到回饋的地方，就是你該慢下來的地方。

先建共享語言，再談功能

用一份純詞彙表(CONTEXT.md)把名詞釘死。命名一致 → 溝通更短、更準、更省 token。

決策屬於人類

AI 一次問一題、附建議答案、事實自己查，但拍板權在你，達成共識前不動手。

垂直切片，不做水平分層

每個工作單位都要能自己 demo（穿透 schema→UI→測試），並保持 CI 綠燈。

測試綁行為、不綁實作

只在公開接縫上測，期望值來自獨立真相來源，讓測試「讀起來像規格、撐得過重構」。

審查分兩軸：標準 × 規格

「寫得好」與「做對事」是兩回事，分開評，別讓一軸掩蓋另一軸。

除錯先重現，別急著猜

沒有穩定可重現的回饋迴路之前，不准提假設。緊迫的迴路是除錯的超能力。

設計深模組，每天投資系統

大能力藏在小介面後；「一個 adapter 是假設，兩個才是真實」。對抗架構熵是每日功課。

⑩ 怎麼實際套用（含「手動版」）

A · 如果你用 Claude Code

安裝 Matt 的 skills plugin（見 ⑪），或把對應 SKILL.md 複製進專案客製。典型一次功能開發：/grill-with-docs → /to-spec 或 /to-tickets → /implement →（內部自動 /code-review）→ commit。

B · 手動版：任何聊天型 AI 都能照做

  1. 釐清：「先別寫任何程式。一次問我一個問題，把這個功能的需求、邊界、名詞定義釘清楚，並幫我維護一份詞彙表。達成共識前不要動工。」
  2. 規格：叫它把共識整理成規格——問題、解法、編號 user stories、Out of Scope、測試要測哪裡。
  3. 切票：「拆成幾張垂直切片，每張都要能自己 demo、標明誰擋著誰，先做沒有相依的。」
  4. TDD 開發：一張票一次。「先寫一個會失敗的測試（測行為、不測內部），再寫最少的碼讓它過，然後才繼續下一個。」頻繁 typecheck / 跑測試。
  5. 雙軸審查：「分兩份審這段 diff：一份只看程式碼標準與壞味道，另一份只看有沒有做到規格（缺漏/範圍蔓延/實作錯）。兩份分開給。」
  6. 卡關時：Bug → 先要它做出可重現的最小案例再談原因；長對話變笨 → 要它產出一份交接文件，開新視窗貼上去續作。
💡 一個立刻能用的切換：下次要 AI 做功能，先禁用「幫我做 X」，改成「先別動手，問我問題直到你完全懂」+「先寫測試」。光這兩招，就能砍掉大半「做出你沒要的東西」與「看似對其實錯」。

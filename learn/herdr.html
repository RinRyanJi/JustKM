🐑 Herdr：AI coding agent 「住」的終端 runtime

官方定位 the runtime your coding agents live on · tmux 式多工器 + 內建「agent 狀態感知」

Rust · Ratatui Terminal Multiplexer Agent-aware Apache 2.0
📑 目錄
⓪ 一句話總結 ① 它解決什麼痛點 ② 心智模型：tmux + 狀態感知 ③ 核心：agent 狀態側欄 ④ 安裝與快速開始 ⑤ CLI 與 Socket API ⑥ 支援哪些 agent ⑦ 遠端與持久化 ⑧ vs tmux / Zellij ⑨ 適合誰、什麼場景 ⑩ 延伸與來源

⓪ 一句話總結

Herdr 是一個「懂 AI agent」的終端多工器——它沿用 tmux 的 session / tab / pane（窗格）+ 持久化模型，但額外知道每個窗格裡跑的是不是 coding agent、現在是工作中(working)、閒置(idle) 還是卡住等你(blocked)，並在側欄一眼呈現。你可以在同一個終端同時養 Claude Code、Codex、Cursor 等十多個 agent，斷線也不會死。

📌 名字由來：Herd = 放牧、牧群。當你同時「養」一群 AI coding agent，Herdr 就是那個幫你牧群、盯著誰在忙誰卡住的牧羊人。單一 Rust 二進位檔、無 Electron，跑在你現有的終端裡（WezTerm / iTerm2 / Kitty…），不是取代終端。

① 它解決什麼痛點

當「一次跑多個 AI coding agent」變成日常，傳統 tmux／多開終端就露出三個痛：

  • 不知道誰在等你：開了五個 agent，哪個跑完了、哪個卡在「要不要繼續 (y/n)」等你回答？得一個一個切過去看。
  • 會話容易死：機器重開、網路斷、終端關掉 → agent 半路陣亡，進度沒了，得從頭再來。
  • agent 之間無法協作：想讓一個 agent 開新窗格、跑指令、讀另一個窗格的輸出 → 一般終端沒有給程式化的介面。

Herdr 的答案：把「終端保活」＋「agent 狀態感知」＋「給 agent 用的程式化 API」三件事合在一個工具裡。

一句話差異：tmux 讓終端活著；Herdr 也讓它活著，但還知道哪個終端是 agent、它現在什麼狀態、以及怎麼「等」它。

② 心智模型：tmux 骨架 + 狀態感知層

如果你用過 tmux／Zellij，觀念幾乎能直接搬過來：

層級是什麼Herdr 的加值
Session一組工作的容器，斷線後仍存活、可重新接上從任何終端 re-attach，agent 不中斷
Tab / Window一個 session 裡的分頁—
Pane（窗格）實際跑指令／agent 的分割區Herdr 會辨識窗格裡的 process 是不是 agent，並標出狀態
側欄 Sidebar（tmux 沒有）列出所有 agent 與其 working / idle / blocked 狀態

操作是雙輸入：鍵盤走 tmux 風格的快捷鍵，同時也支援滑鼠點選、切換、調整窗格。技術上以 Rust + Ratatui（終端 UI 函式庫）打造。

③ 核心賣點：agent 狀態一眼看穿

這是 Herdr 跟一般多工器最大的不同。每個 agent 窗格會被標成三種狀態之一：

狀態意義你該做什麼
workingagent 正在跑（思考／改檔／跑測試）放著，去看別的
blocked卡住在等你（要確認、要授權、要輸入）優先處理——這就是瓶頸
idle做完了或閒置驗收成果、派下一個任務
為什麼這很關鍵：同時養多個 agent 時，真正的瓶頸不是「算力」，而是「你不知道哪個在等你」。把 blocked 的 agent 標出來，等於把你的注意力導到唯一需要人介入的地方——這正是多 agent 工作流能不能規模化的關鍵。

④ 安裝與快速開始

單一二進位檔，安裝很輕：

# 官方安裝腳本
curl -fsSL https://herdr.dev/install.sh | sh

# 或用 Homebrew
brew install herdr

# 啟動（在你現有的終端裡）
herdr

啟動後就進入 Herdr 的 TUI：開分頁、切窗格、在窗格裡跑你的 agent（例如直接 claude 或 codex），側欄就會開始顯示它們的狀態。

⑤ CLI 與 Socket API：給 agent 用的「手」

Herdr 不只給人操作，也提供程式化介面讓 agent 自己驅動終端。這是「agent-native」的核心：

  • 生成窗格：agent 可以自己開新 pane 去跑子任務（例如另起一個測試 runner）。
  • 送指令、讀輸出：以程式方式在窗格裡執行命令並讀回結果，不必靠人複製貼上。
  • agent 之間通訊：透過 CLI／Socket API 協調，讓「主 agent 指揮子 agent」這類多 agent 編排成為可能。
  • 等待與同步：因為 Herdr 知道每個窗格的狀態，就能「等某個 agent 做完再繼續」。
觀念連結：這其實是把「多 agent 編排（orchestration）」下沉到終端層——你不需要另建一套排程框架，終端本身就變成 agent 的執行與協調環境。

⑥ 支援哪些 agent

Herdr 對「agent」是工具中立的——只要在窗格裡跑，它就試著辨識與追蹤。公開資料提到可搭配的包含：

  • Claude Code、Codex、GitHub Copilot CLI、Cursor Agent
  • OpenCode、Grok，以及其他共 15+ 種 agent／CLI 工具

也就是說，你可以在同一個 Herdr session 裡混用不同家的 agent，各跑各的任務，用同一個側欄統一盯狀態。

⑦ 遠端與持久化

能力說明
持久化 session以背景服務常駐；機器重開／網路斷／終端關掉，agent 工作不中斷，可從任何終端重新接上（延續 tmux 的 detach/attach 精神）
遠端 --remote透過 SSH 連遠端主機跑 session，並把本機設定帶過去（forward local config），遠端也有一致的環境
外掛系統可擴充窗格與工作流，讓團隊把自家流程包成 plugin
典型用途：把長時間跑的 agent 丟到遠端伺服器的 Herdr session，關掉筆電、回家再從手機終端接上——agent 還在原地跑。

⑧ vs tmux / Zellij：差在哪

面向tmux / ZellijHerdr
窗格 / 分頁 / session有有（沿用同一套模型）
斷線保活 detach/attach有有
知道窗格裡是不是 agent無有
agent 狀態側欄 (working/blocked/idle)無有
給 agent 的程式化 CLI / Socket API弱內建
滑鼠 + 鍵盤雙輸入部分原生
技術C（tmux）／Rust（Zellij）Rust + Ratatui，單一二進位

簡言之：Herdr ≈ 「為 AI agent 世代重寫的 tmux」。骨架你熟悉，差別是它把「agent 現在什麼狀態、怎麼協調」變成一等公民。

⑨ 適合誰、什麼場景

  • 同時跑多個 coding agent 的人：一眼看出哪個 blocked，把注意力花在刀口上。
  • 做多 agent 編排 / 自動化：需要 agent 能自己開窗格、跑指令、互相協調的程式化介面。
  • 遠端 / 長任務工作流：agent 跑幾小時，要能斷線續跑、換裝置接回。
  • 已經是 tmux 重度使用者：學習成本低，快捷鍵觀念可沿用。
什麼時候不必用：只跑單一 agent、也不需要遠端保活時，直接在終端跑就好；Herdr 的價值在「多、久、要協調」這三種情境才會放大。

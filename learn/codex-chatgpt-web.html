🔌 拆解 codex-chatgpt-web

一個跑在 127.0.0.1 的本地 Responses API 橋接器：把你已登入的「網頁版 ChatGPT」包裝成 Codex 的一個模型，用 ChatGPT 方案額度跑 Codex，不吃 API/Codex 配額，介面與工作流不變。

本地 Responses 代理 Bun · Electron · Playwright MCP 反向工具調用 v5.0.7 MIT
這頁在講什麼？ 逐層拆解「怎麼讓 Codex 把外部網頁 ChatGPT 當一個模型用」—— 從模型清單如何被動手腳、請求怎麼分流、到 Full 模式下 ChatGPT 反過來調用你本機工具（MCP）的完整授權流程、 瀏覽器怎麼被自動化、以及上下文壓縮與安全設計。內容整理自 repo 原始碼（file:line 級）。

⓪ 一句話總結

它把自己偽裝成 OpenAI 官方 Responses API 的本地端點，Codex 把模型請求打過來，它負責分流：

  • 原生模型 → 原封不動轉發給官方後端（透明代理），一切照舊。
  • chatgpt-web/* 模型 → 改用 Playwright 驅動你登入的網頁 ChatGPT 回答，再把結果組回 Responses API 格式。

進階的 Full harness 模式再加一條反向通道：讓網頁 ChatGPT 透過 MCP + OpenAI tunnel 回呼你本機的 Codex 工具（讀寫檔案、跑指令），而且每個回合用一次性 token 嚴格授權。Codex 全程不知道背後其實是一個瀏覽器分頁。

① 它解決什麼問題

Codex（OpenAI 的 CLI/桌面編碼 agent）預設用 API/Codex 額度計費。但很多人手上有 ChatGPT 訂閱方案（Plus / Pro），那份額度是另外一套、獨立計算的訊息配額。

這個專案的動機：把 Codex 的模型後端偷偷換成「網頁版 ChatGPT」，於是：

  • 用 ChatGPT 方案的訊息配額跑 Codex 任務，不消耗你的 Work / Codex / API 配額。
  • 可用到只在網頁開放的模式（Instant / Think / Medium / High / Extra High，甚至 Pro）。
  • 介面、任務、圖片、串流全都留在 Codex 原生 harness 裡，體驗不變。
這是非官方的瀏覽器自動化，不是 OpenAI API。 repo 自己明列 non-goal：不繞過 ChatGPT 方案/workspace/用量/模型限制、不靠重試規避用量上限。ChatGPT 網頁改版可能讓 selector 失效 —— 遇到就讓該回合「明確失敗」，絕不偷換模型或假造成功。使用前請自行評估是否符合你帳號的服務條款。

④ 怎麼把「網頁 ChatGPT」變成一個 Codex 模型？

這是最核心的問題。答案分三步：接管路線 → 混進模型清單 → 按模型分流。

Step 1：接管 Codex 的 Responses 路線

setup 把 Codex ~/.codex/config.toml 裡內建 openai provider 的 openai_base_url 改成指向本地 daemon（http://127.0.0.1:<port>/v1），保留原本 provider 身分。從此 Codex 所有模型流量都先經過這個 daemon。

  • Voice 路線被釘死在官方端點：同時把 experimental_realtime_webrtc_call_base_url 指回 chatgpt.com/backend-api/codex，語音功能不會誤走本地橋接。
  • 逐字可還原：改動全部寫進一份 journal（version:10），記錄改前的原始行；斷開/解除安裝時 byte-for-byte 還原，並採「先寫 recovery 副本 → 再寫 config → 最後寫主 journal」的順序，讓當機後能明確判斷已提交狀態。

Step 2：把 chatgpt-web/* 混進官方模型清單

GET /v1/models 先原封不動轉發到真正的官方後端拿回目錄，然後 augmentNativeModelCatalog() 做「原生一列不動、只追加」：

const nativeModels = catalog.models.filter(m => !slug(m)?.startsWith("chatgpt-web/")); // 原生全照抄
const webModels = availableChatGptWebModelRoutes(config)
  .map(route => buildChatGptWebModel(template, route, config));                // 追加幾列
return { ...catalog, models: [...nativeModels, ...webModels] };

追加的列拿一個原生模型當 template 複製，再覆寫關鍵欄位（slug、顯示名、context window、effort、tool_mode:null、supported_in_api:true 等），對應這些帳號才看得到的路線：

slug顯示effort（固定）gate
chatgpt-web/lightInstantlow—
chatgpt-web/mediumMediummedium—
chatgpt-web/highHighhigh—
chatgpt-web/extra-highExtra Highxhigh帳號需開放
chatgpt-web/proProultra→max需 Pro 帳號
chatgpt-web/luna、/thinkLuna / Thinklow / medium沒有 Sol 選單的帳號
chatgpt-web/zero-risk(-pro)Zero Risk—手動互動模式

後端實際模型是 gpt-5.6-sol / gpt-5.6-luna。每列 effort 固定不可改（模型本身就等於 ChatGPT 的那個模式），Codex 的 Effort/Speed 選項壓不過它。

if (typeof requestedModel === "string" && !isChatGptWebModelSlug(requestedModel)) {
  // 不是 chatgpt-web/* → 原封不動轉發給官方後端
  return await forwardNativeCodexRequest(nativeRequest, "responses", undefined, raw);
}
// 是 chatgpt-web/* → 交給瀏覽器 adapter 去驅動你登入的網頁 ChatGPT
回答你最關心的三個問題：
  • 其它模型還正常嗎？ ✅ 完全正常。非 chatgpt-web/* 一律 native passthrough 原樣轉發，連 image、search、compaction、Voice 都照走原路 —— 它只是個透明代理。
  • 可以挑選模型嗎？ ✅ 就在 Codex 原生模型選單裡挑。因為 /v1/models 把 chatgpt-web/* 混進官方目錄一起回傳，你看到的是「原生模型 + 幾列 ChatGPT Web — …」。
  • 怎麼變成一個模型？ 把網頁 ChatGPT 包成一列符合 Codex 模型 schema 的 catalog row，請求進來就改用瀏覽器回答，SSE 事件再組回 Responses 格式。

兩個容易忽略的細節

  • HTTP 426 握手：GET /v1/responses 一律回 426 Upgrade Required。這是 Codex 探測「有沒有 WebSocket 傳輸」的預熱握手，426 = 「這裡沒有 WS，請用純 HTTP/SSE」，且不會 fallback 換模型。
  • 跨 provider 殘留物清洗：本地產生的 rs_* reasoning id、ocx1: 壓縮 checkpoint，在切回原生模型前會被 scrubBridgeArtifactsForNative() 移除/改寫成一般 user 訊息，避免官方後端去載一個它從沒存過的 item。

⑤ 三種模式 + HITL 本地 exec

模式送訊息本機 Codex 工具機制
Browser-only自動❌把整包 Codex context 丟進一個全新的 ChatGPT「臨時對話」，只取回答；不啟動 broker/tunnel/MCP
Full harness自動✅ 經 MCPChatGPT 透過 outbound tunnel + Codex Native2 connector 回呼本機工具
Zero Risk手動貼上✅ 另一組 connector程式完全不讀寫 ChatGPT DOM；你手動選模型、貼 prompt、按送出，再回 launcher 按「Sent」確認
--hitl（browser-only）自動✅ 本機終端 exectunnel 被擋時的替代路：模型發 [EXEC_REQUEST]，你在終端逐條核准才執行

HITL（Human-In-The-Loop）本地 exec 的設計與限制

當 MCP tunnel 不能用（例如被網路擋），--hitl 讓 browser-only session 直接在終端跑本機指令，每一條都要你按 Enter/y 核准（n/Esc 拒絕、c 先編輯）。模型用文字區塊 [EXEC_REQUEST] 提出指令，核准後結果以 [EXEC_RESULT] 注回同一個瀏覽器回合。

安全邊界很現實，務必理解：
  • 可寫、不做內容沙箱：你核准什麼就跑什麼（含 rm、git commit、sed -i）。唯二內建限制是「指令限制在設定的 workspace 目錄內」＋「每條都要你核准」；沒有自動唯讀強制或指令黑名單。
  • 600 秒逾時、單條輸出上限 10KB；單行指令（command: 當一行解析，delegate 的子任務 prompt 要單引號、不能含換行/單引號）。
  • 只在 browser-only + 前景有 TTY 才啟用；當背景服務或無 TTY 一律 fail-closed（不執行）。
  • 此通道沒有 MCP 子代理工具，模型改用「跑 codex exec 非互動指令」來 delegate 子任務，再用第二個 [EXEC_REQUEST] 讀回結果。

⑥ MCP 工具調用怎麼實現？（Full 模式）

Browser-only 下 ChatGPT 只是純聊天、碰不到你本機。要讓它真的能讀寫檔案、跑指令，就靠 Full 模式的 MCP 反向回呼。它是個三方拆分設計：

owner = ChatGPT-web adapter（在 daemon 裡）—— 把「當前 Codex 回合的工具環境」註冊給 broker │ ▼ newline-JSON over Unix socket / Windows named pipe broker = TurnBroker（daemon 內單例）—— 持有回合環境, 仲裁每一次工具呼叫 ▲ │ claim / invoke / settle MCP server = 獨立子行程（tunnel 生的）—— 對 ChatGPT 暴露 codex_* 工具 它看不到環境, 必須先用 turn token 換 binding

授權生命週期：token → claim → invoke → settle

能力的核心是一個 「本回合專屬」的隨機 token（turn_ + 24 bytes base64url）。daemon 把它編進 ChatGPT 的 prompt，ChatGPT 在回答途中每次 codex_* 工具呼叫都要帶這個 token 回來。每個工具 handler 都跑在 withClaimedTurn 裡：

  1. Claim：MCP server 拿 token 向 broker {method:"claim"}。broker 驗 token（能區分「發給一個已結束回合」vs「從沒存在」）、記下 activity 租約、回一個 不透明的 bindingId + 環境。
  2. Invoke：用 bindingId 呼叫「當前回合真正擁有的工具」，實際在真正的 Codex runtime 裡執行。
  3. Settle：finally 一定送 {method:"activity_complete"}（刻意不帶 AbortSignal，避免取消時遺留租約卡住後續完成），把 activity 移到 tombstone。
三個安全要點：(1) ChatGPT 只能呼叫「當前 outer Codex 回合自己宣告過」的工具，跨不了 turn/task；(2) 內部 bindingId/handle 從不暴露給模型，token 每回合都是新的；(3) 工具是在真正的 Codex runtime 跑的（沙箱、核准彈窗、UI、結果都是 Codex 原生負責），不是重新實作一套 —— 所以工具調用跟你直接用 Codex 一樣真實。

對 ChatGPT 暴露的 bridge 工具

  • codex_exec / codex_write_stdin —— 跑指令 / 寫入或輪詢一個 session
  • codex_apply_patch / codex_view_image
  • codex_tool_inventory —— 分頁列出當前回合有哪些工具（回傳精確 wire_name 與 schema）
  • codex_tool_call —— 用 inventory 給的精確 wire_name 去呼叫（萬用 dispatcher）
  • codex_turn_start / codex_turn_complete —— Zero Risk 用的起訖
  • multi_agent_v1/v2__wait_agent、collaboration__wait_agent —— 子代理輪詢

exec gateway：用生成的 JS 跑巢狀工具

有時 Codex 不暴露離散的 exec_command，而是暴露一個 freeform exec（可跑模型寫的 JS，scope 裡有 tools 註冊表）。這時 bridge 生成一段 JS 丟進那個沙箱：挑對的原生命令工具呼叫、正規化結果再 emit()。同時用一個 Proxy 包住 tools 註冊表：禁止在 exec 裡再遞迴呼叫 exec，並強制 wait_agent 的輪詢間隔。

三個容易踩雷的時間/併發設計

  • wait_agent 固定 30 秒輪詢：因為 MCP 通道是共享序列化的，一個長 block 會餓死被 spawn 的 web 子代理。schema 把 timeout_ms 鎖成 const/min/max=30000，且呼叫端三處強制。一次 timeout ≠ 任務完成，要再檢查進度再等。
  • MCP invocation timeout = 90 秒 < tunnel 約 2 分鐘期限：本地先結束，讓被放棄的呼叫回一個 MCP error，而不是拖垮長壽命的 stdio transport（回 codex_tool_timeout 叫模型別在本回合重試）。
  • completion fence 防競態：瀏覽器判定「回合完成」要 begin() 拿當下 activityRevision（只有「沒有進行中的 activity/invocation」才給），再 commit(revision)；期間任何新 claim 都會讓 revision 變動而使 fence 失效 —— 避免在某個原生工具還在跑時就誤判回合結束。

Compatibility V1（新裝預設）Native

「工具調用沒問題嗎？」 會動，但有實打實前提：要開 ChatGPT Developer Mode、建一個名稱剛好叫 Codex Native2 的 Tunnel connector（Auth: None、Allow all actions）；寫入類動作還要 workspace 管理政策允許；意外的核准彈窗會 fail-closed（除非明確 --auto-approve-tool-calls，且它只點「Allow once」）；tunnel 被網路擋就退回 --hitl。

⑦ 瀏覽器 worker 內幕

真正驅動 ChatGPT 網頁的 runBrowserTurn 跑在一個 helper 子行程裡（daemon 用 newline-JSON stdio 跟它溝通）；分頁本身由 Electron Launcher 擁有，worker 用 CDP connectOverCDP 連上 launcher 租給它的那個 WebContentsView。

五分頁租約：為什麼第 6 個回合會失敗

MAX_CHATGPT_BROWSER_TABS = 5，兩處把關：worker 層（activeRuns.size >= 5 直接拒）與 session registry 層（ChatGptTurnSessions.getOrCreate 數 active，滿了丟同樣錯誤）。理由：每個 active 回合都佔一個真正登入的 ChatGPT document，分頁上限避免過量併發流量觸發帳號濫用偵測。每回合向 launcher 要一個 surfaceId 的分頁租約，結束時釋放。

用 data-turn-id 綁定提交與回應

ChatGPT 的 data-testid="conversation-turn-N" 是顯示索引、會在渲染時重新編號，所以工具刻意改用穩定的 data-turn-id 來綁定。送出前先 captureSubmissionBaseline 記下所有既有 turn 容器；送出後等到出現「相對 baseline 的新 data-turn-id」才算提交被接受（多出 >1 個新 turn 會直接丟錯）。回應鎖定到 [data-turn-id=…] 的那個節點；因為 ChatGPT 會虛擬化/reparent，還有 rebind 邏輯在節點數 ≠ 1 時重綁。

細節控最愛的一手： 貼 prompt 不用 Playwright 打字或 CDP Input.insertText —— 因為那會被 ChatGPT 的 Lexical 編輯器當成「真人逐字輸入」而搞爛反引號 `。改成在頁面內 evaluate 一段 insertPlainTextIntoComposer 直接塞純文字，並用精確 readback 驗證貼對了。

Prompt envelope 與圖片原生附加

可見訊息是「自然語言傳輸契約」＋把任務編成 JSON：<codex_context_json>{version:3, system, messages}</codex_context_json>，外加輸出 schema、傳輸模式（本地工具 / 唯讀 / 壓縮）、以及要模型把 turn_token 原樣帶進每次 Codex Native 呼叫的 resume 尾註。圖片不進 JSON：以 {type:"image_attachment", attachment_ref} 佔位，實際 bytes 用 input[data-testid="upload-photos-input"].setInputFiles() 原生上傳（最多 10 張，遠端 URL 會被拒）。

用量估算與 context 視窗

  • tokenizer 用 tiktoken o200k_base（GPT-5 世代），分塊避免單次爆炸、絕不低估。
  • 各模式視窗（含固定 8,192 token 平台保留）：Instant 41k/自動壓縮 32k；Medium/High 90k/80k；Pro 約 103–104k；Luna 模型窗 1,050,000。
  • 「10% 壓縮保留」其實是 effective_context_window_percent = round(自動壓縮上限 / 視窗)（如 80k/90k≈89%），讓 Codex 在真正塞滿前就先壓縮、留 headroom。
  • 3× Bigger Context：把視窗 ×3（Medium/High 可到 270k），靠把「完整語意記錄」切成 2–3 段 staged 提交（永不切斷一則訊息或 JSON 字串），用二分搜尋同時平衡每段的 token 與 composer 字元預算。

串流：ChatGPT 狀態列 → Codex reasoning/commentary

worker 把 DOM 分成三種 trace：status（思考/步驟列）→ 映射成 Codex 的 thinking_delta（reasoning）；commentary（狀態容器內/首個狀態前的散文）→ text_delta phase=commentary；answer（其餘 .markdown）→ 最終答案串流。答案用 append-only Markdown buffer 提交（區塊穩定 750ms、且後面已出現下一塊才 commit；已提交區塊被改動會丟一致性錯）。

重試、卡住逾時、取消

  • 重試：每回合最多 3 次，只計可重試的 adapter error，30 分鐘 TTL 預算；第 4 次變不可重試的 exhausted error。
  • 三層逾時：橋接上游 stall（預設 300s）；DOM 健康寬限窗（缺回應 60s、空回應 10s、完成鍵 60s、multipart 180s，且被證實的 MCP 進度會暫停缺回應窗）；每 stage 預算（還會退還系統睡眠時間再重新計時）。
  • 取消：每個 await 都串 AbortSignal；取消時按下 Stop 鍵再丟 AbortError。錯誤分類含分頁關閉(499)、被取代(499)、stopped-thinking(502)、以及壓縮 handoff 被接受這種「良性中止」。

⑧ 上下文壓縮子系統

長對話要能 checkpoint 成摘要再繼續。routed 模型產生不了 OpenAI 的加密壓縮 blob，所以自成一套：

  • 透明信封：摘要包成 ocx1:+base64（encode/decodeCompactionSummary）；真正的官方加密 blob 沒前綴，解碼成 null 並顯示為 opaque 註記。
  • v1 替換歷史（/responses/compact）：buildCompactV1Output = 近期 user 訊息（20k token 字元預算內、由新到舊）+ 最多 10 張圖 + 一則 SUMMARY_PREFIX\n<摘要>；1×1 PNG 佔位會被丟掉。v2（{type:"compaction_trigger"}）要求剛好一個 compaction 輸出項。
  • 一次性 checkpoint capability：CompactionTransactionStore 只保管「摘要」這一件事、不持有任何 Codex 工具環境；發一個 control_ token + handoff_ id（有 TTL、單次消費）。model 端用固定 wire name codex.control.compaction_handoff 呼叫剛好一次交出摘要 —— 這條繞過一般 claim 流程、也被濾出 inventory，無法被當普通工具發現/呼叫。
  • retained source vs fallback：優先在「完成回合的那個保留分頁」上做 checkpoint（只暴露那個一次性 control token）；若來源分頁已不在，則開一個全新唯讀臨時對話，把累積 context 重播進去直接產摘要。整條 handoff 有 5 分鐘 liveness 預算，每個 ack 重新計時。
  • continuation 當「證明」不是「推測」：交出 checkpoint 後 daemon 記下 {summaryHash, sourceHashes}；之後的請求要 hash 得對得上這台 daemon 真的產過的 checkpoint 才接受 ——「新行程不得憑空發明一個不存在的 handoff」。
  • Luna 的 rolling checkpoint：Luna 每個完成回合都在答案尾端夾一段「私有 checkpoint」（用 ChatGPT Markdown 序列化逃不掉的純英數 marker 分隔），存進 per-thread store（用父答案 hash 綁定），讓完成歷史不進入 Codex transcript，也就不需要另外的 Codex 壓縮。

⑨ 安全模型與 fail-closed 設計

信任邊界

使用者信任：本地 Codex app、這個 loopback daemon、launcher 的私有 Electron 瀏覽器 profile、你選的 ChatGPT workspace、OpenAI tunnel 服務、你親手建的那個 MCP connector。repo 內容、工具輸出、網站、prompt 文字都是不可信資料。

關鍵不變量

  • Responses 與 health listener 只綁 127.0.0.1；Full 模式只用 outbound tunnel，不開任何對外 port 或防火牆規則。
  • 瀏覽器 state 與 tunnel 憑證存在 app home、權限 0600；秘密絕不進 CLI 參數、log、產生的 profile 或 git。
  • /admin/* 生命週期端點要隨機 bearer token；drain 要「HTTP 請求數」與「瀏覽器/工具回合數」兩個計數器都歸零才准 shutdown（否則 409 refused）。
  • connector 身分即公開 MCP ABI：只認 Codex Native2，舊 Codex Native 永不被當 fallback（避免舊 schema 被誤認為當前能力契約）。

已知風險（repo 自己列的）

  • Prompt injection / 破壞性工具：ChatGPT 看得到可能含惡意指令的 repo 內容與工具結果，Full 模式能寫檔/跑指令 —— 請用可信 workspace、保持 Codex 沙箱/核准設定、只授權你要的 connector 動作（預設不自動核准）。
  • 同機同使用者行程：loopback 沒有獨立 bearer（因為要保留原生 provider 身分），同 OS 使用者的其他行程能連到那個 port —— 請在可信單人帳號上跑，把本機程式碼執行視為信任邊界內。
  • 瀏覽器 session / tunnel 憑證竊取：私有 partition 是敏感登入物件，別同步/上傳/commit；懷疑外洩就登出或撤銷 session、輪換 tunnel key。
  • UI 漂移：ChatGPT DOM 不是穩定 API；selector 收窄，漂移就讓回合失敗，絕不換模型/換傳輸/假造成功。
Non-goals（明列不做的事）： 不防禦被攻陷的本機 OS 使用者或被竄改的 Codex/Electron 二進位；不繞過 ChatGPT 方案、workspace、用量、動作控制或模型限制；不把消費級瀏覽器自動化當成受支援的 OpenAI API 契約。

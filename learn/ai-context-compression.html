⓪ 一句話總結

每個長時間運作的 AI Agent 遲早會塞爆上下文視窗，於是它會「壓縮（compaction）」——把整段對話交給模型寫成一份摘要，再用摘要取代原始歷史。問題是：預設的壓縮會流失關鍵資訊（決策理由、當前狀態、歷史脈絡），壓個 2–3 次後，Agent 就表現得像「剛開機、什麼都忘了」。

💡 本篇重點：各家 Agent 的壓縮機制大同小異（都是「摘要即取代」），所以真正能幫到你的，是一組不綁特定工具的通用策略——主動早壓、外部化記憶、寫交接文件、隔離子任務、用檢索取代塞滿。這些在 Claude Code、Codex、Cursor、Aider… 上都有效。

① 為什麼要壓縮：從「爆視窗」到「降智」

Agent 的上下文視窗是固定的（如 200K token）。一段長對話裡，system prompt、工具定義、AGENTS.md/CLAUDE.md、讀進來的檔案、每一輪的工具輸出，全都在燒預算。撐滿之後有兩種壞結局：

  • 硬爆：超過視窗，直接塞不下、報錯或截斷。
  • 軟爆（降智）：號稱能吃百萬 token，但實測「真正敏銳」的區間小得多。塞太滿時模型會抓不到重點、開始遺漏、變笨——即所謂 context rot 與 lost in the middle。
🚫 壓縮本身也有代價：每壓一次就損失一點細節。研究與實務都指出——連續壓 2–3 次後，Agent 常表現得像「對話剛開始」：忘了為什麼這樣決定、忘了團隊狀態、忘了歷史。所以壓縮不是萬靈丹，怎麼壓、壓什麼、何時壓才是關鍵。

② 壓縮的四個層次（先分清楚你在壓什麼）

「對話壓縮」其實橫跨四個層次，能不能由你控制、通不通用，差很多：

層次壓縮什麼產物你能控制嗎
③ 對話記憶壓縮
（本篇主場）		多輪對話歷史摘要 / 事實清單高 Agent 內建 + 你的習慣
① 硬提示壓縮單次 prompt 的冗餘字更短的文字中 外掛工具
② 軟提示壓縮prompt → 向量/特殊 tokenembedding（人看不懂）低 需訓練/綁模型
④ KV Cache 壓縮推論時的注意力快取底層張量低 自架模型才碰得到
📌 對使用 Claude Code / Codex 的你而言：層次 ③（對話記憶）是你日常真正能掌控的，也是本篇重點。①（如 LLMLingua）是可選的外掛加強；②④屬於模型/框架研發者的領域，理解即可（詳見 ⑦ 專案清單）。

③ 各家 Agent 怎麼壓（對照表）

根據對 Claude Code、Codex CLI、OpenCode、Amp 的實測研究，它們的壓縮設計如下：

Agent觸發時機演算法保留 / 丟棄使用者控制
Claude Code 自動約 ~95% 視窗容量（部分實測 ~83.5%／200K 視窗約 167K）；可手動 /compact LLM 摘要 只留摘要，丟整段歷史 /compact [指示] 可自訂保留內容
Codex CLI token 門檻（依模型約 180K–244K），可設 model_auto_compact_token_limit LLM 摘要（強調「當前進度＋關鍵決策＋待辦」）；OpenAI 模型會呼叫伺服器端 /v1/responses/compact 回傳加密壓縮表示 摘要 ＋ 最近約 20K token 可關閉自動壓縮
OpenCode 動態溢位 isOverflow()（token > 視窗−輸出上限）；可手動 /compact 先 prune 工具輸出，再 LLM 摘要 摘要 ＋ 受保護的最近 40K 工具輸出 可關閉自動壓縮
Amp 只有手動「Handoff」，不自動壓 次級模型「選擇性抽取」關鍵資訊 用 thread 引用按需取回 完全靠使用者紀律
⚠️ 共同弱點：Codex 與 OpenCode 都明白警告「多次壓縮的累積資訊流失」。這也是為什麼下面 ⑤ 的通用策略，本質上都是在「幫壓縮器留住它自己會弄丟的東西」。

④ 共同機制：摘要即取代（Summarize-and-Replace）

除了 Amp，各家的核心演算法幾乎一樣，抽象成一句話就是：

觸發（到門檻） ─► 把整段對話餵給 LLM ─► 寫一份「交接摘要」 ─► 用摘要取代原始歷史 ─► 繼續 │ 摘要通常保留：已完成什麼 · 進行中什麼 · 牽涉哪些檔案 · 下一步 · 使用者關鍵要求/限制

差別只在細節：要不要多留一段最近訊息（Codex 留 ~20K、OpenCode 留 ~40K 工具輸出）、要不要先剪枝再摘要（OpenCode）、摘要 prompt 強調什麼。理解這個共同骨架後，你就懂為什麼通用策略在每家都有效。

⑤ ⭐ 跨 Agent 通用的實戰策略

這是本篇核心。以下策略不綁任何特定 Agent——Claude Code、Codex、Cursor、Aider… 都適用。原則只有一個：別把記憶只託付給會失真的壓縮器。

主動早壓，別等自動觸發

自動壓縮通常在 80–95% 才啟動，那時品質已在下降、還可能打斷你。實務建議在約 60% 就手動壓——要壓的東西少，摘要品質反而更高。（Claude Code /compact、Codex/OpenCode 亦可手動。）

下「保留指示」保護關鍵資訊

壓縮器不知道什麼對你最重要——直接告訴它。例：/compact 只保留我們決定的 API 介面、還沒解決的 bug、以及被否決的方案。把「決策理由、當前狀態、限制」點名保住。

把記憶外部化到檔案（最重要）

不要讓重要資訊只活在對話裡——它會被壓掉。寫進會被持續讀取的檔案：CLAUDE.md / AGENTS.md（專案慣例、術語）、TODO.md / NOTES.md（決策與待辦）、以及頻繁 commit。這些檔案是壓縮壓不掉的「長期記憶」。

用「交接文件（Handoff）」接力到新 session

與其一直壓到降智，不如在乾淨的狀態下產出一份交接文件（做了什麼、現況、下一步、關鍵決策），開一個全新 session 貼上去續作。這招各家都能手動做，Amp 甚至以此為主要機制。

用子代理 / 子任務隔離上下文

把「讀一大堆檔案找答案」這類會吃掉大量 token 的雜活，丟給子代理去做，只把結論帶回主線。主線的上下文因此保持乾淨、不被中間過程淹沒。

用檢索取代「塞好塞滿」

別把整個 repo/文件一次貼進去。改用檢索（RAG / grep / 檔案工具）在需要時才拉相關片段。上下文永遠只裝「此刻用得到的」，是最有效的「壓縮」——因為根本沒放進去。

控管輸入源頭：精簡指令檔、剪工具輸出

Codex 的 AGENTS.md 有 32 KiB 上限；臃腫的指令檔、沒用的工具定義、動輒上千行的檔案 dump，都在開工前就吃掉預算。保持指令檔精瘦、別盲目 cat 大檔、關掉用不到的工具。

一次一個任務，及早收斂

單一 session 塞太多不相關任務，會讓壓縮器難以取捨。一個 session 專注一件事，做完就交接/開新局——這和「小步、垂直切片」的工程紀律一脈相承。

💡 一句話心法：把 Agent 的上下文當成「工作桌」而非「檔案櫃」——桌上只放此刻要用的，長期資料收進檔案(檔案櫃)，需要時再拿。壓縮器負責清桌子，但真正的記憶在檔案裡。

⑥ 進階：外部工具層

若內建機制 + 通用策略還不夠，可再疊上外部工具：

  • 硬提示壓縮器（前處理）：用 LLMLingua 這類工具，在把長文/RAG 內容送進 Agent 前先壓掉冗餘 token（最高 20x、LongLLMLingua 於 RAG 上只用 1/4 token 反而提升 21.4%）。原理：用小模型算困惑度，刪掉「好預測＝低資訊」的字。
  • 外部記憶層：Mem0 等把對話事實抽取存進向量庫，跨 session 持久記憶，需要時檢索回填——等於替 Agent 外掛一顆不會被壓掉的長期腦。
  • 對話記憶壓縮器：見 ⑦ 的 Agent-Memory-Compressor——摘要／抽事實／封存三策略 + 重要性評分，可獨立套在自建 Agent 上。

🔬 技術方塊：LLMLingua 的小模型怎麼算出「資訊量」

硬提示壓縮的核心，是用一顆小模型量化每個 token 的資訊量，把「低資訊＝冗餘」的字刪掉。機制如下：

① 要算的量：自資訊（self-information / surprisal）

對句中第 i 個 token xᵢ，其資訊量定義為它在前文條件下「不被預測到」的程度：

I(xᵢ) = − log p(xᵢ | x₁, x₂, …, xᵢ₋₁) 機率高（好預測）→ −log p 小 → 資訊量低 → 冗餘 → 可刪 機率低（出乎意料）→ −log p 大 → 資訊量高 → 關鍵 → 保留

困惑度（perplexity）只是它的指數形式：PPL = exp(平均 −log p)。低機率 = 高自資訊 = 高困惑度，三者同源。

② 一次前向傳播就全部算出（teacher forcing）

關鍵：不需要讓模型「生成」任何東西——文字本來就在了。把整段 prompt 一次餵進自迴歸小模型（GPT2-small／LLaMA-7B 這類 causal LM），每個位置都會輸出「下一個 token 的機率分布」；因為真正的下一個 token 已知，直接讀出它被賦予的機率即可。

python · 概念示意 
logits = small_model(input_ids)                 # [seq_len, vocab]
logp   = log_softmax(logits, dim=-1)
# 讀出「實際出現的那個 token」被賦予的 log 機率（對齊下一個 token）
token_logp = logp[range(seq_len-1), input_ids[1:]]
self_info  = -token_logp                        # 每個 token 的資訊量

只做單次前向、只讀既有 token 的機率（不 beam search、不生成），所以又快又便宜——這也是「小模型就夠」的原因：我們只需要相對排序誰重要，不需要它產生高品質文字。

③ 從分數到「刪不刪」＋ 為何要迭代

  • 依目標壓縮率／budget controller 分到的預算，把自資訊換算成一個門檻（百分位）；低於門檻 = 冗餘 → 刪。instruction／question 給更高預算、少刪。
  • 迭代的必要：刪掉 token 會改變後文的條件機率（前文變短了），所以 LLMLingua 分段重算——用壓縮後的上下文重新計算下一段的機率，讓分數始終反映「當前實際上下文」，而非一次性獨立打分。
📌 版本差異：上面是 LLMLingua v1／LongLLMLingua 的原理（用 perplexity）。LLMLingua-2 改走另一條路：作者認為 perplexity 是「因果單向 LM 的間接指標」，未必對齊「壓縮」這任務，於是用 GPT-4 標註「該保留哪些 token」→ 訓練 BERT 雙向 encoder 做二元分類。此時「資訊量」不再是 −log p，而是分類器學出來的保留機率（能看左右雙向脈絡、任務無關、快 3–6 倍）。
💡 LongLLMLingua 的加強：v1 的自資訊與「你的問題」無關；LongLLMLingua 改用對比困惑度——比較同一 token 在「有給問題 vs 沒給問題」下的機率變化，把資訊量升級成「與當前問題相關的資訊量」，避免刪掉正是問題所需的字。

⑧ 檢查清單 + 選型

✅ 通用檢查清單（任何 Agent 都適用）

  • ☐ 有沒有在 ~60% 就主動壓，而不是等自動觸發？
  • ☐ 壓縮時有沒有下 保留指示，點名保住決策/狀態/限制？
  • ☐ 重要資訊是否已外部化到 CLAUDE.md/AGENTS.md/TODO.md 並常 commit？
  • ☐ 長任務是否用交接文件 + 新 session，而非硬壓到降智？
  • ☐ 吃 token 的雜活是否丟給子代理、只帶結論回來？
  • ☐ 是否用檢索按需取檔，而非一次塞整個 repo？
  • ☐ 指令檔是否精瘦（Codex AGENTS.md ≤ 32 KiB）、有沒有關掉沒用的工具？

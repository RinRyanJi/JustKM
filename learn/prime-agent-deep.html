① Kernel:ZeroMQ 三通道傳輸

TS host 與 IPython kernel 之間走標準 Jupyter 協定,傳輸層是 ZeroMQ(import { Dealer, Subscriber } from "zeromq")。連線檔記錄五個 port + HMAC 金鑰,實際使用三個主要通道:

通道ZeroMQ socket承載
shellDealerexecute_request / execute_reply / kernel_info_request
iopubSubscriberstdout / stderr / results / errors / status / comm_open
controlDealerinterrupt / shutdown / 執行期間的 host-request 回覆

另有 stdin 與 hb(heartbeat)port。訊息用標準 Jupyter multipart framing,JSON frame 以 HMAC-SHA256 簽章:

<IDS|MSG> signature ← HMAC-SHA256(header+parent+metadata+content) header parent_header metadata content

一般輸出只在 parent_header.msg_id 對上當前執行時才接受;但 comm 訊息在這個過濾之前處理——因為非同步 Python 任務可能在排程 cell 回到 idle 後才開 comm。

⭐ 為什麼 host-request 回覆走 control 通道(而非 shell)

這是最精妙的一點。一個正在跑的 cell 可以 await 任務被接受:

handle = await rlm("subtask")

IPython 序列處理 shell 訊息。若把接受回覆送在 shell 通道會死鎖:當前的 execute_request 要等回覆才能結束,而 kernel 又要等這個 request 結束才會處理那個 shell 回覆——互相卡死。

解法:Python shim 把 comm handler 註冊在 control 通道,host 的接受回覆走那裡;未來完成用 loop.call_soon_threadsafe() 排程(control handler 可能在別的執行緒)。子代理的答案不走這條路——它們之後透過 agent_message 或檔案回來。

執行序列化 vs 子代理並發

KernelManager.execute() 的呼叫是序列化的:一個 kernel 一個共享 namespace,不會同時跑兩個普通 IPython cell。但 RLM 子代理仍可並發——因為每次委派用不同的 comm 與獨立 child runtime。

Python API 匯出

# prime-agent-runtime exports
rlm, run(prompt, **kwargs), find_models(query="", limit=8),
list_subagents(), delete_subagent(selector),
host_request(request_type, payload=None),
RLMSpawnHandle, RLMModel, RLMSubagent, TokenUsage

rlm.run 只吃 name 與 model(精確 provider/model selector);未知參數會直接失敗;model 搜尋限於有效未過期憑證;選不到或 auth preflight 失敗就spawn 失敗,不會靜默 fallback 到別的模型。

② Daemon:復原、傳輸與協定

Reconnect / Replay / Snapshot

  • 每個 sequenced event 屬於某個 worker generation;client 保留最後的 { generation, sequence } 游標,attach 時出示。
  • server 回報請求區間是 complete / partial / unavailable。generation 改變會使舊 sequence 失效。
  • replay 遺失不致命:attach snapshot 是耐久復原基準。DaemonAgentConnection 套用 snapshot、忽略重複或退役 generation 的事件、向 UI 回報「已重新同步」。
  • 大 snapshot 在 worker 端編碼,透過有界 supervisor cache 以不透明 chunk 串流(512 KiB 目標 chunk);supervisor 從不建構 history 大小的物件。

Private Worker Transport(二進位框架)

4-byte JSON header length 4-byte payload length small JSON routing header opaque payload bytes

worker 把公開事件序列化一次;supervisor 只讀 routing header,把同一份 payload buffer 轉發給符合的 client。assistant 串流用私有的 start/delta/end payload,supervisor 每個 delta 只重建一次公開的 message_update——不會反覆把整條增長中的 assistant 訊息從 worker 傳到 supervisor。私有連線用 per-worker token 認證,並圍籬在當前 supervisor generation,防止過時的替補 supervisor 繼續指揮已認領的 worker。

Backpressure(附掛層級)

  • 被阻塞的 client 停止收增量事件;其他 client 與 worker 繼續。
  • supervisor 不保留無界的 per-client 佇列;排空後該附掛從游標追上或收新 snapshot。

Idempotency 與崩潰復原

  • 變更型指令以 clientId + commandId 為 key,dispatch 前先寫 append-only journal。
  • 重複一個已完成指令 → 回傳存好的結果;收到但沒有耐久結果的指令 → 回報uncertain,不重播。
  • worker crash 後:reap 舊 process group 與追蹤的 detached bash 樹 → 逐字稿附上可見的 recovery marker → 在同一 active-session ID 下還原 root → 不重播不確定的副作用。

Coordinated Updates(兩階段)

  1. resident workers 並行建立非破壞性 checkpoint;
  2. supervisor 驗證並原子持久化聚合 manifest;
  3. 每個 prepare 都成功後才 commit 並停 worker。

若 prepare 或 manifest 驗證失敗,已準備的 worker 被釋放,所有 root 繼續運行。協定用 DAEMON_PROTOCOL_VERSION 與 schema revision 獨立版本化;相容新增走 capability 協商,不相容變更才 bump 版本。

③ Compaction:結構化摘要格式

compaction 與 branch summarization 共用同一套結構化摘要格式,由 LLM 產生:

## Goal
[使用者想達成什麼]

## Constraints & Preferences
- [使用者提到的要求]

## Progress
### Done
- [x] [已完成任務]
### In Progress
- [ ] [進行中]
### Blocked
- [受阻項目]

## Key Decisions
## Next Steps
## Critical Context

切點規則(Cut Point Rules)

合法切點:User / Assistant / BashExecution / Custom(custom_message、branch_summary)訊息。絕不切在 tool result——它必須跟著其 tool call。

Split Turns(單一 turn 就爆預算)

一個 turn = 從 user 訊息到下個 user 訊息之間的所有 assistant 回應與 tool call。通常切在 turn 邊界;但當單一 turn 超過 keepRecentTokens,切點落在 turn 中間的某個 assistant 訊息(isSplitTurn = true)。此時產兩份摘要並合併:① 歷史摘要(先前 context)② turn 前綴摘要(這個 split turn 的前半)。

累計檔案追蹤

兩種摘要都累計追蹤檔案:從「被摘要訊息裡的 tool call」+「前次 compaction/branch summary 的 details」抽取 read/modified 檔案,跨多次壓縮或巢狀分支摘要保留完整讀寫歷史。

Entry 結構

interface CompactionEntry {
  type: "compaction"; id; parentId; timestamp;
  summary: string;
  firstKeptEntryId: string;   // 從這裡起的訊息保留給 LLM
  tokensBefore: number;      // 從重建的 context 重算
  customInstructions?: string; // /compact <instructions>
  details?: { readFiles: string[]; modifiedFiles: string[] };
}

LLM 實際看到的 = system prompt + 摘要(來自 cmp entry) + 從 firstKeptEntryId 起的訊息。重複壓縮時,被摘要的跨度從上次的保留邊界起(不是從 compaction entry 本身),以保住上次壓縮存活下來的訊息。

Branch Summarization(/tree)

用 /tree 切到別的分支時,Prime Agent 會摘要你要離開的分支並注入新分支:找共同祖先 → 從舊 leaf 收集到祖先 → 按 token 預算(新的優先)→ 生成摘要 → 在導覽點存 BranchSummaryEntry(含 fromId)。

整體設計哲學:壓縮的是「對話訊息」,IPython kernel 的 Python 狀態不動;摘要是結構化、可累計、可迭代的(帶入前次摘要),而非每次從零重寫——這讓長 session 的「記憶」穩定且可審閱。

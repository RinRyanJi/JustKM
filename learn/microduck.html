🦆 Microduck:用強化學習走路的迷你雙足機器人,它的「大腦」怎麼設計

Pollen Robotics 的開源機器人:約 25cm、800g 的小雙足,靠強化學習策略走路。這個倉庫是「鴨子的大腦」——一塊 Rockchip RK3566 上跑一串 Rust daemon:50 Hz 控制迴圈從神經策略驅動 15 顆伺服,還管無線電、相機,以及「不會把機器人更新到變磚」的升級機制。策略在隔壁 microduck_rl 用 MuJoCo + PPO 訓練、sim2real、匯出 ONNX 給它載。本頁拆它的系統架構——那是整個專案最漂亮的部分。

⓪ 一句話總結

一隻用神經策略走路的玩具大小雙足機器人,而這個倉庫是它的「作業系統 + 大腦」。硬體:RK3566 單板、15 顆 Dynamixel 伺服 + IMU 共用一條序列匯流排、頭上一顆 8×8 ToF 深度、相機。軟體:一群 Rust daemon,robotd 跑 50 Hz 控制迴圈、從 RL 策略算出每顆伺服的動作;其餘 daemon 分別管無線電、相機、設定與更新。走路/翻滾的「本事」是在模擬裡用強化學習訓練出來、再匯成 ONNX 載進來的。

為什麼值得讀:它會走會翻會自己站起來很酷,但真正精彩的是系統設計——「只有一個行程能碰馬達」「三個 daemon 專門為了『控制迴圈掛了也能救回來』而存在」「更新是整包換、驗簽、健康閘門、能自動回滾」。這是一份很好的機器人/嵌入式系統工程教材。授權與硬體細節以倉庫為準。

① 這是什麼 · 會做什麼

Microduck 約 25cm、800g。拿起手把就能開它走;換上輪子、切到 roller 模式,它會載入「另一個大腦」(另一組策略)用滾的。它還會:

  • 走路(手把駕駛)、翻滾(裝輪子+roller 模式)、撿東西(喙碰地、一顆鍵)、自己站起來(被推倒會自行起身)。
  • 還會坐下、踢球、聽指令前滾,以及用「牠自己的聲音」呱呱叫。
  • 切模式可以用 NFC 標籤碰頭(切 walk / roller / laser / soccer,或配對手把);也能用 duckctl 透過藍牙從筆電操作,不用網路也不用 ssh。

硬體重點:Rockchip RK3566 單板;15 顆伺服 + IMU 共用一條 UART(Dynamixel 匯流排);頭部 8×8 ToF 深度感測;相機(經 WebRTC 串流)。

② 大腦從哪來:sim2real 強化學習管線

走路這種事不用手寫控制律,而是在模擬裡用強化學習訓練出策略,再搬到真機(sim2real)。訓練在隔壁倉庫 microduck_rl:

▲ sim2real 的關鍵是域隨機化:訓練時刻意亂動物理參數,逼策略學出對「模擬和真實的差異」不敏感的動作,下真機才不會垮。

所以「換模式」本質是換一個策略:walk 一個、roller 一個;autod 則是「自主大腦」——它跟手把一樣只是個送 intent 的客戶端,開了才動。

③ 系統全貌:一塊板、一串 daemon、一條匯流排

板上跑約十個 daemon,全部透過 Unix socket 以 JSON-RPC 2.0(一行一個物件)溝通。重點是:手把、手機、你的筆電、你的腳本——送的是同一組 API 呼叫(robot.* / update.* / net.* / pad.* / system.*)。

← 左右滑動看完整圖 →
▲ 傳輸(padd/btd/mediad)只是把同一組 API 從 BLE/WebRTC 轉到對應 socket。「app 會用的 API 每天都被手把、腳本跑到」,所以不會悄悄爛掉。

④ robotd:唯一能碰馬達的人(意圖 → 安全層 → 可執行)

整個系統裡只有 robotd 能命令馬達。15 顆伺服 + IMU 共用一條序列匯流排,由 50 Hz 控制迴圈獨佔。所有客戶端送的是意圖(intent)——「用這個速度走」「看那邊」「站起來」——robotd 裡的安全層才決定「實際上能不能、該怎麼執行」。

← 左右滑動看完整圖 →
▲ 「單一馬達權威 + 意圖/安全分離」是這台機器人安全的核心:不管誰下指令,最後都要過同一個安全層,硬體只有一個擁有者。

⑤ 設計靈魂:為「壞掉也能救回來」而生

這份架構最聰明的地方,是假設控制迴圈會壞,然後圍著這個前提設計。

三個 daemon 專門活過「robotd 死掉」

configd、updaterd、btd 不依賴 robotd(沒有 systemd 相依、沒有 ML runtime、沒有媒體堆疊)——因為「控制迴圈起不來的機器人」正是那個你需要去重設定、更新、回滾的機器人。這也是為什麼設定放在 configd 而不是 robotd。相機(mediad)和手把(padd)可以依賴 robotd——「沒相機沒手把的機器人,還是個你能更新的機器人」。

更新是「整包換」,而且驗簽、健康閘門、能回滾

← 左右滑動看完整圖 →
▲ 版本整包放 /opt/robot/daemon/releases/<版本>/,current 是指向當前版的符號連結。換版=原子地移動連結;出事=把連結指回舊版。每次更新都驗證、健康閘門、可逆。
可偷師的原則:把「負責自我修復的部分」和「可能壞掉的主功能」隔離,讓前者永遠不依賴後者;更新用「整包換 + 可回滾」而不是「就地打補丁」;並且自動驗證新版健康、不健康就自己退回去。這套思路在任何需要 OTA 更新的嵌入式/機器人產品都適用。

⑥ 狀態分層:更新不會弄丟你改過的設定

哪些東西更新後還在、哪些會被換掉?規則一句話:releases/<版本>/ 以外的全部,更新與回滾都保留。設定分兩層:

層位置誰決定
基底(image)/etc/robot/robotd.toml映像檔/安裝器寫,OS 更新會換掉
使用者層(owner)/var/lib/robot/robotd.toml只放「這台被改過的鍵」,更新/回滾都留著

兩層由 robotd_params::Params::load 逐鍵合併(表逐鍵、其餘整個取代)。好處:映像檔可以把自己的預設往前演進,而你改過的值仍然成立。更聰明的是:使用者層壞掉不會讓機器人停擺——它被擱置、機器人用基底跑,robotd 回報 degraded 並點名那個檔,而不是 unhealthy(否則會為了一個「沒有任何版本能修的檔」把每個版本都回滾掉)。基底壞了才是致命(那是壞映像)。

這個區分很有洞見:「擁有者決定的」和「映像檔決定的」分放兩個地方,A/B 雙槽 OS 更新時,/etc 跟著映像換、/var/lib/robot(自己的分割區)留著。所以「設定更新後不見了」這種經典痛點,從檔案分層就被根除。

⑦ 傳輸層什麼都不擁有 + 一套統一 API

一堆 daemon 其實不擁有機器人的任何東西,它們只是傳輸:

daemon角色
btd把 API 的子集從 BLE 轉給會回應的 socket(手機用)
padd / netpadd讀手把 → 送和 app 一樣的意圖(netpadd 走 LAN UDP)
mediad相機/音訊管線 + WebRTC 遠端門面(一張原始影格 ~1.8 MiB,刻意不走控制通道)
autod自主大腦,和 padd 一樣只是意圖客戶端,沒開就閒置
tofd / mapdtofd 發布 8×8 深度、誰都不讀;mapd 當訂閱者持地圖,對機器人不下任何指令
robotctlCLI,必須在壞掉的機器人上也能用的工具

因為「傳輸只搬同一組 API」,它們全都可以抽換而不碰機器人行為,而且每天都被用到,所以 app 要用的 API 不會悄悄腐爛。沒有真機?scripts/duck-sim 把真正的 daemon 跑在 MuJoCo 的身體上——一隻鴨子在視窗裡,或四隻當成你能登入的機器。

⑧ 重點 · 關聯 · 來源

七個帶得走的重點

  1. ~25cm/800g 的 RL 雙足鴨;這個倉庫是它的「作業系統 + 大腦」(Rust、RK3566)。
  2. 本事來自 sim2real:MuJoCo + PPO + 域隨機化 → ONNX → robotd 50Hz 載入。
  3. 換模式 = 換一個策略「大腦」(walk/roller…)。
  4. 約十個 daemon,Unix socket + JSON-RPC,所有客戶端送同一組 API。
  5. 只有 robotd 能碰馬達;大家送意圖,安全層決定可執行。
  6. 為「壞掉也能救」設計:三 daemon 活過 robotd 死;更新整包換、驗簽、健康閘門、可回滾、開機計數器兜底。
  7. 狀態分層(image vs owner)讓更新/回滾不弄丟你的設定。

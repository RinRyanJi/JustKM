A · 工具執行流水線

① ToolDefinition 解剖:模型面向 vs host-only

一個註冊的工具(ToolDefinition)= 面向模型的 ToolSchema + 一堆只給 host 用、絕不能洩漏給模型的欄位:

欄位作用面向模型?
ToolSchema(name/description/參數 schema)模型看得到的宣告✅ 是
output(ToolOutputDefinition)強制的權威輸出契約:JSON schema + render()(把值投影成內容)+ presentationMeta()❌ host
execute(args, exec)跑一次呼叫,只回權威的無損 JSON 值❌ host
timeoutMs / isConcurrencySafehost 端排程 metadata❌ host
finalizeContent最後的「僅內容」不變式回調❌ host
presentCall / presentResultUI 呈現器(pending / completed 卡片)❌ host
關鍵設計:白名單防洩漏。註冊表的 schemas() 用明確 allowlist 組出要給模型的 ToolSchema[]——output/execute/finalizeContent/timeoutMs/presentCall/Result 絕不會漏進模型請求。這把「模型該看的」與「host 內部的」用型別牆分開。

execute() 的三條硬約定

  • args 是無損快照、凍結的模型參數(不可被就地改);
  • 非同步工作必須觀察/轉發 exec.signal,且只在自己擁有的工作達到停穩(quiescence)才 settle——呼應防禦模式的「dispose 要停穩」;
  • 註冊表透過 around-dispatch 的 signal 替換保留呼叫方的取消,不會拋棄這個 promise,但無法硬殺同進程程式碼(誠實承認限制)。

② 流水線逐段:從 tool-call 到 tool/result

三個 waterfall(pre-execute / execute / post-execute)可各改寫一次呼叫;由定義自己控制的 finalizeContent 與 tools/result 在其後。逐段:

assistant 訊息含 tool-call block 1 tool/call 執行前先記日誌 ┃ UI: presentCall(args) 出 pending 卡 2 tools/pre-execute waterfall:hooks、權限、沙箱 → allow | deny | ask 3 ctx.approval 一次性詢問(在守衛之前);不存在/無法回答 → deny 4 單調守衛 deny 或 abstain;身分受保護;不可重排的擁有者策略也在此 5 tools/execute waterfall(環繞:timeout / retry / metrics 包住分發) 6 execute() 本體 → fs/write-intent | fs/edit-intent(僅 tool-fs 的檔案變更;先讀後編查在 fs/* 之下) 7 工具自有會話事件 todo/write、fs/observed、hook/invoked、hook/result、tool/code-dispatch 8 tools/post-execute waterfall:accept | block | replace | 加 context 9 外層正規化 對候選結果做無損快照;快照失敗 → 先把失敗規範化(拋錯 → isError) 10 finalizeContent 同步、僅內容的不變式(隨快照固定在可見定義上) 11 tools/result 同步通知:不可變、可 JSON 無損表示的凍結權威結果 12 additionalContexts active-batch FIFO,在記錄的 tool result 之後注入 user/message
段為什麼這樣設計
2→4 分三層把關pre-execute(通用 hook/策略)→ approval(一次性人工)→ 單調守衛(擁有者策略)。approval 在守衛之前,守衛只做「不可重排」的最終否決
5 環繞分發timeout/retry/metrics 是「包在 execute 外面」的關注點,不進工具本體
6 fs 意圖閘檔案變更走 fs/* 事件、有「先讀後編」檢查,而不是工具各自亂寫
9→11 結果收斂無損快照 → 拋錯規範化成 isError → finalizeContent 內容不變式 → tools/result 凍結權威、單一面向模型的結果
12 FIFO 注入額外 context 排在 tool result 之後當 user/message,而非硬塞進本次呼叫,保持因果順序
一句話:「鉤子可以跨越不同工具系列,而無需讓工具與某個策略服務耦合」——策略(權限/沙箱/timeout/結果改寫)全是掛在 seam 上的監聽器,工具本體只管 execute() 回一個無損值。

③ Code Mode(run_code):子呼叫也走同一條流水線

Code Mode 把保留的 run_code 傳輸與它序列化的子呼叫都送進同一條流水線。子呼叫的特別處:

  • 攜帶父級 token(用量歸屬到父);
  • 記錄 tool/code-dispatch 事件;
  • 把拒絕呈現為具約束力的駁回(不是靜默略過);
  • 省略 additionalContexts,以保持「呼叫與結果相鄰」。
對照 Prime Agent:這跟 Prime Agent 讓模型「用程式碼呼叫工具/子代理」是同一路線——把工具呼叫下沉成可程式化、可組合的東西,而非一次一個 JSON tool-call。
B · Cordis 的 scope / effect 機制

④ 兩層扁平 scope:貢獻要嘛全域、要嘛屬於一個 agent

scope 是「按 agent 劃分的註冊單位」。一項貢獻(工具、提示片段、變數、限制、監聽器)只有兩種身分:

  • 全域(global):對所有 agent 可見;或
  • 帶作用域(scoped):恰好屬於一個 scope key。

刻意只有兩層、扁平結構:

  • scoped 註冊不向下繼承給 subagent——子樹行為用 lineage 資料表達,絕不透過 scope 結構;
  • scope key 是不透明識別,按物件同一性比較;約定:一個活躍的 agent 就是自己 scope 的 key。
為什麼扁平而非樹狀:樹狀繼承會讓「這個 agent 到底看得到什麼」變得難以推理、容易漏權限。兩層扁平 + 「可見性只有 global/scoped 二選一」,讓可見性可精確推理;父子關係另用 lineage 純資料承載,永不影響可見性。

⑤ shadowing 與 restriction:按 agent 客製 persona 與工具

Shadowing(最具體者勝)

一個 scoped 的工具/片段/變數,僅在該 scope 內替換同名的全域對應項。這就是「按 agent 定制 persona、按 agent 定制工具變體」的機制——同一個名字,不同 agent 可以有不同實作,互不干擾。

Restriction(把全域工具集為某 scope 過濾)

  • tools.restrict 為單一 scope 過濾全域工具集合;多個 restriction 取交集;
  • scope-local 註冊在過濾之後合併;
  • 被過濾掉的全域工具,既不出現在提示詞,也拒絕執行——與「不存在的工具」無法區分。
安全含義:「過濾掉=從提示消失 + 拒絕執行 + 無法區分於不存在」是很乾淨的最小權限做法——模型看不到、也叫不動被限制的工具,不會靠「知道有這工具」去嘗試繞過。

⑥ agent.ctx / setup window / lineage

agent.ctx:可見性與生命週期同一個事實決定

agent 的帶作用域上下文。透過它做的註冊,既有 scope 可見性,生命週期也綁定到該 scope——同一個事實同時決定這兩件事;其上的監聽器參與該 agent 的 scope 過濾分發。

Scoped dispatch:關於誰的事,用誰的 carrier

關於某 agent 活動的事件,以該 agent 的 carrier 分發(過濾器放行無標籤監聽器 + 主體自身監聽器);關於註冊表本身的事件(如「一個工具被加了」)是註冊表主體事件,保持不過濾。

Setup window:只註冊、不驅動

CreateAgentOptions.setup 是創建時隙:此時 scope 與 agent 物件已存在,但 agent/會話尚未發布、agent/session-start 尚未觸發、首次提示詞尚未組裝。setup 只做註冊,從不驅動 agent——把「組裝環境」與「開始跑」清楚分開。

Lineage:父子關係是資料,不是結構

父子事實以資料攜帶:parentSession、持久的 delegationDepth、執行時的 subagentDepth;從不影響可見性。要控制遞迴深度、追溯來源就讀這些資料,而不是靠 scope 樹。

⑦ effect / disposer / Fiber:可逆生命週期

ctx.effect() 與可逆副作用

提示片段、工具 schema、適配器、監聽器…都經 ctx.effect() 或 ctx.on() 安裝,每個註冊都應回傳一個 disposer(資源釋放函式):reload / teardown 時「按預期撤銷」。若卸載順序有要求,把相關工作放同一個 effect,以確保按序釋放。

ctx.effect(() => { const off = registerSomething() // 安裝副作用 return () => off() // disposer:teardown/reload 時自動被呼叫 })

Fiber:Cordis 的生命週期單位

Cordis 核心提供 Context、Service、Fiber 與事件。Fiber 是掛載的插件實例之生命週期單位——它擁有該插件安裝的 effects,並在 reload / dispose 時把它們一併回收;搭配 vendored 的 cordis-plugin-hmr 就能做熱模組替換。(Fiber 的細節以 Cordis 上游為準。)

為什麼可逆是地基:正因每個貢獻都能乾淨拔除,profile/bundle 的 patch 疊加 才能安全「替換某條目的整段 config」;「沒有特權內核」 也才成立——擴充永遠是掛插件、拔插件,而不是改核心。這就是「一切皆插件」能運作的底層保證。

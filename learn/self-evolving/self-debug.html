🦆 自我除錯 Self-Debug：讓模型自己修自己寫的程式

Teaching Large Language Models to Self-Debug · Chen, Lin, Schärli, Zhou（Google Research, 2023）· 重點在「怎麼實現」

推理時自我修正 rubber duck debugging Spider / TransCoder / MBPP
📑 目錄
⓪ 一句話 ① 想解決什麼 ② 核心想法 ③ 怎麼實現 ④ 關鍵細節 ⑤ 效果與限制 ⑥ 在自我演化地圖的位置 ⑦ 來源

⓪ 一句話

Self-Debug＝讓大型語言模型像人一樣「除錯自己寫的程式」：先產生程式 → 執行拿到回饋（單元測試結果，或讓模型用自然語言解釋自己的程式碼）→ 依回饋修正，如此迴圈。全程不需人類指出對錯，也不需額外訓練，只靠 few-shot 提示。

① 想解決什麼

大型語言模型很會「一次生成」程式碼，但一次寫對的機率有限——生成的程式常常有 bug。傳統的補救辦法是大量取樣：一口氣生成幾十、上百份候選程式，再挑能通過測試的那份。這很燒算力，而且當沒有單元測試可篩（例如 text-to-SQL）時，根本無從挑起。

作者問的問題是：能不能讓模型不要「重寫很多次」，而是「看著自己剛寫的錯誤程式，把它修對」？就像人類工程師不會把有 bug 的程式整份丟掉重寫，而是坐下來 debug。

關鍵限制：作者刻意設定「沒有人類給的正確性標註、也沒有現成錯誤訊息」的情境——模型必須自己判斷哪裡錯了。這比「有 compiler 報錯就照著改」難得多。

② 核心想法：橡皮鴨除錯（Rubber Duck Debugging）

本論文的核心類比來自程式圈的老哏——橡皮鴨除錯法：工程師卡關時，對著桌上的橡皮鴨逐行解釋自己的程式在做什麼，解釋到一半往往就自己發現：「欸，這行跟題目要的不一樣」。不需要橡皮鴨回話，光是「把程式描述出來、跟題目對照」這個動作，就能逼出 bug。

Self-Debug 把這件事搬到 LLM 上：讓模型用自然語言解釋自己剛生成的程式碼、並檢視程式的執行結果，再據此判斷對錯與修正。模型同時扮演「寫程式的人」和「那隻聽解釋的鴨子」。

為什麼重要：先前研究普遍認為「模型自己產生的回饋」對程式生成幫助不大。本論文的貢獻之一，就是證明當沒有單元測試時，光靠模型自我解釋（code explanation）也能有效除錯。

③ 怎麼實現：產生 → 回饋 → 修正 的迴圈

Self-Debug 不改任何模型參數，全靠 few-shot 示範教會模型走一個閉環。一個「除錯回合（debugging turn）」由三步組成，然後重複，直到程式判定為正確、或達到最大回合數就停。

1
生成 Generate
模型依題目（自然語言 / 待翻譯的原始碼）先產生一份程式。
2
執行＋回饋 Feedback
執行程式，蒐集執行結果；再由模型生成一則「回饋訊息」判斷這份程式對不對、哪裡不對。
3
修正 Refine
把「原程式＋執行結果＋回饋訊息」餵回模型，請它產生修正後的新程式，回到第 2 步。

虛擬碼大致長這樣：

# Self-Debug 迴圈（示意，非原始碼）
code = model.generate(problem)              # 步驟 1：生成
for turn in range(max_turns):
    result   = execute(code)                # 執行，取得輸出 / 錯誤 / 測試結果
    feedback = model.explain_and_judge(      # 步驟 2：模型自我解釋＋判斷
                   problem, code, result)
    if feedback.says_correct:               # 判定正確就停
        break
    code = model.refine(                     # 步驟 3：依回饋修正
               problem, code, result, feedback)
return code

三種回饋（feedback）形式

「怎麼實現」的核心變數，就是第 2 步的回饋要提供多少資訊。論文比較了三種由淺到深的回饋：

回饋形式內容適用情境
Simple
簡單回饋		 最陽春：只給一句「這段程式對 / 錯」，不含任何細節；省略了自我解釋步驟。 做為對照基準，衡量「更豐富回饋」到底加了多少值。
Unit Test (UT)
單元測試回饋		 當題目附有單元測試時，除了用執行檢查對錯，還把實際執行結果 / 測試失敗細節納入回饋，資訊最豐富。 MBPP、TransCoder 等有測試可跑的任務。
Code Explanation (Expl)
程式解釋回饋		 讓模型逐行用自然語言解釋自己的程式（＝橡皮鴨），把解釋與（若有的）執行結果一起當回饋。 沒有單元測試的任務（如 text-to-SQL），是本論文最關鍵的貢獻點。

此外，作者也探討了把執行軌跡（execution trace）納入回饋——讓模型像人一樣「模擬程式一步步執行」來理解語意。整體精神是：回饋越貼近人類 debug 的兩種行為（解釋程式、追蹤執行），修正越有效。

三個任務怎麼取得回饋

任務要做什麼回饋來源
Spider（text-to-SQL）自然語言問題 → SQL 查詢沒有標準答案可比對、也沒單元測試 → 靠模型解釋 SQL（Expl）＋執行看回傳表格
TransCoderC++ 程式 → Python 程式（翻譯）有單元測試 → UT 回饋，執行看是否通過
MBPP自然語言 → Python 程式有單元測試 → UT 回饋（也可疊加解釋）

④ 關鍵細節

  • 不需訓練、不需人類回饋：整套方法只用 few-shot 提示，沒有微調模型參數，也不依賴人工標註對錯或現成的 compiler 錯誤訊息。
  • 重用失敗的預測：不像大量取樣「丟掉錯的、重抽新的」，Self-Debug 把失敗程式留下來當作修正的起點，讓每一份生成都能被繼續改進。
  • 樣本效率大幅提升：因為會「修」而不是「重抽」，Self-Debug 能用少得多的生成次數，追平甚至超越生成 10 倍以上候選程式的基準做法。
  • 回饋豐富度是主要變因：從 Simple → Expl → UT，回饋帶的資訊越多，修正效果一般越好；但即使在最弱的「只有自我解釋、無測試」情境，仍能穩定加分。
  • 停止條件：迴圈在「回饋判定程式正確」或「達到最大除錯回合數」時結束。

⑤ 效果與限制

效果

Benchmark提升幅度備註
Spider（text-to-SQL，無單元測試）基準 +2～3%；最難類別題目 +9%只靠 code explanation 回饋達成，證明「無測試也能自我除錯」
TransCoder（C++→Python）最高 +12%有單元測試，UT 回饋
MBPP（text-to-Python）最高 +12%有單元測試

在多個程式生成 benchmark 上取得當時的 state-of-the-art；同時因為會重用失敗程式，樣本效率顯著優於大量取樣。

限制（以原論文為準）

  • 需要能執行程式的環境：回饋很大程度依賴「跑得動程式、拿得到執行結果」；不可執行或副作用強的場景較難套用。
  • 自我解釋的天花板來自模型本身：解釋與判斷都由同一個模型產生，若模型對某類 bug 本來就理解不足，橡皮鴨也叫不醒它。
  • 回合與成本取捨：雖比大量取樣省，但多回合的執行＋生成仍有成本；提升幅度會隨任務、回饋形式而異。

⑥ 在自我演化地圖的位置

回到 自我演化 Agent 綜述 的三維地圖，Self-Debug 落在最內圈：

模型中心（Model-Centric）→ 推理時演化（Inference-Based）→ 序列自我修正（Sequential Self-Correction）

它不改參數，純粹改變「模型怎麼想」：把「產出 → 批判 → 修正」做成一個推理時的迭代迴圈。在綜述的代表工作清單裡，它與 Self-Refine、Reflexion、CRITIC 並列於序列自我修正這一格——差別在 Self-Debug 特別聚焦程式領域，並用「執行結果＋橡皮鴨式自我解釋」作為回饋來源。

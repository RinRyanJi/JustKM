🔎 Stream of Search（SoS）搜尋流

論文《Stream of Search: Learning to Search in Language》怎麼實現 · 把整段「搜尋過程」序列化成語言，讓模型學會搜尋——而不只是背最佳解

論文導讀 Gandhi et al. 2024 結構化推理 · 模型中心演化

⓪ 一句話

Stream of Search：不要只餵模型「正確答案的最短路徑」，而是把整段搜尋過程——包含試錯、走進死路、回溯、剪枝——攤平成一串 token 的「搜尋流」，讓語言模型直接在這種資料上學。學到的模型會把「怎麼搜尋」內化成自己的能力，甚至能超越當初產生訓練資料的搜尋啟發式（heuristic）。

論文以 Countdown（一個湊數字的算術遊戲）為試驗場，從零訓練一個 250M 參數的小語言模型，證明「讓模型看見搜尋的全過程」比「只給最佳解」更能學會推理與自我修正。

① 想解決什麼

一般語言模型在推理任務上被訓練成只預測「最佳解路徑」——資料集裡都是漂亮、直達答案的正確步驟。問題是：

  • 沒學到「怎麼搜尋」。真正解難題需要探索多條路、發現此路不通、退回去換一條。這些「搜尋的動作」在最佳路徑資料裡通通被抹掉了。
  • 沒學到犯錯與回溯。模型從沒看過「錯了怎麼辦」，於是一旦第一步走偏就無法自我修正，只能一路錯到底。
  • 受限於示範者。只模仿最佳路徑，等於把上限鎖死在「產生這些路徑的求解器」身上，很難超越它。
核心痛點：「最佳解路徑」是搜尋的結果，不是搜尋的過程。只教結果，模型永遠學不會遇到沒看過的難題時該如何自己去找答案。

② 核心想法

既然缺的是「過程」，那就把整個搜尋過程本身當成訓練資料。SoS 的關鍵一步是：把一次搜尋（探索哪些狀態、算了什麼、哪裡失敗、從哪裡回溯、剪掉哪些分支）序列化（flatten）成一條連續的語言字串——這條字串就叫「搜尋流（stream of search）」。

作者把各種搜尋操作用一套統一的語言（unified language）表達，涵蓋：

  • 探索（exploration）：嘗試一個中間狀態 / 一次運算。
  • 回溯（backtracking）：此路不通，退回上一個可行的分叉點。
  • 剪枝（pruning）：判斷某分支沒希望，直接放棄。
  • 以及狀態評估、目標比對等其他步驟。
直覺：與其給學生看「標準解答」，不如給他看一位老手解題時的完整草稿紙——包含畫錯的、劃掉的、重來的。看多了草稿，學生自己也學會了「卡住時該怎麼想」。這就是把搜尋「語言化」的意義：搜尋不再是外掛的演算法，而變成模型 next-token 預測能力的一部分。

③ 怎麼實現 🔥

整條 pipeline 分三步：用符號搜尋造資料 → 序列化成 token 流 → 訓練語言模型；之後再用自我改進方法（APA / STaR）讓它超越示範者。

第 1 步 · 用符號搜尋產生「含錯誤與回溯」的軌跡

  • 用符號式（symbolic）搜尋演算法去實際解 Countdown 題目，過程中自然會探索、失敗、回溯——把這整段記錄下來，就是天然的「搜尋過程」資料。
  • 具體用了 BFS（廣度優先）與 DFS（深度優先）兩種搜尋策略，各自再由兩個啟發式函數（heuristic）引導，產生多樣化的搜尋軌跡當訓練集。
  • 刻意保留「不完美」：這些軌跡包含走錯、死路、回頭——正是最佳路徑資料所欠缺、而 SoS 想要的東西。

第 2 步 · 序列化為統一的 token 流

  • 把每條搜尋軌跡按時間順序攤平成一條字串：目前狀態、嘗試的運算、結果、與目標的比對、以及「回溯 / 剪枝」等操作，全部用前述統一語言寫成連續 token。
  • 這樣一來，「搜尋」被完全轉譯成語言模型熟悉的序列預測問題——模型只要學會預測下一個 token，就等於在學會下一步該探索、還是該回溯。
# 「搜尋流」的示意（非逐字，結構以原論文為準）
目標: 24  可用數字: [3, 5, 7, 11]
嘗試: 5 + 7 = 12   → 剩 [3, 11, 12]   離目標尚遠
嘗試: 3 * 11 = 33  → 剩 [12, 33]      超過，剪枝此分支
# ← 回溯到分叉點
回溯 → 剩 [3, 5, 7, 11]
嘗試: 11 - 7 = 4   → 剩 [3, 4, 5]
嘗試: 4 + 5 = 9    ...
...
找到: (11 - 5) * (7 - 3) = 24  ✓

第 3 步 · 在搜尋流上訓練語言模型

  • 從零訓練（from scratch）一個 GPT-Neo 架構、250M 參數的模型，context length 4096 token（要夠長才裝得下一整段搜尋過程）。
  • 訓練目標就是標準的語言模型預測——但因為資料是「搜尋流」而非「最佳路徑」，模型學到的是整套搜尋策略，而非單一答案。

第 4 步 · 用自我改進讓它超越示範者（APA / STaR）

預訓練後的 SoS 模型還能再自我提升：讓模型自己去解題、留下成功的搜尋流當新資料，用策略改進方法微調。論文用了兩種：

  • APA（Advantage-Induced Policy Alignment）：一種以優勢函數引導的策略對齊 / RL 式微調。
  • STaR（Self-Taught Reasoner）：讓模型產生自己的推理軌跡，篩出能得到正確答案的，再拿去微調——反覆迭代自我教學。
為什麼能超越 heuristic？示範者（BFS/DFS + heuristic）只是起點。一旦模型把搜尋能力內化，就能靠自我改進去解連任何一個原始 heuristic 求解器都解不出的題目——這正是「自我演化」的雛形。

④ 關鍵細節

Countdown 任務

  • 玩法：給定一組輸入數字（論文設定為 4 個）與一個目標數，用四則運算把數字組合起來湊出目標。
  • 限制：運算結果限定為非負整數（例如減法只在「大減小」時允許），確保搜尋空間乾淨、可驗證。
  • 為何選它：搜尋空間夠大、需要真正的探索與回溯，又能自動、明確地驗證對錯——是研究「搜尋能力」的理想沙盒。

學到「內化的搜尋策略」

  • 模型不是死背某條路徑，而是學會在遇到新題目時動態地探索、評估、回溯——搜尋成為模型內部能力，而非外部演算法。
  • 因為訓練資料混合了 BFS/DFS 與不同 heuristic，模型等於吸收了多種搜尋策略的綜合，而不侷限於單一策略。

能超越產生資料的 heuristic

  • 只模仿最佳路徑的模型，上限被示範者鎖死；SoS 因為學的是「過程」，經 APA/STaR 自我改進後能解出原始 heuristic 解不了的題。
  • 這說明「看見搜尋全貌 + 自我改進」的組合，可以把模型能力推到超過它的老師。

⑤ 效果與限制

主要結果

比較結果
SoS 預訓練 vs. 只學最佳路徑搜尋準確率提升約 25%（看見搜尋過程 > 只看最佳解）
SoS + APA / STaR 自我改進解出36% 先前無解的題目，其中包含任何一個 heuristic 求解器都解不出的題目
兩個數字的意義：25% 證明「過程 > 結果」這個核心假設；36% 證明模型真的超越了示範者，具備自我演化的潛力。

限制（以原論文為準）

  • 單一、可驗證的領域：實驗集中在 Countdown 這類規則明確、對錯可自動驗證的任務；能否無痛遷移到開放式、難以驗證的真實推理任務，仍待驗證。
  • 小模型、從零訓練：用的是 250M 的小模型專門在此任務上訓練，與大型通用 LLM 的行為未必等價。
  • 依賴符號求解器造資料：需要能寫出符號搜尋 + heuristic 來產生軌跡，換到沒有現成求解器的領域時，資料生成本身就是挑戰。
  • context 長度成本：把整段搜尋攤平成 token 會很長（4096），較複雜的問題可能超出可行的序列長度。

⑥ 在「自我演化」地圖上的位置

回到本站的自我演化 Agent 綜述地圖，Stream of Search 落在模型中心演化（Model-Centric）這一支：

  • 模型中心 → 推理時 → 結構化推理。SoS 與 Tree of Thoughts、Language Agent Tree Search 同屬「把思考展開成樹 / 圖 / 搜尋」的結構化推理路線——差別在 SoS 把搜尋語言化並寫進權重，讓搜尋成為模型內生能力，而非推理時外掛的演算法。
  • 也橫跨到訓練時演化。第 4 步的 APA / STaR 把它連向「離線合成自演化」——模型自己造搜尋資料、自我微調、超越示範者，正是自我演化的核心迴圈。
在綜述表格中，Stream of Search 就被列在② 模型中心演化 → 推理時 → 結構化推理那一格。它是「讓模型本身變強」這條路上，關於如何學會搜尋的代表性一步。

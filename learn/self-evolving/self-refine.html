♻️ 自我精修 Self-Refine

同一個模型三種角色：生成 → 自我回饋 → 依回饋修正，反覆迭代 · 不需再訓練 · Madaan et al., 2023（NeurIPS 2023）

📑 目錄 · 重點在「怎麼實現」

⓪ 一句話

Self-Refine＝讓同一個 LLM「自己改自己的作業」：先生成一個答案，再叫它對自己的答案提出具體、可行動的回饋，然後依這份回饋改寫，如此反覆——完全不需要額外訓練、不需要外部工具或監督，只靠 few-shot prompt 就能讓輸出品質平均提升約 20%。

直覺：對一個夠強的模型來說，「挑出並修好一份既有解答的毛病」通常比「一次就寫出完美解答」容易。Self-Refine 把這個直覺變成一個可以套在任何生成任務上的迴圈。

① 想解決什麼

大型語言模型的標準用法是「一次生成（single-shot）」：給 prompt、拿一段輸出、結束。但這種一次到位常常品質不足——程式碼可以更快、對話可以更貼切、文字可以更通順——而人類寫作本來就是草稿 → 檢視 → 修改的循環。

要讓模型也具備這種「改稿」能力，過去的做法多半要付出昂貴成本：

  • 另外訓練一個修正/獎勵模型（需要標註資料、需要微調算力）；
  • 依賴外部監督或領域工具（編譯器、單元測試、人類回饋）來告訴模型哪裡錯。
Self-Refine 的問題設定很直接：能不能完全不再訓練、也不靠外部監督，只用「同一個現成模型 + 提示」就把單次輸出反覆改好？

② 核心想法

讓同一個凍結的模型在迴圈裡輪流扮演三種角色，不換模型、不改權重：

角色做什麼對應提示
生成者 Generator對任務先產出一個初版答案init prompt
回饋者 Feedback檢視自己剛才的答案，指出具體、可行動的缺點feedback prompt
修正者 Refiner拿著回饋把答案改寫成更好的版本refine / iterate prompt

然後把「回饋 → 修正」當成一個可重複的迭代迴圈：改完再回饋、再改……直到覺得夠好或到達次數上限。

關鍵一步：帶著歷史迭代。每次要模型回饋/修正時，都把先前的答案與回饋一起接回 prompt，讓模型「看得到自己走過的路」，才能從過去的錯誤學習、不重複犯同樣的毛病。

③ 怎麼實現（重點）

整體迴圈

只需要三段 few-shot 提示（init、feedback、refine），演算法用最樸素的迴圈即可：

# 三段提示都用 few-shot 範例寫成，不需訓練，不改權重
y0 = M(p_init  ⊕ x)                      # 生成：對輸入 x 產出初版
for t in range(0, max_iters):
    fb = M(p_feedback ⊕ x ⊕ y_t)          # 回饋：對自己的 y_t 挑毛病（要具體可行動）
    if stop(fb):                          # 停止條件：回饋顯示「已夠好 / 無需再改」
        break
    y_next = M(p_refine ⊕ x ⊕ [歷史 y、歷史 fb] ⊕ fb)   # 修正：帶著歷史一起改寫
    y_t = y_next
return y_t

整段流程自始至終都是同一個 M（例如 GPT-3.5 / GPT-4），差別只在餵進去的提示不同。

feedback 提示怎麼設計

  • 要「具體且可行動（specific & actionable）」：不是只說「這段可以更好」，而是指出哪一處、為什麼不好、該往哪個方向改。這是全法成敗的樞紐（見 §④）。
  • 可帶分數/多面向：對某些任務（如程式最佳化、對話），回饋會就多個維度打分或逐點列出問題，讓後續修正有明確靶子。
  • 用 few-shot 示範「好的回饋長什麼樣」：在 prompt 裡放幾個「答案 → 高品質回饋」的範例，模型就照著產出同樣風格、同樣顆粒度的批評——這就是它「不用訓練」也能給出好回饋的原因。

refine 提示怎麼設計

  • 輸入 = 原任務 x + 前一版答案 + 剛剛那份回饋（外加先前迭代的歷史），要求模型輸出「已根據回饋改進」的新版本。
  • 同樣用 few-shot 示範「拿到這種回饋後，答案該怎麼改」，把「修正」這個動作教給模型。
  • 因為歷史被接進 prompt，模型是在累積的脈絡上改，而不是每輪從零重寫。

停止條件

  • 設定最大迭代次數（實驗中通常是少數幾輪，例如上限約 4 輪；到頂就停）。（以原論文為準）
  • 回饋自己喊停：讓模型在回饋裡輸出一個「無需再修改 / 已達標」的訊號（例如一個停止標記或滿分），偵測到就跳出迴圈。
  • 兩者取先到者；也可搭配任務本身的品質門檻。

為什麼「不需額外訓練」

全部靠 few-shot in-context 提示。生成、回饋、修正三種能力都是用「幾個範例」在 prompt 裡示範出來的，模型權重完全不動，也不需要標註資料、獎勵模型或微調。這使 Self-Refine 可以即插即用在任何夠強的現成 LLM 上。

④ 關鍵細節

為什麼 feedback 一定要「具體可行動」

論文反覆強調：回饋的品質，比迭代的次數更決定成敗。

  • 籠統回饋＝空轉。若只說「再改好一點」，模型沒有明確靶子，修正就只是隨機擾動，甚至越改越差。
  • 可行動回饋＝可執行的修改指令。指名「這個變數命名不清楚→改成 X」「這段迴圈可用雜湊表加速」，修正者才知道具體要動哪裡。
  • 實務上，把回饋寫得更具體，收益大於單純多跑幾輪迴圈。

迭代次數：邊際遞減

  • 多數增益發生在前一、兩輪；之後往往邊際遞減，甚至有「改過頭」的風險。
  • 因此實務上幾輪就夠——搭配停止訊號，避免無意義地一直改。

對基底模型的要求

Self-Refine 吃「模型本身的能力」。它能成立的前提是：模型有能力可靠地評判自己的輸出。模型越強（GPT-4 > GPT-3.5），自我回饋越準、增益越大；反過來，若模型連對錯都判斷不好，這套迴圈就失靈（見 §⑤）。

⑤ 效果與限制

在哪些任務有效

論文在七類生成任務上測試，涵蓋對話、程式、文字風格、推理與受限生成：

任務Self-Refine 帶來的改善（示例）
對話回應生成人類偏好度大幅上升（約 25% → 75%，GPT-4）
程式最佳化（PIE）最佳化率明顯提升（約 +8.7，GPT-4）
程式可讀性改寫可讀性明顯提升（約 +13.9，GPT-4）
情感風格轉換（Yelp）文字品質/偏好度提升（約 +21.6）
受限生成（CommonGen）更能滿足約束、更通順
縮寫生成（Acronym）更貼切、更好記
數學推理（如 GSM8K）提升有限（見下方限制）

整體而言，跨任務平均約 20% 的相對提升，且完全不需要額外訓練。數值與各任務指標以原論文為準。

限制：對「弱回饋」任務效果有限

  • 數學等有唯一正解的推理任務是罩門：模型常常看不出自己算錯了——當它無法可靠判斷答案對錯時，產出的回饋也不可靠，「回饋 → 修正」就無從發揮，甚至可能把對的改錯。
  • 強烈依賴基底模型的自評能力：弱模型給不出具體可行動的回饋，這套方法收益就小。
  • 沒有外部真值校準：因為刻意不用編譯器/測試/人類等外部訊號，遇到需要客觀驗證的任務，天花板受限於模型「自己覺得對不對」。
  • 需要多次呼叫模型，推理成本較高；且要為每個任務準備 few-shot 的 init / feedback / refine 範例。
啟示：Self-Refine 最適合「開放式、好壞是程度問題」的生成任務（對話、寫作、程式風格/效率）；對「有明確對錯、但模型難以自我驗證」的任務，需要引入外部回饋（如工具、測試）或更強的評判者才補得上——這也是後續 Reflexion、CRITIC、Self-Debug 等工作接手的方向。

⑥ 在自我演化地圖的位置

把 Self-Refine 放回本站的自我演化 Agent 綜述地圖：它屬於最內圈的「模型中心演化」。

  • 模型中心（Model-Centric） → 推理時演化（Inference-Based）：不改任何參數，只改「怎麼想」。
  • 再細分到序列自我修正（Sequential Self-Correction）：產出 → 批判 → 修正 的迭代，正是本頁主題。
  • 同一格的鄰居：Self-Debug、Reflexion、CRITIC——Self-Refine 是這條線最基礎、最純粹的「零訓練、純提示」版本，後續工作多在它之上加入外部回饋、記憶或語言強化。
一句話定位：Self-Refine 是「自我演化」最輕量的一種——不動權重、不靠環境，只靠模型在推理當下反覆自我批改。 想看它在整張地圖的位置，見 ② 模型中心演化 · 序列自我修正。

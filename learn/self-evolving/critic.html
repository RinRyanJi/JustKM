🔧 CRITIC：工具互動式批判的自我修正

CRITIC: Large Language Models Can Self-Correct with Tool-Interactive Critiquing · Gou et al., 2023（ICLR 2024）· arXiv 2305.11738

序列自我修正 工具互動 Verify → Correct 迴圈
📑 目錄

⓪ 一句話

一句話：與其讓大型語言模型「閉著眼睛自我反省」，不如讓它像人一樣去用工具查核——呼叫搜尋引擎、程式直譯器、毒性偵測 API 拿到客觀外部回饋，再據此修訂自己的答案。這就是 CRITIC（Self-Correcting with Tool-Interactive Critiquing）。

CRITIC 不需要重新訓練、不需要額外標註資料，只靠少樣本 in-context prompting，就能在問答、數學、除毒三類任務上一致提升凍結模型（如 ChatGPT）的表現。它的核心主張很銳利：純靠模型內省的自我修正並不可靠，真正管用的是「有外部工具當裁判」的批判。

① 想解決什麼

LLM 常常會幻覺捏造事實、寫出有錯的程式碼、產生冒犯性內容。一個直覺的修法是「讓模型自己檢查自己」——先產出答案，再叫它批判、然後修正。但這條路有個致命弱點：

純靠模型自我批判並不可靠，而且容易「自我強化錯誤」。模型本來就不知道答案哪裡錯（否則第一次就不會錯），要它憑同一套內部知識當自己的裁判，往往只是把原本的偏誤重講一遍，甚至把原本正確的答案改壞。

作者用實驗把這點講死：把外部搜尋工具拿掉後，問答任務的提升幾乎歸零、甚至反轉——模型「靠自己」對事實類任務的自我檢核能力，近乎無用。問題因此變成：要從哪裡取得模型「自己造不出來」的可靠回饋訊號？

② 核心想法

答案來自觀察人類怎麼做事：人不會純靠腦補來確認事情——查事實會用搜尋引擎、debug 會跑直譯器、拿不準用語會查工具。CRITIC 把這個習慣搬給 LLM：

核心想法：讓 LLM 與外部工具（搜尋引擎、程式直譯器、專用 API）互動，用工具回傳的客觀證據去驗證自己的輸出，再據此修正。批判的價值在於「工具告訴模型一件它本來不知道的事」，而不是指望模型變成可靠的自我稽核者。

可以把 CRITIC 寫成一個簡單的複合函數：

output* = CRITIC(x)  =  correct( x , verify(x) )

# verify(x)：把候選輸出 x 丟給外部工具，取得客觀回饋（證據 / 錯誤訊息 / 分數）
# correct(x, feedback)：模型讀回饋，改寫出更好的輸出
# 再把 output* 當成新的 x，重複這個迴圈直到夠好或達上限

關鍵不在於模型「更會反省」，而在於把批判接地（grounding）到一個模型無法偽造的外部訊號上。這使 CRITIC 與只靠模型自身回饋的 Self-Refine 等方法形成對比。

③ 怎麼實現（Verify → Correct 迴圈）

CRITIC 是一個推理時（inference-time）的流程，不改模型參數，全靠 few-shot 示範教模型如何呼叫工具、如何讀回饋。一輪迭代分三步：

單輪三步驟

  1. ① 產出初稿（Generate）：模型先用自己的內部知識，對輸入 x 產生一個候選答案 ŷ。
  2. ② 工具互動式驗證（Verify / Critique）：模型主動生成對工具的呼叫（例如一段搜尋查詢、一段要執行的程式、一次 API 請求），拿回客觀回饋——檢索到的證據、直譯器的輸出或錯誤訊息、毒性分數等；再結合回饋寫出一段批判（critique），指出哪裡可能有問題。
  3. ③ 依回饋修正（Correct）：模型讀進批判與工具回饋，產出修訂後的答案 ŷ'。

迭代直到收斂

把修訂後的答案當作新的候選，重複「驗證 → 修正」。論文回報大約在三輪修正內就能取得有效提升；實務部署常在 1–2 輪批判就收斂。因為迴圈可能過度編輯或來回震盪，需要一個停止準則——固定迭代預算，或用工具回饋達到某個品質門檻就停。

# CRITIC 的 Verify→Correct 迴圈（示意）
y = LLM.generate(x)                         # ① 初稿
for step in range(MAX_ITERS):               # 停止準則：迭代上限
    call     = LLM.propose_tool_call(x, y)  # ② 模型自己決定怎麼查
    feedback = TOOL.run(call)               #    搜尋/直譯器/API 的客觀回饋
    critique = LLM.critique(x, y, feedback)
    if is_good_enough(critique, feedback):  # 門檻式停止：已無問題就收工
        break
    y = LLM.correct(x, y, critique, feedback) # ③ 依回饋改寫
return y
類比：這正是「人拿著工具查核」的流程——寫完先跑一次程式看報錯、講完事實先 Google 一下、發文前先過一遍敏感詞偵測，然後才據此改稿。CRITIC 把這個「用工具核對再改」的動作變成模型可反覆執行的迴圈。

④ 關鍵細節

為何外部回饋勝過純內省

CRITIC 最重要的實證是一個消融（ablation）：拿掉外部工具、只讓模型自我批判，問答的提升幾乎歸零甚至變負。原因是自我修正要成立，得先「知道自己錯了」——但對事實與計算類任務，模型的錯誤恰恰源於它不知道正確資訊，用同一套內部知識當裁判無法補上這個缺口。工具提供的是模型無法偽造、且獨立於模型信念的訊號，這才是提升的真正來源。

一句記憶點：CRITIC 之所以有效，是因為工具告訴模型一件它本來不知道的事，而不是模型突然變成可靠的自我稽核者。

哪些工具對哪類任務

任務類型外部工具工具提供的客觀回饋
自由形式問答
（開放領域 QA、事實查核）		搜尋引擎 / 搜尋 API檢索到的相關網頁與證據，用來核對事實宣稱是否成立
數學程式合成
（數理推理）		Python 程式直譯器執行結果、例外/錯誤訊息，用來抓出計算與程式邏輯錯誤
毒性降低
（內容除毒）		毒性分類器 / 內容審核 API毒性機率分數，指出哪段內容需要改寫得更無害

三類任務都遵循同一個 verify → correct 骨架，差別只在換哪個工具當裁判、以及怎麼把工具回饋轉成批判。這種「換工具即換任務」的模組化，是 CRITIC 能一套框架跨多領域的原因。（工具的具體版本以原論文為準）

⑤ 效果與限制

效果

把 CRITIC 套在 ChatGPT 等凍結模型上，三類任務都一致提升：

任務回報提升
開放領域問答（3 個資料集平均）+7.7 F1 分數
數學推理（3 個基準平均）+7.0 個百分點 絕對增益
毒性降低毒性機率下降約 79.2%（最顯著的單項結果）

而且這一切不需訓練、不需標註，只靠 in-context 少樣本示範，屬於「開箱即用」的推理時增強。（各項數字以原論文表格為準）

限制

  • 強烈依賴工具品質。沒有可靠外部訊號時，模型可能認不出自己的錯，甚至把原本正確的答案改壞——效果的天花板由工具決定。
  • 需要停止準則。迴圈可能過度編輯或來回震盪，得靠迭代上限或品質門檻收斂。
  • 不是萬用。對「沒有好工具可查」的主觀 / 開放式任務，CRITIC 的優勢會收斂；它擅長的是有客觀可驗證答案的任務。
  • 成本與延遲。每一輪都要呼叫工具並多次推理，比單次生成貴。

⑥ 在「自我演化地圖」的位置

對照本站自我演化 Agent 綜述導讀的三大維度，CRITIC 落在最內圈：

模型中心（②）→ 推理時演化 → 序列自我修正
CRITIC 不改參數，靠「怎麼想」變強；具體是「產出 → 批判 → 修正」的序列自我修正路線，與 Self-Refine、Self-Debug、Reflexion 同列。它的獨特貢獻是把批判接地到外部工具，證明了序列自我修正要真正管用，往往需要外部訊號而非純內省。

順著地圖往外，CRITIC 也搭起通往環境中心演化（③）的橋：它所依賴的「搜尋、直譯器、API」正是「工具增強 / 環境回饋」的雛形——同一個直覺，後續被 ReAct、Voyager 等工作推廣成更完整的工具使用與環境互動。

⚙️ NavBot-EN01 的電子與韌體:SimpleFOC + 串級 PID 自平衡怎麼寫

前一篇「組裝篇」把輪腿機器人拼起來;這篇讀它的倉庫原始碼,看那顆「大腦」到底怎麼讓它站住。重點兩塊:電子系統用了哪些關鍵晶片(ESP32、無刷驅動 L6234、磁編碼 AS5600、IMU MPU6050),以及韌體怎麼用 SimpleFOC 控無刷馬達、再疊一整套串級 PID 做倒立擺自平衡。附真實的 PID 增益與接腳。

⓪ 一句話總結

這個倉庫是 NavBot-EN01 的完整工程檔:機構 STP、4 塊 PCB、韌體、工具全在裡面。韌體的核心是兩層:(1) 用 SimpleFOC 把兩顆無刷輪馬達變成「可以精準下扭力」的致動器;(2) 在上面疊一套串級 PID 控制器(車身角、角速度、速度、位置、偏航、側傾,外加一個自動零點估計與一個帶積分的綜合項),構成倒立擺自平衡。感測是 MPU6050(IMU)+ 兩顆 AS5600 磁編碼器(讀輪角),UI 用 WebSocket + JSON 的網頁。

和組裝篇的關係:這頁是 輪腿機器人組裝篇 的「讀原始碼」另一半——組裝篇講怎麼拼、這篇講那顆大腦的電子與控制怎麼運作。倉庫 fork 自 MuShibo/Micro-Wheeled_leg-Robot。數字(增益、接腳)引自倉庫原始碼,換版本會變。

② FOC:把無刷馬達變成「可精準下扭力」的致動器

自平衡要的不只是「轉」,而是「我要多少扭力、現在就要」。無刷馬達要做到這點得用 FOC(磁場導向控制)——即時知道轉子角度,把電流控在最有效的方向。倉庫用開源的 SimpleFOC 函式庫:

// 兩顆輪馬達:7 極對,各配一顆三相驅動(3PWM)
BLDCMotor motor1 = BLDCMotor(7);
BLDCMotor motor2 = BLDCMotor(7);
BLDCDriver3PWM driver1 = BLDCDriver3PWM(32, 33, 25, 22);
BLDCDriver3PWM driver2 = BLDCDriver3PWM(26, 27, 14, 12);

// 兩顆 AS5600 在兩條 I2C 上,給 FOC 當轉子角度回授
MagneticSensorI2C sensor1 = MagneticSensorI2C(AS5600_I2C);
MagneticSensorI2C sensor2 = MagneticSensorI2C(AS5600_I2C);

有了 FOC,上層的平衡控制器只要輸出「要多少力矩」,SimpleFOC 就把它變成正確的三相電流——這讓③的 PID 可以乾淨地只管「平衡」這件事。

③ 平衡大腦:一疊串級 PID(含真實增益)

這才是「它為什麼站得住」的本體。原始碼宣告了一整組 PID 控制器,從變數名與增益可以看出它是個串級(cascade)+ 狀態回授的倒立擺控制器:內層管角度/角速度(快、保持直立),外層管速度/位置(讓它不漂走),再加偏航(轉向)與側傾,最後用一個帶積分的綜合項收斂。

可調:原始碼用了 SimpleFOC 的 Commander,可以從序列埠即時改這些 PID 增益——這就是自平衡車最耗時的「調參」入口。

④ 自動零點與濾波:為什麼需要一個「零點估計」

倒立擺有個現實難題:真正的平衡角不等於你以為的 0°。重心因為裝配誤差、電池位置、腿姿而偏,machine 的「站直角度」會有個未知偏置。若把目標角寫死 0°,它會一直往一邊慢慢跑。

解法是 pid_zeropoint(P=0.002,很小、很慢)+ 低通濾波 lpf_zeropoint(Tf=0.1):用「輪子長期的移動趨勢」反推真正的平衡零點,緩慢修正目標角。輪子一直往前漂 → 代表零點估偏了 → 把目標角微調,直到輪子不再長期漂移。這等於讓機器人自己找到它的平衡點,不必人工校。另有 lpf_joyy(Tf=0.2,平滑搖桿)、lpf_roll(Tf=0.3)。

直覺:零點估計是「慢變量追蹤」——它不參與高速的保持直立,只在背景慢慢校正「直立到底是幾度」。這是自平衡車能長時間不漂走、免手調零點的關鍵小招。

⑤ 雙核 + 通訊:一核跑控制,一核跑網頁

ESP32 是雙核,原始碼有獨立的 cpu0_task——把即時控制(FOC + PID 迴圈)和通訊/UI分到不同核心,互不卡頓。通訊這塊:

  • 網頁 UI 走 WebSocket + JSON:網頁本身存在 flash,手機瀏覽器連上就是遙控器,用 ArduinoJson 收送狀態與指令;另有 WebServer、ble(藍牙)路徑。
  • WiFi 兩模式:AP(機器人當熱點,預設 navbot_en01-…、192.168.1.11)或 STA(連既有 WiFi);僅 2.4GHz。
  • 參數存 EEPROM:eeprom_util 把校正/設定寫進去,重開機還在。
為什麼要分核:自平衡的 FOC+PID 迴圈必須穩定高速、不能被 WiFi/網頁的忙碌拖慢;把它釘在一個核心上跑,是嵌入式即時控制的常見且正確做法。

⑥ 表情:GIF → bin → SPIFFS(順便學 ESP32 檔案系統)

它臉上會演表情。做法是把 GIF 轉成機器人能播的格式、存進 ESP32 的檔案系統:

  1. 用 Tools/Gif_to_Bin 裡的 gif_to_bin.py:python gif_to_bin.py yourFile.gif → 產生 yourFile.bin。
  2. bin 檔上傳到 ESP32 的 SPIFFS 分區(所以建置時要改分區方案,留空間給表情檔)。
  3. 上傳工具用 arduino-esp32fs-plugin——但 Arduino IDE 2 不支援外掛,作者改用 IDE 1 上傳;上傳時的分區方案要和燒錄時一致。
一個真實的坑:「IDE2 不支援檔案系統上傳外掛」是很多人卡住的地方。要嘛裝 IDE1 專門上傳 SPIFFS,要嘛用新的上傳方式;分區方案前後不一致也會讓表情檔讀不到。

⑦ 建置與校正流程

  • 環境:Arduino IDE 2;開發板管理員裝 esp32 v2.0.3;選 ESP32 Dev Module。
  • 函式庫:用 Src/libraries 內的 ZIP 逐一加入(ArduinoJson、WebSocket 等);另從函式庫管理員裝 Queue。
  • 分區:改分區方案(SPIFFS 存表情檔)。
  • 編譯:第一次可能很久——作者最長 24 分鐘。
  • 伺服校正:左腿伺服 ID=1、右腿 ID=2;全蹲到機械極限的校正值 = 2048;用 FEETECH(FD)除錯軟體設定。
  • 上電:電池 XH2.54 → 紅燈(通電)→ 輪子 FOC 初始化(輪/腿會動)→ 藍燈(電量足)→ 按 EN 重啟 → 連 WiFi → 192.168.1.11 → 扶穩、輪子輕觸地 → 按「Robot go!」站起來。

⑧ 重點 · 關聯 · 來源

七個帶得走的重點

  1. 倉庫=完整工程檔(機構 STP、4 PCB、韌體、工具);fork 自 MuShibo 的 Micro-Wheeled_leg-Robot。
  2. 關鍵晶片:ESP32 + L6234(無刷驅動)+ AS5600(磁編碼)+ MPU6050(IMU)+ STS3032(腿伺服)。
  3. SimpleFOC 把無刷輪變成「可精準下扭力」,平衡層才能乾淨地只管平衡。
  4. 平衡是串級 PID:內層角/角速度(快)+ 外層位置/速度(慢)+ 偏航 + 側傾 + 綜合項 lqr_u(帶積分)。
  5. 自動零點(pid_zeropoint+LPF)讓它自己找平衡角、不漂走、免手調零點。
  6. 雙核:一核跑 FOC+PID 即時控制、一核跑 WebSocket+JSON 網頁 UI;參數存 EEPROM。
  7. 表情 GIF→bin→SPIFFS;IDE2 不支援上傳外掛要用 IDE1;首編最久 24 分鐘。

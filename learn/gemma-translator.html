⓪ 一句話總結

Gemma Translator 是一台「說一句、翻一句」的雙向語音口譯機,完全跑在一台樹莓派上、全程不連網。它把三件事串起來:Moonshine 把你說的話轉成文字(STT)、Gemma(E2B) 透過 LiteRT-LM 把文字翻成目標語言、再由 Moonshine 語音合成把譯文念出來(TTS)。

這個 repo(PiSugar/whisplay-gemma-translator)是 Jdaie Lin 把 Google 開源的 Gemma Translator 簡化成兩塊板子的版本:一台 Raspberry Pi 5(8GB),加一片 Whisplay HAT+(自帶觸控螢幕、雙麥克風、喇叭)。開機即用、資料不出裝置,支援阿拉伯語、英語、西語、日語、中文、韓語共 6 種語言互譯。

為什麼有意思:它是「端側小模型」浪潮一個很具體的落地——不是 demo 一個聊天框,而是把 聽→翻→說 整條語音鏈壓進一台巴掌大、離線、靠電池就能帶著走的裝置。旅行、無網環境、隱私敏感場合都用得上。

① 為什麼要「離線」語音翻譯

雲端翻譯 App 已經很好用,但「全在裝置上跑」換來的是四個雲端給不了的東西:

  • 沒網也能用:出國、山區、飛機上、展場——最需要翻譯的場合,往往正是沒有穩定網路的場合。
  • 隱私:對話不上傳、不留伺服器紀錄。醫療、法律、商務談判尤其在意。
  • 零延遲往返:不必等封包來回,延遲只取決於本機算力。
  • 零 token 費:推理成本一次性(買硬體),不是每句話計費。

難點也很直接:語音翻譯需要「三個模型接力」——聽(STT)、翻(LLM)、說(TTS),每一個單獨都不小,要三個一起塞進一台 8GB 記憶體的樹莓派還要即時,考驗的是「選對輕量模型 + 對的執行期」。這正是本專案值得拆解的地方。

可搭電池:PiSugar 本業是樹莓派電源/電池模組。配上電池,這台就是真正「帶著走、離線、掌心大」的口譯機——這也是它和「桌上跑個 demo」最不一樣的地方。

④ 三個模型、一條管線

核心資料流很乾淨:麥克風 → 聽 → 翻 → 說 → 喇叭,中間用 token 串流(SSE)把譯文邊翻邊吐:

← 左右滑動看完整圖 →
▲ 三個模型接力。後端維持一個「持續對話」的 Gemma session;譯文以 token SSE 串流,首字很快就出來,不必等整句翻完。

後端是一支 Python HTTP 伺服器,持有一個常駐的 Gemma 對話;前端用 SSE(Server-Sent Events)逐 token 接收譯文即時上螢幕。為了控管記憶體,對話 token 到 3200 會重置、上限 4096,並快取 2 份語音模型實例。

⑤ 為什麼用 Moonshine,而不是 Whisper

Moonshine 是 Useful Sensors 開源、專為邊緣裝置設計的語音辨識(也含語音合成)。在這種「即時、短句、跑在 Pi 上」的場景,它比 Whisper 更適合,關鍵在架構:

← 左右滑動看完整圖 →
▲ Whisper 對不足 30 秒的音訊會補零到 30 秒再跑完整編碼器;Moonshine 的推論成本隨實際音訊長度縮放,短句(對話常態)因此快得多。
可偷師的一點:選模型不是只看「誰的 benchmark 高」,而是看誰的架構貼合你的輸入分佈。對話是一堆短句,Whisper 的 30 秒固定視窗在這裡是純浪費;Moonshine 用「變長輸入」把這塊省下來,才換到即時體感。

⑥ Gemma E2B + LiteRT-LM:怎麼塞進 8GB

翻譯這關由 Gemma 的 E2B 變體負責,跑在 LiteRT-LM 上。兩個名詞要拆開理解:

E2B 的「E」= Effective(有效參數)

Gemma 端側系列用 E2B / E4B 命名,「E」代表 effective(有效)參數。靠 Per-Layer Embeddings(PLE) 等技術,E2B 的原始參數約 5B,但記憶體足跡壓到像傳統 2B 模型(約 2GB 等級即可跑),E4B 則約 8B 原始、跑起來像 4B。這就是它能進 8GB 樹莓派的關鍵——用「有效參數」而非「原始參數」來衡量它吃多少資源。

LiteRT-LM = Google 的端側執行期

LiteRT 是 Google 端側推論執行期(TensorFlow Lite 的新名),LiteRT-LM 是其專門跑大語言模型的版本。Google 透過 LiteRT-LM 直接發佈 Gemma 的端側包(E2B 檔約 2.58GB、E4B 約 3.65GB),讓它在 CPU/邊緣裝置上就能載入。

翻譯為什麼用 LLM 而不是傳統 NMT?因為 LLM 能一併吃下「語氣、上下文、口語」,而且一個模型涵蓋多語對(這裡 6 種語言互譯),不必為每個語言對各養一個翻譯模型。代價是它比專用 NMT 大——所以才需要 E2B 這種「有效參數」設計 + LiteRT-LM 這種端側執行期來配平。

⑦ 軟體與互動設計

技術棧

  • 前端:React + Vite,復古終端機(retro-terminal)風格,專為小螢幕設計。
  • 後端:Python HTTP 伺服器,持有常駐的 Gemma 對話,以 SSE 串流譯文。
  • 執行環境:Python 3.10+、Node.js 18+(建議 20 LTS);OS 為 Linux/macOS(裝置端用 Raspberry Pi OS / Debian)。

兩種對話版面

  • 橫向(預設):單一操作者,用空白鍵在「兩位對話者」之間切換方向。
  • 直向:兩位操作者各持一端,各自有專屬按鍵。
  • 快捷鍵:Z 鍵 push-to-talk(按著說)、方向鍵輪換語言、設定面板切換模式。

三種啟動方式

# 開發:啟動全部服務,UI 在 :5173
./start.sh
# 正式:編譯後資產,服務在 :3000
./start.sh --prod
# 家電式部署:systemd 服務 + Chromium kiosk 全螢幕 + 自動下載 LiteRT 模型
./deploy-pi.sh

設定存在瀏覽器 localStorage,可綁定不同 bind address/port,讓同一區網的其他裝置也能連上這台翻譯機。

⑧ 值得偷師的思路 / 來源

  1. 語音 AI 是「三個模型接力」,不是一個。聽(STT)、翻/答(LLM)、說(TTS)各選各的最佳輕量模型,用一條串流管線接起來——這是所有本地語音裝置的通用骨架。
  2. 選模型看「架構貼不貼你的輸入」。對話多是短句,Moonshine 的變長輸入省掉 Whisper 的 30 秒補零,才換到 sub-200ms 的即時感。benchmark 高不等於場景合適。
  3. 「有效參數」是端側的關鍵字。Gemma E2B 用 PLE 把 5B 原始參數跑成 2B 的記憶體足跡——評估端側模型時,要看它實際吃多少 RAM,而不是參數表上的數字。
  4. 執行期跟模型一樣重要。LiteRT-LM 這種端側 runtime,是「研究權重」變成「Pi 上跑得動」的橋(對照站內 CAM++/ONNX 的角色)。
  5. 做成「家電」而不是「demo」。deploy-pi.sh 把它變成插電即用、開機進 kiosk 的一台裝置——這一步才把技術變成產品。

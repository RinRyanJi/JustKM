① 這 repo 是什麼 / 適用工具

官方 · Microsoft .NETMITgithub.com/dotnet/skills ↗

定位：dotnet/skills 是 .NET 團隊官方維護的「core skills 與 custom agents 集合」，目標是讓各家 coding agent 在寫 C# / .NET 時，能遵循官方認可的做法，而不是憑訓練記憶亂寫。整個 repo 對齊 agentskills.io 的 Agent Skills 開放標準——每個 skill 就是一份 SKILL.md（含 frontmatter 的 name / description）加上參考文件與腳本，靠漸進揭露（progressive disclosure）在對的時機被 agent 載入。

結構：plugin → skills

repo 以「plugin（外掛）」為單位組織，路徑為 plugins/<plugin>/skills/<skill>/SKILL.md。一個 plugin 可含多個 skill；例如 dotnet-test 底下就有 20 多個測試相關 skill。本頁挑出 12 個核心 plugin 逐一拆解。repo 中另有 dotnet11、dotnet-template-engine、dotnet-test-migration、dotnet-experimental 等 plugin，本頁未逐一展開（以官方 repo 為準）。

適用工具

工具安裝方式（以官方 repo 為準）

和 anthropics/skills 教「Skill 長什麼樣」不同，dotnet/skills 是把 .NET 官方的『正確做法』沉澱成一條條可觸發工作流——每個 skill 的 description 就是它的觸發條件。以下逐 skill 看它「何時被叫出來、實際做什麼、有什麼值得偷師」。

② dotnet（核心 · C# 語言伺服器）

pluginskills/setup-local-sdk

① 用途：最基礎的 .NET plugin，提供「common .NET development skills」，並透過 .NET CLI 啟動一個 C# LSP（Language Server Protocol）伺服器，讓 agent 對 .cs 檔有真正的語意層理解（定義跳轉、診斷、型別資訊），而不是純文字比對。

② 何時觸發：任何 C# / .NET 專案的日常開發都會用到；setup-local-sdk skill 在需要「初始化本地開發環境」時被叫出。前提是機器已裝 .NET 10 SDK 且 dotnet 在 PATH 上。

③ 技術重點：把 Roslyn 系的語言伺服器接進 agent，等於把 IDE 級的程式碼智能餵給模型；setup-local-sdk 處理 SDK 版本、global.json 對齊等前置。

值得偷師：與其讓模型「猜」符號位置，不如接一顆 LSP 當 ground truth。任何語言的 agent 工作流都可套這招——先給語意層工具，再談生成。

③ dotnet-advanced

plugincsharp-scriptsdotnet-pinvokenuget-trusted-publishing

① 用途：針對「非標準、進階」場景的 .NET 技能，補足一般開發之外的深水區。

② 何時觸發 / 涵蓋的 skill：

  • csharp-scripts：撰寫/執行 C# 腳本情境（如 dotnet run app.cs 這類單檔腳本）。
  • dotnet-pinvoke：需要 P/Invoke 與原生（native）函式庫互操作時。
  • nuget-trusted-publishing：安全地發佈 NuGet 套件的可信發佈流程。

③ 技術重點：互操作邊界（marshalling、平台呼叫）、腳本化 C#、供應鏈安全的套件發佈——都是「標準教學少提、但正式專案會踩」的題目。

值得偷師：把「進階但低頻」的知識獨立成 plugin，平時不佔 context，需要時才載入——這正是漸進揭露的價值。

④ dotnet-data（Entity Framework Core）

pluginoptimizing-ef-core-queriescreate-datadriven-aspnetcore

① 用途：資料存取與 EF Core 的最佳實踐，核心是把「慢查詢」變快。

② 何時觸發：EF Core 查詢太慢、產生過多 SQL、round-trip 過多，或要新建一個 data-driven 的 ASP.NET Core 專案時。

③ 技術重點（optimizing-ef-core-queries 實際內容）：方法論是「先看產生的 SQL → 一次只套一個修法 → 再量測」，涵蓋：

  • N+1：用 Select 投影或 Include eager-loading 消除重複查詢，避免 lazy loading。
  • Cartesian explosion：多個 collection Include 造成列爆炸時，用 AsSplitQuery() 拆成多次查詢避免父資料重複。
  • 投影（projection）：用 Select 在資料庫端 reshape/aggregate，少 materialize 整個 entity。
  • compiled queries：熱路徑用 EF.CompileQuery / EF.CompileAsyncQuery 省掉每次 LINQ 轉譯開銷。
  • 分頁效率、未建索引的過濾條件等。
值得偷師：「量測 → 只改一處 → 再量測」的迭代紀律，避免一次塞一堆優化卻不知哪個有效——這是效能調校的正解，不限於 EF。

⑤ dotnet-diag（診斷 · 效能 · 崩潰分析）

pluginanalyzing-dotnet-performancedotnet-trace-collectdump-collectmicrobenchmarking…等 7 個

① 用途：效能調查、除錯、事件/崩潰分析的一整套診斷技能。

② 何時觸發 / 涵蓋的 skill：analyzing-dotnet-performance（效能反模式掃描）、dotnet-trace-collect（收集 trace）、dump-collect（收集 dump）、microbenchmarking（微基準）、clr-activation-debugging（CLR 啟動除錯）、android-tombstone-symbolication 與 apple-crash-symbolication（行動端崩潰符號化）。

③ 技術重點（analyzing-dotnet-performance 實際內容）：它掃描約 50 種 .NET 效能反模式，橫跨 async、記憶體、字串、集合、LINQ、regex、序列化、I/O。做法不是跑 runtime profiler，而是五步靜態分析：載入 reference（如 critical-patterns.md）→ 偵測程式碼訊號決定要查哪些類別 → 用 grep 配方做精確計數（例如搜 .Substring(、RegexOptions.Compiled）→ 依 Critical / Moderate / Info 分級 → 產出「熱路徑優先」的具體修法。

值得偷師：把資深工程師腦中的「反模式清單」變成 grep 可執行的偵測配方＋嚴重度分級，讓 agent 的效能審查可重現、有優先序，而不是每次憑感覺。

⑥ dotnet-msbuild（建置系統診斷與最佳化）

pluginbinlog-failure-analysisbuild-parallelismincremental-buildmsbuild-antipatterns…等 19 個

① 用途：MSBuild 建置的診斷、加速與現代化——這是 .NET 專案「建不起來 / 建太慢」的主場。

② 何時觸發 / 涵蓋的 skill（19 個，代表項）：

  • 診斷：binlog-generation／binlog-failure-analysis（產生並分析 binlog 找失敗根因）、build-perf-baseline／build-perf-diagnostics／eval-performance。
  • 加速：build-parallelism、incremental-build、msbuild-server。
  • 結構/衛生：directory-build-organization、property-patterns、item-management、target-authoring、extension-points、resolve-project-references、check-bin-obj-clash、copy-to-output-directory、including-generated-files。
  • 現代化：msbuild-modernization、msbuild-antipatterns。

③ 技術重點：把 MSBuild 這種「黑箱感很重」的建置系統拆成可觀測（binlog）＋可優化（平行/增量/server）＋可維護（Directory.Build.props 組織、target 撰寫）三層。

值得偷師：19 個細粒度 skill 各管一件小事——遇到建置問題時 agent 只載入最相關的 1～2 個，示範了「大主題拆小 skill」如何兼顧覆蓋率與 context 節省。

⑦ dotnet-nuget（套件與依賴管理）

pluginconvert-to-cpm

① 用途：NuGet 套件與依賴的管理。

② 何時觸發：convert-to-cpm——當一個多專案 solution 的套件版本散落各 .csproj、難以統一時，把它轉成 Central Package Management（CPM）：用單一 Directory.Packages.props 集中管理版本。

③ 技術重點：CPM 是官方推薦的依賴治理做法，能消除版本漂移、讓升級只改一處。（此 plugin 收錄 skill 較精簡，其餘套件相關進階題目見 dotnet-advanced 的 nuget-trusted-publishing；以官方 repo 為準。）

值得偷師：「版本集中化」是大型 monorepo 的關鍵治理動作，把它做成一鍵重構 skill，避免人手逐檔改漏。

⑧ dotnet-upgrade（框架升級與相容性）

pluginmigrate-dotnet9-to-dotnet10migrate-dotnet10-to-dotnet11migrate-nullable-referencesdotnet-aot-compat…等 6 個

① 用途：把專案系統化升級到新版 .NET，並解掉沿路所有 breaking change。

② 何時觸發 / 涵蓋的 skill：逐版升級（migrate-dotnet8-to-dotnet9、migrate-dotnet9-to-dotnet10、migrate-dotnet10-to-dotnet11）、啟用可空參考型別（migrate-nullable-references）、AOT 相容性（dotnet-aot-compat）、Thread.Abort 遷移（thread-abort-migration）。

③ 技術重點（migrate-dotnet9-to-dotnet10 實際內容）：不靠 Upgrade Assistant，而是六步手動流程：評估專案（找出 build/test 指令、確認 SDK、判斷用到哪些技術面）→ 改 TFM（net9.0 → net10.0、套件升到 10.0.x、解 NU1510 等）→ 修 build 錯誤與 source-incompatible 變更（C# 14 的 field/extension 關鍵字、SYSLIB 過時警告、ASP.NET Core／EF Core／密碼學 API 變動）→ 處理行為變更（SIGTERM、BackgroundService 執行緒、SQLite DateTime offset 等）→ 更新基礎設施（Dockerfile Debian→Ubuntu、CI 的 global.json）→ 驗證（clean build、跑測試、必要時容器化、安全審查）。每一步都夾帶增量編譯檢查。

值得偷師：升級不是「改個版號」而是「評估→改→修編譯→修行為→修基建→驗證」的分層流程，且每步都建置驗證。這份 checklist 化的升級劇本，是把易漏的遷移知識固化下來的範本。

⑨ dotnet-maui（跨平台 App）

plugindotnet-maui-doctormaui-shell-navigationmaui-data-bindingmaui-collectionview…等 8 個

① 用途：.NET MAUI 跨平台（iOS / Android / Windows / macOS）App 開發與環境設定。

② 何時觸發 / 涵蓋的 skill：環境健檢 dotnet-maui-doctor，以及 MAUI 常見主題：maui-app-lifecycle、maui-shell-navigation、maui-data-binding、maui-collectionview、maui-dependency-injection、maui-safe-area、maui-theming。

③ 技術重點（dotnet-maui-doctor 實際內容）：跨 macOS/Windows/Linux 驗證整套 MAUI 環境——.NET SDK、workloads（maui/android/ios）、Microsoft OpenJDK、Android SDK、Xcode、Windows SDK——然後自動修復缺件並重驗，最後建一個測試專案確認端到端可用。關鍵設計是所有版本需求都從 NuGet API 動態查（讀 WorkloadDependencies.json），絕不寫死，隨工具鏈演進自動保持正確。

值得偷師：「環境需求動態查、不寫死」＋「修完再驗、建測試專案作煙霧測試」——這讓一個環境診斷工具不會隨版本更新就過期。

⑩ dotnet-ai（AI / ML 技術選型）

plugintechnology-selection

① 用途：在 .NET 8+ 應用中「選對 AI/ML 技術並落地」——涵蓋從傳統 ML 到 LLM 編排再到本地推論的全光譜。

② 何時觸發（technology-selection 的 description）：要在 .NET 專案加入 AI/ML 功能、需在 ML.NET、Microsoft.Extensions.AI、Microsoft Agent Framework、GitHub Copilot SDK、ONNX Runtime、OllamaSharp 之間做技術選型時。

③ 技術重點：

  • 傳統 ML（ML.NET）：分類、迴歸、分群、異常偵測、推薦——結構化資料、可重現、確定性。
  • LLM 整合：以 Microsoft.Extensions.AI 作 provider-agnostic 的 chat／embedding 抽象層；文本生成、摘要、推理。
  • RAG / 向量檢索：Microsoft.Extensions.VectorData.Abstractions 搭配向量資料庫連接器（Azure AI Search、pgvector、Qdrant、Redis、Milvus、MongoDB、Pinecone、SQL 等）。
  • Agentic / 本地推論：tool calling 多步推理、ONNX Runtime 自訂模型、OllamaSharp 本地模型。
核心判準（原文）：「Do NOT use an LLM for tasks that ML.NET handles well（表格資料分類、迴歸、分群）——LLM 對這些任務更慢、更貴、且非確定性。」另外它明確標註 Semantic Kernel 已被新抽象層取代（deprecated）。
值得偷師：官方直接教你「什麼時候不要用 LLM」。一個好的 AI skill 的價值往往在於劃清邊界、給選型判準，而不是無腦推 LLM。

⑪ dotnet-aspnetcore（Web API / 服務）

plugindotnet-webapiminimal-api-file-uploadconfiguring-opentelemetry-dotnetconvert-blazor-server-to-webapp

① 用途：用 ASP.NET Core 建結構良好的 HTTP API 與服務。

② 何時觸發 / 涵蓋的 skill：dotnet-webapi（建 Web API 端點）、minimal-api-file-upload（minimal API 檔案上傳）、configuring-opentelemetry-dotnet（可觀測性/OpenTelemetry）、convert-blazor-server-to-webapp（Blazor Server 轉新 Web App 模型）。

③ 技術重點（dotnet-webapi 實際內容）：強調正確的 HTTP 語意與可測試架構——

  • controller-based 或 minimal API 擇一，不混用。
  • DTO 用 immutable sealed record＋XML 註解豐富 OpenAPI；不直接曝露 domain entity。
  • 正確狀態碼（POST → 201、DELETE → 204、找不到 → 404）。
  • .NET 9+ 用內建 OpenAPI，拒用 Swashbuckle。
  • 全域例外處理回傳 RFC 7807 Problem Details；service 層以 interface 注入以利測試。
  • 時間用 DateTimeOffset、enum 以字串序列化（JsonStringEnumConverter）、每個端點都帶 CancellationToken；附 .http 檔手動測試。
值得偷師：skill 明確寫出「不涵蓋什麼」（通用 C#、EF 優化、gRPC、SignalR 各有專屬 skill）——清楚的邊界讓觸發更精準，也避免和別的 skill 打架。

⑫ dotnet-blazor（互動式 Web 元件）

plugincreate-blazor-projectplan-ui-changeauthor-componentconfigure-auth…等 9 個

① 用途：Blazor 互動式 Web UI 的完整開發流程。

② 何時觸發 / 涵蓋的 skill（9 個）：從專案起手 create-blazor-project、規劃 UI 變更 plan-ui-change、撰寫元件 author-component、蒐集使用者輸入 collect-user-input、元件協作 coordinate-components、取送資料 fetch-and-send-data、設定驗證 configure-auth、支援預渲染 support-prerendering、JS 互操作 use-js-interop。

③ 技術重點：這組 skill 幾乎照著「真實開發一個 Blazor 功能的順序」排列——先 plan-ui-change 規劃，再 author-component 實作，涵蓋 render mode / 預渲染、元件間狀態協作、資料存取、驗證授權、與既有 JS 生態互通等 Blazor 特有的坑。

值得偷師：用「一條開發旅程」把 skill 排序（規劃→撰寫→接資料→加驗證→處理預渲染），agent 能照場景一步步取用，而不是丟一大坨參考文件。

⑬ dotnet-test（測試執行與品質分析）

pluginrun-testscoverage-analysiscrap-scoretest-gap-analysistest-smell-detection…等 22 個

① 用途：不只是「跑測試」，而是一整套測試品質工程——執行、涵蓋率、測試異味、可測性、風險評分。

② 何時觸發 / 涵蓋的 skill（22 個，分群）：

  • 執行/專案：run-tests、scaffold-dotnet-test-project、writing-mstest-tests、filter-syntax、test-tagging、mtp-hot-reload、platform-detection。
  • 涵蓋率/風險：coverage-analysis、crap-score、find-untested-sources、test-gap-analysis。
  • 品質/異味：assertion-quality、grade-tests、test-anti-patterns、test-smell-detection、test-analysis-extensions、code-testing-extensions、code-testing-agent。
  • 可測性重構：testability-obstacle、detect-static-dependencies、generate-testability-wrappers、migrate-static-to-wrapper。

③ 技術重點（crap-score 實際內容）：計算方法/類別/檔案的 CRAP（Change Risk Anti-Patterns）分數，公式 CRAP(m) = comp(m)² × (1 − cov(m))³ + comp(m)——複雜度平方、乘上未涵蓋率的立方，把「又複雜又沒測」的方法指數級標紅（<5 良好、5–15 尚可、15–30 需補、>30 緊急）。流程是 dotnet test（coverlet／MTP）收涵蓋率 → 數決策點算複雜度 → 從 Cobertura XML 抽每方法涵蓋率 → 計分排序。硬性規則：「Never estimate coverage」——收不到就回報失敗，絕不猜數字。

值得偷師：①把「該補哪裡的測試」變成可計算、可排序的單一風險指標（CRAP），讓 agent 有客觀優先序；②「拿不到真實數據就報錯、不編造」的紀律，正是可信賴 agent 的底線。

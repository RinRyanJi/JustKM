① 這個 repo 是什麼 / 怎麼安裝

精選技能包 · Jesse Vincent MIT GitHub ↗

官方定位：README 開宗明義說它是「a complete software development methodology for your coding agents」——一套完整的、給 coding agent 用的軟體開發方法論，建立在一組可組合的 skill 加上「確保 agent 真的會去用這些 skill」的初始指示之上。

它的核心信念是：agent 不該一接到需求就衝去寫程式，而該先退一步，問你到底想達成什麼，再走「設計 → 規格審查 → 實作計畫 → subagent 驅動開發（含兩階段審查）」的紀律化流程。整個 repo 本質上是把一位資深工程師的自律，轉寫成 agent 會照著做的規則。

② 測試與除錯

這三個 skill 是整套方法論的「品質地基」——它們共通的手法是把一句不可違反的鐵律放在最前面，逼 agent 在寫程式或宣稱完成之前先付出代價。

🧪 test-driven-development

①用途把 TDD 變成 agent 的預設反射：任何 feature 或 bugfix，先寫會失敗的測試，再寫實作。

②何時觸發「Use when implementing any feature or bugfix, before writing implementation code」——新功能、修 bug、重構、改行為一律適用；例外（丟棄式原型、生成碼、設定檔）需人類夥伴同意。

③做法重點核心是那條鐵律與 RED-GREEN-REFACTOR 循環：

THE IRON LAW：NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
  • RED：寫一個最小、聚焦單一行為的失敗測試（少 mock、用真實程式）。
  • Verify RED（強制）：跑測試，確認它是「fail 而非 error」，且失敗訊息如預期、是因為功能缺失而不是 typo。
  • GREEN：寫「剛好讓測試過」的最簡程式，不多做。
  • Verify GREEN（強制）：確認本測試過、其他測試也還過、輸出乾淨。
  • REFACTOR：綠燈後才去除重複、改名、抽 helper，並維持測試常綠。
值得偷師：「先看著測試失敗」這一步被列為 強制。事後補的測試「pass immediately, proving nothing」——一次就過的測試什麼都證明不了，這正是人類也常偷懶的地方。

🔍 systematic-debugging

①用途遇到 bug、測試失敗、非預期行為時，強制先做根因調查，不准直接丟修法。

②何時觸發「Use when encountering bugs, test failures, or unexpected behavior before proposing fixes.」尤其在有時間壓力、快速修法看起來很明顯、已失敗數次、或其實不懂問題時更要用。

③四階段根因分析

NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
  1. Root Cause Investigation：完整讀錯誤訊息與 stack trace、穩定重現、檢視近期改動、在元件邊界蒐證、把壞值往回追到源頭。
  2. Pattern Analysis：找到能動的相似程式，逐點比對「能動 vs 壞掉」的所有差異，理解依賴與假設。
  3. Hypothesis and Testing：提出單一、具體的假設，用最小、隔離的改動驗證；失敗就換假設。
  4. Implementation：先寫失敗測試，只實作一個針對根因的修法，驗證不弄壞其他測試。
值得偷師：Three strikes rule——同一個 bug 修三次都失敗，該質疑的是架構本身，而不是繼續打補丁。這條把「越修越亂」的死路直接封住。

✅ verification-before-completion

①用途禁止「沒有證據就宣稱完成」，把「Evidence before claims, always」變成收尾閘門。

②何時觸發在任何「成功 / 完成」宣稱之前、表達滿意之前、commit 或開 PR 之前、切換到下一個任務之前，都要先過驗證閘。

③五步驗證閘

NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE
  1. Identify：找出能證明你這句話的那道指令。
  2. Run：完整、重新地跑一次（不能拿舊輸出充數）。
  3. Read：讀完整輸出與 exit code。
  4. Verify：確認輸出真的支持你的宣稱。
  5. Only then：才做出宣稱，並附上證據。
值得偷師：它把「should / probably / seems」這類模糊避險詞、以及「Great! Done!」這種驗證前就先慶祝的語氣，都明列為紅旗。對 agent（和人）最有效的紀律，往往是先抓住語氣裡的破綻。

③ 協作與流程

這一組把「從一個念頭到合併進主幹」的完整開發流程拆成可交接、可審查的步驟。它們串起來就是 superpowers 的主幹：brainstorming → writing-plans → executing-plans / subagent-driven-development → code review → finishing-a-development-branch。

💡 brainstorming

①用途用蘇格拉底式對話，把模糊點子磨成「已核准的設計」後才動工。

②何時觸發任何創造性工作（新功能、新元件、加行為）開始之前。

③流程重點九步：探索專案脈絡 → 需要時才提供視覺輔助（mockup/圖）→ 一次問一個釐清問題 → 提 2-3 個方案含取捨與建議 → 分段呈現設計、逐段徵求核准 → 把設計文件寫到 docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md → 規格自我審查（找 placeholder／矛盾／模糊）→ 等使用者審核 → 只轉交給 writing-plans。

值得偷師：設有一道 Hard Gate——在拿到設計核准前，不准呼叫任何實作 skill、不准寫任何程式，「不論專案看起來多簡單」。因為「簡單」的專案最常藏著沒被檢查的假設。

📝 writing-plans

①用途把規格轉成「假設工程師對這 codebase 零背景」也能照做的逐任務實作計畫。

②何時觸發手上已有規格/需求、要做多步驟工作、還沒開始寫程式時。

③檢查點與結構計畫要有 header（功能名＋一句目標、架構概述、技術棧、來自規格的精確全域限制）；每個任務含檔案路徑、介面（吃什麼／產出什麼）、bite-sized 步驟：寫測試 → 跑（失敗）→ 實作 → 跑（通過）→ commit，而且要放真實程式碼區塊而非虛擬碼。存到 docs/superpowers/plans/YYYY-MM-DD-<feature>.md。

值得偷師：硬性禁止 placeholder——不准出現「TBD」「add validation」「handle edge cases」這種佔位字；自我審查時要主動搜這些紅旗字並清掉。把「計畫」逼到可以直接執行的顆粒度。

▶️ executing-plans

①用途在獨立 session 裡執行寫好的計畫，帶審查檢查點。

②何時觸發已有一份細到 bite-sized 的計畫、準備開跑時。

③流程與停損點先用 git worktree 開隔離工作區 → 讀完整計畫、批判性地找缺口並先跟夥伴確認 → 逐任務 in_progress → 照步驟做 → 跑驗證 → completed → 最後轉交 finishing-a-development-branch。遇到 blocker（缺依賴、測試失敗、指示不清）、計畫有重大缺口、或反覆驗證失敗就立即停。

值得偷師：「Never start implementation on main/master without explicit consent」——沒經明確同意，不在主幹上動工。以及「寧可問，不要用猜的硬闖障礙」。

🤖 subagent-driven-development

①用途用「每個任務派一個全新 implementer subagent」的方式執行計畫，並做兩階段審查。

②何時觸發已有完整計畫、任務多為獨立、且要留在當前 session 內完成時。

③兩階段審查 + fix loop核心公式：「Fresh subagent per task + task review (spec + quality) + broad final review」。每個任務：記下 BASE commit → 派 implementer（給它任務簡報路徑與回報檔路徑，不貼 session 歷史）→ 產 review 包、派 task reviewer（用 diff 檔而非 console 輸出），reviewer 同時卡規格符合度與程式品質兩關 → 需要就進 fix loop（最多 5 輪，1-3 輪叫回原 implementer，4-5 輪換更強模型的新 implementer）。全部完成後，再用最強模型做整枝 final review。

值得偷師：兩點很聰明。其一「Never pause between tasks」——一路把計畫跑完，只在 BLOCKED 或真正卡住時才停，避免碎片化。其二用 ledger + git log 當復原地圖：即使 context 被壓縮，commit 還在 git 裡，信任帳本勝過信任記憶。並依任務難度選模型（機械任務用便宜模型，架構與 final review 用最強模型）。

🧵 dispatching-parallel-agents

①用途面對 2 個以上「彼此獨立、無共享狀態」的任務時，並行派專門 subagent，保留自己的 context 做協調。

②何時觸發多個失敗散落在不同測試檔／子系統、每個問題能各自獨立理解、沒有共享狀態時；若失敗彼此相關則不要用。

③做法重點四步：辨識獨立領域 → 為每個 agent 寫聚焦任務（明確範圍、目標、限制、輸出格式）→ 在單一回應裡發出所有 dispatch 呼叫＝並行執行 → 讀摘要、確認無衝突、跑全套測試再整合。給 agent 的 prompt 要自足、含錯誤訊息與測試名，並明確限制如「Do NOT change production code」。

值得偷師：「Multiple dispatch calls in one response = parallel execution」——把並行的觸發方式講成一條可操作規則，而不是抽象概念；同時強調寧可具體（「Fix agent-tool-abort.test.ts」）也不要「Fix all the tests」這種空泛指令。

🌲 using-git-worktrees

①用途為功能開發建立隔離工作區，避免改動污染當前分支。

②何時觸發要開始一段會改動程式的工作、需要乾淨隔離時（executing-plans / subagent-driven-development 的第 0 步都會叫它）。

③流程重點信念是「Detect existing isolation first. Use native tools. Fall back to git. Never fight the harness.」——先偵測是否已隔離（比對 GIT_DIR 與 GIT_COMMON、用 --show-superproject-working-tree 防 submodule）；優先用平台原生工具（如 EnterWorktree／/worktree），不得已才手動 git worktree add；建立前先確認目錄已被 git-ignore，預設放 .worktrees/；接著自動裝依賴、跑一次基準測試確認乾淨。

值得偷師：「Never fight the harness」——先偵測環境已經幫你做了什麼，而不是無腦硬跑 git 指令。這對「同一套流程要跑在很多不同 agent runtime 上」特別重要。

📤 requesting-code-review

①用途在合併前派一個 code reviewer subagent 抓問題，信條是「Review early, review often」。

②何時觸發每個 subagent 任務完成後、大功能做完後、合併進主幹前必做；卡關、重構前、修完難纏 bug 後則建議做。

③做法重點取 BASE_SHA / HEAD_SHA → 用 code-reviewer.md 模板派通用 subagent，填入描述、預期功能、起訖 commit → 依嚴重度處理：Critical 立刻修、Important 前進前修、Minor 記錄待辦，並可用技術證據合理反駁。

值得偷師：理由講得很誠實：「reviewing the diff inline burns the context window you need to keep driving the work」——自己在主線讀 diff 會燒掉你要拿來推進工作的 context，所以外包給只拿到聚焦脈絡的 subagent。這是「context 就是預算」的具體管理法。

📥 receiving-code-review

①用途收到 review 意見時，用技術嚴謹取代「表演式同意」。

②何時觸發收到 review 回饋、準備動手改之前，尤其當回饋看起來不清楚或技術上有疑慮時。

③五步回應READ（讀完不急著反應）→ UNDERSTAND（用自己的話複述，不懂就問）→ VERIFY（對照實際 codebase）→ EVALUATE（判斷在此脈絡是否技術正確）→ RESPOND（技術性接受，或有理有據地反駁）。一次改一項、逐項測試。

值得偷師：明文禁止「You're absolutely right!」「Great point!」這類討好語。對外部 reviewer 要「skeptical but verify」——若建議會弄壞功能、缺乏完整脈絡、違反 YAGNI 或牴觸既有架構決策，就該反駁。用程式行動證明你懂，而不是嘴上附和。

🏁 finishing-a-development-branch

①用途實作完成、測試全綠後，決定如何把工作整合進 codebase。

②何時觸發實作完成、測試通過、要收尾整合時（executing-plans 與 subagent-driven-development 的終點）。

③流程重點「Verify tests → Detect environment → Present options → Execute choice → Clean up.」先跑全套測試，紅燈就停；偵測是一般 repo／具名 worktree／detached HEAD；確定 base branch（不確定就問）；提供選項（本地合併／推上去開 PR／保留分支）；本地合併後要在合併結果上再驗證測試；清理只刪 .worktrees/ 或 worktrees/ 底下的 worktree。

值得偷師：幾條保命規則——「只在使用者打出「discard」這個字時才刪工作」、未經授權不 force-push、合併結果測試失敗要先查清楚、保留 worktree 讓夥伴能對 PR 回饋繼續迭代。把「不可逆動作」全部上鎖。

④ 元層（skill 的 skill）

這兩個 skill 決定「skill 系統本身怎麼運作」：一個教 agent 何時該去用 skill，一個教你怎麼寫出真的有效的 skill。

🧭 using-superpowers

①用途建立最上層工作流：任何行動之前（包含問釐清問題、探索檔案）先叫出相關 skill。

②何時觸發對話一開始就適用——「Invoke relevant or requested skills BEFORE any response or action — including clarifying questions」。進入 plan mode 前，若還沒 brainstorm 就先叫 brainstorming。

③做法重點核心是一句強制令：「If a skill applies to your task, YOU DO NOT HAVE A CHOICE. YOU MUST USE IT.」——就算你覺得只有 1% 機率相關也要用。派工有優先序：流程 skill 先跑（brainstorming、systematic-debugging），再跑實作 skill。並列出十二種「我在找藉口不用 skill」的合理化紅旗（例如「這很簡單」「這 skill 太重了」）。覆寫優先序：使用者明講的直接指令 > skill > 預設行為。

值得偷師：它把「agent 明明有工具卻不用」這個真實失敗模式當成頭號敵人，用「你沒有選擇」的絕對語氣加上一張合理化清單來堵——這正是所有 skill 集合最容易失效的地方。

✍️ writing-skills

①用途建立、修改、驗證 skill；把「寫 skill」本身當成一種對流程文件做的 TDD。

②何時觸發「Use when creating new skills, editing existing skills, or verifying skills work before deployment」。判準：這技巧不直覺、會跨專案重用、適用面廣、別人也受益，才值得寫成 skill。

③做法重點同樣有鐵律：

NO SKILL WITHOUT A FAILING TEST FIRST
  • RED：先讓 subagent 在沒有這個 skill、且有壓力的情境下跑，記錄真實的失敗行為與它們用的合理化說詞。
  • GREEN：寫最小、只針對那些失敗的 skill，同情境再跑一次、驗證合規回來了。
  • REFACTOR：找出測試中冒出的新合理化，逐一加上明確反制，重測到「bulletproof」。

結構上，description 只能寫觸發條件（「Use when...」＋症狀關鍵字），不可摘要流程步驟——否則 agent 會照描述做而不去讀本文。常載入的 skill 控制在 200 字內，其餘 500 字內，重型參考另拆檔案。

值得偷師：「Skill Discovery Optimization」——把 description 當成搜尋觸發器來設計，塞進 agent 真的會搜的錯誤訊息、症狀（flaky、hanging）、同義詞、工具名；命名用動詞開頭（condition-based-waiting 而非 async-test-helpers）。等於把「怎麼讓 agent 找得到並用得對 skill」也工程化。

⑤ 整套值得偷師的地方

把 14 個 skill 拉高一層看，superpowers 反覆用了幾招，值得抄進任何團隊（含人類）的工作流：

  • 一句鐵律放最前面。TDD、debugging、verification、writing-skills 都用「NO … WITHOUT … FIRST」的全大寫鐵律當鉚釘，把最容易被跳過的那一步鎖死。
  • 先看它失敗。不論是測試（Verify RED）還是 skill（RED 基線），都要求先觀察沒有它時會怎麼壞——沒失敗過的東西不算驗證過。
  • Hard Gate 與停損點。brainstorming 的設計核准閘、executing-plans 的 blocker 停損、finishing 的「只認 discard 這個字」，把不可逆動作全部上鎖。
  • context 當預算管理。把 review、實作外包給拿到聚焦脈絡的 subagent，用 ledger + git log 當復原地圖，保護協調者自己的 context window。
  • 依難度選模型、能並行就並行。機械任務用便宜模型、架構與 final review 用最強模型；獨立任務在同一回應裡一次派出去。
  • 抓語氣裡的破綻。把「should/probably/seems」「You're absolutely right!」這些避險詞與討好語明列為紅旗——最有效的紀律常是先管住措辭。
一句話總結：superpowers 不是「更多提示詞」，而是把資深工程師的自律與流程紀律，逐條寫成 agent 沒得商量的規則。

🧰 mattpocock/skills 逐 skill 拆解

給真工程師的 skills，不是做秀——對治 AI agent 四大失敗模式：對齊、冗長、品質、架構退化

作者 Matt Pocock 授權 MIT Engineering 13 Productivity 7
📑 目錄
① 這 repo 是什麼 / 怎麼安裝 ② Engineering 工程類（13） ③ Productivity 生產力類（7） ④ 相關與來源

① 這個 repo 是什麼 / 怎麼安裝

定位：Matt Pocock（TypeScript 教學者、Total TypeScript 作者）維護的 agent skills 集合，副標「skills for real engineers」。核心主張是小而可組合的 skill，而非硬套的大框架——把多年工程經驗編成一條條能被 agent 觸發的工作流，專門對治 AI agent 的四大失敗模式：對齊（做錯需求）、冗長（廢話與過度輸出）、品質（測試與審查草率）、架構退化（模組越改越淺）。

怎麼安裝

# Claude Code（外掛市集）
claude plugins install mattpocock-skills
# 或在 session 內
/plugin install mattpocock-skills

# 其他 agent / 想動手改的人
npx skills@latest add mattpocock/skills

裝好後，每個 repo 跑一次 /setup-matt-pocock-skills，設定 issue tracker、triage 標籤與文件存放位置。許多 skill 會共用專案根目錄的 CONTEXT.md（領域詞彙表 / glossary）與 ADR。

兩種觸發方式

觸發方式意思典型例子
使用者觸發需你主動用斜線指令叫出（disable-model-invocation），模型不會自作主張grill-with-docs、implement、handoff
模型觸發模型讀 description 判斷情境後自動援引，也可手動叫tdd、diagnosing-bugs、code-review
下面每個 skill 標的觸發方式，以其 SKILL.md frontmatter 為準；repo 內容會更新，實際以官方 repo 為準。

② Engineering 工程類（13）

從「需求對齊」到「規格 → 票 → 實作 → 審查 → 除錯」的完整開發環，多數環節都把 grilling（逼問）與 domain-modeling（詞彙）當底層原件重複使用。

grill-with-docs

使用者觸發對齊 / 建領域模型
用途：用一場「毫不留情的訪談」把計畫或設計逼到清楚，同時邊談邊產出文件（ADR 與詞彙表）。
做法重點：本質是組合技——跑一場 /grilling 逼問，過程中掛 /domain-modeling 即時把談定的詞彙寫進 CONTEXT.md，值得記錄的決策生成 ADR。
值得偷師：把「澄清需求」和「留下文件」綁成同一動作——澄清完，glossary 與 ADR 也順手長出來，不用事後補寫。

to-spec

使用者觸發對齊 / 規格
用途：把當前對話直接轉成正式規格並發到 issue tracker，不再另開訪談。
做法重點：先探索 codebase 現況、套用 glossary 詞彙並尊重既有 ADR；定義測試 seam（盡量少、理想只有一個）並與使用者確認；產出含問題陳述、解法、大量 user story（As [actor], I want…, so that…）、實作決策、測試策略、範疇邊界的結構化規格，發布時貼上 ready-for-agent 標籤。
值得偷師：規格避免寫死檔案路徑、改用散文描述——讓 spec 不因重構失效；並用「測試 seam 最小化」逼出乾淨的模組邊界。

to-tickets

使用者觸發對齊 / 拆票
用途：把計畫、規格或對話拆成帶明確阻塞依賴的曳光彈（tracer-bullet）票，發到 tracker。
做法重點：每張票是垂直切片（穿過 schema／API／UI／測試各層、能獨立完成），大小控制在一個 context window；寬幅重構用 expand-contract（先加新形態、分批遷移、再刪舊形態）保持 CI 常綠；每張票明確宣告它被哪些票阻塞。輸出可為本地 .scratch/<feature>/issues/ markdown，或原生 tracker issue。
值得偷師：「垂直切片 + 阻塞邊」讓每張票都能被 agent 單獨抓來做完並驗證，避免橫向分層造成的半成品堆積。

wayfinder

使用者觸發對齊 / 大型規劃
用途：把跨多個 agent session 的大型規劃，做成 tracker 上的一張決策地圖，一次解一個決策票直到路徑清楚。
做法重點：先用 /grilling+/domain-modeling 定義「終點」；廣度優先繪出決策邊界，建 wayfinder:map 地圖 issue（含 Destination、Notes、未明處放「Not yet specified」＝戰爭迷霧）；子決策做成帶阻塞關係的 child issue；research 型票可平行派子 agent。原則是只產決策、不做交付，一 session 一票（research 除外）。
值得偷師：「戰爭迷霧」隱喻——只把已經夠銳利、能精確陳述的問題升成票，模糊的懷疑先留在迷霧裡，避免過早過度規劃。

implement

使用者觸發品質 / 實作
用途：依規格或一組票把工作實作出來。
做法重點：在雙方談定的整合點用 /tdd 開發；過程中頻繁跑型別檢查、常跑個別測試檔、完成時跑一次完整測試套件；實作完用 /code-review 審查；最後 commit 到當前分支。
值得偷師：把「實作」定義成一條含 TDD、頻繁型檢、收尾審查的流水線，而不是「把 code 寫出來」而已——品質關卡內建在流程裡。

tdd

模型觸發品質 / 測試
用途：紅→綠→重構的測試先行開發；使用者想 test-first 建功能／修 bug、提到 red-green-refactor 或想要整合測試時援引。
做法重點：好測試「透過公開介面驗證行為、而非實作細節」，讀起來像規格、能撐過重構；寫任何測試前先寫下並與使用者確認要測的 seam；一次一個測試配一段實作的垂直切片；重構留到 code review 而非實作環。避開實作耦合、套套邏輯（tautological）、橫向切片三大反模式。
值得偷師：「先寫下 seam 並確認」這一步——把測試邊界外顯成可討論的契約，是避免測試脆弱化的關鍵閘門。

code-review

模型觸發品質 / 審查
用途：沿兩條獨立軸線審查變更——Standards（是否合 repo 慣例）與 Spec（是否忠實實作需求），用平行子 agent 避免 context 污染。
做法重點：先定 fixed point（commit／branch／main），用 git diff <point>...HEAD 三點比對取 diff，壞 ref 或空 diff 立刻 fail fast；依序尋找 spec（commit 內的 issue 引用 → 使用者給的路徑 → docs/specs/.scratch）；標準面除了 repo 文件，還墊一層 Fowler《重構》第 3 章的 code smell 基線；兩個子 agent 各限 400 字回報，最後分 ## Standards／## Spec 呈現、不跨軸排序。
值得偷師：把審查拆成兩條互不干擾的軸、各用獨立子 agent——避免「一邊看規範一邊看需求」時的注意力污染，且輸出限字數逼出重點。

diagnosing-bugs

模型觸發品質 / 除錯
用途：難纏 bug 與效能回歸的診斷迴圈；使用者說「diagnose／debug this」或回報壞掉／噴錯／很慢時援引。
做法重點：六階段——①先建立能對這個 bug 變紅的緊密 pass/fail 訊號（一個可跑、確定性、快、agent 能跑的指令）；②重現並最小化（逐一砍輸入與設定）；③提出 3–5 個可證偽假設；④對每個預測下探針（優先 debugger，再打帶唯一 tag 的 log）；⑤先在正確 seam 寫回歸測試再修；⑥清理探針、寫根因進 commit，並反思架構能否從源頭預防。
值得偷師：「先做出能穩定變紅的訊號，再談原因」——把除錯從猜測變成有回饋迴圈的科學流程；假設必須可證偽。

domain-modeling

模型觸發對齊 / 詞彙
用途：建立並打磨專案的領域模型 / ubiquitous language；使用者想釘死術語、記錄架構決策，或別的 skill 需要維護詞彙時援引。
做法重點：用詞與 CONTEXT.md 衝突時當場點出；把模糊／過載的詞收斂成精準的正典詞（如 Customer vs. User）；用具體邊界情境壓力測試；拿文件對照真實 code 找矛盾；即時把談定的詞寫回 CONTEXT.md（純詞彙表、不放實作細節）；ADR 只在「難逆轉 + 沒背景會意外 + 真有取捨」三條件都成立時才建。
值得偷師：把 glossary 當「純詞彙表」單一真相來源、與規格／決策分家；ADR 有明確的三條件門檻，避免文件通膨。

improve-codebase-architecture

使用者觸發架構退化
用途：找出並處理架構摩擦，專門挖「deepening opportunities」——把淺模組重構成更深、更好測的模組。
做法重點：三階段——①探索：不全掃，若沒指定範圍就看近期 commit 找常改的熱點，讀 glossary 與 ADR，子 agent 列出摩擦點（概念要在許多小模組間跳、介面複雜度逼近實作、只為可測而抽出的純函式反而藏 bug、耦合外洩、難測區）；用「刪除測試」判斷淺模組。②產出自帶的 HTML 報告（寫到 $TMPDIR，每張卡含 Files／Problem／Solution／Benefits／前後 Mermaid 圖／推薦強度）。③選定後進 /grilling 迴圈定案、/domain-modeling 更新詞彙。
值得偷師：「deletion test」——問「拿掉這個淺模組，複雜度會集中還是只是搬家？」是判斷該不該重構的鋒利啟發式；並用視覺化 HTML 報告承載建議。

triage

使用者觸發流程 / 議題分流
用途：用一台狀態機把 issue 與外部 PR 分流、逐步精煉。
做法重點：類別二選一（bug／enhancement），狀態六選一（needs-triage／needs-info／ready-for-agent／ready-for-human／wontfix）；發現流程按最舊優先分三桶呈現，外部 PR 標 [PR]、內部協作者 PR 排除；分流單一議題時先蒐證、推薦類別與狀態並說明理由、驗證主張（重現 bug／確認 PR diff）、必要時逼問、再落地。所有 triage 留言須以「This was generated by AI during triage.」開頭。
值得偷師：把「分流」形式化成明確的類別×狀態狀態機，並強制 AI 留言標示來源——治理與透明度內建在流程。

research

模型觸發對齊 / 調查
用途：針對問題查高信任的一手來源，把發現寫成 repo 內的 Markdown；使用者想研究主題、蒐集文件／API 事實，或把讀資料的活外包給背景 agent 時援引。
做法重點：開背景 agent 邊查邊讓你繼續工作；以一手來源為準（官方文件、原始碼、規格、first-party API，而非二手詮釋）；每個主張都追回擁有它的權威來源；結果寫成單一 Markdown 檔、每個主張附引用；依 repo 既有慣例存放。
值得偷師：「每個主張都要追回一手來源並附引用」——把研究輸出變成可稽核的東西，對抗 LLM 的自信幻覺。

prototype

模型觸發對齊 / 探索
用途：做用完即丟的原型回答設計問題；使用者想確認狀態模型／邏輯對不對，或探索 UI 該長怎樣時援引。
做法重點：先辨識底層問題——邏輯驗證 → 產可分享的 HTML，附自由操作按鈕與引導走查，用邊界情境壓測狀態機；UI 探索 → 在同一路由生成數個視覺方案，用 URL 參數與浮動控制列切換。共通原則：明確標為原型、就近放、狀態留記憶體、跳過測試與抽象、每個動作後顯示完整狀態、最後 commit 到丟棄分支並把定案整合回 main。
值得偷師：「disposable by design」——原型刻意不寫測試、不做抽象，用最低摩擦換取設計問題的快速答案，並明訂用完即刪的紀律。

③ Productivity 生產力類（7）

不綁特定 codebase 的通用工作流：逼問、交接、教學、問卷、再溝通，以及兩個被別的 skill 重複援用的底層原件。

grilling

模型觸發底層原件
用途：用毫不留情的提問壓力測試使用者的思考；是 grill-me、grill-with-docs、wayfinder 等多個 skill 背後共用的逼問原件。
做法重點：把訪談組成一棵決策樹，分編號回合進行——①找出前置已定、可立刻問的「frontier」；②一次問完該層所有問題（附編號與建議答案）；③等使用者回答；④重算 frontier（答案解鎖下游問題）；⑤frontier 清空才算完。原則：派子 agent 查環境事實、絕不問使用者可查到的東西；決策歸使用者、事實由 agent 發掘；達成共識前不行動。
值得偷師：「決策樹 + frontier」把訪談變成有終止條件的演算法；並嚴格切分「使用者做決策 / agent 查事實」，不拿可查的問題浪費人。

grill-me

使用者觸發對齊 / 逼問
用途：一場毫不留情的訪談，把計畫或設計打磨到所有設計分支都解掉。
做法重點：本質就是叫出一場 /grilling session（薄封裝，把逼問原件暴露成使用者可直接觸發的入口）。
值得偷師：把可重用的原件（grilling）再包一層極薄的使用者入口——同一能力，模型自動用一個名字、人手動用另一個名字。

handoff

使用者觸發冗長 / 交接
用途：把當前對話壓縮成交接文件，讓另一個 agent 接手。
做法重點：總結本 session 讓新 agent 讀懂脈絡；存到 OS 暫存目錄（不進工作區）；用路徑／URL 引用既有 spec、plan、ADR、issue、commit、diff，而非複製內容；加一段「建議 skill」告訴接手者下一步該叫哪些 skill；交出前遮蔽 API key、密碼、PII；若使用者說明了下一 session 的重點就照那個結構寫。
值得偷師：交接靠「引用而非複製」壓縮 context，還內建一段「建議接手者用哪些 skill」——把 agent 之間的接力做成標準協定。

teach

使用者觸發學習
用途：在一個工作區內教使用者一個新技能或概念，跨多次 session 有狀態。
做法重點：工作區含 MISSION.md（把教學錨定在真實目標）、RESOURCES.md（精選一手來源）、learning-records/、lessons/*.html、reference/*.html、NOTES.md；用「合意困難」（提取練習、間隔、交錯）優先儲存強度而非流暢感；每課瞄準最近發展區、短且能快速完成、給一個具體小勝並附一手引用；知識一律來自可信外部資源、不靠模型內建記憶；目標不清時先問使用者的底層動機。
值得偷師：把認知科學（desirable difficulty、spacing、ZPD）落成檔案結構與短課設計；並堅持「知識來自外部一手來源、非 parametric knowledge」。

to-questionnaire

使用者觸發對齊 / 決策
用途：把你答不了的決策，轉成給別人（決策者）填的問卷。
做法重點：三步——①一次對話定收件人的角色、專業、與你的關係（校準語氣與背景量）；②一次對話定你自己解不了的具體決策或事實；③產出依重要性排序、主題分組的問卷，存 to-questionnaire-<slug>.md，含目的、背景、作答指引、每組單一主題＋簡短理由、結尾兜底問題。核心原則「Grill the send, not the subject」——訪談的是發送者（誰收、要什麼），問卷本身才問實質問題。
值得偷師：「逼問發送者而非主題」的區分——先搞清楚要問誰、要什麼，再讓文件去問實質，避免把問卷寫成自問自答。

wait-what

使用者觸發冗長 / 再溝通
用途：「停，剛那則訊息沒 land」——把上一則沒說清楚的訊息重新表述一次。
做法重點：暫停並要脈絡；改用 ASD-STE100 Simplified Technical English（航空業的受控技術英語）重講；引用 CONTEXT.md 的 ubiquitous language 定義；重點是 re-pitch 而非硬往下走，先確保雙方理解一致。
值得偷師：借用「受控自然語言（STE）」這種工業級標準來對治溝通歧義——不是叫模型「講清楚點」，而是給它一套明確的語言規範。

writing-for-agents

模型觸發底層原件 / meta
用途：寫給 agent 讀的文件；建立或編輯 skill、改 AGENTS.md 或 CLAUDE.md 時援引。這是整個 repo 的寫作方法論。
做法重點：幾條核心——context pointer 靠措辭而非目標觸發，前置引導詞、一分支一觸發；辨明「兩種負擔」（context load 每回合花 token vs. cognitive load 人要記哪些文件何時看）；資訊三層（in-file steps／in-file reference／disclosed reference）＋漸進揭露；每個步驟要有完成準則（清晰＋帶要求）；用「leading words」（既有概念）錨定行為，且否定句無效（「Don't do X」反而激活 X，要講正向目標）；剪枝：單一真相來源、只快取昂貴查詢、每行都測是否有用、獵殺 no-op。
值得偷師：「否定句會激活它否定的東西，改講正向目標」與「每個步驟要有可判定的完成準則」——是寫 prompt／skill／CLAUDE.md 立刻能用的鐵律。
補充：repo 內工程類另有 ask-matt（依情境路由到對的 skill）、setup-matt-pocock-skills（初始設定）、codebase-design、resolving-merge-conflicts、wizard 等；本頁聚焦題目指定的 20 個核心 skill，其餘以官方 repo 為準。

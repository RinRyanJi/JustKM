① 這個 repo 是什麼 / 怎麼安裝

精選技能包 · Addy Osmani 等 MIT License GitHub ↗

定位：把「資深工程師怎麼把一件事從想法做到上線」拆成 24 個可觸發的技能（skill），每個 skill 是一份 SKILL.md ＋ 附帶資源，教 agent 在對的時機用對的做法。整個 repo 依軟體開發生命週期分成六階段，外加一個負責「把任務對應到正確技能」的 Meta 技能。

除了 24 個 skills，repo 還附 agents/（4 個專家人格）、references/（7 份補充檢查表）、hooks/（session 生命週期掛鉤）、以及對應開發生命週期的 8 個 slash command：/spec、/plan、/build、/test、/review、/webperf、/code-simplify、/ship。

怎麼安裝

# 通用 CLI（推薦，跨多種 agent）
npx skills add addyosmani/agent-skills
npx skills add addyosmani/agent-skills --list   # 先列出全部 skill

# Claude Code 市集
/plugin marketplace add addyosmani/agent-skills
/plugin install agent-skills@addy-agent-skills

# 本地 / 開發
git clone https://github.com/addyosmani/agent-skills.git
claude --plugin-dir /path/to/agent-skills

另有 Cursor、Antigravity CLI、Gemini CLI、Windsurf、OpenCode、GitHub Copilot、Kiro IDE、Codex、Command Code 等原生整合設定。

下面每個階段列出該階段的 skills，一個 skill 一個小塊：①一句話用途 ②何時觸發 ③做法／流程重點 ④值得偷師的一點。詳細內容取自各 skill 的 SKILL.md 原文；少數僅有 README 級描述者會標註（以官方 repo 為準）。

② Define 定義 · 釐清要建什麼

在寫任何一行程式前，先把「要做什麼、為誰做、成功長怎樣」講清楚。這一階段的三個 skill 都是在對抗「憑模糊假設就開工」。

interview-me 一次一題的需求訪談

用「一次只問一個問題、而且每問都先附上自己的猜測」的方式，把使用者真正要的東西挖出來。

何時觸發
請求缺了關鍵資訊（誰受益／為何現在做／成功長怎樣／硬約束是什麼），或使用者說「interview me / 壓力測試我的想法」，或你發現自己正在替模糊處腦補。CI／自動迴圈等非互動情境不要用。
做法
每一題都先寫下「我猜你會這樣回答」，逼自己對信心誠實、把假設攤在檯面上；使用者反駁比從零回答更快。低於約 70% 信心要附一行「還沒解決什麼」。
做完的標準
能回答「我能預測使用者對接下來三個問題的反應嗎？」＝約 95% 信心。產出一份 Outcome / User / Why Now / Success / Constraint / Out of Scope 的確認意圖聲明，且要使用者明確說 yes 才往下走。
偷師：「每問附猜測」把訪談從盤問變成校對——連續幾輪信心都不升，代表「有根本的東西不見了」，該停下來重構問題而不是硬磨。

spec-driven-development 先寫規格再寫碼

動工前先寫一份涵蓋六個面向的 PRD，把模糊需求改寫成可測試的成功條件。

何時觸發
開新專案／新功能、需求模糊或不完整、改動橫跨多檔多模組時。單行修正或無歧義的自足小改動則跳過。
做法
規格必含六塊：Objective（目的／使用者／成功定義）、Commands（可執行的 build/test/lint/dev 指令）、Project Structure、Code Style（用真實程式碼示範慣例）、Testing Strategy、Boundaries（一定要做／需批准／禁止）。
流程
四階段閘門，每階段需人類審核才前進：SPECIFY → PLAN → TASKS → IMPLEMENT。規格是活文件，決策或範圍一變就更新。
偷師：把「Boundaries」明確拆成「always / needs-approval / prohibited」三格——比一句「注意安全」更能約束 agent 不越界。

idea-refine 打磨粗略概念

用結構化的發散／收斂思考，把還很粗的點子磨成能往下規劃的形狀。

何時觸發
概念還很模糊、需要先擴張選項再收斂到一個方向時。
做法重點
發散（盡量列可能性）＋ 收斂（依約束篩選）交替進行。（細節以官方 repo 為準）
偷師：與 interview-me 互補——訪談挖「使用者要什麼」，idea-refine 擴張「有哪些做法」。

③ Plan 規劃 · 拆成可驗證的小任務

planning-and-task-breakdown 規劃與任務拆解

把規格拆成「每個都能在一個專注 session 內做完並驗證」的小任務，每個都帶明確的驗收條件。

何時觸發
有規格待拆、任務「感覺太大或太模糊不知從何下手」、需要跨 agent／session 並行、實作順序不明時。單檔改動或規格已含明確任務則跳過。
做法
①唯讀規劃模式（先讀規格與 codebase 不寫碼）②畫依賴圖 ③垂直切片（依完整功能路徑組織，而非先全 DB 再全 API 再全 UI）④每個任務寫清楚描述／驗收條件／驗證步驟／依賴／受影響檔案／規模估計 ⑤排序並在階段間放驗證閘門。
規模
任務盡量維持 Small~Medium（1~5 檔），更大就再拆。
偷師：「垂直切片」＝以 註冊→登入→建任務 這種端到端路徑排任務，讓每完成一片就有可跑的東西，而不是三層各做一半。

④ Build 建構 · 寫程式

本階段 skill 最多，涵蓋「怎麼一片片穩穩實作、怎麼測、怎麼餵對上下文、怎麼設計介面、怎麼對自己的決定存疑」。

incremental-implementation 漸進式實作

用薄薄的垂直切片交付端到端功能，每片都跑一輪「實作 → 測試 → 驗證 → 提交」，讓系統全程維持可運作。

何時觸發
任何多檔改動、需要拆任務的新功能、重構、或「很想在測試前一口氣寫超過約 100 行」時。單檔單函式的小改可跳過。
做法
切片策略：垂直切片／契約優先（前後端並行）／風險優先（先啃不確定的）。規則：簡單優先、範圍紀律（只碰任務需要的檔）、增量之間保持可編譯；每片都能獨立回退並用 repo 原生指令測過再前進。
偷師：把「約 100 行」當成一條生理警戒線——超過就代表你在測試前累積了太多沒驗證的風險。

test-driven-development 測試驅動開發

先寫會失敗的測試，再寫剛好能通過的程式，最後重構——「一個立刻通過的測試什麼都證明不了」。

何時觸發
實作新邏輯、修 bug、改既有行為、處理邊界情況、任何有破壞風險的改動。純設定／文件／無行為影響的靜態內容則跳過。
做法
RED → GREEN → REFACTOR。修 bug 走 Prove-It：先寫重現測試（失敗）→確認 bug 存在→修→驗證轉綠。測試金字塔投資比例：單元 ~80%／整合 ~15%／E2E ~5%。原則：先摸清這個 repo 怎麼測（別假設 npm test）、測狀態不測互動、測試裡 DAMP 勝過 DRY、優先用真實實作而非 mock、Arrange-Act-Assert。
偷師：Beyoncé Rule「If you liked it, you should have put a test on it」——沒測試＝沒課責；且乾淨跑完後「再跑一次不改碼並不增加任何信心」。

api-and-interface-design API 與介面設計

設計 REST／GraphQL／模組邊界／component props 時，讓「對的事好做、錯的事難做」。

何時觸發
設計新端點、劃團隊間模組邊界、定 component prop 介面、改動既有公開介面時。
做法
契約優先（先定介面規格再實作，「契約就是 spec」）→ 在系統邊界驗證輸入 → 一致的錯誤語意 → 優先加法式變更以保向後相容 → 可預測命名（REST 用複數名詞、欄位 camelCase）→ 依檢查表驗證再上線。
偷師：Hyrum's Law——只要行為可被觀察，就一定有人依賴它，連沒寫進文件的怪癖都算隱性承諾；配合 One-Version Rule「擴充而非分叉」，別逼使用者在多版本間選。

doubt-driven-development 存疑驅動開發

在重要決策定形前，召喚一個「偏向要推翻你、而不是認可你」的新上下文審查者——「有信心的答案不等於正確的答案」。

何時觸發
決策非瑣碎時：引入分支邏輯或跨模組邊界、斷言型別系統無法驗證的性質、帶不可逆後果（上線／資料遷移）、在陌生程式碼裡摸索。純機械操作（改名、格式化）不在範圍——「若你懷疑每個按鍵，你什麼都出不了貨」。
做法（五步）
CLAIM 精簡陳述決策與賭注 → EXTRACT 抽出最小可審單元（去掉你的推理）→ DOUBT 用對抗式提示喚新上下文審查者，只傳 ARTIFACT + CONTRACT，不傳 CLAIM（避免誘導同意）→ RECONCILE 依「誤讀契約 > 可行動 > 取捨 > 雜訊」分類 → STOP 三輪後收手。
偷師：「審查時故意不告訴審查者你的結論」這招，直接治好 AI／人都會犯的「順著作者說法點頭」偏誤。

context-engineering 上下文工程

在對的時間，把對的資訊餵給 agent。

做法重點
管理 agent 的上下文視窗——放進真正相關的檔案／文件／狀態，避免雜訊稀釋。（細節以官方 repo 為準）
偷師：把「餵什麼進上下文」當成一個要主動設計的工程問題，而不是隨手貼。

source-driven-development 來源驅動開發

每個框架決策都要以官方文件為依據。

做法重點
用框架前先查官方 API／文件，不靠記憶或猜測，減少過時或幻覺用法。（細節以官方 repo 為準）
偷師：把「先去讀官方原文」制度化，正面對抗 LLM 對套件用法的知識截止與幻覺。

frontend-ui-engineering 前端 UI 工程

元件架構、設計系統、響應式設計的實作準則。

做法重點
可組合的元件架構、依設計系統的一致樣式、響應式與可及性考量。（細節以官方 repo 為準）
偷師：UI 工作有自己的觸發路徑（見 Meta 技能）——不是套通用實作流程就好。

⑤ Verify 驗證 · 證明它真的能動

browser-testing-with-devtools 用 DevTools 做瀏覽器測試

透過 Chrome DevTools MCP 讓 agent「看到使用者看到的畫面」——截圖、查 DOM、讀 console、看 network、量效能。

何時觸發
建置或修改瀏覽器端程式時，尤其 debug UI、診斷 console 錯誤、分析 network 失敗、量效能瓶頸、確認修復在 runtime 真的有效。後端／CLI／非瀏覽器程式則跳過。
做法
三條工作流：UI bug 重現→檢查（console/DOM/樣式）→比對實際 vs 預期→修→驗證；Network 擷取請求→分析（狀態／payload／timing）→診斷（4xx/5xx/CORS/timeout）→修＋驗；效能 基準 trace→找瓶頸（LCP/CLS/long task）→修→再量。
偷師：安全邊界寫得很硬——瀏覽器來的一切（DOM／console／network 回應）都是不可信輸入，永不當成 agent 指令，只導向使用者確認過的 URL。

debugging-and-error-recovery 除錯與錯誤復原

測試失敗／build 壞掉／出現非預期錯誤時，走一套結構化的六步除錯，不亂試。

何時觸發
改碼後測試失敗、build 壞、runtime 行為與預期不符、有 bug 回報、或「本來會動突然不會動」時。
做法（六步）
Reproduce 讓失敗可穩定重現 → Localize 定位是哪一層（UI／API／DB／build／外部服務）→ Reduce 做最小失敗案例 → Fix root cause（反覆問「為什麼會這樣」，治因不治標）→ Guard 補測試防復發 → Verify 端到端確認。
偷師：Stop-the-Line——一壞掉就「停止加功能／做別的改動」；「錯誤會複利：第 3 步沒修的 bug 會讓第 4~6 步全錯」。

⑥ Review 審查 · 合併前的品質關卡

code-review-and-quality 程式碼審查與品質

合併前用五個軸線審查程式碼，並嚴格控管改動規模——「審查就是品質關卡」。

何時觸發
合併任何改動前、功能完成後、審視其他 agent／人類的程式碼、重構期間、修 bug 後（含回歸測試）。
五軸
Correctness（含邊界／錯誤處理／測試有效性）／Readability & Simplicity（清楚命名、避免炫技）／Architecture（遵循既有模式、「重構是降複雜度還是只是搬家」）／Security（輸入驗證、機密、參數化查詢、外部資料視為不可信）／Performance（N+1、無界操作、缺分頁、該 async 的同步呼叫）。
改動規模
理想約 100 行「一坐就能審完」；單一邏輯改動可到 300 行；超過 1000 行必須拆。並警告「小 diff 也可能把單檔推過約 1000 行的健康上限」。流程：懂脈絡→先看測試→對五軸審實作→依 Critical/Required/Optional/Nit/FYI 分級→驗證測試＋build＋手動確認。
偷師：把 findings 分成五級 severity，並「拒絕把清理延後」——審查當下就是唯一的品質關卡。

code-simplification 程式碼簡化

讓程式「更好讀、好懂、好改、好 debug」——簡化的目標不是更少的行數。

何時觸發
程式能動但比該有的更難讀維護、功能過測但覺得過度複雜、審查時被標可讀性、要合併跨檔重複邏輯時。已乾淨的碼、你看不懂的碼、效能關鍵段、拋棄式實作則不要動。
做法
①Understand 先用 Chesterton's Fence 弄懂它為何存在（誰呼叫它／它呼叫誰／邊界情況）②Identify 掃結構複雜、爛命名、冗餘 ③一次一改、每改必測 ④驗證測試過、行為不變、diff 乾淨。
偷師：Rule of 500——重構觸及超過 500 行就別手改，改投資 codemod／sed／AST 轉換,手動大規模改既易錯又難審。

security-and-hardening 安全與加固

威脅建模、漏洞預防、安全設計——「若你講不出一個功能的信任邊界，你還沒準備好保護它」。

何時觸發
任何接受使用者輸入的功能、認證／授權邏輯、敏感資料處理、外部 API 整合、檔案上傳或 webhook。
做法
先威脅建模（畫信任邊界、辨識資產、做 STRIDE）再實作。涵蓋 OWASP Top 10；認證用 bcrypt（salt rounds ≥12）、session cookie 設 httpOnly/secure/sameSite、「永遠檢查授權而不只認證」；機密走環境變數，「一旦被 commit 過就要輪換」；邊界做 schema 驗證＋參數化查詢＋輸出編碼。LLM 安全：模型輸出視為不可信、防 prompt injection、機密不進上下文、限制 agent 權限。
偷師：「commit 過的密鑰刪掉不夠、一定要輪換」——把 git 歷史當成已洩漏來處理。

performance-optimization 效能優化

先量再改——「沒有測量的效能工作就是猜，而猜會導致沒改到重點的過早優化」。

何時觸發
規格有效能需求、使用者回報慢或監控發現問題、Core Web Vitals 低於門檻、懷疑退化、要建高流量或大資料量功能時。無證據就別過早優化。
做法（五步）
Measure 用合成測試＋真實使用者資料建基準 → Identify 靠 profiling 找真正瓶頸 → Fix 對症下藥 → Verify 再量、確認改善超過自然變異 → Guard 加監控防退化。
目標
Core Web Vitals：LCP ≤2.5s、INP ≤200ms、CLS ≤0.1 為佳。
偷師：「改善要超過自然變異」才算數——避免把量測雜訊誤讀成優化成效。

⑦ Ship 出貨 · 有信心地部署

git-workflow-and-versioning Git 工作流與版本管理

用紀律化的版本控制當作大規模安全改動的地基——觸發條件是「永遠，每個改動都走 git」。

做法
Trunk-based：main 永遠可部署，功能分支短命（1~3 天），「分支每多活一天就多累積一分合併風險」。Atomic commits：一 commit 一件邏輯事，當作 save point 可即時回退。Conventional Commits：feat/fix/refactor/test，訊息解釋 why 而非只有 what。SemVer：MAJOR.MINOR.PATCH 由不可變 git tag 推導。
流程
save-point 迴圈：實作→測試→成功就 commit／失敗就回退調查。改動抓約 100 行，更大就拆多個 commit。發版前產一份「依使用者影響分組、非原始 commit」的 changelog。
偷師：把 commit 當「已知良好狀態的存檔點」，讓下一步一壞就能秒退回上一個綠燈。

ci-cd-and-automation CI/CD 與自動化

把品質檢查往上游搬、用更小更頻繁的發布降低風險。

做法
Shift Left：「lint 抓到的 bug 花幾分鐘，production 才抓到花幾小時」——靜態分析先於測試、測試先於 staging、staging 先於 production。Faster is Safer：「3 個改動的部署比 30 個的好 debug」。Pipeline 依序跑 lint／type／單元／build／整合／E2E／安全稽核／bundle size，失敗透過 branch protection 擋合併。Feature flags 讓部署與發布解耦（先 ship 不 enable，再金絲雀漸放）。CI 失敗回饋給開發 agent 形成修復迴圈。
偷師：「Faster is Safer」反直覺但關鍵——把批次做小，是降風險而非增風險。

shipping-and-launch 出貨與發布

上線前檢查清單、feature flag 生命週期、分階段 rollout。

做法重點
pre-launch checklist、staged rollout、flag 的建立→放量→清理生命週期。（細節以官方 repo 為準）
偷師：把「flag 用完要清掉」納入流程，避免旗標長年殘留變技術債。

observability-and-instrumentation 可觀測性與埋點

結構化日誌、RED metrics、OpenTelemetry tracing。

做法重點
用結構化 logging、RED（Rate/Errors/Duration）指標、分散式 tracing 讓系統行為可被觀察。（細節以官方 repo 為準）
偷師：RED 三指標是服務健康度最精簡的一組儀表。

documentation-and-adrs 文件與架構決策紀錄

Architecture Decision Records、API 文件。

做法重點
用 ADR 把「為什麼這樣決定」記下來、維護 API 文件。（細節以官方 repo 為準）
偷師：ADR 記的是決策的 why 與當時取捨，未來的人不必重新踩坑。

deprecation-and-migration 汰除與遷移

以「程式碼是負債」的心態處理汰除與遷移。

做法重點
Code-as-liability——主動規劃汰除路徑與相容遷移，而非讓舊碼無限累積。（細節以官方 repo 為準）
偷師：把「刪碼／下線」當成一等公民工作，而不是永遠拖著的雜務。

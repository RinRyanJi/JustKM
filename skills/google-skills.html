① 怎麼看這個 repo

官方 · Google Apache 2.0 skills/ 下分 cloud / ads / analytics GitHub ↗

定位：google/skills 是 Google 官方的 Agent Skills 集合，幾乎把「怎麼正確操作 Google Cloud 與 Google 產品」做成一條條可觸發的工作流。repo 正在積極開發中，skill 數量龐大（skills/cloud 一處就有九十多個），本頁不逐一深拆，而是依分類、每類挑 1~3 個代表 skill 深入，其餘列名。

結構：所有 skill 收在 skills/ 下,再分成三大目錄:

目錄內容規模
skills/cloudGoogle Cloud 全家桶：入門、AI/ML、基礎設施、資料庫、治理、開發者工具、Web 託管、整合方案大宗（約 90+）
skills/adsGoogle Ads API、Data Manager API、Mobile Ads SDK、IMA SDK12 個
skills/analyticsGoogle Analytics Admin / Data API2 個

怎麼用：執行 npx skills add google/skills，安裝時勾選需要的 skill;也可透過 Claude Code、Codex、Antigravity CLI 的 plugin 機制安裝(各平台指令略有不同，以官方 repo 為準)。

關於本頁：內容整理自 google/skills 公開 README 與各 skill 的 SKILL.md（撰寫時，main 分支）。skill 清單、描述與安裝方式會持續更新，實際一律以官方 repo 最新內容為準；本頁刻意不列 star 等熱度數據。

② 入門（Getting Started）

這類 skill 處理「站上 GCP 的第一哩路」：如何證明身分、拿到憑證、把專案地基打好。多以 google-cloud-recipe-* 命名，是其他所有操作類 skill 的前置。

google-cloud-recipe-auth代表深拆

用途：Google Cloud 驗證與授權的專家指引——涵蓋人類使用者、服務身分、Application Default Credentials（ADC）與安全存取最佳實踐。（frontmatter category：GettingStarted）

觸發：當使用者問「怎麼向 GCP API 證明身分」「本機開發／部署怎麼設憑證」「怎麼用存取控制保護應用」時。

做法重點（五步）：

  • 釐清情境：誰／什麼在驗證、程式跑在哪、目標資源是什麼
  • 選驗證方式：人類向（Console、gcloud CLI、ADC）或服務向（Service Account、Workload Identity）
  • 安全實作：避免靜態金鑰，優先用附掛的 Service Account、身分模擬（impersonation）或短期權杖
  • 設定授權：把主體綁到最小權限的 IAM 角色
  • 驗證設定：確認憑證可用、限制確實生效

核心主張：開發別用 Service Account 金鑰檔，生產環境優先用「自動供給權杖的附掛身分」。

③ AI / ML

這是 repo 的重點戰場：Agent Platform（Vertex AI 系）的部署／微調／評估／RAG／提示管理、Gemini 各式 API,以及 BigQuery 的 AI/ML 能力。很多 skill 走「用 Google GenAI SDK 操作，執行耗資源動作前要先取得使用者確認」的模式。

agent-platform-rag-engine-management代表深拆

用途：用 Google GenAI SDK 管理與查詢 Agent Platform 的 RAG Engine 語料庫（Corpora），取得有依據（grounded）的上下文。（category：AiAndMachineLearning）

觸發：列出／檢視 RAG 語料庫或檔案、擷取上下文、或要「以某語料庫為依據」生成內容時。明確排除：一般資料庫查詢（改用 SQL／Spanner 類 skill）、Workspace RAG、其他 RAG 產品如 gRAG。

做法重點：

  • 環境設定：GCP 驗證、建 Python venv、安裝 google-cloud-aiplatform 與 google-genai
  • 探索：資源名未知時先列出語料庫與檔案
  • 檢視 → 擷取 → 生成：查語料庫 metadata → 以語意相似度取回上下文 → 用取回內容生成有依據的答案；耗資源動作前要求使用者明確確認
bigquery-ai-ml

用途：把 BigQuery 當 AI/ML 引擎用——延伸 bigquery-basics,加入預測、異常偵測等能力（依 README 描述）。與 Gemini 各 API 一起構成「資料 + 生成」的組合拳。

④ 基礎設施（GKE 為大宗）

整個 repo 數量最多的一塊，GKE（Google Kubernetes Engine）幾乎自成一個子系列:叢集建立、升級、網路、儲存、安全、自動擴展、可觀測性、AI 工作負載除錯、TPU 監控⋯⋯另外還有儲存（Cloud Storage、Filestore）、全域前端／負載平衡、網路可觀測性。

gke-cluster-creation代表深拆

用途：用預先定義的模板（Autopilot、Standard Regional、GPU/AI Inference、AI Hypercompute）規劃並執行 GKE 叢集建立、供給與「生產就緒稽核」。

觸發：建新叢集、供給 GKE 環境、選叢集模式／架構、稽核叢集就緒度時。不用於應用上線或部署設定（那是 gke-app-onboarding）。

做法重點（四步）：

  • 探索與蒐集：找現有叢集,收集 project_id / location / cluster_name / 環境類型
  • 選模式：列出五種模板與取捨——Golden Path Autopilot（建議預設）、Autopilot Dev/Test（省成本、非生產）、Standard Regional（客製）、GPU Inference（L4）、AI Hypercompute（大規模 LLM 訓練）
  • 審閱設定：先顯示設定區塊、確認後再建立
  • 執行與驗證：用 MCP 工具建立、監看進度、驗證設定生效

關鍵守則：非有未滿足的需求就預設 Autopilot;偏離黃金路徑要警告額外負擔;GPU／區域叢集要明講成本與配額;把 Day-0 決策（網路、私有節點）標為「日後難改」。

⑤ 資料庫與分析

Google Cloud 五大資料庫／分析引擎各有 *-basics:AlloyDB、BigQuery、Bigtable、Cloud SQL、Spanner,再加上 BigFrames、資料譜系（data lineage）與 Airflow 遷移。這類 skill 多聚焦在「provisioning + schema 設計 + 查詢 + 效能診斷」。

bigquery-basics代表深拆

用途：管理 BigQuery 的 dataset、table、job——跑 SQL、管資源（datasets/tables/views）、做基本資料匯入與分析。（category：BigDataAndAnalytics）

觸發：要操作 BigQuery、執行 SQL 查詢、管理 dataset/table/view、匯入或分析資料時。

做法重點（四階段設定）：

  • 用 gcloud 啟用 BigQuery API
  • 建 dataset 組織相關 table
  • 以 JSON 定義 schema 建 table
  • 用 bq CLI 跑標準 SQL 查詢

另附核心概念、CLI、用戶端函式庫（Python/Java/Node/Go）、Terraform IaC、安全最佳實踐等延伸指南;預測／異常偵測則交給 bigquery-ai-ml。

spanner-basics

用途：協助供給 Spanner instance/database、設計高效能 schema、查詢資料。觸發：設計主鍵（primary key）、寫 SQL 或用戶端函式庫程式碼、診斷效能問題時——特別強調「用主鍵設計換效能」。

⑥ 管理與治理

營運面的 skill:Cloud Monitoring / Logging、成本分析、SLO 告警、Workload Manager,以及把 Google Well-Architected Framework（WAF）六大支柱各做成一個 skill（成本、營運卓越、效能、可靠、安全、永續）。

cloud-monitoring-chart-generation代表深拆

用途：把 PromQL 或 ListTimeSeries 查詢，轉成合法的 Cloud Monitoring「Server-Driven UI（SDUI）」widget protobuf textproto,可餵給 Dashboards API、gcloud CLI 或宣告式供給工具。（category：CloudObservabilityAndMonitoring）。不負責指標探索或查詢合成本身。

做法重點（三階段管線）：

  • Stage 1 基線合成：跑 compute_labels.py,由指標 metadata／資源類型／查詢結構產出候選標籤與單位
  • Stage 2 LLM 語意設計:寫出 SemanticPlotSpec JSON（標題、Y 軸、圖型預設 LINE、單位覆寫）;PromQL 的 rate 函式會把累積計數器換算成每秒率，於單位加 /s
  • Stage 3 組裝與驗證:跑 assemble_widget_proto.py 產出 UUID 檔名的 textproto,再用 validate_chart.py 驗證;若沙箱擋腳本,改為直接合成 textproto 並提供離線驗證指令

⑦ 開發者工具

這類 skill 少而關鍵——核心是替 gcloud CLI 加上安全護欄。它不是「教你某個服務」,而是所有 gcloud 操作的底層安全層。

gcloud代表深拆

用途：為 gcloud CLI 操作提供「安全關鍵」的驗證、護欄與資料精簡。（category：CloudInfrastructureAndServices）。觸發：規劃、生成、建構、提議或執行任何 gcloud 指令時，包含回答 gcloud 語法／旗標問題;不用於寫用戶端函式庫或原始 REST/gRPC。

做法重點：

  • 強制預先驗證：提議／執行前先跑 gcloud help <leaf_command>,不靠過時記憶,在子指令層級驗證語法（防止指令幻覺）
  • 資料精簡（必要）：list 操作一律加 --limit / --filter / --format;用 list --limit=1 --format=json 探 schema
  • 安全約束：以 --quiet 非互動執行、明確帶 --project 與 location;IAM 變更／刪除／計費／加密須使用者明確授權;破壞性操作先 --dry-run / --validate-only
  • 執行規則：只單一指令,禁 pipe／重導向／指令替換;保留使用者指定的旗標;走「語法驗證 → 參數確認 → dry-run 提案 → 授權執行」四步
值得學的模式：這個 skill 是「怎麼讓 agent 安全地跑 CLI」的教科書級範例——先查 help、強制精簡輸出、破壞性動作要授權。裝其他操作類 skill 時它常是隱形前置。

⑧ Web 與應用託管

面向「把應用跑起來、對外服務」的無伺服器與託管平台:Cloud Run 與 Firebase。

cloud-run-basics代表深拆

用途：管理 Cloud Run 的 services、jobs、worker pools。（category：Serverless）。觸發：部署回應 HTTP 的應用（services）、跑事件觸發／排程任務（jobs）、或常駐的 pull-based 背景處理（worker pools）時。

做法重點：

  • 前置：啟用 Cloud Run 與 Cloud Build API,指派 Cloud Run Admin、Source Developer 等 IAM 角色
  • 三種部署路徑：容器映像的 services（自動擴展）／可平行化的 jobs（跑到完成）／常駐的 worker pools（如訊息佇列消費者）
  • 關鍵要求：部署的程式碼必須監聽 0.0.0.0（不是 127.0.0.1）並用注入的 $PORT（預設 8080）,否則開機即崩
  • 部署選項：容器映像（偏好 Artifact Registry 勝過 Docker Hub）、由原始碼 buildpacks 部署、或免建置直接部署預編譯二進位檔以快速迭代

本類其餘 skill（列名）

⑨ 廣告與分析

這兩塊在 skills/ads 與 skills/analytics,離 GCP 基礎設施較遠,面向行銷／變現開發者:Google Ads API、Data Manager API、行動廣告 SDK、IMA SDK,以及 Google Analytics 的 Admin／Data API。

ads / google-ads-api-quickstart代表深拆

用途：帶開發者從零到第一個成功的 Google Ads API 請求——憑證設定、從 6 種用戶端函式庫或 REST 擇一、設定環境、跑「取回 campaigns」腳本,並排解常見設定錯誤。

觸發：設定 Ads API 憑證與 developer token、在 Python/Java/.NET/PHP/Ruby/Perl/REST 間選路徑、排解 USER_PERMISSION_DENIED 或 DEVELOPER_TOKEN_NOT_APPROVED 時。

做法重點：

  • 取得五個驗證參數:Developer Token、OAuth2 Client ID／Secret、Refresh Token、Client Customer ID、（存取子帳號時的）Login Customer ID
  • 選整合路徑（官方函式庫或 REST）
  • 動態版本解析（強制）:自動解析最新 API 與 runtime 版本,絕不寫死版本（除非明確要求）
